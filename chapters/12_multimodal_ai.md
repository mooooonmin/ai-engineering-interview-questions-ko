<summary><b>Q1. 멀티모달 AI 모델이란 무엇이며, 서로 다른 유형의 데이터를 어떻게 처리하나요?</b></summary>

**멀티모달 AI 모델** 은 텍스트, 이미지, 오디오, 동영상 같은 **여러 종류(모달리티)의 데이터를 함께 입력받거나 출력하는** 모델입니다. 예: 사진을 보고 질문에 답하기, 음성으로 대화하기, 텍스트로 이미지 생성하기.

**처리 방식의 핵심: 모든 모달리티를 "토큰 벡터"로 바꾸기**

1. **모달리티별 인코더**
   - 텍스트: 토크나이저 + 임베딩
   - 이미지: 비전 인코더(ViT 등)가 이미지를 패치로 나눠 벡터 시퀀스로 변환
   - 오디오: 스펙트로그램 → 오디오 인코더(Whisper 인코더 등) 또는 오디오 코덱 토큰
   - 동영상: 프레임 샘플링 → 이미지 인코더 + 시간 정보
2. **공통 공간으로 정렬(projection)**
   - 각 인코더 출력을 LLM의 임베딩 공간에 맞추는 투영 층(어댑터)을 둡니다.
3. **통합 처리**
   - 이미지·오디오 토큰과 텍스트 토큰을 하나의 시퀀스로 이어 트랜스포머가 함께 처리합니다.
4. **출력**
   - 텍스트 출력이 기본이고, 이미지·음성 생성은 별도 디코더(확산 모델, 오디오 디코더)나 생성 토큰으로 처리합니다.

**학습 단계 (VLM 예)**

1. 이미지-캡션 쌍으로 어댑터를 학습해 정렬(인코더·LLM은 고정)
2. 멀티모달 지시 데이터로 전체 또는 일부를 파인튜닝

**과제:** 모달리티 간 정렬, 이미지 토큰이 많아 생기는 비용, 한 모달리티를 무시하는 문제, 교차 모달 환각.

<summary><b>Q2. 비전-언어 모델(VLM)은 이미지를 어떻게 처리하나요?</b></summary>

**일반적인 VLM 구조 (LLaVA 계열)**

```
이미지 → [비전 인코더 (ViT/CLIP/SigLIP)] → 패치 특징 벡터들
      → [프로젝터 (MLP)] → LLM 임베딩 공간의 "이미지 토큰"
텍스트 → [토크나이저 + 임베딩] → 텍스트 토큰
         [이미지 토큰 + 텍스트 토큰] → [LLM] → 텍스트 답변
```

**단계별 설명**

1. **전처리:** 이미지를 정해진 해상도로 조정합니다. 고해상도 이미지는 여러 타일로 나눠 각각 인코딩하고 전체 축소본도 함께 넣는 방식(동적 해상도)이 흔합니다.
2. **비전 인코딩:** 이미지를 패치(예: 14×14 픽셀)로 나누고 ViT가 각 패치의 특징 벡터를 계산합니다. 대조 학습으로 텍스트와 정렬된 인코더(CLIP, SigLIP)를 주로 씁니다.
3. **투영:** MLP가 시각 특징을 LLM이 이해하는 임베딩으로 변환합니다. 토큰 수를 줄이기 위해 풀링·압축(Q-Former, 리샘플러)을 쓰기도 합니다.
4. **결합 처리:** 이미지 토큰을 텍스트 프롬프트와 함께 LLM에 넣으면, LLM은 셀프 어텐션으로 텍스트와 이미지 정보를 함께 참조해 답을 생성합니다.

**다른 구조:** 크로스 어텐션으로 이미지 특징을 LLM 층에 주입하는 방식(Flamingo 계열), 처음부터 이미지와 텍스트를 함께 학습하는 네이티브 멀티모달 모델.

**실무 포인트**

- 이미지 한 장이 수백~수천 토큰을 차지해 비용과 지연에 큰 영향을 줍니다.
- 작은 글씨·세밀한 부분은 해상도와 타일링 설정에 따라 인식 성능이 크게 달라집니다.

**더 읽어보기 (영문):** [Multimodal AI](https://outcomeschool.com/blog/multimodal-ai), [How does a Vision-Language Model (VLM) work?](https://outcomeschool.com/blog/vision-language-model-vlm)

<summary><b>Q3. 이미지 임베딩은 어떻게 동작하나요?</b></summary>

**이미지 임베딩** 은 이미지를 그 내용(물체, 장면, 스타일)을 담은 **고정 길이 벡터** 로 표현한 것입니다. 비슷한 이미지는 벡터 공간에서 가깝게 위치합니다.

**생성 방법**

1. **CNN 기반:** ResNet 같은 분류 모델의 마지막 분류층 직전 출력(풀링된 특징)을 임베딩으로 사용.
2. **ViT 기반:** 이미지를 패치로 나눠 트랜스포머로 처리하고 [CLS] 토큰이나 평균 풀링 결과를 사용.
3. **학습 방식에 따른 차이**
   - **지도 학습(분류):** 클래스 구분에 최적화된 특징
   - **자기 지도 학습(DINO, SimCLR):** 같은 이미지의 두 변형본은 가깝게 학습 → 시각적 유사성에 강함
   - **이미지-텍스트 대조 학습(CLIP, SigLIP):** 캡션과 같은 공간에 정렬 → **텍스트로 이미지 검색** 가능

**활용**

- 이미지 검색(비슷한 상품 찾기), 중복·유사 이미지 탐지
- 텍스트-이미지 교차 검색, 제로샷 분류
- 이미지 클러스터링, 추천
- 멀티모달 RAG

**실무 고려 사항**

- 목적에 맞는 모델 선택: 시각적 유사성(같은 디자인의 상품)인지, 의미적 유사성("해변의 일몰")인지에 따라 적합한 모델이 다릅니다.
- 전처리(자르기, 해상도)가 결과에 영향을 줍니다.
- 도메인(의료 영상, 산업 부품)이 다르면 파인튜닝이 필요할 수 있습니다.

**더 읽어보기 (영문):** [How do Image Embeddings work?](https://outcomeschool.com/blog/how-do-image-embeddings-work)

<summary><b>Q4. CLIP은 어떻게 동작하며, 멀티모달 AI에서 왜 중요한가요?</b></summary>

**CLIP (Contrastive Language-Image Pre-training)** 은 OpenAI가 2021년 발표한 모델로, **이미지와 텍스트를 같은 임베딩 공간에 정렬** 합니다.

**구조와 학습**

- **이미지 인코더**(ViT 또는 ResNet)와 **텍스트 인코더**(트랜스포머) 두 개를 둡니다.
- 인터넷에서 모은 약 4억 개의 (이미지, 캡션) 쌍으로 **대조 학습** 을 합니다.
  1. 배치에 N개의 쌍이 있으면 N×N 유사도 행렬을 계산합니다.
  2. 대각선(짝이 맞는 쌍)의 유사도는 높이고, 나머지(짝이 아닌 쌍)는 낮추도록 학습합니다(이미지→텍스트, 텍스트→이미지 양방향 교차 엔트로피).

**제로샷 분류**

- "a photo of a cat", "a photo of a dog" 같은 문장을 임베딩하고, 이미지 임베딩과 가장 가까운 문장을 고르면 별도 학습 없이 분류할 수 있습니다.

**왜 중요한가**

- **멀티모달의 다리:** 텍스트로 이미지를 검색하고, 이미지를 텍스트 공간에서 다룰 수 있게 했습니다.
- **VLM의 눈:** 많은 VLM(LLaVA 등)이 CLIP 계열 비전 인코더를 사용합니다.
- **이미지 생성의 조건화:** Stable Diffusion 등이 CLIP 텍스트 인코더를 프롬프트 이해에 사용했습니다.
- **범용성:** 라벨 데이터 없이 다양한 시각 작업에 활용됩니다.

**한계:** 세밀한 공간 관계·숫자 세기·작은 글씨에 약하고, 웹 데이터의 편향을 그대로 가집니다. 개선 모델로 SigLIP(시그모이드 손실), OpenCLIP 등이 있습니다.

**더 읽어보기 (영문):** [What is Contrastive Learning?](https://outcomeschool.com/blog/contrastive-learning), [How do Image Embeddings work?](https://outcomeschool.com/blog/how-do-image-embeddings-work)

<summary><b>Q5. 멀티모달 모델의 핵심 아키텍처에는 무엇이 있나요?</b></summary>

**1. 듀얼 인코더 (대조 학습형)**

- 모달리티별 인코더가 각자 임베딩을 만들고 같은 공간에서 비교합니다. 예: CLIP, SigLIP, CLAP(오디오).
- 용도: 검색, 분류, 유사도. 생성은 하지 못합니다.

**2. 인코더 + 프로젝터 + LLM (어댑터형, 후기 결합)**

- 사전 학습된 비전 인코더 출력을 프로젝터로 LLM 입력 공간에 맞춰 넣습니다. 예: LLaVA, 많은 오픈 VLM.
- 장점: 기존 LLM과 인코더를 재사용해 학습이 저렴합니다.

**3. 크로스 어텐션 주입형**

- LLM 층 사이에 크로스 어텐션 층을 추가해 이미지 특징을 참조합니다. 예: Flamingo, 일부 Llama 비전 모델.
- 장점: 이미지 토큰을 시퀀스에 직접 넣지 않아 긴 텍스트 처리 비용이 덜 늘어납니다.

**4. 쿼리 기반 압축 (Q-Former, 리샘플러)**

- 학습 가능한 쿼리 토큰이 이미지 특징에서 필요한 정보만 뽑아 적은 수의 토큰으로 압축합니다. 예: BLIP-2.

**5. 네이티브(초기 결합) 멀티모달**

- 처음부터 텍스트·이미지·오디오 토큰을 하나의 모델로 함께 학습합니다. 이미지를 이산 토큰으로 바꿔 생성까지 같은 모델이 하기도 합니다. 예: 최신 상용 멀티모달 모델들, Chameleon 계열 연구.
- 장점: 모달리티 간 깊은 상호작용, 음성 입출력처럼 자연스러운 통합.

**6. 생성 모델**

- 텍스트 조건 확산 모델(이미지·영상 생성), 오디오 코덱 + 자기회귀 모델(음성·음악 생성).

**선택 기준:** 이해만 필요한지 생성까지 필요한지, 학습 비용, 지연(이미지 토큰 수), 모달리티 간 상호작용의 깊이.

**더 읽어보기 (영문):** [Multimodal AI](https://outcomeschool.com/blog/multimodal-ai)

<summary><b>Q6. 확산 모델(Stable Diffusion, DALL-E, Flux)로 이미지를 생성하는 과정은 어떻게 동작하나요?</b></summary>

**핵심 아이디어:** 이미지에 노이즈를 조금씩 더해 완전한 노이즈로 만드는 과정을 정의하고, 그 **역과정(노이즈 제거)** 을 신경망이 학습합니다. 생성 시에는 무작위 노이즈에서 시작해 단계적으로 노이즈를 제거해 이미지를 만듭니다.

**학습**

1. 학습 이미지에 무작위 시점 t의 노이즈를 더합니다.
2. 모델이 "더해진 노이즈"(또는 원본, 속도)를 예측하도록 학습합니다.
3. 텍스트 캡션을 조건으로 함께 넣어, 텍스트에 맞는 이미지를 생성하는 법을 배웁니다.

**생성 (잠재 확산 모델, Stable Diffusion 방식)**

```
프롬프트 → [텍스트 인코더 (CLIP/T5)] → 텍스트 임베딩
무작위 노이즈 (잠재 공간) → [디노이저 (U-Net 또는 DiT)] × N단계
     (각 단계에서 텍스트 임베딩을 크로스 어텐션으로 참조)
→ 깨끗한 잠재 표현 → [VAE 디코더] → 최종 이미지
```

- **잠재 공간:** 픽셀 대신 VAE로 압축한 작은 공간(예: 1/8 해상도)에서 확산을 수행해 계산량을 크게 줄입니다.
- **Classifier-Free Guidance(CFG):** 조건 있는 예측과 조건 없는 예측의 차이를 키워 프롬프트를 더 강하게 따르게 합니다. 값이 너무 크면 이미지가 과포화·부자연스러워집니다.
- **샘플러:** DDPM, DDIM, DPM-Solver 등. 단계 수(예: 20~50)와 품질·속도의 트레이드오프.

**최신 흐름**

- U-Net 대신 **확산 트랜스포머(DiT)**, 노이즈 제거 대신 직선 경로를 학습하는 **흐름 정합(flow matching, rectified flow)** — Stable Diffusion 3, Flux 등이 이런 방식입니다.
- 증류로 1~4단계만에 생성하는 빠른 모델.

**더 읽어보기 (영문):** [Diffusion Models](https://outcomeschool.com/blog/diffusion-models)

<summary><b>Q7. 텍스트 음성 변환(TTS)이란 무엇이며, 어떤 모델이 사용되나요?</b></summary>

**TTS(Text-to-Speech)** 는 텍스트를 자연스러운 음성으로 합성하는 기술입니다.

**전통적인 2단계 구조**

1. **음향 모델:** 텍스트(음소) → 멜 스펙트로그램. 예: Tacotron 2, FastSpeech 2
2. **보코더:** 멜 스펙트로그램 → 파형. 예: WaveNet, HiFi-GAN

**최신 접근**

- **엔드 투 엔드 모델:** VITS처럼 텍스트에서 파형까지 한 번에.
- **오디오 코덱 토큰 + 언어 모델:** 음성을 이산 토큰(EnCodec 등)으로 바꾸고, LLM처럼 자기회귀로 음성 토큰을 생성합니다. 짧은 샘플로 목소리를 복제하는 제로샷 음성 클로닝이 가능해졌습니다(VALL-E 계열).
- **확산·흐름 정합 기반 TTS:** 고품질 음성 생성.
- **음성 네이티브 LLM:** 텍스트 생성과 음성 생성을 하나의 모델이 처리.

**음성 에이전트에서의 스트리밍 TTS**

- 전체 문장이 완성되기를 기다리지 않고, **들어오는 텍스트 조각을 받아 바로 첫 오디오를 만들기 시작** 합니다. 첫 오디오까지의 시간(TTFA)이 대화의 자연스러움을 좌우합니다.
- 문장 단위로 받아 합성하거나, 토큰 단위 증분 합성을 지원하는 모델을 씁니다.

**선택 기준:** 음질·자연스러움, 첫 오디오 지연, 언어·억양 지원, 감정·속도 조절, 음성 클로닝 필요 여부, 비용, 라이선스와 오용 방지(목소리 도용).

<summary><b>Q8. 음성 텍스트 변환(Whisper)은 어떻게 동작하나요?</b></summary>

**Whisper** 는 OpenAI가 2022년 공개한 음성 인식(ASR) 모델로, 약 68만 시간의 다국어 음성-텍스트 데이터로 학습한 **인코더-디코더 트랜스포머** 입니다.

**동작 과정**

1. **전처리:** 오디오를 16kHz로 변환하고 **30초 단위** 로 자릅니다. 각 구간을 로그-멜 스펙트로그램으로 바꿉니다.
2. **인코더:** 스펙트로그램을 합성곱 층과 트랜스포머 인코더로 처리해 음향 표현을 만듭니다.
3. **디코더:** 인코더 출력을 크로스 어텐션으로 참조하며 텍스트 토큰을 자기회귀로 생성합니다.
4. **특수 토큰으로 다중 작업:** 시작 부분의 특수 토큰으로 언어 식별, 전사/번역(영어로) 선택, 타임스탬프 출력 여부를 지정합니다. 하나의 모델이 여러 작업을 처리합니다.

**특징**

- 대규모·다양한 약지도 데이터 덕분에 잡음, 억양, 전문 용어에 비교적 강합니다.
- 다양한 크기(tiny~large)가 있어 속도와 정확도를 선택할 수 있습니다.

**한계와 실무 대응**

- **30초 창 구조:** 실시간 스트리밍에 원래 최적화되어 있지 않습니다. 실시간 용도에는 청크 단위 처리, VAD로 발화 구간 분리, 또는 스트리밍 전용 ASR 모델을 사용합니다.
- **환각:** 무음·잡음 구간에서 없는 문장을 만들어 내는 경우가 있어 VAD로 무음을 제거합니다.
- **화자 분리** 는 기본 제공되지 않아 별도 모델과 결합합니다.
- **가속:** faster-whisper(CTranslate2), whisper.cpp, 증류 모델(distil-whisper), 배치 처리.

**평가 지표:** 단어 오류율(WER), 한국어 등은 문자 오류율(CER)도 함께 봅니다.

<summary><b>Q9. 실시간 음성 에이전트의 엔드 투 엔드 지연 시간 예산(VAD, ASR, LLM, TTS, 네트워크)을 잡아 보세요. 시간은 어디에서 소요되나요?</b></summary>

**측정 기준:** 사용자가 말을 멈춘 순간부터 에이전트의 **첫 오디오가 들리는 순간** 까지(voice-to-voice 지연). 사람 간 대화의 턴 전환은 보통 수백 ms 수준이라, 약 1초를 넘으면 어색하게 느껴지기 시작합니다.

**지연 예산 예시 (캐스케이드 방식, 대략적 범위)**

| 단계 | 대략적 시간 | 설명 |
|---|---|---|
| 오디오 캡처·네트워크 업링크 | 30~100ms | 마이크 버퍼, 패킷 전송 |
| **턴 종료 감지 (VAD/엔드포인팅)** | 200~800ms | 사용자가 말을 마쳤다고 판단하기까지 기다리는 침묵 시간 — **가장 큰 항목인 경우가 많음** |
| ASR 최종화 | 50~200ms | 스트리밍 ASR이면 대부분 이미 처리됨 |
| **LLM 첫 토큰 (TTFT)** | 150~600ms | 모델 크기, 프롬프트 길이, 캐싱 여부 |
| LLM 첫 문장 완성 | 100~300ms | TTS로 넘길 최소 단위 |
| TTS 첫 오디오 | 80~250ms | 스트리밍 TTS 기준 |
| 네트워크 다운링크·재생 버퍼 | 30~100ms | |
| **합계** | **약 0.7~2초** | |

**시간이 가장 많이 드는 곳과 줄이는 방법**

- **턴 감지:** 고정 침묵 시간 대신 의미 기반 턴 감지 모델, 말하는 속도에 맞춘 동적 엔드포인팅, 추측 생성(말이 끝나기 전에 미리 생성 시작).
- **LLM:** 작고 빠른 모델, 짧은 시스템 프롬프트 + 프롬프트 캐싱, 짧은 구어체 응답 지시, 같은 리전 배치.
- **TTS:** 스트리밍 TTS, 첫 문장 단위 즉시 합성.
- **도구 호출:** 필러 발화로 공백 숨기기, 병렬 호출.
- **네트워크:** WebRTC, 사용자와 가까운 리전, 서비스 간 동일 리전.

**측정:** 단계별 타임스탬프를 기록해 p50/p95를 추적하고, 실제 통화에서 사용자 체감(끊김, 겹침)과 함께 봅니다.

<summary><b>Q10. 음성 AI 에이전트의 턴테이킹(turn-taking)이란 무엇이며, 사용자가 말을 마쳤는지 어떻게 감지하나요?</b></summary>

**턴테이킹** 은 대화에서 **누가 언제 말할지** 를 주고받는 과정입니다. 음성 에이전트는 사용자가 말을 끝냈는지 판단해 응답을 시작하고, 사용자가 끼어들면 멈춰야 합니다. 이 판단이 대화의 자연스러움을 크게 좌우합니다.

**사용자가 말을 마쳤는지 감지하기 (엔드포인팅)**

1. **침묵 기반 (VAD + 타임아웃)**
   - 음성 활동 감지(VAD)로 말소리가 멈춘 뒤 일정 시간(예: 500~800ms) 침묵이 이어지면 턴 종료로 판단합니다.
   - 단순하지만, 짧게 잡으면 생각하느라 잠깐 멈춘 사용자의 말을 끊고, 길게 잡으면 응답이 느려집니다.
2. **모델 기반 (의미·운율 판단)**
   - 지금까지의 전사 텍스트(문장이 완결되었는가)와 억양·말끝 운율을 보고 턴이 끝났을 확률을 예측합니다.
   - "제 주문 번호는…"처럼 끝나지 않은 문장에서는 더 기다리고, "네, 그걸로 해 주세요."처럼 완결된 말에서는 빨리 응답합니다.
3. **동적 엔드포인팅**
   - 사용자의 말하는 속도·습관, 대화 맥락(질문에 대한 짧은 대답 vs 긴 설명)에 따라 기다리는 시간을 조절합니다.
4. **긴 생각 멈춤 처리**
   - 숫자를 불러 주거나 정보를 찾느라 멈추는 상황을 고려해, 문맥상 이어질 것 같으면 더 기다리거나 "천천히 말씀하세요" 같은 반응을 보냅니다.

**말을 끊는 실수가 생기는 이유:** 고정된 짧은 침묵 임계값, 잡음·숨소리 처리 미흡, 문맥을 보지 않는 판단.

**평가:** 조기 끊김 비율(사용자가 이어서 말한 비율), 응답 지연, 사용자 만족도를 함께 봅니다.

<summary><b>Q11. 문장 단위 청킹은 음성 에이전트의 지연 시간을 어떻게 줄이나요?</b></summary>

**문제:** LLM이 응답 전체를 다 생성한 뒤 TTS로 넘기면, 긴 응답일수록 사용자는 오래 침묵을 듣게 됩니다.

**문장 단위 청킹**

- LLM이 토큰을 스트리밍하는 동안 버퍼에 쌓다가, **문장 경계(마침표, 물음표, 느낌표, 적절한 쉼표)를 만나면 그 문장을 즉시 TTS로 보냅니다.**
- TTS가 첫 문장을 말하는 동안 LLM은 다음 문장을 계속 생성하므로, 생성과 음성 합성이 **파이프라인처럼 겹쳐** 진행됩니다.

```
LLM:  [문장1 생성][문장2 생성][문장3 생성]
TTS:          [문장1 합성·재생][문장2 합성·재생][문장3 ...]
→ 첫 오디오 시점 = 첫 문장 완성 + TTS 첫 오디오 시간
```

**왜 단어 단위가 아니라 문장 단위인가**

- TTS는 문장 전체를 알아야 자연스러운 억양·강세를 만들 수 있습니다. 너무 잘게 보내면 끊기고 어색한 음성이 됩니다.
- 반대로 너무 길게 모으면 지연이 늘어납니다.

**실무 요령**

- 첫 조각은 짧게(첫 절이나 쉼표에서 끊어 빨리 시작), 이후는 문장 단위로.
- 숫자·약어의 마침표("3.5", "Dr.")를 문장 끝으로 오인하지 않도록 규칙 처리.
- LLM에게 짧은 문장으로 시작하도록 지시하면 효과가 커집니다("네, 확인해 볼게요." 같은 짧은 첫 문장).
- 사용자가 끼어들면 대기 중인 문장들을 즉시 취소합니다.

<summary><b>Q12. 음성 에이전트의 추측성(선제적, speculative/preemptive) LLM 생성이란 무엇이며, 지연 시간을 어떻게 줄이나요?</b></summary>

**아이디어:** 사용자가 말을 **완전히 끝내기 전에**, 지금까지의 부분 전사 결과로 LLM 응답 생성을 미리 시작합니다. 턴 종료가 확정되면 이미 준비된 응답을 바로 내보냅니다.

**동작**

1. 스트리밍 ASR이 부분 전사를 내는 동안, 사용자가 잠시 멈추거나 턴 감지 모델이 "곧 끝날 것 같다"고 판단하면 LLM 생성을 시작합니다.
2. 사용자가 실제로 말을 끝냈고 최종 전사가 추측에 사용한 텍스트와 같거나 의미상 같으면 → 생성된 응답(또는 이미 합성된 첫 오디오)을 즉시 재생합니다.
3. 사용자가 말을 이어 가거나 내용이 바뀌면 → 추측 결과를 버리고 새 전사로 다시 생성합니다.

**효과**

- 턴 감지 대기 시간과 LLM TTFT가 **겹쳐서** 진행되므로 체감 지연이 크게 줄어듭니다.
- 턴 감지를 조금 보수적으로(길게) 잡아도 응답이 느려지지 않아, 말을 끊는 실수와 지연 사이의 균형을 맞추기 쉬워집니다.

**대가와 주의점**

- 버려지는 생성이 생겨 **LLM 비용이 늘어납니다.** 추측 시작 조건을 조정해 낭비를 관리합니다.
- **부작용 있는 행동 금지:** 추측 단계에서는 도구 호출(결제, 예약)을 실행하지 않고, 확정 후에만 실행합니다.
- 추측 결과를 재사용해도 되는지 판단하는 비교 로직(텍스트 일치, 의미 유사도)이 필요합니다.

<summary><b>Q13. 음성 에이전트의 필러 문구(filler phrase)란 무엇이며, 도구 호출의 지연 시간을 어떻게 숨기나요?</b></summary>

**필러 문구** 는 에이전트가 실제 답을 준비하는 동안 침묵을 메우기 위해 먼저 말하는 짧은 발화입니다. 예: "잠시만요, 확인해 볼게요.", "네, 주문 내역을 찾아보고 있어요."

**왜 필요한가**

- 음성 대화에서 1~2초 이상의 침묵은 사용자를 불안하게 만들고, 연결이 끊긴 것으로 오해하게 합니다.
- DB 조회, 외부 API, 검색 같은 도구 호출은 수백 ms~수 초가 걸립니다.

**구현 방식**

1. **LLM이 도구 호출과 함께 짧은 안내를 먼저 생성:** 도구 호출 전 "확인해 볼게요"를 말하도록 프롬프트에 지시하고, 그 문장을 즉시 TTS로 보낸 뒤 도구를 실행합니다.
2. **하네스가 자동으로 삽입:** 도구 호출이 시작되면 도구 종류에 맞는 미리 준비된 문구를 재생합니다(지연이 일정 시간을 넘을 때만).
3. **미리 합성된 오디오:** 자주 쓰는 필러는 미리 합성해 두면 TTS 지연 없이 즉시 재생됩니다.

**자연스럽게 만드는 요령**

- 같은 문구를 반복하지 않도록 여러 변형을 순환합니다.
- 구체적일수록 좋습니다("배송 상태를 조회하고 있어요"가 "잠시만요"보다 신뢰감).
- 짧은 도구 호출에는 필러를 쓰지 않습니다(필러가 오히려 지연을 늘림).
- 대기가 길어지면 진행 상황 업데이트("조금만 더 기다려 주세요")를 추가합니다.

<summary><b>Q14. 음성 에이전트에서 느리거나 오래 걸리는 도구 호출을 어떻게 처리하나요?</b></summary>

**1. 침묵 숨기기**

- 필러 문구로 즉시 반응하고, 대기가 길어지면 주기적으로 진행 상황을 안내합니다.

**2. 비동기 처리**

- 수십 초 이상 걸리는 작업(보고서 생성, 외부 승인)은 대화를 막지 말고 백그라운드로 실행합니다. "확인되면 바로 알려 드릴게요. 그동안 다른 도움이 필요하신가요?"
- 결과가 나오면 대화 흐름에 자연스럽게 끼워 넣거나 문자·이메일로 후속 안내합니다.

**3. 지연 자체 줄이기**

- 독립적인 도구 호출은 병렬로 실행합니다.
- 대화 초반에 필요할 가능성이 높은 데이터(고객 정보, 최근 주문)를 미리 불러옵니다(프리페치).
- 자주 쓰는 조회 결과 캐싱, 빠른 전용 API 사용.

**4. 타임아웃과 실패 처리**

- 도구별 타임아웃을 두고, 실패하면 솔직하게 안내하고 대안을 제시합니다("지금 시스템 응답이 늦어요. 다시 시도할까요, 아니면 상담원을 연결해 드릴까요?").

**5. 대기 중 상호작용**

- 사용자가 기다리는 동안 말하면(끼어들기) 이를 처리할 수 있어야 합니다. 도구 실행은 계속하되 새 발화에 응답하거나, 사용자가 취소를 원하면 중단합니다.

**6. 설계 단계에서**

- 음성 채널에서는 느린 작업을 피하는 도구 설계(요약된 빠른 조회 API)를 우선합니다.

<summary><b>Q15. 음성 에이전트에서 바지인(barge-in, 사용자의 말 끊기)을 어떻게 처리하나요?</b></summary>

**바지인** 은 에이전트가 말하는 도중에 사용자가 끼어들어 말하는 것입니다. 사람 대화에서는 자연스러운 일이므로, 에이전트는 즉시 멈추고 들어야 합니다.

**처리 흐름**

1. **감지:** 에이전트가 말하는 동안에도 사용자 오디오를 계속 듣고 VAD로 음성 시작을 감지합니다.
   - **에코 제거(AEC)** 가 필수입니다. 에이전트 자신의 목소리가 마이크로 다시 들어와 끼어들기로 오인되지 않게 합니다.
2. **진짜 끼어들기인지 판단:** 기침, 배경 소음, "음", "네네" 같은 맞장구(backchannel)는 끼어들기가 아닐 수 있습니다. 최소 발화 길이, 음성 인식 결과(의미 있는 단어인가), 맞장구 분류로 구분합니다.
3. **즉시 중단:** 진짜 끼어들기라면
   - 재생 중인 오디오를 즉시 멈추고(클라이언트 버퍼까지 비우기),
   - 대기 중인 TTS 작업과 LLM 생성을 취소합니다.
4. **맥락 갱신:** 대화 기록에 **실제로 사용자에게 들린 부분까지만** 에이전트 발화로 남깁니다. 말하지 못한 부분을 했다고 기록하면 이후 대화가 어긋납니다.
5. **새 발화 처리:** 사용자의 말을 듣고 응답합니다. "아니, 그게 아니라…" 같은 정정이면 이전 응답을 수정합니다.

**설계 고려**

- 매우 짧은 지연으로 멈추는 것이 중요합니다(멈추는 데 오래 걸리면 대화가 겹쳐 불편).
- 중요한 안내(법적 고지 등)는 끼어들기를 제한하는 구간을 둘 수 있습니다.
- 끼어들기 오탐(소음으로 멈춤)과 미탐(계속 말함) 비율을 측정해 임계값을 조정합니다.

<summary><b>Q16. ASR + LLM + TTS를 이어 붙인 캐스케이드 방식과 네이티브 음성-음성(speech-to-speech) 모델: 각각의 트레이드오프는 무엇인가요?</b></summary>

| 기준 | 캐스케이드 (ASR → LLM → TTS) | 네이티브 음성-음성 모델 |
|---|---|---|
| 지연 | 단계마다 지연이 쌓임 (스트리밍으로 완화) | 낮은 편, 중간 변환 없음 |
| 자연스러움 | 감정·억양 정보가 텍스트 변환에서 손실 | 말투·감정·웃음 등 비언어 정보 이해·표현 |
| 제어·디버깅 | 각 단계의 텍스트를 확인 가능, 문제 지점 파악 쉬움 | 내부가 불투명, 디버깅 어려움 |
| 구성 요소 선택 | 최고의 ASR·LLM·TTS를 각각 고를 수 있음 | 한 모델에 묶임 |
| 도구 호출·추론 | 강한 텍스트 LLM의 추론·도구 능력 그대로 활용 | 모델에 따라 도구 사용·추론이 상대적으로 약할 수 있음 |
| 가드레일 | 텍스트 단계에서 검사·필터 쉬움 | 음성 출력에 대한 실시간 안전 검사가 어려움 |
| 로깅·감사 | 전사 텍스트로 쉽게 기록 | 별도 전사 필요 |
| 비용 | 구성 요소별로 최적화 가능 | 모델 단가에 따라 다름 |
| 목소리 커스터마이징 | TTS로 자유롭게 | 제공되는 목소리로 제한될 수 있음 |

**선택 가이드**

- **캐스케이드가 맞는 경우:** 업무 처리형 에이전트(예약, 고객 지원)처럼 도구 호출이 많고, 정확성·규정 준수·감사가 중요한 경우. 대부분의 프로덕션 콜센터 에이전트.
- **음성-음성이 맞는 경우:** 자연스러운 대화 경험이 핵심인 경우(동반자, 언어 학습, 감정 표현이 중요한 상호작용), 최저 지연이 필요한 경우.
- **혼합:** 음성-음성 모델로 대화하면서 텍스트 전사를 병렬로 생성해 로깅·가드레일에 사용하거나, 복잡한 작업만 텍스트 LLM에 위임하는 구성도 있습니다.

<summary><b>Q17. 반이중(half-duplex) 음성 에이전트와 전이중(full-duplex) 음성 에이전트의 차이는 무엇인가요?</b></summary>

**반이중(half-duplex)**

- 무전기처럼 **한 번에 한 쪽만** 말합니다. 사용자가 말하면 에이전트는 듣고, 에이전트가 말할 때는 사용자 입력을 처리하지 않거나(또는 끼어들기 감지만 하고 멈춤) 순서대로 주고받습니다.
- 대부분의 캐스케이드 음성 에이전트가 이 방식(+ 끼어들기 감지)으로 동작합니다.
- 전형적인 구조: **VAD**(침묵이 일정 시간, 예: 0.5~1초 이어지면 말이 끝났다고 판단) → **ASR**(음성→텍스트) → **LLM** → **TTS**(텍스트→음성) → 재생. 단계마다 지연이 더해지고, 사용자가 잠깐 멈추기만 해도 말을 끊고 답할 수 있습니다.
- 끼어들기(barge-in) 감지는 배경 소음이나 에이전트 자신의 목소리(에코)에 잘못 반응할 수 있어 에코 제거가 필요합니다.
- 장점: 구현이 단순하고 예측 가능, 턴 관리가 명확. 단계 사이에 도구 호출·검증을 끼워 넣기 쉬워 고객 지원 같은 업무형 에이전트에 유리합니다.
- 단점: 대화가 "주고받기"처럼 느껴지고, 맞장구·동시 발화 같은 자연스러운 상호작용이 어렵습니다.

**전이중(full-duplex)**

- 전화 통화처럼 **양쪽이 동시에 말하고 들을 수 있습니다.** 모델이 말하는 동안에도 사용자 음성을 계속 이해하고, 상황에 따라 계속 말할지, 멈출지, 맞장구("네", "음")를 칠지 스스로 판단합니다.
- 주로 음성 입출력을 동시에 처리하는 네이티브 음성 모델로 구현합니다(Moshi 같은 연구 모델 등).
- **Moshi(Kyutai, 2024) 예:** 오디오를 80ms 단위(초당 12.5프레임)로 처리하며, 사용자 음성 스트림과 자기 음성 스트림을 동시에 모델링합니다. 매 프레임 말할지 침묵할지를 모델이 직접 출력하므로 침묵 타이머가 필요 없습니다. 음성 토큰보다 텍스트 토큰을 살짝 먼저 예측해(inner monologue) 내용 품질을 높이고, 이론상 160ms, 실제 약 200ms의 응답 지연을 보고했습니다. 사람 사이 대화의 턴 간격도 보통 200ms 안팎입니다.
- 장점: 사람 대화에 가까운 자연스러움, 빠른 반응, 맞장구와 겹침 처리.
- 단점: 학습·구현이 어렵고, 행동 제어(언제 말할지)·디버깅·안전 검사가 복잡합니다.

| | 반이중 | 전이중 |
|---|---|---|
| 동시 말하기 | 불가 (끼어들기 시 멈춤) | 가능 |
| 턴 결정 | 명시적 엔드포인팅 규칙 | 모델이 연속적으로 판단 |
| 맞장구 | 어려움 | 자연스러움 |
| 성숙도 | 프로덕션 표준 | 발전 중 |

**더 읽어보기 (영문):** [How do half-duplex and full-duplex voice agents differ?](https://outcomeschool.com/blog/half-duplex-vs-full-duplex-voice-agents)

<summary><b>Q18. 멀티모달 RAG란 무엇이며, 텍스트 전용 RAG와 어떻게 다른가요?</b></summary>

**멀티모달 RAG** 는 텍스트뿐 아니라 **이미지, 표, 차트, 도면, 슬라이드, 오디오, 동영상** 같은 다양한 형태의 자료를 검색하고, 이를 멀티모달 LLM에 근거로 제공해 답을 생성하는 방식입니다.

**텍스트 RAG와의 차이**

| 단계 | 텍스트 RAG | 멀티모달 RAG |
|---|---|---|
| 인덱싱 | 텍스트 청크 임베딩 | 이미지·표·영상 장면을 임베딩하거나 텍스트로 변환 |
| 검색 | 텍스트 질의 ↔ 텍스트 | 텍스트 질의 ↔ 이미지/텍스트, 이미지 질의 ↔ 이미지 |
| 생성 | 텍스트 LLM | 이미지 등을 직접 볼 수 있는 멀티모달 LLM |
| 근거 표시 | 문장 인용 | 이미지·페이지·영상 시점 참조 |

**구현 방식**

1. **텍스트화 방식:** 이미지·표를 VLM 캡션, OCR, 표 마크다운으로 변환해 텍스트 RAG로 처리. 간단하지만 시각 정보가 손실될 수 있습니다.
2. **멀티모달 임베딩 방식:** CLIP 계열로 이미지와 텍스트를 같은 공간에 임베딩해 직접 검색.
3. **페이지 이미지 방식:** 문서 페이지를 이미지로 임베딩(ColPali 계열)해 레이아웃·차트를 그대로 검색하고, 검색된 페이지 이미지를 VLM에 넣어 답변.
4. **혼합:** 요약 텍스트로 검색하고 원본 이미지·표를 생성 단계에 전달.

**과제**

- 이미지 토큰 비용과 지연, 모달리티별 점수 척도 차이(병합 시 정규화·RRF), 차트·도면의 정확한 해석, 출처 표시 UI.

**활용 예:** 제품 매뉴얼(그림 포함) Q&A, 의료 영상 보고서, 엔지니어링 도면 검색, 금융 보고서의 차트 질의, 강의 영상 검색.

<summary><b>Q19. 이미지와 텍스트를 모두 처리하는 시스템을 어떻게 만드나요?</b></summary>

**1. 요구사항 정리**

- 무엇을 해야 하나: 이미지 이해(설명, 질의응답, 추출), 이미지 검색, 이미지 생성, 문서(이미지+텍스트) 처리?
- 입력 형태(사진, 스캔 문서, 스크린샷, 차트), 규모, 지연, 개인정보.

**2. 구성 예 (이해·질의응답 중심)**

```
입력 (텍스트 + 이미지) → [전처리: 크기 조정, 형식 변환, EXIF·개인정보 제거]
  → [라우터: 이미지가 필요한 질문인가?]
  → [멀티모달 LLM (VLM)] ← (필요 시) RAG: 관련 문서·이미지 검색
  → [후처리·가드레일 (텍스트 + 이미지 안전성)] → 응답
```

**3. 모델 선택**

- **API 멀티모달 모델:** 빠른 구축, 높은 품질.
- **오픈 VLM 자체 호스팅:** 데이터 통제, 파인튜닝, 대량 처리 비용 절감.
- **특화 모델 조합:** OCR(문서), 객체 탐지, CLIP 임베딩(검색)을 VLM과 함께 사용하면 비용과 정확도를 함께 개선할 수 있습니다.

**4. 설계 포인트**

- **이미지 토큰 비용 관리:** 필요한 해상도로 줄이기, 관심 영역만 잘라 보내기, 이미지가 필요 없는 요청은 텍스트 모델로.
- **저장:** 원본 이미지는 객체 저장소, 컨텍스트에는 참조와 메타데이터.
- **검색이 필요하면:** 멀티모달 임베딩 인덱스 + 캡션·OCR 텍스트 인덱스.
- **안전성:** 이미지 속 텍스트 인젝션, 부적절한 이미지, 개인정보(얼굴, 문서 속 번호).

**5. 평가**

- 이미지 유형별 테스트셋(사진, 차트, 표, 손글씨, 저해상도), 이미지 근거 정확성, 지연·비용.

<summary><b>Q20. 멀티모달 임베딩이란 무엇이며, 교차 모달(cross-modal) 검색에 어떻게 사용되나요?</b></summary>

**멀티모달 임베딩** 은 서로 다른 모달리티(텍스트, 이미지, 오디오 등)를 **하나의 공통 벡터 공간** 에 표현해, 의미가 같은 것끼리 가깝게 놓이도록 한 임베딩입니다. "강아지가 공원에서 뛰는 사진"과 그 문장이 가까운 벡터가 됩니다.

**만드는 방법**

- 모달리티별 인코더를 두고, (이미지, 캡션) 같은 짝 데이터로 **대조 학습** 해 같은 공간에 정렬합니다. 예: CLIP, SigLIP(이미지-텍스트), CLAP(오디오-텍스트), ImageBind(여러 모달리티).
- 최근에는 VLM을 기반으로 이미지와 텍스트를 함께 입력받아 임베딩을 만드는 모델도 있습니다.

**교차 모달 검색 흐름**

```
[인덱싱] 이미지 → 이미지 인코더 → 벡터 → 벡터 DB
[검색]   "빨간 소파가 있는 거실" → 텍스트 인코더 → 벡터 → 가장 가까운 이미지 벡터 검색
```

- 같은 방식으로 이미지 → 텍스트(이미지와 맞는 설명·상품 찾기), 오디오 → 텍스트 검색도 가능합니다.

**활용**

- 상품 이미지 검색("이런 스타일의 원피스"), 사진 라이브러리 검색, 제로샷 분류, 멀티모달 RAG, 콘텐츠 중복 탐지, 영상 장면 검색.

**실무 주의점**

- 텍스트-텍스트, 텍스트-이미지 유사도는 점수 분포가 달라 임계값·병합을 모달리티 조합별로 조정해야 합니다.
- 세밀한 속성(정확한 색상, 숫자, 공간 관계)은 임베딩만으로 구분이 약할 수 있어, 메타데이터 필터·캡션 키워드·VLM 리랭킹으로 보완합니다.
- 도메인 특화 이미지(의료, 산업)는 파인튜닝이 필요할 수 있습니다.

**더 읽어보기 (영문):** [Multimodal AI](https://outcomeschool.com/blog/multimodal-ai)

<summary><b>Q21. 멀티모달 AI 시스템은 어떻게 평가하나요?</b></summary>

**1. 작업별 지표**

| 작업 | 지표 |
|---|---|
| 이미지 캡션 | CIDEr, SPICE, CLIPScore, 사람 평가 |
| 시각적 질의응답(VQA) | 정답 정확도 (MMMU, VQAv2, DocVQA, ChartQA 등 벤치마크) |
| 문서·OCR | 필드 정확도, 문자 오류율(CER) |
| 교차 모달 검색 | recall@k, MRR |
| 이미지 생성 | 프롬프트 일치도(CLIPScore, VQA 기반 평가), 품질(FID, 사람 선호도), 다양성 |
| 음성 | WER(ASR), MOS(TTS 자연스러움), 지연 |

**2. 멀티모달 특유의 평가 항목**

- **시각적 근거성(grounding):** 답이 실제로 이미지 내용에 근거하는가, 이미지를 무시하고 텍스트로만 추측하지 않는가 → 이미지를 바꾸거나 제거했을 때 답이 적절히 바뀌는지 테스트
- **객체 환각:** 이미지에 없는 물체를 말하는 비율(POPE 같은 평가)
- **세밀한 인식:** 작은 글씨, 숫자, 개수 세기, 공간 관계
- **견고성:** 해상도, 회전, 조명, 압축, 다른 촬영 조건

**3. 시스템 평가**

- 자체 평가셋: 실제 입력 이미지 유형(사진, 스크린샷, 문서, 차트)별로 구성
- LLM/VLM 판정자 + 사람 평가 (판정자의 시각 이해 한계를 고려해 사람 검증 비중을 높게)
- 지연, 이미지당 비용

**4. 안전성**

- 교차 모달 공격(이미지 속 지시), 유해 이미지 처리, 얼굴·개인정보 관련 동작, 편향(인물 이미지에 대한 고정관념).

<summary><b>Q22. 실시간 멀티모달 AI 처리의 어려움은 무엇인가요?</b></summary>

**1. 지연**

- 이미지·영상 프레임은 많은 토큰이 되어 TTFT가 길어집니다. 음성 대화는 1초 이내 반응이 필요합니다.
- 대응: 해상도·프레임 수 줄이기, 변화가 있을 때만 프레임 전송, 경량 모델로 1차 처리 후 필요할 때만 대형 모델 호출, 스트리밍 파이프라인.

**2. 데이터량과 대역폭**

- 연속 영상·오디오 스트림은 네트워크와 처리량 부담이 큽니다.
- 대응: 엣지(기기)에서 전처리·압축·이벤트 감지, 필요한 구간만 서버로.

**3. 모달리티 동기화**

- 오디오, 영상, 텍스트의 시간 정렬(립싱크, 화면 내용과 말의 대응)이 필요합니다.
- 대응: 공통 타임스탬프, 버퍼링 전략.

**4. 연속적인 맥락 관리**

- 실시간 스트림은 끝이 없어 컨텍스트가 계속 늘어납니다.
- 대응: 슬라이딩 윈도우, 주기적 요약, 중요한 이벤트만 기억.

**5. 비용**

- 계속 들어오는 데이터를 대형 모델로 모두 처리하면 비용이 폭증합니다.
- 대응: 계층형 처리(경량 감지 → 대형 모델 분석), 샘플링.

**6. 신뢰성과 안전**

- 실시간이라 사람 검토가 어렵고, 오판의 영향이 즉각적입니다(실시간 모더레이션, 자율 시스템).
- 대응: 보수적 임계값, 안전한 기본 동작, 사후 감사 로그.

**7. 환경 변화**

- 소음, 조명, 카메라 흔들림, 네트워크 끊김에 견뎌야 합니다.

<summary><b>Q23. AI로 동영상 이해(video understanding)를 어떻게 처리하나요?</b></summary>

**동영상의 어려움:** 데이터가 매우 크고(초당 수십 프레임), 시간에 따른 변화(동작, 사건 순서)를 이해해야 하며, 오디오·자막 정보도 함께 있습니다.

**처리 파이프라인**

1. **프레임 샘플링**
   - 일정 간격(예: 1~2초당 1프레임) 또는 장면 전환 감지로 키프레임 선택. 움직임이 중요하면 샘플링을 촘촘하게.
2. **시각 인코딩**
   - 프레임을 이미지 인코더로 임베딩하고, 토큰 수를 줄이기 위해 풀링·압축.
   - 시간 정보(프레임 순서, 타임스탬프)를 함께 제공.
3. **오디오·텍스트 정보 결합**
   - ASR로 음성 전사, 자막·OCR(화면 속 텍스트) 추출. 많은 질문이 실제로는 대사·자막으로 답할 수 있습니다.
4. **모델 처리**
   - 동영상 입력을 지원하는 멀티모달 LLM에 프레임 시퀀스 + 전사 텍스트를 넣어 요약·질의응답.
   - 긴 동영상은 구간별로 처리 후 종합(map-reduce)하거나, 장면 단위 인덱스를 만들어 질문과 관련된 구간만 검색해 처리(비디오 RAG).
5. **전용 작업 모델**
   - 동작 인식, 객체 추적, 이벤트 감지 같은 작업은 특화 모델이 더 정확하고 저렴할 수 있습니다.

**활용:** 영상 요약·챕터 생성, 장면 검색, 하이라이트 추출, 보안 영상 이벤트 감지, 강의 영상 Q&A, 콘텐츠 모더레이션.

**비용 관리:** 프레임 수 × 프레임당 토큰이 비용을 결정하므로, 질문 유형에 따라 필요한 구간·해상도만 처리하고 결과를 인덱싱해 재사용합니다.

</details>

<summary><b>Q24. 시각적 질의응답(VQA, Visual Question Answering)이란 무엇인가요?</b></summary>

**VQA** 는 **이미지와 그 이미지에 대한 자연어 질문을 입력받아 답을 생성하는 작업** 입니다.

**예시**

- 이미지: 식탁 사진 / 질문: "접시 위에 사과가 몇 개 있나요?" → "3개"
- 이미지: 영수증 / 질문: "총 결제 금액은?" → "45,000원"
- 이미지: 막대 차트 / 질문: "가장 매출이 높은 분기는?" → "3분기"

**요구되는 능력**

- 물체 인식, 속성(색, 크기), 개수 세기, 공간 관계("왼쪽에 있는"), 글자 읽기(OCR), 상식 추론, 차트·표 해석, 다단계 추론

**접근 방식의 변화**

- **초기:** CNN 이미지 특징 + RNN 질문 인코딩을 결합해 정해진 답 후보 중에서 분류.
- **현재:** 비전-언어 모델(VLM)이 이미지 토큰과 질문을 함께 처리해 자유 형식으로 답을 생성. 대부분의 범용 멀티모달 LLM이 VQA를 수행합니다.

**벤치마크:** VQAv2(일반 사진), TextVQA(이미지 속 글자), DocVQA(문서), ChartQA(차트), MMMU(전문 분야 다학제), 객체 환각 평가(POPE).

**실무 과제**

- **언어 사전 지식 의존:** 이미지를 제대로 보지 않고 질문만으로 그럴듯한 답을 추측하는 경향("바나나는 무슨 색?" → 이미지와 무관하게 "노란색").
- 개수 세기, 작은 글씨, 정확한 공간 관계에서 오류가 잦습니다.
- 개선: 고해상도·타일링, 관심 영역 확대(크롭), 근거 영역 표시 요구, 특화 모델(OCR, 탐지)과 결합.

</details>

<details>
<summary><b>Q25. 문서 이해(document understanding)란 무엇이며, 모델은 레이아웃이 있는 문서를 어떻게 파싱하나요?</b></summary>

**문서 이해** 는 PDF, 스캔 문서, 양식, 송장, 계약서처럼 **텍스트와 레이아웃(위치, 표, 제목 구조, 그림)이 함께 의미를 갖는 문서** 에서 내용과 구조를 추출하고 이해하는 작업입니다.

**왜 텍스트 추출만으로 부족한가**

- 표의 행·열 관계, 양식의 "항목명: 값" 위치 관계, 다단 레이아웃의 읽는 순서, 머리말·각주, 체크박스, 도장·서명은 위치 정보가 있어야 해석됩니다.

**파싱 접근 방식**

1. **파이프라인 방식**
   - OCR(텍스트 + 좌표) → 레이아웃 분석(영역 감지: 제목, 문단, 표, 그림) → 읽는 순서 결정 → 표 구조 인식(셀 복원) → 구조화 출력(마크다운, JSON).
   - 도구: Docling, Unstructured, Marker, PaddleOCR, 클라우드 문서 AI 서비스.
2. **레이아웃 인식 모델**
   - 텍스트 토큰 + 위치 좌표 + 이미지 특징을 함께 입력받는 모델(LayoutLM 계열)로 필드 추출·분류.
3. **OCR 없는 엔드 투 엔드 모델**
   - 문서 이미지를 바로 구조화 텍스트로 변환(Donut, Nougat 계열).
4. **VLM 기반**
   - 페이지 이미지를 멀티모달 LLM에 넣어 마크다운 변환이나 질문 기반 추출. 복잡한 레이아웃에 유연하지만 비용이 크고, 숫자를 잘못 읽는 환각에 주의해야 합니다.

**실무 조합**

- 디지털 PDF는 텍스트 레이어 + 레이아웃 분석, 스캔본은 OCR 또는 VLM, 복잡한 표·차트는 VLM 보완.
- 추출 값은 원문 위치와 함께 저장하고, 합계 검증 같은 규칙으로 확인합니다.

**평가:** 필드 추출 정확도, 표 구조 정확도(TEDS 같은 지표), 읽는 순서 정확도, 문서 유형별 성능.

</details>

<summary><b>Q26. 비전-언어 모델은 어떻게 파인튜닝하나요?</b></summary>

**1. 목적 정의**

- 특정 도메인 이미지 이해(의료 영상, 산업 결함, 위성 사진), 특정 문서 양식 추출, 출력 형식 고정, 특정 언어 지원 등.

**2. 데이터 준비**

- (이미지, 지시/질문, 답변) 형식의 대화 데이터를 모델의 채팅 템플릿에 맞춰 만듭니다.
- 실제 사용 분포를 반영하고, 어려운 사례(작은 글씨, 저화질, 애매한 사례)를 포함합니다.
- 라벨 품질이 핵심 — 도메인 전문가 검수. 강한 VLM으로 초안을 만들고 사람이 수정하는 방식도 효율적입니다.

**3. 무엇을 학습할지 선택**

| 대상 | 언제 |
|---|---|
| LLM 부분만 (LoRA) | 출력 형식, 도메인 용어, 추론 방식 적응 — 가장 흔함 |
| 프로젝터 | 시각 특징과 언어의 정렬 개선 |
| 비전 인코더 | 이미지 도메인이 일반 사진과 크게 다를 때(의료, 위성) — 데이터·비용이 더 필요 |

- 메모리 절약: QLoRA, 그래디언트 체크포인팅, 이미지 해상도·타일 수 조정.

**4. 학습 설정**

- 낮은 학습률, 1~3 에포크, 검증 손실과 작업 지표로 조기 종료.
- 망각 방지를 위해 일반 멀티모달 데이터를 일부 섞습니다.

**5. 평가**

- 학습에 쓰지 않은 이미지로 작업 정확도, 객체 환각률, 이미지 근거성(이미지를 바꿨을 때 답이 바뀌는지), 일반 능력 유지 여부.

**도구:** Hugging Face Transformers + PEFT + TRL, 모델별 공식 파인튜닝 스크립트, LLaMA-Factory 등.

<details>
<summary><b>Q27. 프로덕션에서 멀티모달 AI의 지연 시간과 비용 측면의 고려 사항은 무엇인가요?</b></summary>

**비용·지연의 주요 원인**

- **이미지 토큰:** 이미지 한 장이 해상도에 따라 수백~수천 토큰이 됩니다. 고해상도 타일링은 토큰을 크게 늘립니다.
- **동영상:** 프레임 수 × 프레임당 토큰.
- **오디오:** 초당 토큰 수, 실시간 처리 시간.
- **업로드·전처리:** 큰 파일의 전송과 디코딩.

**최적화 방법**

1. **해상도와 양 줄이기**
   - 작업에 필요한 최소 해상도로 축소, 관심 영역만 잘라서 전송.
   - 동영상은 키프레임만, 오디오는 무음 제거(VAD).
   - API의 "low detail" 같은 저해상도 모드 활용.
2. **라우팅과 계층 처리**
   - 이미지가 필요 없는 질문은 텍스트 모델로.
   - OCR·분류·탐지 같은 작업은 전용 경량 모델로 처리하고, 복잡한 추론만 대형 VLM으로.
3. **캐싱과 재사용**
   - 같은 이미지에 대한 캡션·임베딩·OCR 결과를 저장해 재사용.
   - 같은 이미지에 여러 질문을 하면 프롬프트 캐싱 활용(이미지를 프롬프트 앞부분에 고정).
4. **비동기·배치**
   - 실시간이 필요 없는 문서·영상 처리는 배치 API, 큐 기반 처리.
5. **엣지 처리**
   - 기기에서 압축·필터링·간단한 판단을 먼저 수행.
6. **스트리밍**
   - 음성·생성 결과를 스트리밍해 체감 지연 단축.

**측정:** 요청 유형별 입력 토큰(이미지 토큰 포함), 지연 p95, 요청당 비용을 분리해 추적하고, 해상도·프레임 설정 변경 시 품질 평가와 함께 비교합니다.

</details>

<summary><b>Q28. 멀티모달 콘텐츠 모더레이션을 어떻게 처리하나요?</b></summary>

**과제:** 텍스트, 이미지, 오디오, 동영상, 그리고 이들의 **조합** 이 위반을 만들 수 있습니다. 각각은 무해하지만 함께 보면 혐오가 되는 밈(이미지 + 문구)이 대표적입니다.

**처리 구조**

```
콘텐츠 → [모달리티별 전처리]
   텍스트: 정규화
   이미지: 해시 매칭(알려진 불법 콘텐츠), OCR(이미지 속 글자)
   오디오: ASR 전사
   동영상: 키프레임 + 오디오 전사
 → [모달리티별 경량 분류기] (노출, 폭력, 혐오 상징, 무기, 독성 텍스트)
 → [결합 판단] 멀티모달 모델로 이미지+텍스트 맥락 해석 (애매한 경우만)
 → [정책 판정과 조치] 허용 / 연령 제한 / 흐림 처리 / 삭제 / 사람 검토
```

**핵심 설계 포인트**

- **비용 계층화:** 대부분은 해시·경량 분류기로 처리하고, 애매하거나 고위험인 경우만 비싼 멀티모달 모델·사람 검토로.
- **교차 모달 맥락:** 밈, 풍자, 뉴스 보도처럼 맥락에 따라 판단이 다른 경우를 위해 텍스트와 이미지를 함께 보는 판정 단계.
- **최우선 범주:** 아동 안전(알려진 해시 매칭 + 분류기 + 즉시 신고 절차), 테러·극단주의, 자해.
- **적대적 회피 대응:** 이미지 속 글자, 왜곡된 텍스트, 이미지 변형, 오디오 속 메시지.
- **지역·문화 정책:** 지역별 기준과 현지 검토자.

**운영:** 사람 검토 도구(검토자 보호 기능 포함), 이의 제기, 정책별 정밀도·재현율 모니터링, 새로운 위반 유형을 학습 데이터로 반영.

<summary><b>Q29. 텍스트-동영상 생성이란 무엇이며, 현재 최신 기법에는 무엇이 있나요?</b></summary>

**텍스트-동영상 생성** 은 텍스트 프롬프트(필요하면 이미지·참조 영상)로 동영상을 만들어 내는 기술입니다. 이미지 생성보다 훨씬 어려운 이유는 **시간적 일관성**(물체·인물이 프레임 간에 유지됨), **물리적 자연스러움**(움직임, 충돌), **긴 시간 구조** 를 함께 만족해야 하기 때문입니다.

**주요 기법 (발전 흐름)**

1. **이미지 확산 모델의 시간 확장**
   - 이미지 확산 모델에 시간 축 어텐션·합성곱 층을 추가해 프레임 간 일관성을 학습.
2. **잠재 비디오 확산 + 확산 트랜스포머(DiT)**
   - 동영상을 비디오 VAE로 압축한 시공간 잠재 공간에서, 시공간 패치를 트랜스포머로 처리하며 노이즈를 제거합니다. 여러 해상도·길이·화면비를 하나의 모델로 처리할 수 있습니다. 최근 주요 상용·오픈 모델 대부분이 이 계열입니다.
3. **흐름 정합(flow matching)** 같은 학습 목표로 효율 개선.
4. **자기회귀·하이브리드 방식**
   - 동영상을 토큰으로 바꿔 순차 생성하거나, 확산과 결합해 긴 영상을 이어서 생성.
5. **제어와 조건화**
   - 이미지→동영상, 카메라 움직임 제어, 포즈·깊이 맵 조건, 참조 인물·스타일 유지, 오디오 동시 생성.

**주요 과제**

- 막대한 학습·추론 연산량, 긴 영상에서의 일관성, 물리 법칙 위반(손가락, 물체 통과), 텍스트 렌더링.
- 딥페이크·저작권 등 오용 위험 → 워터마킹, C2PA, 실존 인물 생성 제한.

**평가:** 프롬프트 일치도, 시간적 일관성, 화질, 움직임의 자연스러움(사람 평가와 VBench 같은 벤치마크).

</details>

<summary><b>Q30. 멀티모달 융합 기법을 설명하세요: 초기 융합(Early Fusion)과 후기 융합(Late Fusion).</b></summary>

**융합(fusion)** 은 서로 다른 모달리티의 정보를 **어느 단계에서, 어떻게 합칠지** 에 대한 설계입니다.

**초기 융합 (Early Fusion)**

- 모달리티를 **입력 또는 낮은 수준의 특징 단계에서 합친 뒤** 하나의 모델이 함께 처리합니다.
- 예: 이미지 패치 토큰과 텍스트 토큰을 처음부터 하나의 시퀀스로 트랜스포머에 넣기, 네이티브 멀티모달 모델.
- 장점: 모달리티 간 세밀한 상호작용을 처음부터 학습(예: 이미지의 특정 부분과 단어의 관계).
- 단점: 학습 비용이 크고, 모달리티별 데이터가 짝으로 많이 필요하며, 한 모달리티가 빠지면 대응이 어렵습니다.

**후기 융합 (Late Fusion)**

- 모달리티마다 **독립된 모델이 각각 결과(점수, 예측)를 낸 뒤 마지막에 합칩니다.**
- 예: 이미지 분류기 점수 + 텍스트 분류기 점수를 가중 평균하거나 투표, 검색에서 모달리티별 결과를 RRF로 병합.
- 장점: 단순하고, 모달리티별 최적 모델을 따로 쓰며, 일부 모달리티가 없어도 동작합니다.
- 단점: 모달리티 간 상호작용을 거의 반영하지 못합니다(밈처럼 조합으로만 의미가 생기는 경우를 놓침).

**중간 융합 (Intermediate / Hybrid Fusion)**

- 각 모달리티를 어느 정도 따로 인코딩한 뒤, **중간 표현 단계에서 합칩니다.**
- 예: 비전 인코더 출력을 프로젝터로 LLM에 주입(LLaVA), 크로스 어텐션으로 연결(Flamingo).
- 사전 학습된 인코더를 재사용하면서 상호작용도 학습할 수 있어 현재 VLM에서 가장 흔합니다.

| | 초기 융합 | 중간 융합 | 후기 융합 |
|---|---|---|---|
| 상호작용 | 가장 깊음 | 중간~깊음 | 얕음 |
| 학습 비용 | 높음 | 중간 | 낮음 |
| 모달리티 누락 대응 | 어려움 | 중간 | 쉬움 |

</details>

<summary><b>Q31. 비전-언어 모델이 사실과 다른 이미지 설명을 생성합니다. 어떻게 고치나요?</b></summary>

**흔한 오류 유형:** 이미지에 없는 물체를 언급(객체 환각), 개수·색·위치 오류, 글자 잘못 읽기, 일반적인 장면 지식으로 추측해 채우기.

**원인**

- 언어 모델의 사전 지식이 강해 "보통 이런 장면에는 이런 것이 있다"고 추측
- 해상도 부족으로 세부를 보지 못함
- 학습 데이터 캡션의 부정확성
- 길게 설명할수록 뒷부분에서 환각 증가

**해결 방법**

1. **입력 품질 개선**
   - 고해상도·타일링 모드 사용, 관심 영역 확대(크롭) 후 재질문.
2. **프롬프트 개선**
   - "이미지에서 명확히 보이는 것만 설명하고, 확실하지 않으면 불확실하다고 표시하라."
   - 자유 설명 대신 구조화 질문(물체 목록 → 각 속성)으로 나눠 묻기.
   - 설명을 짧게 제한(긴 설명일수록 환각 증가).
3. **도구로 검증**
   - 객체 탐지 모델로 언급된 물체가 실제로 있는지 확인, OCR로 글자 확인, 개수는 탐지 결과로 계산.
   - 두 번째 VLM 호출로 "이 설명의 각 항목이 이미지에 있는가?" 검증(자기 검증).
4. **디코딩 기법**
   - 이미지를 약화시킨 입력과 비교해 언어 사전 지식에만 의존한 토큰을 억제하는 방법(대조 디코딩 계열) 같은 연구 기법도 있습니다.
5. **모델 개선**
   - 환각 평가가 좋은 모델로 교체, 정확한 캡션과 "없는 물체" 부정 사례를 포함한 데이터로 파인튜닝, 선호도 학습으로 환각을 벌점화.

**측정:** 객체 환각 평가(POPE 류), 자체 이미지 세트의 사실 정확도, 항목별 오류율.

</details>

<summary><b>Q32. VLM이 단일 이미지 질문에는 답하지만 여러 페이지 문서에서는 실패합니다. 어떻게 고치나요?</b></summary>

**실패 원인**

- 여러 페이지 이미지를 모두 넣으면 이미지 토큰이 폭증해 컨텍스트 한도를 넘거나, 해상도를 낮춰 글자를 읽지 못합니다.
- 페이지 간 정보를 연결(표가 다음 페이지로 이어짐, 앞 페이지 정의 참조)하는 추론이 약합니다.
- 많은 이미지 속에서 필요한 페이지를 찾지 못합니다(긴 컨텍스트의 중간 정보 누락과 비슷).

**해결 방법**

1. **페이지 검색 후 질의 (멀티모달 RAG)**
   - 각 페이지를 임베딩(페이지 이미지 임베딩 또는 텍스트 추출 후 임베딩)해 인덱싱하고, 질문과 관련된 상위 몇 페이지만 VLM에 넣습니다.
2. **텍스트·구조 추출 병행**
   - 문서 파서·OCR로 전체 텍스트와 표를 마크다운으로 추출해 텍스트 LLM이 처리하고, 차트·그림처럼 시각 정보가 필요한 페이지만 이미지로 제공합니다.
3. **페이지별 처리 후 종합 (map-reduce)**
   - 각 페이지에서 질문 관련 정보를 추출하고, 결과를 모아 최종 답을 만듭니다.
4. **문서 구조 활용**
   - 목차·제목 계층을 먼저 파악해 관련 섹션 페이지로 이동하는 에이전트 방식.
5. **입력 구성 개선**
   - 페이지 번호를 명시하고, 이어지는 표는 페이지를 합쳐 하나로 제공.
6. **모델 선택·파인튜닝**
   - 다중 이미지·긴 문서 벤치마크(멀티페이지 DocVQA 류) 성능이 좋은 모델 사용, 다중 페이지 문서 데이터로 파인튜닝.

**평가:** 페이지 수별, 정답이 위치한 페이지별, 여러 페이지 정보 결합이 필요한 질문별 정확도를 따로 측정합니다.

</details>

<summary><b>Q33. 멀티모달 LLM이 이미지를 무시하고 텍스트만으로 설명을 생성합니다. 어떻게 고치나요?</b></summary>

**증상 확인 방법:** 이미지를 다른 이미지로 바꾸거나 빈 이미지를 넣어도 답이 거의 같으면, 모델이 이미지를 보지 않고 텍스트 단서(질문, 파일명, 주변 문맥)만으로 추측하는 것입니다.

**원인**

- **언어 사전 지식 우세:** 질문 자체에 답의 힌트가 있거나, 흔한 패턴으로 추측 가능할 때 이미지를 덜 봅니다.
- **입력 문제:** 이미지가 실제로 전달되지 않음(형식 오류, 업로드 실패), 해상도가 너무 낮음, 이미지가 프롬프트의 엉뚱한 위치에 있음.
- **텍스트 컨텍스트 과다:** 긴 텍스트가 이미지 정보를 묻음.
- **학습 편향:** 텍스트만으로 풀리는 학습 데이터가 많았음.

**해결 방법**

1. **입력 파이프라인 점검**
   - 이미지가 실제로 모델에 들어가는지, 해상도·형식이 맞는지 확인합니다(가장 먼저).
2. **프롬프트 개선**
   - "이미지에 보이는 내용만을 근거로 답하라", "답의 근거가 되는 이미지 속 요소를 먼저 서술하라"처럼 시각적 근거를 요구합니다.
   - 이미지를 질문 앞에 배치하는 등 모델 권장 순서를 따릅니다.
   - 오해를 부르는 텍스트 단서(파일명, 무관한 설명)를 제거합니다.
3. **단계 분리**
   - 1단계: 이미지에서 관련 사실 추출(관찰) → 2단계: 그 관찰을 바탕으로 답변(추론).
4. **해상도·크롭**
   - 세부가 중요하면 고해상도 모드나 관심 영역 확대.
5. **모델 개선**
   - 시각적 근거성이 좋은 모델로 교체, 이미지 없이는 답할 수 없는 데이터(같은 질문·다른 이미지 → 다른 답)로 파인튜닝.

**평가:** 이미지 교체·제거 테스트를 평가셋에 포함해 "이미지 의존도"를 지표로 관리합니다.

</details>

<details>
<summary><b>Q34. 확산 모델이 텍스트 프롬프트의 정밀한 제어 요구 사항을 무시합니다. 제어 가능성을 어떻게 높이나요?</b></summary>

**흔한 실패:** 물체 개수("사과 3개"), 공간 배치("왼쪽에 고양이, 오른쪽에 개"), 속성 결합("빨간 컵과 파란 책" → 색이 뒤바뀜), 이미지 속 글자, 특정 포즈·구도.

**원인:** 텍스트 인코더가 복잡한 문장 구조를 충분히 표현하지 못하고, 학습 캡션이 이런 세부를 정확히 담지 않았기 때문입니다.

**개선 방법**

1. **더 나은 모델·텍스트 인코더**
   - 큰 언어 모델 기반 텍스트 인코더(T5 계열 등)를 쓰는 최신 모델은 복잡한 프롬프트를 더 잘 따릅니다.
2. **프롬프트 설계**
   - 명확하고 구체적으로, 중요한 요소를 앞쪽에. LLM으로 사용자 프롬프트를 상세한 설명으로 확장(프롬프트 리라이팅).
   - 네거티브 프롬프트로 원치 않는 요소 제외.
3. **가이던스 조정**
   - CFG 스케일을 높이면 프롬프트를 더 강하게 따르지만, 너무 높으면 품질이 떨어집니다.
4. **구조적 조건 제어**
   - **ControlNet / T2I-Adapter:** 윤곽선, 깊이 맵, 포즈 골격, 분할 맵으로 구도·형태를 정확히 지정.
   - **영역 지정 생성:** 바운딩 박스·마스크로 위치별 프롬프트 지정(GLIGEN, 영역 프롬프트).
   - **IP-Adapter, 참조 이미지:** 스타일·인물 일관성 유지.
5. **반복 편집**
   - 인페인팅으로 틀린 부분만 다시 생성, 지시 기반 이미지 편집 모델.
6. **생성 후 검증과 재시도**
   - VLM·객체 탐지로 개수·배치·글자를 검사하고, 조건을 만족하는 결과만 선택(여러 장 생성 후 고르기).
7. **파인튜닝**
   - 정밀한 캡션 데이터로 파인튜닝하거나, 특정 개념은 LoRA·DreamBooth로 학습.

</details>

<details>
<summary><b>Q35. 확산 모델이 선명하지만 반복적인 이미지를 생성합니다. 품질과 다양성의 균형을 어떻게 맞추나요?</b></summary>

**원인**

- **높은 CFG(가이던스) 스케일:** 프롬프트를 강하게 따르게 하면 선명하고 정확해지지만, 결과가 비슷비슷해지고(모드 붕괴처럼), 색이 과포화됩니다.
- **증류된 소수 단계 모델:** 빠른 대신 다양성이 줄어드는 경향.
- **선호도 학습·미적 파인튜닝:** 특정 "보기 좋은" 스타일로 수렴.
- **같은 시드·고정된 프롬프트 템플릿.**

**균형 맞추는 방법**

1. **가이던스 조정**
   - CFG 스케일을 낮추면 다양성이 늘어납니다. 품질과 다양성을 함께 측정하며 최적값을 찾습니다.
   - **가이던스 일정 조절:** 생성 초기(전체 구도 결정)에는 약하게, 후반(세부)에는 강하게 적용하거나, 일부 구간에만 가이던스를 적용하는 기법.
2. **샘플링 다양화**
   - 시드 다양화, 확률적 샘플러(노이즈를 추가하는 샘플러), 초기 노이즈 다양화.
3. **프롬프트 다양화**
   - LLM으로 같은 의도의 다양한 프롬프트 변형(구도, 조명, 스타일)을 생성해 사용.
4. **모델 차원**
   - 다양한 데이터로 파인튜닝, 선호도 학습 시 다양성 손실 관리, 다양성을 보존하는 증류 기법.
5. **선택 단계**
   - 여러 장을 생성한 뒤 서로 다른 결과를 골라 보여 주기(임베딩 거리 기반 다양성 선택).

**측정:** 품질(사람 선호도, 미적 점수), 프롬프트 일치도, 다양성(생성 이미지 간 임베딩 거리, 서로 다른 결과 비율), FID·정밀도/재현율 계열 지표를 함께 봅니다.

</details>

<details>
<summary><b>Q36. 확산 모델이 이미지 한 장을 만드는 데 너무 오래 걸립니다. 샘플링 속도를 어떻게 높이나요?</b></summary>

**속도를 결정하는 요소:** (샘플링 단계 수) × (단계당 디노이저 계산량) + VAE 디코딩 + 오버헤드.

**1. 단계 수 줄이기**

- **고급 샘플러:** DPM-Solver++, UniPC 같은 ODE 솔버는 20~30단계로도 좋은 품질을 냅니다(초기 DDPM의 수백~천 단계 대비).
- **증류 모델:** 일관성 모델(LCM), 적대적 확산 증류(SDXL Turbo 계열), 정류 흐름 증류 등으로 **1~4단계** 생성. 다양성·세부 품질이 약간 줄어들 수 있습니다.
- **흐름 정합 모델:** 직선에 가까운 경로를 학습해 적은 단계로도 품질 유지.

**2. 단계당 계산 줄이기**

- **저정밀도:** FP16/BF16, FP8, 양자화.
- **컴파일·커널 최적화:** torch.compile, TensorRT, Flash Attention, xFormers.
- **캐싱:** 인접 단계 간 변화가 작은 중간 특징을 재사용하는 기법(DeepCache 계열 등).
- **CFG 비용 줄이기:** CFG는 단계마다 두 번 계산하므로, 가이던스 증류 모델이나 일부 단계만 CFG 적용.
- **작은 모델·낮은 해상도:** 저해상도로 생성 후 업스케일러로 확대.

**3. 시스템 수준**

- **배치 처리:** 여러 요청을 묶어 GPU 활용률 향상.
- **빠른 미리보기:** 적은 단계·저해상도로 먼저 보여 주고, 선택된 것만 고품질로 다시 생성.
- **경량 VAE 디코더:** 디코딩 시간 단축(TAESD 같은 근사 디코더는 미리보기에 유용).
- 하드웨어 업그레이드, 다중 GPU 병렬화.

**평가:** 각 최적화 후 지연과 함께 품질(사람 선호, 프롬프트 일치도)을 비교해 허용 가능한 손실인지 확인합니다.

</details>
