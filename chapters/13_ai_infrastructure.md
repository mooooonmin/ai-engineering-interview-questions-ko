<summary><b>Q1. 프로덕션 LLM 배포에서 추론 속도를 어떻게 높이나요?</b></summary>

**먼저 무엇을 빠르게 할지 구분:** 첫 토큰까지 시간(TTFT), 토큰 생성 속도(TPOT), 전체 처리량(throughput). 각각 최적화 방법이 다릅니다.

**모델 수준**

- **양자화:** FP8/INT8/INT4로 메모리 읽기량을 줄여 디코드 가속(디코드는 메모리 대역폭 병목).
- **작은 모델·증류:** 품질이 허용되는 가장 작은 모델 사용.
- **효율적 구조:** GQA/MLA(작은 KV 캐시), MoE(토큰당 계산 감소).

**디코딩 수준**

- **추측 디코딩:** 드래프트 모델·Medusa·EAGLE·MTP로 한 번에 여러 토큰 검증.
- 출력 길이 줄이기(간결한 응답, 구조화 출력).

**서빙 엔진 수준**

- **연속 배칭 + PagedAttention:** GPU 활용률·처리량 대폭 향상(vLLM, SGLang, TensorRT-LLM).
- **프리픽스(프롬프트) 캐싱:** 반복 프롬프트의 프리필 생략 → TTFT 감소.
- **청크 프리필, 프리필-디코드 분리:** 혼합 트래픽에서 지연 안정화.
- 최적화 커널: Flash Attention, CUDA 그래프, 커널 퓨전.

**하드웨어·병렬화**

- 최신 GPU(높은 메모리 대역폭, FP8 지원), 텐서 병렬화로 단일 요청 지연 감소.

**애플리케이션 수준**

- 프롬프트 길이 최적화, 시맨틱 캐시, 스트리밍(체감 지연), 라우팅(쉬운 요청은 작은 모델), 병렬 호출.

**측정:** 실제 트래픽과 비슷한 부하로 TTFT·TPOT·처리량을 벤치마크하고, 최적화마다 품질 평가를 함께 확인합니다.

<summary><b>Q2. LLM 최적화 기법</b></summary>

LLM 최적화는 **메모리, 연산, 지연, 처리량, 비용** 을 개선하는 기법들로 나눌 수 있습니다.

| 기법 | 무엇을 개선하나 | 핵심 아이디어 |
|---|---|---|
| **양자화** | 메모리, 디코드 속도 | 가중치·KV 캐시를 낮은 비트로 |
| **KV 캐시** | 생성 속도 | 이전 토큰의 K·V 재사용 |
| **PagedAttention** | 메모리 효율, 배치 크기 | KV 캐시를 블록 단위로 관리 |
| **연속 배칭** | 처리량 | 끝난 요청 자리에 즉시 새 요청 투입 |
| **Flash Attention** | 메모리, 속도 | 어텐션을 블록 단위로 SRAM에서 계산 |
| **추측 디코딩** | 생성 지연 | 초안 토큰을 한 번에 검증 |
| **프리픽스 캐싱** | TTFT, 비용 | 공통 프롬프트 KV 재사용 |
| **GQA/MQA/MLA** | KV 캐시 크기 | K·V 헤드 공유·압축 |
| **MoE** | 토큰당 연산 | 일부 전문가만 활성화 |
| **증류** | 모델 크기 | 큰 모델 능력을 작은 모델로 |
| **가지치기(pruning)** | 모델 크기 | 중요도 낮은 가중치·층 제거 |
| **텐서·파이프라인 병렬화** | 큰 모델 실행, 지연 | 여러 GPU에 분산 |
| **프리필-디코드 분리** | 지연 안정성 | 두 단계를 다른 GPU 풀에서 |

**적용 순서 제안**

1. 좋은 서빙 엔진 사용(연속 배칭, PagedAttention, 프리픽스 캐싱이 기본 제공)
2. 양자화(FP8 또는 INT4) — 품질 평가와 함께
3. 프롬프트·출력 길이 최적화, 캐싱
4. 추측 디코딩
5. 더 작은 모델·증류·라우팅

<summary><b>Q3. LLM 추론용 GPU는 어떻게 고르나요?</b></summary>

**1. 메모리 용량 (가장 먼저)**

- 필요 메모리 ≈ 가중치 + KV 캐시 + 활성화·오버헤드
  - 가중치: 파라미터 수 × 바이트 수 (70B × FP16 2바이트 ≈ 140GB, INT4 ≈ 35~40GB)
  - KV 캐시: 컨텍스트 길이 × 동시 요청 수에 비례 (긴 컨텍스트·큰 배치면 가중치보다 커질 수 있음)
- 한 장에 안 들어가면 텐서 병렬화로 여러 장(같은 노드 내 고속 연결 필요).

**2. 메모리 대역폭**

- 디코드는 메모리 대역폭 병목이라, **토큰 생성 속도는 대역폭에 크게 좌우** 됩니다. HBM 대역폭이 높은 GPU가 유리합니다.

**3. 연산 성능과 지원 정밀도**

- 프리필(긴 프롬프트)·큰 배치는 연산 성능(TFLOPS)이 중요합니다.
- FP8·FP4를 하드웨어로 지원하면 양자화 이득이 큽니다.

**4. GPU 간 연결**

- 여러 GPU로 큰 모델을 돌리면 NVLink 같은 고속 연결이 지연에 큰 영향을 줍니다.

**5. 소프트웨어 생태계**

- 서빙 엔진·커널 지원(CUDA 생태계가 가장 성숙, AMD ROCm 등도 발전 중).

**6. 비용 효율**

- **처리량당 비용**($/백만 토큰)으로 비교합니다. 비싼 GPU가 더 많은 요청을 처리해 결국 더 저렴할 수 있습니다.
- 가용성(클라우드 재고), 예약·스팟 가격.

**예시 판단**

- 7~8B 모델, 소규모 트래픽: 24~48GB급 GPU 한 장
- 70B 모델: 80GB급 GPU 여러 장(FP16) 또는 양자화 시 1~2장
- 대규모 MoE·긴 컨텍스트: 고대역폭·대용량 메모리 GPU 여러 장, 노드 간 고속 네트워크

**결론:** 후보 GPU에서 실제 모델·트래픽 패턴으로 벤치마크해 **SLO를 만족하는 처리량당 비용** 이 가장 낮은 것을 고릅니다.

<summary><b>Q4. 딥러닝에서 GPU는 어떻게 동작하나요?</b></summary>

**왜 GPU인가:** 딥러닝의 핵심 연산은 **대규모 행렬 곱셈** 이고, 이는 서로 독립적인 수많은 곱셈·덧셈으로 나눌 수 있습니다. CPU는 소수의 강력한 코어로 복잡한 순차 작업에 강하고, GPU는 **수천 개의 단순한 코어로 같은 연산을 대량 병렬 처리** 하는 데 강합니다.

**GPU의 구조 (NVIDIA 기준)**

- **SM(Streaming Multiprocessor):** GPU는 수십~백여 개의 SM으로 구성되고, 각 SM에 많은 CUDA 코어와 **텐서 코어** 가 있습니다.
- **텐서 코어:** 작은 행렬 곱셈-누산(예: 4×4)을 한 번에 처리하는 전용 유닛. FP16, BF16, FP8 같은 저정밀도에서 매우 빠릅니다. 딥러닝 성능의 핵심입니다.
- **실행 모델:** 수천 개의 스레드를 32개 묶음(warp)으로 같은 명령을 동시에 실행합니다(SIMT).

**메모리 계층**

| 메모리 | 크기 | 속도 |
|---|---|---|
| 레지스터 | 매우 작음 | 가장 빠름 |
| 공유 메모리 / L1 (SM 내부 SRAM) | 수백 KB/SM | 매우 빠름 |
| L2 캐시 | 수십 MB | 빠름 |
| HBM (GPU 메인 메모리) | 수십~수백 GB | 대역폭 높지만 상대적으로 느림 |

- 성능 최적화의 핵심은 **느린 HBM 접근을 줄이고 빠른 SRAM에서 최대한 계산하는 것** 입니다(Flash Attention의 원리).

**병목 개념**

- **연산 병목:** 큰 행렬곱(학습, 프리필) → 텐서 코어 성능이 한계
- **메모리 병목:** 데이터 읽기가 연산보다 많음(LLM 디코드) → 메모리 대역폭이 한계

**학습과 추론**

- 학습: 순전파·역전파 모두 큰 행렬곱 + 큰 메모리(가중치·기울기·옵티마이저 상태), 여러 GPU 간 통신(NVLink, InfiniBand).
- 추론: 배치·양자화·KV 캐시 관리로 GPU 활용률을 높이는 것이 관건.

<summary><b>Q5. CUDA 커널은 어떻게 동작하나요?</b></summary>

**CUDA 커널** 은 GPU에서 실행되는 함수입니다. CPU(호스트)가 커널을 실행(launch)하면, GPU에서 **수많은 스레드가 같은 코드를 서로 다른 데이터에 대해 동시에 실행** 합니다.

**실행 계층**

- **스레드(thread):** 가장 작은 실행 단위. 자기 인덱스로 처리할 데이터를 결정합니다.
- **블록(block):** 스레드 묶음(최대 1024개 등). 같은 블록의 스레드는 **공유 메모리** 를 함께 쓰고 동기화할 수 있습니다. 하나의 블록은 하나의 SM에서 실행됩니다.
- **그리드(grid):** 블록들의 묶음. 커널 실행 하나가 그리드 하나입니다.
- **워프(warp):** 하드웨어는 32개 스레드를 한 묶음으로 같은 명령을 동시에 실행합니다. 워프 안에서 조건문으로 갈라지면(divergence) 성능이 떨어집니다.

**간단한 예: 벡터 덧셈**

```cuda
__global__ void add(const float* a, const float* b, float* c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;   // 내가 맡을 원소 번호
    if (i < n) c[i] = a[i] + b[i];
}
// 호스트에서: add<<<(n + 255) / 256, 256>>>(a, b, c, n);  // 블록당 256 스레드
```

**성능의 핵심**

1. **메모리 접근 최적화:** 인접 스레드가 인접 메모리를 읽게 해서(coalescing) 한 번에 묶어 읽기. HBM 접근을 줄이고 공유 메모리·레지스터 재사용(타일링).
2. **점유율(occupancy):** SM에 충분한 워프를 올려 메모리 대기 시간을 다른 워프 실행으로 숨기기.
3. **커널 퓨전:** 여러 연산을 한 커널로 합쳐 중간 결과를 HBM에 쓰고 읽는 왕복을 없애기(Flash Attention, 퓨즈드 LayerNorm 등).
4. **텐서 코어 활용:** 행렬곱은 텐서 코어용 라이브러리(cuBLAS, CUTLASS)나 명령 사용.
5. **커널 실행 오버헤드 줄이기:** 작은 커널을 많이 실행하면 실행 비용이 커지므로 CUDA 그래프로 묶기.

**실무:** 대부분은 PyTorch, cuBLAS, cuDNN, Flash Attention 같은 최적화된 커널을 사용하고, 직접 작성할 때는 Triton(파이썬 기반 커널 언어)으로 더 쉽게 작성하기도 합니다.

<summary><b>Q6. Google TPU는 어떻게 동작하나요?</b></summary>

**TPU(Tensor Processing Unit)** 는 Google이 신경망 연산, 특히 **대규모 행렬 곱셈** 에 특화해 설계한 전용 가속기(ASIC)입니다. 범용 GPU와 달리 처음부터 딥러닝 워크로드에 맞춰 설계되었습니다.

**핵심: 시스톨릭 배열(systolic array) 기반 행렬 연산 유닛(MXU)**

- 수많은 곱셈-누산(MAC) 유닛을 격자 형태로 배치하고, 데이터가 **심장 박동처럼 유닛 사이를 리듬 있게 흘러가며** 계산됩니다.
- 가중치를 배열에 올려 두고 입력 데이터를 흘려보내면, 각 유닛이 곱셈 후 결과를 옆 유닛으로 넘겨 누적합니다.
- 중간 결과를 메모리에 쓰지 않고 유닛 간에 직접 전달하므로 **메모리 접근이 크게 줄어** 에너지 효율과 처리량이 높습니다.

**구성 요소**

- MXU(행렬 연산), 벡터 유닛(활성화 함수 등 원소별 연산), 스칼라 유닛(제어), 고대역폭 메모리(HBM).
- 저정밀도(BF16 등) 연산 중심 — BF16 형식 자체가 Google에서 TPU용으로 널리 쓰이기 시작했습니다.

**확장: TPU Pod**

- 수천 개의 TPU 칩을 전용 고속 인터커넥트(ICI)로 연결한 슈퍼컴퓨터 단위로 대규모 학습을 수행합니다.

**소프트웨어**

- **XLA 컴파일러** 가 모델 계산 그래프를 TPU에 최적화된 명령으로 컴파일합니다. JAX, TensorFlow, PyTorch/XLA로 사용합니다.
- 정적 형태(고정된 텐서 크기)에서 최고 성능을 내므로, 동적 형태가 많은 작업은 패딩·버킷팅이 필요할 수 있습니다.

**GPU와 비교**

- TPU: 대규모 행렬 연산·대규모 분산 학습에 효율적, Google Cloud 전용, 컴파일 중심.
- GPU: 범용성과 생태계(CUDA), 다양한 클라우드·온프레미스, 커스텀 커널 작성이 쉬움.

<summary><b>Q7. LPU는 어떻게 동작하나요?</b></summary>

**LPU(Language Processing Unit)** 는 Groq가 개발한 추론 전용 칩으로, **LLM 토큰 생성의 지연을 최소화** 하는 데 초점을 둡니다. Groq의 서비스는 매우 높은 초당 토큰 수로 알려졌습니다.

**설계 철학: 결정적(deterministic) 실행과 온칩 메모리**

1. **대용량 온칩 SRAM 중심**
   - GPU는 가중치를 외부 HBM에서 읽어 오는 것이 디코드의 병목입니다.
   - 예: 70B 모델을 8비트로 돌리면 토큰 하나마다 가중치 약 70GB를 읽어야 합니다. HBM 대역폭이 약 3TB/s라면 토큰당 약 23ms, 즉 사용자 한 명 기준 초당 약 43토큰이 상한입니다. 토큰은 앞 토큰에 의존해 순서대로 만들어지므로 이 한계를 병렬화로 피할 수 없습니다.
   - LPU는 칩 안의 매우 빠른 SRAM에 데이터를 두고 계산해 메모리 대역폭 병목을 크게 줄입니다.
   - 대신 칩 하나의 SRAM 용량이 작아, 큰 모델은 **수많은 칩에 나눠 배치** 해야 합니다.
2. **컴파일러가 모든 것을 미리 스케줄링**
   - 캐시, 동적 스케줄러, 분기 예측 같은 하드웨어의 "불확실한" 요소를 줄이고, 컴파일러가 어떤 연산이 언제 어디서 실행되고 데이터가 언제 어디로 이동할지를 **사이클 단위로 미리 결정** 합니다.
   - 실행 시간이 예측 가능하고 칩 간 통신까지 정확히 맞물려, 대기 시간이 거의 없습니다.
3. **칩 간 연결**
   - 여러 칩이 하나의 큰 프로세서처럼 동작하도록 동기화된 고속 연결로 데이터를 주고받습니다.

**장점**

- 낮고 일정한 지연, 높은 단일 사용자 토큰 생성 속도 → 실시간 음성 에이전트, 대화형 앱에 유리.

**트레이드오프**

- 칩당 SRAM이 수백 MB 수준이라 70B 모델이면 수백 개 칩이 필요해 하드웨어 규모가 큼.
- KV 캐시도 같은 작은 SRAM을 나눠 써야 해, 긴 컨텍스트와 많은 동시 사용자에 불리함.
- 학습보다는 추론 특화, 지원 모델·생태계가 GPU보다 제한적.
- 처리량당 비용은 워크로드에 따라 GPU와 비교해 평가해야 합니다.

**더 읽어보기 (영문):** [How does an LPU work?](https://outcomeschool.com/blog/how-does-an-lpu-work)

</details>

<details>
<summary><b>Q8. 70B 모델을 서빙하는 데 필요한 GPU 메모리(가중치, KV 캐시, 활성화 값)를 추정해 보세요. 80 GB GPU 한 장에 들어가나요?</b></summary>

**1. 가중치**

| 정밀도 | 70B 기준 |
|---|---|
| FP16/BF16 (2바이트) | ≈ 140 GB |
| FP8/INT8 (1바이트) | ≈ 70 GB |
| INT4 (0.5바이트 + 양자화 메타데이터) | ≈ 35~40 GB |

**2. KV 캐시** (Llama 3 70B 급 구성 가정: 80층, KV 헤드 8개, 헤드 차원 128)

- 토큰당 = 2(K,V) × 80 × 8 × 128 × 2바이트(FP16) ≈ **0.31 MB**
- 8K 토큰 시퀀스 하나 ≈ 2.5 GB
- 동시 요청 16개 × 8K ≈ 40 GB
- KV 캐시를 FP8로 저장하면 절반

**3. 활성화·오버헤드**

- 추론 시 활성화는 학습보다 훨씬 작지만, 프리필 중 임시 버퍼, CUDA 컨텍스트, 엔진 작업 공간으로 보통 수 GB 이상을 잡습니다.

**80 GB 한 장에 들어가나?**

- **FP16:** 가중치만 140 GB → **불가능.** 최소 2장(실제로는 KV 캐시 공간을 위해 4장 이상, 텐서 병렬화).
- **FP8:** 가중치 70 GB + 오버헤드 → KV 캐시에 남는 공간이 거의 없어 **실용적이지 않음.** 2장이 현실적.
- **INT4:** 가중치 약 35~40 GB → 남은 약 30~35 GB를 KV 캐시에 사용 가능. **한 장에서 서빙 가능**(8K 컨텍스트 기준 동시 요청 십여 개 수준). 단 품질 손실을 평가해야 합니다.

**결론과 고려 사항**

- "들어간다"와 "잘 서빙된다"는 다릅니다. 가중치만 겨우 들어가면 KV 캐시 공간이 없어 배치가 작아지고 처리량이 낮아집니다.
- 긴 컨텍스트(128K)를 지원하려면 요청 하나의 KV 캐시만 수십 GB가 되므로 여러 장이 필요합니다.
- 실제 판단은 목표 컨텍스트 길이, 동시 요청 수, 품질 요구(양자화 허용 수준)로 계산합니다.

</details>

<summary><b>Q9. 루프라인(roofline) 계산을 해 보세요: 배치 크기 1에서 H100 한 장은 70B 모델로 초당 몇 개의 토큰을 생성할 수 있나요?</b></summary>

**루프라인 모델:** 성능 상한 = min(최대 연산 성능, 메모리 대역폭 × 산술 강도). 배치 크기 1의 디코드는 산술 강도가 매우 낮아 **메모리 대역폭이 한계** 입니다.

**가정 (대략적인 공개 사양 기준)**

- H100 SXM HBM 대역폭 ≈ 3.35 TB/s
- 디코드 한 토큰마다 **모델 가중치 전체를 한 번 읽어야** 함 (KV 캐시 읽기는 짧은 컨텍스트에서 상대적으로 작아 일단 무시)

**계산**

| 정밀도 | 가중치 크기 | 이론 상한 (대역폭 ÷ 크기) |
|---|---|---|
| FP16 | 140 GB | 3.35 / 0.14 ≈ **24 토큰/초** (단, 140GB는 80GB 한 장에 들어가지 않음) |
| FP8 | 70 GB | 3.35 / 0.07 ≈ **48 토큰/초** |
| INT4 | ~35 GB | 3.35 / 0.035 ≈ **96 토큰/초** |

**실제 값은 더 낮습니다**

- 실제로 달성하는 메모리 대역폭은 이론치의 대략 60~80% 수준
- KV 캐시 읽기(컨텍스트가 길수록 증가), 커널 실행 오버헤드, 역양자화 비용
- 그래서 INT4 기준 실측은 이론 상한보다 상당히 낮은 수치가 나오는 것이 일반적입니다.

**연산 쪽 확인 (왜 메모리 병목인가)**

- 토큰당 연산 ≈ 2 × 파라미터 수 = 140 GFLOPs
- H100의 수백 TFLOPS(밀집 BF16 기준 약 1,000 TFLOPS급)로는 이론상 초당 수천 토큰도 가능 → 연산은 남아돌고 메모리가 병목입니다.

**시사점**

- 배치를 키우면 가중치를 한 번 읽어 여러 요청에 쓰므로 **전체 처리량이 거의 배치 크기만큼 증가** 합니다(연산 한계에 도달하기 전까지).
- 단일 사용자 속도를 높이려면 양자화(읽을 바이트 감소), 추측 디코딩(한 번 읽기로 여러 토큰), 텐서 병렬화(여러 GPU의 대역폭 합산)가 효과적입니다.

</details>

<details>
<summary><b>Q10. 분산 학습에서 모델 병렬화와 데이터 병렬화의 차이는 무엇인가요?</b></summary>

**데이터 병렬화 (Data Parallelism)**

- **모델 전체를 각 GPU에 복제** 하고, 데이터(배치)를 나눠 각 GPU가 다른 데이터로 순전파·역전파를 합니다.
- 각 GPU가 계산한 기울기를 **All-Reduce** 로 평균 내어 모든 복제본을 같은 가중치로 갱신합니다.
- 장점: 구현이 쉽고 확장성이 좋음(GPU를 늘리면 처리량이 거의 비례 증가).
- 한계: **모델 전체(+기울기, 옵티마이저 상태)가 GPU 한 장에 들어가야** 합니다. 큰 LLM에는 그대로 쓸 수 없습니다.
- 메모리 절약 변형: ZeRO, FSDP(가중치·기울기·옵티마이저 상태를 GPU들에 나눠 저장).

**모델 병렬화 (Model Parallelism)**

- **모델 자체를 여러 GPU에 나눠** 배치합니다. 모델이 한 장에 들어가지 않을 때 필요합니다.
- 종류:
  - **텐서 병렬화:** 한 층 안의 행렬 연산을 GPU들에 나눔(층 내부 분할). 통신이 잦아 고속 연결(NVLink) 필요, 보통 한 노드 안에서 사용.
  - **파이프라인 병렬화:** 층들을 단계별로 나눠 GPU마다 일부 층을 담당(층 간 분할). 마이크로 배치로 파이프라인을 채워 유휴 시간을 줄임.
  - **전문가 병렬화:** MoE의 전문가들을 GPU에 나눠 배치.
  - **시퀀스/컨텍스트 병렬화:** 긴 시퀀스를 나눠 처리.

| | 데이터 병렬화 | 모델 병렬화 |
|---|---|---|
| 나누는 것 | 데이터 | 모델 |
| GPU당 모델 | 전체 복제 (또는 ZeRO로 분할 저장) | 일부 |
| 주 통신 | 기울기 All-Reduce | 층 간 활성화·부분 결과 |
| 목적 | 처리량 확대 | 큰 모델을 올리기 |

**실제 대규모 학습:** 여러 방식을 결합한 **3D 병렬화**(데이터 × 텐서 × 파이프라인, + 전문가·시퀀스)를 사용합니다. 예: 노드 내부는 텐서 병렬, 노드 간은 파이프라인, 전체 복제본 간은 데이터 병렬.

</details>

<summary><b>Q11. 텐서 병렬화(tensor parallelism)란 무엇이며, 대형 모델 서빙에 어떻게 도움이 되나요?</b></summary>

**텐서 병렬화** 는 하나의 층 안에서 **가중치 행렬을 여러 GPU에 나눠 저장하고, 행렬곱을 GPU들이 나눠 계산** 하는 방식입니다(Megatron-LM 방식이 대표적).

**동작 (트랜스포머 MLP 예)**

1. 첫 번째 선형층 가중치를 **열 방향** 으로 나눕니다. GPU마다 출력의 일부 열을 계산합니다(통신 불필요).
2. 활성화 함수는 각 GPU에서 독립적으로 적용합니다.
3. 두 번째 선형층 가중치를 **행 방향** 으로 나눠, 각 GPU가 부분 합을 계산합니다.
4. **All-Reduce** 로 부분 합을 더해 최종 출력을 얻습니다.

- 어텐션은 **헤드 단위** 로 GPU에 나눕니다(GPU마다 일부 헤드 담당).
- 결과적으로 층마다 몇 번의 All-Reduce 통신이 필요합니다.

**서빙에 주는 이점**

- **큰 모델을 올릴 수 있음:** 70B 모델 FP16(140GB)을 4장에 나누면 GPU당 약 35GB.
- **단일 요청 지연 감소:** 디코드는 메모리 대역폭 병목인데, 여러 GPU가 각자 가중치 일부를 동시에 읽으므로 **유효 대역폭이 합산** 되어 토큰 생성이 빨라집니다.
- **KV 캐시 공간 확보:** 가중치가 나뉜 만큼 GPU마다 KV 캐시 공간이 늘어 더 큰 배치·긴 컨텍스트 처리.

**비용과 한계**

- 층마다 통신이 발생해 GPU 간 **고속 연결(NVLink 등)이 필수** 입니다. 노드 간(느린 네트워크)으로 확장하면 통신이 병목이 됩니다. 그래서 보통 한 서버(8 GPU) 안에서 사용합니다.
- GPU 수를 늘릴수록 통신 비율이 커져 효율이 떨어집니다. 작은 모델은 텐서 병렬화보다 GPU마다 별도 복제본을 두는 편이 처리량이 높을 수 있습니다.

**서빙 엔진 설정:** vLLM `--tensor-parallel-size 4`처럼 지정합니다.

</details>

<summary><b>Q12. 파이프라인 병렬화(pipeline parallelism)란 무엇인가요?</b></summary>

**파이프라인 병렬화** 는 모델의 **층들을 연속된 구간(스테이지)으로 나눠 GPU마다 하나의 구간을 맡기는** 방식입니다. 예: 80층 모델을 4개 GPU에 20층씩.

**동작**

- 입력은 GPU1(1~20층) → GPU2(21~40층) → GPU3 → GPU4 순서로 흐르고, 스테이지 사이에는 **활성화 값만** 전달합니다(통신량이 텐서 병렬화보다 적음).

**문제: 파이프라인 버블**

- 배치 하나를 그대로 흘리면, GPU1이 계산하는 동안 나머지는 놀고, 마지막 GPU가 계산할 때는 앞 GPU들이 놉니다.

**해결: 마이크로 배치**

- 배치를 작은 마이크로 배치로 쪼개 연속으로 흘려보내, 여러 스테이지가 동시에 서로 다른 마이크로 배치를 처리하게 합니다(공장 조립 라인처럼).

```
시간 →   t1   t2   t3   t4   t5
GPU1:   m1   m2   m3   m4
GPU2:        m1   m2   m3   m4
GPU3:             m1   m2   m3 ...
```

- 학습에서는 순전파와 역전파를 섞어 스케줄링(GPipe, 1F1B 방식 등)해 버블과 메모리 사용을 줄입니다.

**장단점**

| 장점 | 단점 |
|---|---|
| 통신량이 적어 **노드 간** 확장에 적합 | 버블로 인한 유휴 시간 |
| 모델이 매우 커도 층 단위로 분산 가능 | 스테이지 간 부하 균형이 필요 |
| | 단일 요청 지연은 줄지 않음(순차 통과) |

**사용:** 대규모 학습에서 텐서 병렬화(노드 내)와 함께 노드 간 분산에 주로 쓰입니다. 추론에서는 모델이 한 노드에 들어가지 않을 때 사용합니다.

</details>

<summary><b>Q13. 연속 배칭(continuous batching)은 LLM 추론 처리량을 어떻게 높이나요?</b></summary>

**기존 정적 배칭의 문제**

- 요청 여러 개를 하나의 배치로 묶어 처리하면, **배치 안의 모든 요청이 끝날 때까지** 새 요청을 받지 못합니다.
- LLM은 요청마다 출력 길이가 크게 다릅니다(10토큰 vs 1,000토큰). 짧은 요청이 끝나도 그 자리는 긴 요청이 끝날 때까지 비어 있어 GPU가 낭비되고, 새 요청은 대기열에서 기다립니다.

**연속 배칭 (반복 단위 스케줄링)**

- 배치를 **매 디코드 단계(토큰 하나 생성)마다** 다시 구성합니다.
- 요청 하나가 끝나면 **즉시 그 자리에 대기 중인 새 요청을 넣습니다.**
- 새 요청의 프리필과 기존 요청의 디코드를 같은 단계에서 함께 처리하기도 합니다(청크 프리필과 결합).

```
정적:  [A A A A A A][B B]......[C ...]   ← B가 끝나도 A가 끝날 때까지 대기
연속:  단계마다 끝난 자리에 새 요청 투입 → GPU가 항상 꽉 찬 배치로 동작
```

**왜 처리량이 크게 오르나**

- 디코드는 메모리 대역폭 병목이라, 배치가 클수록 가중치 한 번 읽기로 더 많은 토큰을 생성합니다. 연속 배칭은 배치를 항상 가득 채워 GPU 활용률을 높입니다.
- 새 요청의 대기 시간도 줄어듭니다.
- 정적 배칭 대비 처리량이 수 배 이상 향상되었다는 보고가 많습니다.

**함께 필요한 것:** 요청마다 KV 캐시 길이가 계속 달라지므로 **PagedAttention** 같은 유연한 KV 메모리 관리가 사실상 필수입니다. vLLM, SGLang, TensorRT-LLM(in-flight batching), TGI가 기본 제공합니다.

<summary><b>Q14. 추측 디코딩(speculative decoding)이란 무엇이며, 추론 속도를 어떻게 높이나요?</b></summary>

**아이디어:** 작고 빠른 **드래프트(초안) 모델** 이 다음 토큰 여러 개를 먼저 추측하고, 큰 **타깃 모델** 이 그 토큰들을 **한 번의 순전파로 동시에 검증** 합니다.

**절차**

1. 드래프트 모델이 k개 토큰(예: 4~8개)을 빠르게 생성합니다.
2. 타깃 모델이 원래 문맥 + k개 추측 토큰을 한 번에 처리해, 각 위치에서 자기 확률 분포를 계산합니다.
3. 앞에서부터 차례로 추측 토큰을 **수락 또는 거부** 합니다(수락 확률 = 타깃 확률과 드래프트 확률의 비교).
4. 처음 거부된 위치에서 타깃 분포로 토큰 하나를 새로 샘플링하고, 이후 추측은 버립니다.
5. 반복합니다.

**왜 빨라지나**

- 디코드는 메모리 대역폭 병목이라, 타깃 모델이 토큰 1개를 처리하든 5개를 처리하든 **가중치를 읽는 시간은 거의 같습니다.** 남는 연산 능력으로 여러 토큰을 동시에 검증하는 셈입니다.
- 추측이 평균 3개씩 수락되면, 타깃 모델의 순전파 한 번으로 토큰 약 3~4개를 얻습니다.

**품질:** 수락·거부 규칙 덕분에 **출력 분포가 타깃 모델 단독 생성과 수학적으로 같습니다.** 품질 손실이 없는 가속입니다.

**효과를 좌우하는 요소**

- **수락률:** 드래프트 모델이 타깃을 잘 흉내 낼수록 높아집니다(같은 계열 작은 모델, 증류된 드래프트).
- 코드·정형화된 텍스트처럼 예측하기 쉬운 출력에서 효과가 큽니다.
- 배치가 큰 고처리량 환경에서는 GPU 연산 여유가 적어 이득이 줄어듭니다.

**변형:** 별도 드래프트 모델 없이 추가 헤드로 추측(Medusa), 특징 수준 추측(EAGLE), 입력 텍스트에서 n-gram으로 추측(프롬프트 룩업), 멀티 토큰 예측(MTP) 헤드 활용.

**더 읽어보기 (영문):** [Speculative Decoding](https://outcomeschool.com/blog/speculative-decoding)

<summary><b>Q15. Medusa(멀티 헤드 추측 디코딩)는 어떻게 동작하나요?</b></summary>

**Medusa** 는 별도의 드래프트 모델 없이, 타깃 모델 자체에 **여러 개의 추가 예측 헤드(Medusa heads)** 를 붙여 추측 디코딩을 하는 방법입니다(Cai 외, 2024).

**구조**

- 기존 LM 헤드는 다음 토큰(t+1)을 예측합니다.
- Medusa 헤드 k개를 추가해, 같은 마지막 은닉 상태로 **t+2, t+3, …, t+k+1번째 토큰** 을 각각 예측하게 합니다. 각 헤드는 작은 신경망(한두 층)입니다.

**동작**

1. 한 번의 순전파로 기존 헤드와 Medusa 헤드들이 여러 위치의 후보 토큰들을 동시에 냅니다.
2. 각 위치의 상위 후보들을 조합해 여러 후보 시퀀스를 **트리** 형태로 만듭니다.
3. **트리 어텐션:** 특수한 어텐션 마스크로 여러 후보 경로를 다음 순전파 한 번에 함께 검증합니다.
4. 가장 길게 수락된 경로를 채택합니다.

**출력 동일성 주의:** 그리디 디코딩에서는 원래 모델과 같은 출력을 내지만, 샘플링에서는 속도를 위해 "typical acceptance"라는 완화된 수락 규칙을 쓰므로 원래 모델의 분포를 정확히 보장하지는 않습니다. 거절 샘플링으로 분포를 그대로 유지하는 일반 추측 디코딩과 다른 점입니다.

**학습**

- **Medusa-1:** 기반 모델은 고정하고 Medusa 헤드만 학습 → 저렴하고 원래 모델 품질 유지.
- **Medusa-2:** 기반 모델과 함께 학습 → 수락률 향상, 대신 학습 레시피 관리 필요.
- 학습 데이터가 없으면 모델 자신의 출력으로 학습(자기 증류)할 수 있습니다.

**장점**

- 별도 드래프트 모델을 관리·서빙할 필요가 없습니다(메모리·배포 단순).
- 같은 모델의 은닉 상태를 쓰므로 분포 불일치가 적습니다.
- 논문 보고 기준 Medusa-1은 약 2.2배, Medusa-2는 2.3~3.6배의 속도 향상을 보였습니다(작업·설정에 따라 다름).

**한계:** 뒤쪽 위치(멀리 있는 토큰)일수록 예측 정확도가 떨어집니다. 이 점을 개선한 것이 특징 수준에서 순차적으로 예측하는 EAGLE 계열입니다.

**더 읽어보기 (영문):** [Medusa - Multi-Head Speculative Decoding](https://outcomeschool.com/blog/decoding-medusa)

<summary><b>Q16. EAGLE(특징 수준 추측 디코딩)은 어떻게 동작하나요?</b></summary>

**EAGLE** 은 토큰을 직접 추측하는 대신, 타깃 모델의 **특징(LM 헤드 바로 앞의 은닉 상태, 논문 표현으로는 second-to-top-layer feature) 수준에서 다음 특징을 예측** 하는 가벼운 드래프트 네트워크로 추측 디코딩을 하는 방법입니다(Li 외, 2024).

**핵심 관찰**

- 토큰 시퀀스보다 **특징(feature) 시퀀스가 더 규칙적이고 예측하기 쉽다.**
- 다만 샘플링에서 오는 불확실성 때문에, 특징만으로는 다음 특징이 모호할 수 있습니다 → 한 단계 앞의 **토큰 정보도 함께** 입력합니다.

**동작**

1. 드래프트 헤드(트랜스포머 디코더 층 하나 정도의 가벼운 네트워크)가 입력으로 (현재 특징, 이미 샘플링된 다음 토큰의 임베딩)을 받아 다음 위치의 특징을 예측합니다.
2. 예측한 특징을 타깃 모델의 LM 헤드에 통과시켜 토큰 분포를 얻고, 이를 반복해 여러 단계 앞까지 **자기회귀적으로** 추측합니다(Medusa처럼 위치별로 독립 예측하지 않음).
3. 후보들을 트리로 구성하고, 타깃 모델이 트리 어텐션으로 한 번에 검증합니다. 출력 분포는 타깃 모델과 동일하게 유지됩니다.

**Medusa와 비교**

| | Medusa | EAGLE |
|---|---|---|
| 예측 대상 | 각 위치 토큰을 독립적으로 | 특징을 순차적으로 (토큰 정보 포함) |
| 먼 위치 정확도 | 빠르게 떨어짐 | 상대적으로 유지 |
| 수락률·속도 | 좋음 | 일반적으로 더 높음 |

**발전:** EAGLE-2는 드래프트 모델의 신뢰도에 따라 **트리 모양을 동적으로 조정** 하고, EAGLE-3는 여러 층의 특징을 활용해 수락률을 더 높였습니다. vLLM, SGLang, TensorRT-LLM 등에서 지원합니다.

**더 읽어보기 (영문):** [EAGLE - Feature-Level Speculative Decoding](https://outcomeschool.com/blog/decoding-eagle)

<summary><b>Q17. LLM의 N-gram 추측(N-gram Speculation)이란 무엇이며, 생성 속도를 어떻게 높이나요?</b></summary>

**N-gram 추측** 은 별도의 드래프트 모델 없이, **이미 있는 텍스트(프롬프트와 지금까지 생성한 내용)에서 반복되는 패턴을 찾아 다음 토큰들을 추측** 하는 추측 디코딩 방식입니다. "프롬프트 룩업 디코딩"이라고도 부릅니다.

**동작**

1. 최근 생성된 마지막 n개 토큰(예: 3개)을 키로 삼습니다.
2. 프롬프트와 지금까지의 출력에서 같은 n-gram이 나온 위치를 찾습니다.
3. 그 위치 **바로 뒤에 이어졌던 토큰들** 을 추측 토큰으로 사용합니다.
4. 타깃 모델이 한 번의 순전파로 추측 토큰들을 검증하고, 맞는 만큼 수락합니다(일반 추측 디코딩과 동일한 검증, 출력 품질 동일).

**언제 효과가 큰가**

- 출력이 입력을 많이 **그대로 복사** 하는 작업:
  - 코드 수정(기존 코드 대부분을 다시 출력)
  - 문서 편집·교정, 요약에서 원문 인용
  - RAG 답변에서 문서 문장 인용
  - 구조화 출력(반복되는 JSON 키)
- 이런 경우 추측이 길게 수락되어 큰 속도 향상을 얻을 수 있습니다.

**장점**

- 추가 모델·학습이 필요 없고 구현이 매우 간단하며 메모리 비용이 거의 없습니다.

**한계**

- 입력과 겹치지 않는 창의적·새로운 텍스트 생성에서는 추측이 거의 맞지 않아 효과가 없습니다(검증 비용만 약간 추가).

**사용:** vLLM 등의 서빙 엔진이 n-gram 기반 추측 옵션을 제공합니다. 작업 특성에 따라 드래프트 모델·EAGLE과 선택하거나 조합합니다.

**더 읽어보기 (영문):** [N-gram Speculation in LLMs](https://outcomeschool.com/blog/n-gram-speculation-in-llms)

<summary><b>Q18. KV 캐시란 무엇이며, 그 메모리를 어떻게 관리하나요?</b></summary>

**KV 캐시** 는 자기회귀 생성 중에 이미 처리한 토큰들의 **Key·Value 벡터를 층마다 저장해 재사용** 하는 것입니다. 새 토큰을 만들 때 과거 토큰의 K·V를 다시 계산하지 않아도 되어 생성이 빨라집니다.

**메모리 크기**

```
KV 캐시 = 2 × 층 수 × KV 헤드 수 × 헤드 차원 × 시퀀스 길이 × 배치 크기 × 바이트 수
```

- 길이와 배치에 **선형으로** 늘어나며, 긴 컨텍스트·큰 배치에서는 모델 가중치보다 커질 수 있습니다. 결국 **동시 처리 가능한 요청 수를 결정** 합니다.

**메모리 관리 기법**

1. **PagedAttention:** 고정 크기 블록 단위로 필요할 때 할당 → 단편화·과다 예약 제거, 블록 공유 가능.
2. **프리픽스 공유·캐싱:** 같은 시스템 프롬프트·문서의 KV를 여러 요청이 공유.
3. **양자화:** KV를 FP8/INT8/INT4로 저장해 2~4배 절약.
4. **구조적 감소:** GQA/MQA/MLA를 쓰는 모델 선택.
5. **제거(eviction)·압축:** 슬라이딩 윈도우, 어텐션 싱크 + 최근 토큰 유지, 중요도 기반 토큰 제거.
6. **오프로딩:** 오래 대기 중인 요청의 KV를 CPU 메모리·SSD로 옮겼다가 복원.
7. **선점과 재계산:** 메모리가 부족하면 일부 요청을 잠시 멈추고 나중에 KV를 다시 계산.
8. **스케줄링:** 긴 요청과 짧은 요청을 분리 서빙, 최대 컨텍스트 길이 제한.

**모니터링:** KV 캐시 사용률, 선점(preemption) 발생률, 대기열 길이를 보고 GPU 수·배치 설정을 조정합니다.

<summary><b>Q19. 페이지드 어텐션(Paged Attention)이란 무엇인가요?</b></summary>

**PagedAttention** 은 vLLM(2023)에서 제안한 기법으로, 운영체제의 **가상 메모리 페이징** 아이디어를 KV 캐시 관리에 적용한 것입니다.

**기존 방식의 문제**

- 요청마다 KV 캐시를 위한 **연속된 메모리** 를 미리 확보해야 했습니다.
- 출력 길이를 미리 모르므로 최대 길이만큼 예약 → 실제로 쓰지 않는 공간 낭비(과다 예약), 요청들 사이의 빈 공간(단편화).
- 연구에서는 기존 시스템이 KV 캐시 메모리의 상당 부분(60~80%)을 낭비한다고 보고했습니다.

**PagedAttention의 방식**

1. KV 캐시를 **고정 크기 블록**(예: 블록당 16토큰)으로 나눕니다.
2. 각 요청은 **블록 테이블** 로 "논리적 블록 번호 → 물리적 GPU 메모리 블록"을 매핑합니다. 물리 블록은 메모리 어디에 흩어져 있어도 됩니다.
3. 토큰이 생성되어 블록이 차면 그때 새 블록을 하나 할당합니다.
4. 어텐션 커널이 블록 테이블을 따라 흩어진 블록에서 K·V를 읽어 계산합니다.

**효과**

- 낭비가 마지막 블록의 빈 칸 정도로 줄어 **같은 GPU에서 훨씬 많은 요청을 동시에 처리** → 처리량 대폭 향상.
- **블록 공유:** 같은 프롬프트를 쓰는 요청들(병렬 샘플링, 빔 서치, 공통 시스템 프롬프트)이 물리 블록을 공유하고, 내용이 달라질 때만 복사합니다(copy-on-write).
- 선점·스왑이 블록 단위로 쉬워집니다.

**지금의 위치:** 연속 배칭과 함께 현대 LLM 서빙 엔진의 사실상 표준 기법이 되었습니다(vLLM, SGLang, TensorRT-LLM 등 다양한 형태로 구현).

<details>
<summary><b>Q20. GGUF는 어떻게 동작하나요?</b></summary>

**GGUF** 는 llama.cpp 생태계에서 쓰는 **모델 파일 형식** 으로, 양자화된 모델을 일반 하드웨어(CPU, 맥, 소비자 GPU)에서 효율적으로 실행하도록 설계되었습니다. 이전 형식(GGML)을 개선한 후속 형식입니다.

**파일 구조**

1. **헤더:** 형식 식별자, 버전, 텐서 수, 메타데이터 수
2. **메타데이터 (키-값):** 모델 구조(층 수, 헤드 수, 컨텍스트 길이, RoPE 설정), **토크나이저**(어휘, 병합 규칙, 특수 토큰), 채팅 템플릿, 양자화 정보
3. **텐서 정보:** 각 텐서의 이름, 모양, 양자화 타입, 데이터 위치(오프셋)
4. **텐서 데이터:** 정렬된 가중치 데이터

**특징**

- **단일 파일:** 가중치·토크나이저·설정이 한 파일에 있어 배포·관리가 쉽습니다.
- **메모리 매핑(mmap):** 파일을 메모리에 바로 매핑해 빠르게 로딩하고, 필요한 부분만 실제로 읽습니다.
- **다양한 양자화 타입:** Q8_0, Q6_K, Q5_K_M, Q4_K_M, Q3_K, Q2_K, IQ 계열 등. 가중치를 블록 단위로 나누고 블록마다 스케일을 저장합니다. "K-quants"는 블록을 계층적으로 나누고 층·텐서별 중요도에 따라 다른 비트를 섞어 품질을 높입니다.
- **확장 가능한 메타데이터:** 새 모델 구조가 나와도 형식을 깨지 않고 정보를 추가할 수 있습니다.

**사용 흐름**

```bash
# Hugging Face 모델 → GGUF 변환 → 양자화
python convert_hf_to_gguf.py ./model --outfile model-f16.gguf
./llama-quantize model-f16.gguf model-Q4_K_M.gguf Q4_K_M
./llama-server -m model-Q4_K_M.gguf
```

**크기 감각:** 7B 모델은 16비트로 약 14GB지만, Q4_K_M으로 양자화하면 약 4GB로 줄어 일반 노트북에서도 실행할 수 있습니다.

**선택 요령:** Q4_K_M 정도가 크기와 품질의 균형점으로 많이 쓰이고, 품질이 중요하면 Q5·Q6·Q8, 메모리가 매우 부족하면 Q3 이하(품질 저하 확인 필요). Ollama, LM Studio 등이 GGUF를 사용합니다.

**더 읽어보기 (영문):** [How does GGUF work?](https://outcomeschool.com/blog/how-does-gguf-work)

<summary><b>Q21. 엣지 및 모바일 배포를 위해 추론을 어떻게 최적화하나요?</b></summary>

**제약:** 작은 메모리(수 GB, 다른 앱과 공유), 제한된 연산, 배터리·발열, 앱 크기, 다양한 기기 사양.

**1. 모델 선택과 축소**

- 소형 모델(대략 1~4B 파라미터), 작업 특화 모델
- **증류:** 큰 모델의 능력을 작은 모델로
- **가지치기:** 덜 중요한 층·헤드·뉴런 제거

**2. 양자화 (가장 효과적)**

- 4비트 가중치(GGUF Q4, AWQ/GPTQ, 플랫폼별 형식), 활성화 8비트
- 모바일 NPU가 지원하는 정밀도(INT8/INT4)에 맞추기
- 양자화 후 작업별 품질 평가

**3. 하드웨어 가속 활용**

- 플랫폼 런타임: Core ML(애플), MLX(맥), LiteRT/TFLite·NNAPI(안드로이드), ONNX Runtime, ExecuTorch, llama.cpp(Metal, Vulkan)
- NPU·GPU 위임, 연산자 퓨전, 메모리 레이아웃 최적화

**4. 추론 설정**

- 짧은 컨텍스트, KV 캐시 양자화, 프리픽스 캐시 재사용
- 추측 디코딩(작은 드래프트 모델 또는 n-gram)
- 출력 길이 제한

**5. 시스템 설계**

- 모델 지연 로딩, 사용하지 않을 때 메모리 해제
- 여러 작업은 하나의 기반 모델 + 작업별 LoRA 어댑터
- 무거운 작업(인덱싱)은 충전 중·유휴 시간에
- **하이브리드:** 어려운 요청은 클라우드로 넘기는 라우팅(사용자 동의, 개인정보 고려)

**6. 배포**

- 기기 사양별로 다른 크기·양자화 모델 제공, 모델은 앱과 분리해 다운로드

**측정:** 기기별 첫 토큰 시간, 토큰/초, 최대 메모리, 배터리 소모, 발열, 작업 품질.

<summary><b>Q22. 모델 양자화(INT8, INT4, FP16, BF16)란 무엇이며, 품질에 어떤 영향을 주나요?</b></summary>

**양자화** 는 모델 가중치(그리고 선택적으로 활성화·KV 캐시)를 더 적은 비트로 표현하는 것입니다.

**형식 비교**

| 형식 | 비트 | 특징 | 품질 영향 (일반적 경향) |
|---|---|---|---|
| **FP32** | 32 | 학습 기본 정밀도 | 기준 |
| **FP16** | 16 | 지수 5비트, 가수 10비트. 정밀하지만 표현 범위가 좁아 오버플로 위험 | 추론에서 사실상 무손실 |
| **BF16** | 16 | 지수 8비트(FP32와 같은 범위), 가수 7비트. 범위가 넓어 학습에 안정적 | 사실상 무손실, 학습·추론 표준 |
| **FP8** | 8 | E4M3/E5M2 형식, 최신 GPU 하드웨어 지원 | 적절한 스케일링 시 매우 작은 손실 |
| **INT8** | 8 | 정수, 스케일 값으로 실수 근사 | 가중치 INT8은 대체로 거의 무손실, 활성화까지 하면 이상치 처리 필요 |
| **INT4** | 4 | 16단계만 표현, 그룹별 스케일 필요 | 작은 손실~눈에 띄는 손실 (방법·모델에 따라) |
| **2~3비트** | 2~3 | 극단적 압축 | 품질 저하가 뚜렷, 특수 기법 필요 |

**품질에 영향을 주는 요소**

- **양자화 방법:** 단순 반올림보다 GPTQ, AWQ, SmoothQuant 같은 오차 보정 방법이 훨씬 좋습니다.
- **그룹 크기:** 작을수록 정밀(메모리 약간 증가).
- **모델 크기:** 큰 모델일수록 양자화에 강한 경향.
- **작업:** 수학·코드·긴 추론·다국어(저자원 언어)가 먼저 나빠지고, 일반 대화는 상대적으로 덜 나빠집니다.
- **양자화 대상:** 가중치만 할지, 활성화·KV 캐시까지 할지.

**얻는 것:** 메모리 절감(16비트 대비 8비트 1/2, 4비트 약 1/4), 디코드 속도 향상(메모리 대역폭 절약), 같은 GPU에서 더 큰 배치·긴 컨텍스트.

**실무 원칙:** BF16/FP8을 기본으로, 비용·메모리가 더 중요하면 INT4를 시도하되 **반드시 내 작업 평가셋으로 품질을 확인** 합니다.

<summary><b>Q23. AI 워크로드의 오토스케일링을 어떻게 구현하나요?</b></summary>

**일반 웹 서비스와 다른 점**

- **GPU 인스턴스 기동이 느림:** 인스턴스 확보 + 컨테이너 시작 + 수십 GB 모델 가중치 로딩에 수 분이 걸릴 수 있습니다.
- **CPU 사용률은 좋은 지표가 아님:** GPU 사용률도 배치 처리 특성상 오해를 부를 수 있습니다.
- **GPU 자원이 비싸고 부족할 수 있음:** 원하는 때 원하는 만큼 확보되지 않을 수 있습니다.

**스케일링 지표 (LLM 서빙)**

- **대기열 길이 / 대기 중인 요청 수** (가장 직접적)
- **TTFT p95** 증가, 동시 처리 중인 요청 수
- **KV 캐시 사용률**, 선점 발생률
- 초당 입력·출력 토큰 수

**구현 방법**

1. **쿠버네티스 기반:** HPA 또는 KEDA로 커스텀 지표(대기열 길이 등) 기반 스케일링, GPU 노드 그룹 오토스케일러(Karpenter, Cluster Autoscaler).
2. **관리형 서비스:** 클라우드의 관리형 엔드포인트, 서버리스 GPU 플랫폼.

**콜드 스타트 대응**

- **웜 풀:** 미리 띄워 둔 대기 인스턴스 유지
- **빠른 가중치 로딩:** 로컬 NVMe 캐시, 미리 구운 머신 이미지, 스트리밍 로딩, 같은 리전 저장소
- **예측 스케일링:** 시간대·요일 패턴, 이벤트 일정 기반 사전 확장
- **최소 인스턴스 수** 를 SLO에 맞게 유지

**스케일 다운**

- 진행 중인 요청을 끝낸 뒤 종료(드레이닝), 너무 잦은 확장·축소(진동)를 막는 안정화 시간 설정.

**비용 최적화**

- 기본 부하는 예약 인스턴스, 피크는 온디맨드, 중단 가능한 배치 작업은 스팟 인스턴스.
- 피크 시간에 배치 작업을 늦추는 우선순위 정책과 결합.

<summary><b>Q24. AI 서빙 인프라에서 로드 밸런싱은 어떤 역할을 하나요?</b></summary>

**기본 역할:** 여러 추론 인스턴스에 요청을 분산해 처리량을 높이고, 장애 인스턴스를 피하며, 지연을 낮춥니다.

**LLM 서빙에서 단순 라운드로빈이 부족한 이유**

- 요청마다 비용이 크게 다릅니다(입력 100토큰 vs 10만 토큰, 출력 10 vs 2,000).
- 요청이 오래 연결을 유지합니다(스트리밍).
- 인스턴스마다 **KV 캐시 상태** 가 달라, 어디로 보내느냐에 따라 캐시 재사용 여부가 달라집니다.

**LLM에 적합한 로드 밸런싱 전략**

1. **부하 인지(load-aware) 라우팅**
   - 인스턴스별 대기열 길이, 처리 중인 토큰 수, KV 캐시 사용률을 보고 가장 여유 있는 곳으로 보냅니다(최소 미처리 요청 기준 등).
2. **프리픽스(캐시) 인지 라우팅**
   - 같은 시스템 프롬프트·같은 대화의 요청을 **같은 인스턴스** 로 보내 프리픽스 캐시 적중률을 높입니다(일관 해싱, 프리픽스 해시 기반). TTFT와 비용이 크게 줄어듭니다.
   - 부하 균형과 캐시 적중 사이의 균형을 맞춥니다.
3. **세션 고정(sticky session)**
   - 멀티턴 대화, 스트리밍 ASR 같은 상태 유지 작업.
4. **모델·어댑터 인지 라우팅**
   - 여러 모델이나 LoRA 어댑터가 서로 다른 인스턴스에 있을 때 해당 모델이 로딩된 곳으로.
5. **우선순위·요금제별 분리**
   - 실시간과 배치, 유료와 무료 트래픽을 다른 풀로.

**신뢰성 기능:** 헬스 체크, 비정상 인스턴스 제외, 타임아웃·재시도, 리전 간 장애 조치.

**구현:** Envoy, Nginx, 쿠버네티스 게이트웨이 + LLM 인지 확장(예: Kubernetes Gateway API Inference Extension), 서빙 엔진의 라우터(vLLM·SGLang 라우터), LLM 게이트웨이.

</details>

<summary><b>Q25. 여러 모델을 서빙할 때 GPU 메모리를 어떻게 관리하나요?</b></summary>

**상황:** 여러 크기·종류의 모델(대형 채팅 모델, 소형 분류 모델, 임베딩 모델, 여러 파인튜닝 버전)을 제한된 GPU로 서빙해야 합니다.

**전략**

1. **멀티 LoRA 서빙 (같은 기반 모델의 파인튜닝 변형이 많을 때)**
   - 기반 모델 하나만 GPU에 올리고, 작은 LoRA 어댑터들을 요청별로 적용합니다. 수십~수백 개 어댑터를 하나의 GPU에서 서빙할 수 있습니다(vLLM, LoRAX, S-LoRA).
2. **모델 공존 (작은 모델 여러 개)**
   - 한 GPU에 여러 모델을 함께 올리고 메모리를 나눠 씁니다(vLLM의 `gpu_memory_utilization` 조정, 프로세스 분리).
   - **MIG(Multi-Instance GPU):** 지원 GPU를 하드웨어 수준에서 여러 개의 독립 GPU로 분할해 격리와 예측 가능한 성능 확보.
   - MPS로 여러 프로세스가 GPU를 공유.
3. **동적 로딩·언로딩**
   - 사용 빈도가 낮은 모델은 요청이 올 때 로딩하고, 일정 시간 미사용 시 내립니다(LRU). 로딩 지연을 줄이기 위해 CPU 메모리에 가중치를 캐시해 두거나 빠른 저장소를 사용합니다.
4. **양자화로 메모리 절약**
   - 모델별 FP8/INT4 적용으로 더 많은 모델을 올리기.
5. **모델별 전용 풀 + 트래픽 기반 배치**
   - 트래픽이 많은 모델은 전용 인스턴스, 적은 모델은 공유 풀.
6. **KV 캐시 예산 관리**
   - 모델마다 KV 캐시 공간이 필요하므로, 공존 시 각 모델의 최대 동시 요청·컨텍스트 길이를 계획에 반영합니다.

**모니터링:** 모델별 메모리 사용, 로딩·언로딩 빈도, 콜드 로딩 지연, GPU 사용률을 보고 배치를 조정합니다.

<summary><b>Q26. 모델 샤딩(model sharding)이란 무엇이며, 언제 사용하나요?</b></summary>

**모델 샤딩** 은 모델의 파라미터(그리고 학습 시에는 기울기·옵티마이저 상태)를 **여러 장치(GPU, 노드)에 나눠 저장·계산** 하는 것을 통틀어 부르는 말입니다.

**샤딩 방식**

| 방식 | 나누는 기준 | 주 용도 |
|---|---|---|
| **텐서 병렬 샤딩** | 층 내부의 행렬을 나눔 | 추론·학습, 노드 내 |
| **파이프라인 샤딩** | 층 단위로 나눔 | 노드 간 분산 |
| **전문가 샤딩** | MoE 전문가를 장치별로 배치 | 대형 MoE |
| **ZeRO/FSDP 샤딩** | 파라미터·기울기·옵티마이저 상태를 데이터 병렬 장치들에 나눠 저장, 필요할 때 모아 계산 | 학습 메모리 절약 |
| **체크포인트 샤딩** | 가중치 파일을 여러 조각으로 저장 | 저장·로딩 편의 (병렬 로딩) |

**언제 사용하나**

- **모델이 장치 하나의 메모리에 들어가지 않을 때** (예: 70B FP16 = 140GB > 80GB)
- 학습 시 옵티마이저 상태까지 포함하면 메모리가 수 배로 늘어날 때
- **단일 요청 지연을 줄이고 싶을 때:** 텐서 병렬화로 여러 GPU의 메모리 대역폭을 함께 사용
- 큰 MoE 모델 서빙

**언제 피하나**

- 모델이 한 장에 충분히 들어가면, 샤딩 대신 **여러 독립 복제본** 을 두는 것이 통신 비용이 없어 처리량이 더 좋은 경우가 많습니다.
- 장치 간 연결이 느리면 통신이 병목이 됩니다.

**고려 사항:** 고속 인터커넥트(NVLink, InfiniBand), 장치 간 부하 균형, 장애 시 전체 샤드 그룹이 영향을 받음, 샤딩 구성에 맞는 체크포인트 저장·로딩.

</details>

<summary><b>Q27. AI 서비스의 요청 대기열(queuing)과 우선순위 스케줄링을 어떻게 구현하나요?</b></summary>

**왜 필요한가:** GPU·제공사 한도는 유한하고 요청은 몰려서 들어옵니다. 대기열 없이 모두 받아들이면 모든 요청이 느려지거나 시스템이 무너집니다.

**구조**

```
요청 → [입장 제어: 속도 제한, 최대 대기열 길이 초과 시 즉시 429]
     → [우선순위 대기열들]
          P0: 실시간 유료 사용자 / 핵심 기능
          P1: 실시간 무료 사용자
          P2: 내부 도구
          P3: 배치·백그라운드 작업
     → [스케줄러] → 추론 서버 (연속 배칭)
```

**스케줄링 정책**

1. **엄격한 우선순위:** 높은 우선순위가 항상 먼저. 단, 낮은 우선순위가 영원히 처리되지 않는 기아(starvation) 문제 → **노화(aging)**: 오래 기다린 요청의 우선순위를 점점 올림.
2. **가중 공정 큐(WFQ):** 우선순위별로 처리 비율을 할당(예: 70/20/10).
3. **테넌트 간 공정성:** 한 고객이 대기열을 독점하지 않도록 테넌트별 할당량·라운드로빈.
4. **비용 인지:** 요청 크기(예상 토큰)를 고려해, 거대한 요청 하나가 많은 작은 요청을 막지 않게 합니다.
5. **기한(deadline) 인지:** SLO 기한을 넘길 요청은 미리 거절하거나 다른 경로(작은 모델)로.

**구현 요소**

- 메시지 큐(Redis, SQS, Kafka) 또는 서빙 엔진 내장 스케줄러의 우선순위 기능
- 대기열 길이·대기 시간 기반 **부하 차단(load shedding)**: 감당할 수 없으면 빠르게 거절
- 비실시간 작업은 별도 비동기 큐 + 배치 API 활용
- 사용자에게 대기 상태·예상 시간 안내

**모니터링:** 우선순위별 대기 시간 p95, 거절률, 기아 발생 여부, SLO 위반률.

</details>

<summary><b>Q28. 자체 호스팅 AI 추론과 API 기반 AI 추론의 비용 트레이드오프는 무엇인가요?</b></summary>

**비용 구조 비교**

| | API 기반 | 자체 호스팅 |
|---|---|---|
| 과금 | 토큰당 (사용한 만큼) | GPU 시간당 (사용하든 안 하든) |
| 고정비 | 거의 없음 | GPU 인스턴스, 운영 인력, 모니터링 |
| 변동비 | 트래픽에 정비례 | 트래픽이 늘어도 용량 안에서는 거의 일정 |
| 숨은 비용 | 대량 사용 시 단가 부담, 속도 제한 대응 | 엔지니어링·운영 인력, 유휴 용량, 장애 대응, 모델 업데이트 |

**손익분기점 개념**

- 자체 호스팅 비용 ≈ (필요 GPU 수 × 시간당 비용) + 운영 비용
- GPU 사용률이 높게 유지되면 토큰당 비용이 API보다 낮아질 수 있지만, **사용률이 낮으면(트래픽이 들쭉날쭉) 오히려 훨씬 비쌉니다.**
- 비교는 반드시 **처리량당 비용**(실제 SLO를 만족하는 상태에서의 $/백만 토큰)으로 합니다.

**자체 호스팅이 유리한 경우**

- 대량·안정적인 트래픽(GPU를 계속 바쁘게 쓸 수 있음)
- 작은 오픈 모델로 충분한 작업(분류, 추출, 임베딩)
- 파인튜닝 모델을 대량으로 서빙
- 데이터 통제·규제 요구(비용 외 이유)

**API가 유리한 경우**

- 트래픽이 적거나 변동이 큼, 초기 단계
- 최고 성능의 최신 모델이 필요
- ML 인프라 운영 역량이 없음
- 빠른 실험과 모델 교체

**혼합 전략:** 대량·단순 작업은 자체 호스팅 소형 모델, 어려운 작업은 API 대형 모델로 라우팅하는 구성이 많습니다. 정기적으로 실제 사용량 데이터로 비용을 재계산합니다.

</details>

<summary><b>Q29. 서버리스 AI 배포에서 콜드 스타트 지연 시간을 어떻게 처리하나요?</b></summary>

**콜드 스타트의 구성 (GPU 서버리스)**

1. GPU 인스턴스 확보
2. 컨테이너 이미지 다운로드·시작 (AI 이미지는 수 GB)
3. 런타임 초기화 (CUDA, 라이브러리)
4. **모델 가중치 로딩** (수 GB~수십 GB를 저장소에서 GPU 메모리로) — 보통 가장 큼
5. 워밍업 (커널 컴파일, CUDA 그래프 캡처)

수십 초에서 수 분이 걸릴 수 있어, 첫 요청 사용자의 경험을 크게 해칩니다.

**줄이는 방법**

1. **최소 웜 인스턴스 유지:** 항상 1개 이상 실행 상태로 두기(비용 vs 지연 트레이드오프). 트래픽 패턴에 맞춘 예약 스케일링.
2. **가중치 로딩 가속**
   - 로컬 NVMe·노드 캐시에 가중치 미리 저장, 같은 리전의 빠른 저장소
   - safetensors + 메모리 매핑, 병렬·스트리밍 로딩
   - 양자화로 가중치 크기 축소
   - GPU 메모리 스냅샷·체크포인트 복원 기능(플랫폼 지원 시)
3. **컨테이너 최적화:** 이미지 경량화, 레이어 캐시, 이미지 미리 풀링(pre-pull), 가중치를 이미지 밖으로 분리.
4. **워밍업 미리 수행:** 컴파일된 엔진·캐시 재사용, 시작 시 더미 요청으로 워밍업 후 트래픽 받기.
5. **작은 모델로 임시 응답:** 콜드 스타트 중에는 작은 모델이나 API로 폴백.
6. **요청 측 대응:** 비동기 처리(작업 접수 후 결과 알림), 사용자에게 준비 중 상태 표시.

**판단 기준:** 지연 SLO가 엄격하고 트래픽이 꾸준하면 서버리스보다 상시 인스턴스가 적합하고, 트래픽이 드물고 간헐적이면 서버리스 + 웜 인스턴스 최소화가 비용 효율적입니다.

</details>

<summary><b>Q30. 중복 연산을 줄이기 위한 모델 캐싱을 어떻게 구현하나요?</b></summary>

**캐싱 계층 (가까운 것부터)**

1. **KV 캐시 (요청 내부)**
   - 생성 중 이전 토큰의 K·V 재사용. 모든 서빙 엔진이 기본 제공.
2. **프리픽스(프롬프트) 캐시 (요청 간)**
   - 공통 앞부분(시스템 프롬프트, 도구 정의, 문서, 이전 대화)의 KV를 요청 사이에 재사용합니다.
   - 자체 호스팅: vLLM 자동 프리픽스 캐싱, SGLang RadixAttention. 캐시 적중을 높이도록 같은 프리픽스 요청을 같은 인스턴스로 라우팅.
   - API: 제공사 프롬프트 캐싱(캐시 지점 지정 또는 자동).
   - 설계: 고정 내용을 앞에, 가변 내용을 뒤에.
3. **정확 일치 응답 캐시**
   - (모델, 프롬프트, 파라미터)의 해시 → 응답. 온도 0의 결정적 요청, 반복 배치 작업에 유효.
4. **시맨틱 캐시**
   - 의미가 비슷한 질문의 응답 재사용(임베딩 유사도 + 임계값). FAQ형 트래픽에 효과적.
5. **중간 결과 캐시**
   - 임베딩, 검색 결과, 도구 호출 결과, 문서 파싱 결과.

**구현 시 주의**

- **캐시 키:** 모델 버전, 프롬프트 버전, 파라미터, 사용자 권한 범위·테넌트를 포함해 잘못된 재사용 방지.
- **무효화:** TTL, 근거 데이터 변경 시 관련 캐시 삭제, 모델·프롬프트 변경 시 전체 무효화.
- **개인정보:** 사용자별 데이터가 담긴 응답은 공유 캐시에 넣지 않기.
- **품질:** 시맨틱 캐시 임계값을 평가셋으로 정하고, 잘못된 캐시 응답률 모니터링.

**측정:** 계층별 캐시 적중률, 절감된 토큰·비용, TTFT 개선.

<summary><b>Q31. 동기 추론과 비동기 추론의 차이는 무엇이며, 각각은 언제 사용하나요?</b></summary>

**동기 추론 (Synchronous)**

- 클라이언트가 요청을 보내고 **응답이 올 때까지 연결을 유지하며 기다립니다**(스트리밍 포함).
- 사용 사례: 채팅, 자동완성, 음성 에이전트, 실시간 검색, 사용자가 화면 앞에서 결과를 기다리는 모든 상호작용.
- 요구: 낮은 지연, 높은 가용성, 피크 대응 용량.

**비동기 추론 (Asynchronous)**

- 클라이언트가 작업을 제출하면 **작업 ID를 즉시 받고**, 처리는 백그라운드에서 진행됩니다. 결과는 나중에 조회(polling)하거나 웹훅·알림으로 받습니다.

```
POST /jobs → {"job_id": "123", "status": "queued"}
   ... 워커가 대기열에서 꺼내 처리 ...
GET /jobs/123 → {"status": "done", "result": ...}   또는 웹훅 호출
```

- 사용 사례: 대량 문서 처리, 긴 동영상 분석, 보고서 생성, 데이터셋 일괄 분류·임베딩, 평가 실행, 오래 걸리는 에이전트 작업.

**비교**

| | 동기 | 비동기 |
|---|---|---|
| 지연 요구 | 수백 ms~수십 초 | 분~시간 허용 |
| 연결 | 유지 | 즉시 반환 |
| 부하 대응 | 피크 용량 확보 필요 | 대기열이 흡수, 평탄하게 처리 |
| 실패 처리 | 클라이언트 재시도 | 큐 기반 재시도, 데드 레터 큐 |
| 비용 | 상대적으로 높음 | 배치 API 할인, 저렴한 시간대·스팟 인스턴스 활용 가능 |

**선택 기준:** 사용자가 결과를 즉시 봐야 하면 동기, 그렇지 않으면 비동기로 바꾸는 것이 비용·안정성 면에서 유리합니다. 하나의 제품에서 둘을 함께 쓰는 경우가 많습니다(예: 즉시 짧은 답 + 상세 분석은 비동기로 나중에 전달).

</details>

<summary><b>Q32. FSDP(Fully Sharded Data Parallel)란 무엇이며, DeepSpeed ZeRO와 어떻게 다른가요?</b></summary>

**배경:** 일반 데이터 병렬화는 GPU마다 모델 전체(파라미터 + 기울기 + 옵티마이저 상태)를 복제하므로, 큰 모델은 GPU 한 장의 메모리에 들어가지 않습니다. Adam 혼합 정밀도 기준으로 파라미터당 약 16바이트가 필요합니다.

**ZeRO (Zero Redundancy Optimizer, DeepSpeed)**

- 데이터 병렬 GPU들이 **중복 저장하던 상태를 나눠 저장** 해 메모리 중복을 제거합니다.
  - **ZeRO-1:** 옵티마이저 상태 분할
  - **ZeRO-2:** + 기울기 분할
  - **ZeRO-3:** + 파라미터 분할 (계산 직전에 필요한 층의 파라미터를 다른 GPU에서 모아 오고(all-gather), 사용 후 버림)
- 추가 기능: ZeRO-Offload / ZeRO-Infinity(CPU 메모리·NVMe로 오프로딩), 다양한 학습 최적화가 DeepSpeed 라이브러리에 통합.

**FSDP (PyTorch)**

- ZeRO-3와 같은 아이디어를 **PyTorch 네이티브** 로 구현한 것입니다.
- 모델을 단위(보통 트랜스포머 블록)로 감싸, 각 단위의 파라미터·기울기·옵티마이저 상태를 GPU들에 나눠 저장합니다.
- 순전파·역전파 때 해당 단위의 파라미터를 all-gather하고, 기울기는 reduce-scatter로 다시 나눕니다.
- 샤딩 전략 선택 가능(전체 샤딩, 기울기·옵티마이저만 샤딩, 노드 내 샤딩 + 노드 간 복제 같은 하이브리드).
- 최신 버전(FSDP2)은 PyTorch의 DTensor 기반으로 텐서 병렬화 등과 결합하기 쉬워졌습니다.

**차이 요약**

| | DeepSpeed ZeRO | PyTorch FSDP |
|---|---|---|
| 소속 | DeepSpeed 라이브러리 (Microsoft) | PyTorch 본체 |
| 단계 선택 | ZeRO-1/2/3 명시적 단계 | 샤딩 전략 옵션 |
| 통합 | DeepSpeed 설정·엔진 사용 | PyTorch 코드에 자연스럽게 통합 |
| 오프로딩 | CPU·NVMe 오프로딩이 강력 | CPU 오프로딩 지원 |
| 생태계 | DeepSpeed 기능 묶음 | torch.compile, DTensor 등 PyTorch 기능과 결합 |

**공통 트레이드오프:** 메모리는 크게 줄지만 GPU 간 통신이 늘어나므로, 고속 네트워크와 통신-계산 겹치기(prefetch)가 성능에 중요합니다. Hugging Face Accelerate·Trainer에서 둘 다 사용할 수 있습니다.

<details>
<summary><b>Q33. TTFT, TPOT, 처리량(throughput)이란 무엇이며, 서로 어떤 트레이드오프 관계에 있나요?</b></summary>

**정의**

- **TTFT (Time To First Token):** 요청 후 첫 토큰이 나올 때까지의 시간. 대기열 대기 + 프리필 시간. 체감 반응성을 결정합니다.
- **TPOT (Time Per Output Token) / ITL (Inter-Token Latency):** 첫 토큰 이후 토큰 하나를 생성하는 평균 시간(토큰 간 간격). 스트리밍 읽기 속도를 결정합니다.
- **전체 지연 ≈ TTFT + TPOT × (출력 토큰 수 - 1)**
- **처리량:** 시스템 전체가 초당 처리하는 토큰 수(또는 요청 수). 비용 효율을 결정합니다.

**트레이드오프**

1. **배치 크기 ↑ → 처리량 ↑, TPOT ↑**
   - 디코드는 메모리 병목이라 배치를 키우면 가중치 한 번 읽기로 더 많은 토큰을 만들어 처리량이 크게 오릅니다.
   - 하지만 단계당 계산량이 늘어 각 요청의 토큰 간 간격(TPOT)은 길어집니다.
2. **프리필 처리 방식 ↔ TTFT와 TPOT**
   - 새 요청의 프리필을 우선 처리하면 TTFT는 짧아지지만, 진행 중인 디코드가 멈춰 다른 요청의 TPOT가 튑니다.
   - 디코드를 우선하면 TPOT는 안정적이지만 새 요청의 TTFT가 늘어납니다.
   - 청크 프리필, 프리필-디코드 분리로 이 충돌을 완화합니다.
3. **텐서 병렬화 ↑ → 요청당 지연 ↓, GPU당 처리량 효율 ↓** (통신 오버헤드)
4. **추측 디코딩:** 작은 배치에서 TPOT를 크게 줄이지만, 큰 배치(높은 처리량)에서는 이득이 줄거나 오히려 손해일 수 있습니다.

**실무에서의 목표 설정**

- 사용 사례별 SLO를 정합니다(예: 채팅은 TTFT p95 < 1초, TPOT p95 < 50ms).
- SLO를 만족하는 범위 안에서 처리량을 최대화합니다(**굿풋, goodput**: SLO를 지킨 요청만 센 처리량).
- 배치 작업은 지연보다 처리량, 실시간 대화는 지연을 우선합니다.

<summary><b>Q35. 인프라 수준의 모델 라우팅이란 무엇이며, 요청을 복잡도와 비용에 따라 어떻게 라우팅하나요?</b></summary>

**인프라 수준 모델 라우팅** 은 애플리케이션이 특정 모델을 지정하지 않아도, 게이트웨이·라우터가 **요청 특성에 맞춰 가장 적합한 모델·배포로 자동 분배** 하는 것입니다.

**라우팅 기준**

- **복잡도·난이도:** 단순 질문 → 소형 모델, 복잡한 추론·코딩 → 대형·추론 모델
- **작업 유형:** 코드, 수학, 요약, 번역, 분류 → 특화 모델
- **비용·예산:** 요금제, 테넌트 예산, 남은 할당량
- **지연 요구:** 실시간 → 빠른 모델, 배치 → 저렴한 모델·배치 API
- **컨텍스트 길이:** 긴 입력 → 긴 컨텍스트 지원 모델
- **가용성·부하:** 장애·속도 제한·대기열 상태에 따라 다른 제공사·리전
- **데이터 규정:** 민감 데이터 → 자체 호스팅·특정 리전 모델

**복잡도 판단 방법**

1. **규칙:** 입력 길이, 키워드, 기능·엔드포인트별 고정 매핑 (가장 단순·저렴)
2. **분류 모델:** 작은 분류기나 임베딩 기반 라우터로 난이도·유형 예측
3. **품질 예측 라우터:** "소형 모델이 이 요청을 충분히 잘 처리할 확률"을 학습해 임계값 이상이면 소형 모델로(RouteLLM 같은 접근)
4. **캐스케이드:** 소형 모델이 먼저 답하고, 확신도가 낮거나 검증(형식, 판정자)에 실패하면 대형 모델로 재요청

```
요청 → [라우터] ─ 쉬움 (예: 70%) → 소형 모델
               ─ 보통 (25%)      → 중형 모델
               ─ 어려움 (5%)     → 대형 추론 모델
         └ 소형 결과 검증 실패 시 → 상위 모델로 승격
```

**운영**

- 경로별 품질·비용·지연을 지속 모니터링하고, 라우팅 오류(소형이 실패한 사례)를 수집해 라우터를 재학습합니다.
- 라우터 자체의 지연과 비용이 절감 효과보다 작아야 합니다.
- 품질 목표를 유지하는 범위에서 비용을 최소화하는 임계값을 평가셋으로 찾습니다.
