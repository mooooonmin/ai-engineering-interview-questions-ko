<summary><b>Q1. 검색 증강 생성(RAG)이란 무엇이며, 왜 중요한가요?</b></summary>

**RAG(Retrieval-Augmented Generation)** 는 LLM이 답을 생성하기 전에 **외부 지식 저장소에서 관련 정보를 검색해 프롬프트에 넣어 주는** 방식입니다(Lewis 외, 2020).

**LLM만 쓸 때의 문제**

- **지식 컷오프:** 학습 이후의 정보를 모릅니다.
- **사내·개인 정보 부재:** 회사 문서, 고객 데이터는 학습되지 않았습니다.
- **환각:** 모르는 것도 그럴듯하게 지어냅니다.
- **출처 불명:** 답의 근거를 확인할 수 없습니다.

**RAG가 주는 이점**

- **최신성:** 문서만 갱신하면 모델 재학습 없이 지식이 업데이트됩니다.
- **근거 기반 답변:** 검색된 문서를 바탕으로 답해 환각이 줄고, 출처를 인용할 수 있습니다.
- **접근 제어:** 사용자 권한에 맞는 문서만 검색해 보안 요구를 맞출 수 있습니다.
- **비용 효율:** 파인튜닝보다 훨씬 저렴하고 빠르게 구축·수정할 수 있습니다.

**대표 활용:** 사내 문서 Q&A, 고객 지원 챗봇, 법률·의료 문서 검색, 코드베이스 질의, 제품 매뉴얼 도우미.

**핵심 한계:** "검색이 틀리면 답도 틀린다." RAG 품질의 대부분은 **검색 품질**(청킹, 임베딩, 하이브리드 검색, 리랭킹)에서 결정됩니다.

<summary><b>Q2. 기본적인 RAG 시스템의 아키텍처를 설명하세요.</b></summary>

RAG는 크게 **오프라인 인덱싱 파이프라인** 과 **온라인 질의 파이프라인** 으로 나뉩니다.

```
[인덱싱 - 오프라인]
문서(PDF, 웹, DB) → 로딩/파싱 → 정제 → 청킹 → 임베딩 → 벡터 DB 저장(+메타데이터)

[질의 - 온라인]
사용자 질문 → (질문 재작성) → 질문 임베딩 → 벡터 검색 top-k
            → (리랭킹) → 프롬프트 조립(지시 + 컨텍스트 + 질문) → LLM 생성 → 답 + 출처
```

**인덱싱 단계**

1. **로딩·파싱:** 다양한 형식의 문서에서 텍스트, 표, 메타데이터(제목, 날짜, 권한)를 추출합니다.
2. **청킹:** 검색 단위로 적당한 크기(예: 200~1,000 토큰)로 나눕니다.
3. **임베딩:** 각 청크를 벡터로 변환합니다.
4. **저장:** 벡터 DB(또는 벡터 인덱스 + 키워드 인덱스)에 저장합니다.

**질의 단계**

1. 질문을 같은 임베딩 모델로 벡터화합니다.
2. 유사도가 높은 청크 상위 k개를 검색합니다(메타데이터 필터 적용).
3. 선택적으로 리랭커로 순서를 정밀하게 다시 매깁니다.
4. 상위 청크를 프롬프트에 넣고 "주어진 문서에 근거해 답하라"고 지시합니다.
5. LLM 답변과 출처를 반환합니다.

**운영 구성 요소:** 문서 변경 감지·재인덱싱, 캐시, 평가·모니터링, 접근 제어.

<summary><b>Q3. RAG 파이프라인의 핵심 구성 요소는 무엇인가요?</b></summary>

| 구성 요소 | 역할 | 주요 선택지 |
|---|---|---|
| **문서 로더/파서** | 원본에서 텍스트·구조 추출 | PDF 파서, OCR, HTML 파서, Unstructured, Docling |
| **청커(Chunker)** | 문서를 검색 단위로 분할 | 고정 크기, 재귀, 의미 기반, 구조 기반 |
| **임베딩 모델** | 텍스트를 벡터로 변환 | OpenAI, Cohere, BGE, E5 등 |
| **벡터 저장소** | 벡터 저장과 근사 최근접 검색 | pgvector, Pinecone, Weaviate, Qdrant, Milvus, FAISS |
| **키워드 인덱스** | 정확한 용어 매칭 | BM25 (Elasticsearch, OpenSearch) |
| **리트리버** | 질문에 맞는 후보 검색 | 벡터, 하이브리드, 메타데이터 필터 |
| **리랭커** | 후보를 정밀하게 재정렬 | 크로스 인코더, LLM 리랭커 |
| **쿼리 변환기** | 질문 재작성·분해·확장 | HyDE, 멀티 쿼리 |
| **프롬프트 조립** | 지시 + 컨텍스트 + 질문 결합 | 템플릿, 인용 지시 |
| **생성 LLM** | 최종 답변 작성 | API 모델, 오픈 모델 |
| **후처리·가드레일** | 인용 확인, 안전성 검사 | 출처 검증, PII 필터 |
| **평가·관측** | 품질 측정과 모니터링 | 검색 지표, 충실도, 트레이싱 |

**면접에서 강조할 점**

- 각 구성 요소가 전체 품질에 영향을 줍니다. 특히 **파싱과 청킹** 은 과소평가되기 쉽지만 문제의 큰 원인입니다.
- 검색 품질(찾았는가)과 생성 품질(제대로 답했는가)을 **분리해서 평가** 해야 어디를 고칠지 알 수 있습니다.

<summary><b>Q4. 청킹(chunking) 전략이란 무엇이며, 적절한 청크 크기는 어떻게 정하나요?</b></summary>

**청킹** 은 긴 문서를 검색·임베딩의 단위가 되는 작은 조각으로 나누는 것입니다.

**왜 중요한가**

- 임베딩 모델과 LLM에는 입력 길이 한계가 있습니다.
- 청크가 검색 결과의 단위가 되므로, 청크 하나가 **하나의 완결된 의미** 를 담아야 검색이 정확합니다.

**크기에 따른 트레이드오프**

| | 작은 청크 (예: 100~200 토큰) | 큰 청크 (예: 1,000+ 토큰) |
|---|---|---|
| 검색 정밀도 | 높음 (주제가 하나) | 낮음 (여러 주제가 섞여 임베딩이 흐려짐) |
| 문맥 | 부족 (앞뒤 맥락이 잘림) | 풍부 |
| 프롬프트 토큰 | 적게 듦 | 많이 듦 |

**크기 정하는 방법**

1. **문서 특성:** FAQ는 질문-답 하나가 한 청크, 기술 문서는 섹션 단위, 법률 문서는 조항 단위가 자연스럽습니다.
2. **질문 특성:** 짧은 사실 질문이 많으면 작게, 설명·요약형 질문이 많으면 크게.
3. **임베딩 모델의 최적 길이:** 모델이 학습된 입력 길이를 고려합니다.
4. **실험:** 256, 512, 1,024 토큰 등 여러 크기로 인덱싱해 **평가셋의 검색 재현율(recall@k)과 최종 답 품질** 을 비교합니다. 결국 데이터로 정해야 합니다.

**일반적인 시작점:** 300~800 토큰, 10~20% 겹침(overlap).

**보완 기법**

- **부모-자식 청킹:** 작은 청크로 검색하고 큰 부모 청크를 LLM에 넘김
- **컨텍스트 추가:** 청크에 문서 제목·섹션 경로를 붙이거나 LLM이 쓴 맥락 설명을 덧붙임(Contextual Retrieval)

<summary><b>Q5. 고정 크기 청킹, 의미 기반(semantic) 청킹, 재귀(recursive) 청킹을 비교하세요.</b></summary>

**1. 고정 크기 청킹**

- 토큰 수(또는 글자 수) 기준으로 일정하게 자르고, 경계 손실을 줄이기 위해 겹침을 둡니다.
- 장점: 가장 단순하고 빠르며 예측 가능합니다.
- 단점: 문장·문단 중간에서 잘려 의미가 끊길 수 있습니다.

**2. 재귀 청킹 (recursive character splitting)**

- 구분자 우선순위 목록(예: `\n\n` → `\n` → `. ` → ` `)을 두고, 큰 단위부터 나눠 보다가 여전히 크면 더 작은 구분자로 다시 나눕니다.
- 장점: 문단·문장 경계를 최대한 지키면서 크기를 맞춥니다. 실무 기본값으로 많이 씁니다(LangChain의 `RecursiveCharacterTextSplitter`).
- 단점: 의미 단위가 아닌 문자 구분자 기준이라, 주제 전환을 정확히 잡지는 못합니다.

**3. 의미 기반 청킹 (semantic chunking)**

- 문장마다 임베딩을 구하고, 인접 문장 간 유사도가 크게 떨어지는 지점(주제 전환)에서 자릅니다.
- 장점: 청크 하나가 하나의 주제를 담아 검색 정밀도가 좋아질 수 있습니다.
- 단점: 인덱싱 비용(문장별 임베딩)이 들고, 청크 크기가 들쭉날쭉하며, 임계값 조정이 필요합니다. 항상 더 나은 결과를 보장하지는 않습니다.

| | 고정 크기 | 재귀 | 의미 기반 |
|---|---|---|---|
| 구현 난이도 | 매우 쉬움 | 쉬움 | 보통 |
| 인덱싱 비용 | 낮음 | 낮음 | 높음 |
| 의미 보존 | 낮음 | 중간 | 높음 |
| 크기 일관성 | 높음 | 높음 | 낮음 |

**그 외:** 문서 구조 기반 청킹(마크다운 제목, HTML 태그, 코드의 함수 단위), LLM 기반 청킹(명제 단위로 분해) 등이 있습니다.

**실무 조언:** 재귀 청킹으로 시작해 평가 지표를 기준으로 개선하고, 문서에 구조가 있으면 구조 기반 청킹을 우선 고려합니다.

**더 읽어보기 (영문):** [Chunking Strategies for RAG](https://outcomeschool.com/blog/chunking-strategies-for-rag)

<summary><b>Q6. 컨텍스트 기반 검색(Contextual Retrieval)이란 무엇이며, RAG를 어떻게 개선하나요?</b></summary>

**문제:** 청크는 문서에서 잘려 나온 조각이라 **맥락을 잃습니다.** 예: "이 회사의 매출은 전 분기 대비 3% 증가했다." → 어느 회사, 어느 분기인지 청크만 보면 알 수 없어 검색에서 놓칩니다.

**Contextual Retrieval (Anthropic이 2024년 소개한 방법)**

1. 인덱싱 시 각 청크에 대해 LLM에게 **문서 전체와 해당 청크** 를 주고, "이 청크가 문서에서 어떤 맥락에 있는지 1~2문장으로 설명하라"고 요청합니다.
2. 생성된 맥락 설명을 청크 앞에 붙입니다.
   - 예: "이 내용은 ACME사의 2023년 2분기 실적 보고서 중 매출 섹션입니다. 이 회사의 매출은 ..."
3. 맥락이 붙은 청크로 **임베딩(Contextual Embeddings)** 과 **BM25 인덱스(Contextual BM25)** 를 모두 만듭니다.

**효과**

- 청크가 독립적으로도 의미를 가져 검색 실패가 크게 줄어듭니다. 소개 자료에서는 하이브리드 검색과 리랭킹을 함께 쓸 때 검색 실패율이 큰 폭으로 감소했다고 보고했습니다.

**비용 관리**

- 청크마다 LLM 호출이 필요하지만, 같은 문서의 청크들은 문서 부분이 동일하므로 **프롬프트 캐싱** 으로 비용을 크게 줄일 수 있습니다. 인덱싱 시 1회 비용입니다.

**더 간단한 대안**

- 청크 앞에 문서 제목, 섹션 경로(제목 계층), 날짜 같은 메타데이터를 붙이는 것만으로도 상당한 효과가 있습니다.

<summary><b>Q7. 임베딩 모델이란 무엇이며, 텍스트를 어떻게 벡터로 변환하나요?</b></summary>

**임베딩 모델** 은 텍스트를 받아 그 의미를 담은 **고정 길이 벡터**(예: 384, 768, 1536차원)를 출력하는 모델입니다. 의미가 비슷한 텍스트는 벡터 공간에서 가깝게 배치됩니다.

**변환 과정 (트랜스포머 기반 임베딩 모델)**

1. **토큰화:** 텍스트를 토큰으로 나눕니다.
2. **인코딩:** 트랜스포머 인코더(주로 BERT 계열, 최근에는 LLM 기반도 있음)가 각 토큰의 문맥 벡터를 계산합니다.
3. **풀링(pooling):** 토큰 벡터들을 하나의 벡터로 합칩니다.
   - 평균 풀링(mean pooling), [CLS] 토큰 사용, 마지막 토큰 사용(디코더 기반) 등
4. **정규화:** 보통 길이를 1로 맞춰 코사인 유사도 = 내적이 되게 합니다.

**어떻게 "의미"를 학습하나: 대조 학습**

- (질문, 관련 문서) 같은 **양성 쌍** 은 가깝게, 관련 없는 문서(음성)는 멀게 만드는 손실로 학습합니다.
- 배치 안의 다른 예시를 음성으로 쓰는 in-batch negative, 헷갈리는 음성을 일부러 넣는 hard negative mining이 성능의 핵심입니다.

**종류**

- **양방향 인코더(bi-encoder):** 질문과 문서를 따로 임베딩 → 미리 계산해 둘 수 있어 대규모 검색에 적합
- **크로스 인코더:** 질문과 문서를 함께 넣어 점수 계산 → 정확하지만 느려서 리랭킹에 사용

**실무 포인트:** 비대칭 검색(짧은 질문 ↔ 긴 문서)용 모델은 질문과 문서에 서로 다른 접두어(예: `query:`, `passage:`)를 요구하기도 하므로, 모델 사용법을 지켜야 성능이 나옵니다.

<summary><b>Q8. RAG 시스템에 쓸 임베딩 모델은 어떻게 고르나요?</b></summary>

**선택 기준**

1. **검색 품질 (가장 중요)**
   - MTEB 같은 공개 벤치마크의 **검색(Retrieval) 항목** 점수를 참고하되, 최종 판단은 **내 데이터로 만든 평가셋** 에서의 recall@k, nDCG로 합니다. 벤치마크 순위와 실제 도메인 성능은 다를 수 있습니다.
2. **언어 지원**
   - 한국어 등 대상 언어 성능, 다국어·교차 언어 검색 지원 여부.
3. **도메인 적합성**
   - 법률, 의료, 코드 등 전문 분야라면 도메인 특화 모델이나 파인튜닝 가능성을 봅니다.
4. **입력 길이**
   - 최대 입력 토큰(512, 8K 등)이 청크 크기보다 충분히 커야 합니다.
5. **차원 수와 비용**
   - 차원이 클수록 저장 공간과 검색 비용이 늘어납니다. 일부 모델은 차원을 줄여 써도 성능이 유지되는 방식(Matryoshka 표현)을 지원합니다.
6. **배포 방식**
   - API(관리 편함, 데이터 외부 전송) vs 자체 호스팅(데이터 통제, 대량 처리 시 저렴).
7. **속도·처리량**
   - 인덱싱할 문서량과 질의 지연 요구사항을 만족하는지.
8. **안정성**
   - 모델이 바뀌면 전체 재인덱싱이 필요하므로, 장기적으로 쓸 수 있는 모델인지 고려합니다.

**평가 절차 예시**

1. 실제 질문 100~300개와 정답 문서를 준비합니다.
2. 후보 모델 3~5개로 각각 인덱싱합니다.
3. recall@5, recall@20, MRR 비교 + 지연·비용 비교.
4. 하이브리드 검색·리랭커를 붙였을 때의 최종 성능도 확인합니다(임베딩 차이가 리랭킹 후 줄어들기도 함).

<summary><b>Q9. 에이전틱 RAG(Agentic RAG)를 설명하세요.</b></summary>

**에이전틱 RAG** 는 "질문 → 한 번 검색 → 답"으로 고정된 기존 RAG와 달리, **LLM 에이전트가 검색 과정을 스스로 계획하고 반복** 하는 방식입니다.

**기존 RAG의 한계**

- 검색을 항상 한 번만 하고, 결과가 부족해도 그대로 답합니다.
- 여러 문서를 조합해야 하는 질문(멀티홉)이나 여러 소스(문서 + DB + 웹)를 써야 하는 질문에 약합니다.

**에이전틱 RAG에서 에이전트가 하는 일**

- **검색 여부 판단:** 검색이 필요 없는 질문은 바로 답합니다.
- **소스 선택(라우팅):** 벡터 DB, SQL DB, 웹 검색, API 중 무엇을 쓸지 고릅니다.
- **질문 분해:** 복잡한 질문을 하위 질문으로 나눠 각각 검색합니다.
- **반복 검색:** 결과를 평가하고 부족하면 질문을 바꿔 다시 검색합니다.
- **자기 검증:** 생성한 답이 검색 결과에 근거하는지 확인하고 필요하면 수정합니다.

```
질문: "작년 매출 1위 제품의 반품률은 경쟁 제품보다 높은가?"
→ [SQL] 작년 매출 1위 제품 조회
→ [문서 검색] 해당 제품 반품 보고서
→ [문서 검색] 경쟁 제품 반품 데이터
→ 결과 비교 후 답변 (부족하면 추가 검색)
```

**장단점**

- 장점: 복잡한 질문에 강하고, 다양한 소스를 통합합니다.
- 단점: LLM 호출이 여러 번이라 지연과 비용이 크고, 동작 예측과 디버깅이 어렵습니다.

**실무 팁:** 모든 질문에 쓰기보다, 단순 질문은 기본 RAG로 처리하고 복잡한 질문만 에이전틱 경로로 라우팅하는 구성이 효율적입니다. 최대 반복 횟수와 비용 한도도 둡니다.

<summary><b>Q10. 하이브리드 검색(hybrid search)이란 무엇이며, 순수 벡터 검색보다 왜 나은가요?</b></summary>

**하이브리드 검색** 은 **키워드 기반 검색(BM25 등 희소 검색)** 과 **임베딩 기반 의미 검색(밀집 검색)** 을 함께 사용하고 결과를 합치는 방식입니다.

**두 검색의 강점과 약점**

| | 키워드 검색 (BM25) | 벡터 검색 |
|---|---|---|
| 잘 찾는 것 | 정확한 용어, 제품 코드, 이름, 숫자, 약어 | 동의어, 바꿔 말하기, 의미가 비슷한 표현 |
| 못 찾는 것 | "환불" ↔ "돈 돌려받기" 같은 다른 표현 | 드문 고유명사, 모델 번호 `XR-2041`, 정확 일치가 필요한 용어 |

**결과 합치기 방법**

1. **RRF(Reciprocal Rank Fusion):** 점수 척도가 서로 다르므로 순위만 사용합니다.
   ```
   score(d) = Σ 1 / (k + rank_i(d))    # 보통 k = 60
   ```
   간단하고 튜닝이 거의 필요 없어 가장 많이 씁니다.
2. **가중 점수 합:** 각 점수를 정규화한 뒤 `α·벡터점수 + (1-α)·BM25점수`. α를 평가셋으로 조정합니다.

**왜 더 나은가**

- 서로의 약점을 보완해 대부분의 벤치마크와 실무에서 **재현율이 단독 검색보다 높게** 나옵니다.
- 특히 기업 문서처럼 전문 용어, 코드, 고유명사가 많은 데이터에서 효과가 큽니다.

**구현:** Elasticsearch/OpenSearch, Weaviate, Qdrant, Vespa, pgvector + 전문 검색 등 많은 저장소가 하이브리드 검색을 지원합니다. 하이브리드로 넓게 찾은 뒤 **리랭커** 로 정밀하게 정렬하는 조합이 일반적인 모범 사례입니다.

**더 읽어보기 (영문):** [How does Hybrid Search work?](https://outcomeschool.com/blog/how-does-hybrid-search-work)

<summary><b>Q11. 리랭킹(re-ranking)이란 무엇이며, RAG의 검색 품질을 어떻게 높이나요?</b></summary>

**리랭킹** 은 1차 검색이 가져온 후보 문서(예: 50~100개)를 **더 정확하지만 느린 모델로 다시 점수 매겨 순서를 재정렬** 하는 단계입니다.

**2단계 검색 구조**

```
질문 → [1단계: 빠른 검색] 수백만 문서 중 후보 100개 (벡터/BM25/하이브리드)
     → [2단계: 리랭킹] 100개를 정밀 채점 → 상위 5개만 LLM에 전달
```

**왜 정확도가 높아지나**

- 1단계의 bi-encoder는 질문과 문서를 **따로** 임베딩해 비교하므로, 둘 사이의 세밀한 상호작용을 보지 못합니다.
- 리랭커(주로 **크로스 인코더**)는 질문과 문서를 **함께** 입력받아 모든 토큰 간 어텐션으로 관련성을 판단합니다. 훨씬 정확하지만 문서마다 모델을 실행해야 해서 후보가 적을 때만 쓸 수 있습니다.

**효과**

- LLM에 넣는 문서 수를 줄이면서도 정답 문서가 포함될 확률을 높입니다 → 비용 절감, "lost in the middle" 완화, 환각 감소.
- 1단계 재현율(recall@100)이 높고 리랭킹으로 정밀도(precision@5)를 올리는 역할 분담입니다.

**리랭커 종류:** 크로스 인코더(Cohere Rerank, BGE-reranker 등), ColBERT 같은 후기 상호작용 모델, LLM 기반 리랭커.

**고려 사항:** 리랭킹은 수십~수백 ms의 지연을 추가합니다. 후보 수와 모델 크기를 지연 예산에 맞춰 조정합니다.

**더 읽어보기 (영문):** [How does a Reranker work?](https://outcomeschool.com/blog/how-does-a-reranker-work)

<summary><b>Q12. ColBERT란 무엇이며, 후기 상호작용(late interaction) 검색은 어떻게 동작하나요?</b></summary>

**ColBERT** 는 bi-encoder의 속도와 크로스 인코더의 정확도 사이에서 균형을 잡은 검색 모델입니다(Khattab & Zaharia, 2020).

**세 가지 방식 비교**

- **Bi-encoder:** 질문·문서를 각각 **벡터 하나** 로 압축 → 내적. 빠르지만 정보 손실이 큼.
- **크로스 인코더:** 질문과 문서를 **함께** 넣어 모든 토큰이 상호작용. 정확하지만 문서를 미리 계산해 둘 수 없음.
- **ColBERT (후기 상호작용):** 질문·문서를 각각 인코딩하되, **토큰마다 벡터를 하나씩 유지** 하고, 비교는 마지막 단계에서 토큰 단위로 합니다.

**점수 계산: MaxSim**

```
score(q, d) = Σ_{질문 토큰 i} max_{문서 토큰 j} (q_i · d_j)
```

- 질문의 각 토큰이 문서에서 **가장 잘 맞는 토큰** 을 찾고, 그 최대 유사도를 모두 더합니다.
- "이 질문의 각 단어가 문서 어딘가에 잘 대응되는가"를 세밀하게 보는 셈입니다.

**장점**

- 문서 토큰 벡터는 미리 계산해 둘 수 있어 대규모 검색이 가능합니다.
- 토큰 단위 매칭이라 bi-encoder보다 정확하고, 도메인이 바뀌어도 일반화가 잘 되는 편입니다.
- 키워드 정확 매칭과 의미 매칭의 장점을 일부 함께 가집니다.

**단점**

- 문서마다 토큰 수만큼 벡터를 저장해야 해 **저장 공간이 훨씬 큽니다.** ColBERTv2는 잔차 압축으로 이를 크게 줄였고, PLAID 같은 엔진으로 검색을 빠르게 합니다.

**활용:** 1단계 검색기로도, 리랭커로도 쓰입니다. 이미지 문서 검색용 ColPali처럼 멀티모달로 확장된 변형도 있습니다.

**더 읽어보기 (영문):** [ColBERT - Late Interaction Retrieval Explained](https://outcomeschool.com/blog/decoding-colbert)

- **후보가 아주 많거나 1단계 검색 자체를 강화하고 싶을 때:** ColBERT.
- **질문이 복잡한 추론을 요구하거나(예: "이 정책 변경이 우리 계약에 영향을 주는가") 소량의 고가치 질의:** LLM 리랭커.
- **계층형 조합:** 하이브리드 검색(1,000개) → 크로스 인코더(상위 50개) → LLM 리랭커(상위 10개) 같은 다단계도 가능합니다.

<summary><b>Q14. RAG에서 여러 문서에 걸친 질문과 멀티홉(multi-hop) 질문을 어떻게 처리하나요?</b></summary>

**유형 구분**

- **여러 문서 집계형:** "올해 출시한 제품들의 공통 불만은?" → 여러 문서에서 정보를 모아 종합
- **멀티홉형:** "A 프로젝트 리더가 이전에 이끈 프로젝트의 예산은?" → 첫 검색 결과(리더 이름)로 다음 검색을 해야 함

단일 검색으로는 두 번째 단계의 문서를 찾을 수 없다는 것이 문제입니다. 질문 자체에 "그 리더의 이름"이 없기 때문입니다.

**해결 방법**

1. **질문 분해 (query decomposition)**
   - LLM이 질문을 하위 질문으로 나눕니다. "1) A 프로젝트 리더는 누구인가? 2) 그 사람이 이끈 이전 프로젝트는? 3) 그 예산은?"
2. **반복 검색 (iterative retrieval)**
   - 첫 검색 결과를 바탕으로 다음 검색 질의를 생성합니다. IRCoT처럼 추론 단계마다 검색을 섞는 방식도 있습니다.
3. **에이전틱 RAG**
   - 에이전트가 "충분한 정보를 모았는가"를 판단하며 필요한 만큼 검색합니다.
4. **GraphRAG / 지식 그래프**
   - 엔티티와 관계를 미리 그래프로 만들어 두면, "리더 → 이전 프로젝트 → 예산"을 그래프 탐색으로 직접 따라갈 수 있습니다.
5. **집계형 질문**
   - 검색 범위를 넓혀(top-k 증가, 메타데이터 필터로 대상 문서 전체 조회) map-reduce로 문서별 요약 후 종합합니다.
   - 데이터가 정형화되어 있다면 SQL로 처리하는 것이 더 정확합니다.

**평가:** HotpotQA 같은 멀티홉 데이터셋이나, 자체 멀티홉 질문셋으로 단계별 검색 성공률을 측정합니다.

<summary><b>Q15. RAG 시스템에서 "중간에서 길을 잃는(lost in the middle)" 문제란 무엇인가요?</b></summary>

**정의:** 검색된 여러 문서를 프롬프트에 넣었을 때, LLM이 **앞과 뒤에 있는 문서는 잘 활용하지만 중간에 있는 문서의 정보는 놓치는** 현상입니다.

**RAG에서 특히 문제가 되는 이유**

- 정답 문서를 검색해 놓고도, 그 문서가 10개 중 5번째에 들어가면 답에 반영되지 않을 수 있습니다.
- "더 많이 넣으면 더 정확해진다"는 직관이 틀리게 됩니다. 문서를 늘리면 재현율은 오르지만 중간 정보 활용률이 떨어져 최종 정확도는 오히려 낮아질 수 있습니다.

**대응**

1. **적게, 정확하게 넣기:** 리랭킹으로 상위 3~5개만 넣습니다.
2. **배치 순서 조정:** 가장 관련성 높은 문서를 **맨 앞과 맨 뒤** 에 두고, 덜 중요한 문서를 중간에 둡니다(LangChain의 LongContextReorder 같은 방식).
3. **질문 위치:** 긴 컨텍스트 **뒤에** 질문과 지시를 둡니다.
4. **문서 구조화:** 각 문서를 번호와 태그로 감싸 모델이 구분하기 쉽게 합니다.
5. **인용 우선 생성:** "먼저 관련 문장을 인용하고 그다음 답하라"로 모델이 전체를 다시 훑게 합니다.
6. **문서별 처리:** 문서마다 관련 정보를 먼저 추출하고 결과를 합칩니다.

**측정:** 정답 문서의 위치를 바꿔 가며 정확도를 재는 테스트로 내 시스템과 모델의 민감도를 확인합니다.

**더 읽어보기 (영문):** [The Lost in the Middle Problem in LLMs](https://outcomeschool.com/blog/lost-in-the-middle-problem-in-llms)

<summary><b>Q16. RAG 시스템은 어떻게 평가하나요? 충실도(faithfulness), 관련성(relevance), 컨텍스트 정밀도/재현율(context precision/recall)을 설명하세요.</b></summary>

RAG 평가는 **검색 품질** 과 **생성 품질** 을 분리해서 봐야 어디가 문제인지 알 수 있습니다.

**검색 지표**

- **컨텍스트 재현율(context recall):** 답에 필요한 정보가 검색된 컨텍스트에 **얼마나 포함되었는가**. 낮으면 검색이 필요한 문서를 놓치고 있다는 뜻입니다.
- **컨텍스트 정밀도(context precision):** 검색된 컨텍스트 중 **실제로 관련된 비율**, 그리고 관련 문서가 상위에 있는가. 낮으면 노이즈가 많다는 뜻입니다.
- 전통적 지표: recall@k, MRR, nDCG(정답 문서 라벨이 있을 때).

**생성 지표**

- **충실도(faithfulness, groundedness):** 답의 각 주장이 **검색된 컨텍스트로 뒷받침되는가**. 답을 주장 단위로 쪼개고 각각 컨텍스트에서 근거를 찾는 방식으로 측정합니다. 낮으면 환각입니다.
- **답변 관련성(answer relevance):** 답이 **질문에 제대로 답하고 있는가**. 엉뚱하거나 회피하는 답을 잡습니다.
- **정확성(answer correctness):** 정답(ground truth)이 있을 때 답이 사실적으로 맞는가.

**진단 표**

| 컨텍스트 재현율 | 충실도 | 의미 | 조치 |
|---|---|---|---|
| 낮음 | - | 검색 실패 | 청킹, 임베딩, 하이브리드, 쿼리 변환 |
| 높음 | 낮음 | 생성 단계 환각 | 프롬프트, 모델, 인용 강제 |
| 높음 | 높음, 정답률 낮음 | 정답 데이터/질문 이해 문제 | 평가셋 점검, 질문 해석 |

**평가 방법**

- 자동화: RAGAS, TruLens, DeepEval 같은 도구가 LLM-as-a-judge로 위 지표를 계산합니다.
- 판정 LLM의 점수가 사람 평가와 맞는지 소량 샘플로 검증합니다.
- 실제 질문 기반 평가셋을 만들고, 변경 시마다 회귀 테스트를 돌립니다.
- 운영 중에는 사용자 피드백(좋아요/싫어요), 재질문률도 함께 봅니다.

**더 읽어보기 (영문):** [LLM Evaluation](https://outcomeschool.com/blog/llm-evaluation)

<summary><b>Q17. Self-RAG를 설명하세요. 모델은 언제 검색할지를 어떻게 결정하나요?</b></summary>

**Self-RAG** 는 LLM이 **검색이 필요한지 스스로 판단하고, 검색 결과와 자기 답변을 스스로 평가** 하도록 학습한 프레임워크입니다(Asai 외, 2023).

**기존 RAG의 문제**

- 질문과 상관없이 항상 검색하므로, 불필요한 검색이 오히려 답을 흐리거나 비용을 늘립니다.
- 검색된 문서가 쓸모없어도 그대로 사용합니다.

**핵심: 반성 토큰(reflection tokens)**

모델이 생성 중에 특수 토큰을 출력해 스스로 판단하도록 학습합니다.

| 토큰 | 판단 내용 |
|---|---|
| **Retrieve** | 지금 검색이 필요한가? (예/아니오/계속) |
| **IsRel** | 검색된 문서가 질문과 관련 있는가? |
| **IsSup** | 생성한 문장이 문서로 뒷받침되는가? (완전/부분/없음) |
| **IsUse** | 최종 답이 유용한가? (1~5점) |

**동작 흐름**

1. 생성 중 모델이 `Retrieve=예`를 내면 검색을 수행합니다.
2. 검색된 여러 문서 각각에 대해 병렬로 답 후보를 만들고, IsRel·IsSup·IsUse로 평가합니다.
3. 점수가 가장 좋은 후보를 선택합니다.

**학습 방법:** 강한 모델(GPT-4)로 반성 토큰 라벨을 만들어 비평 모델을 학습하고, 그 비평 모델로 대량 데이터에 라벨을 달아 생성 모델을 학습합니다.

**실무 적용**

- 원 논문처럼 모델을 학습시키지 않더라도, 같은 아이디어를 **프롬프트·에이전트 단계로 구현** 할 수 있습니다: 검색 필요 여부 판단 → 문서 관련성 평가 → 답의 근거 확인 → 부족하면 재검색(Corrective RAG도 비슷한 접근).

**더 읽어보기 (영문):** [Agentic RAG](https://outcomeschool.com/blog/agentic-rag)

<summary><b>Q18. GraphRAG란 무엇이며, 기존 RAG 대신 언제 사용하나요?</b></summary>

**GraphRAG** 는 문서에서 **엔티티(사람, 조직, 개념)와 관계를 추출해 지식 그래프를 만들고**, 이 그래프 구조를 검색과 답변 생성에 활용하는 RAG 방식입니다. Microsoft Research의 GraphRAG(2024)가 대표적입니다.

**구축 과정 (Microsoft GraphRAG 방식)**

1. 문서를 청크로 나누고, LLM으로 각 청크에서 엔티티와 관계를 추출합니다.
2. 이를 합쳐 지식 그래프를 만듭니다.
3. 그래프를 커뮤니티 탐지 알고리즘(Leiden)으로 계층적 주제 그룹으로 나눕니다.
4. 각 커뮤니티에 대해 LLM이 요약 보고서를 미리 작성합니다.

**검색 방식**

- **로컬 검색:** 질문과 관련된 엔티티를 찾고, 그 주변 이웃 관계와 원문 청크를 함께 컨텍스트로 씁니다. 특정 대상에 대한 질문에 적합합니다.
- **글로벌 검색:** 커뮤니티 요약들을 map-reduce로 종합합니다. "이 데이터셋의 주요 주제는?" 같은 **전체를 아우르는 질문** 에 강합니다.

**기존 RAG 대신 쓰면 좋은 경우**

- **전체 요약·주제 질문:** 기존 RAG는 top-k 청크만 보므로 "전체적으로 어떤 경향이 있나"에 답하기 어렵습니다.
- **멀티홉 관계 질문:** "A와 B를 연결하는 사람은?"처럼 관계를 따라가야 하는 질문.
- **엔티티 중심 데이터:** 조직도, 사건 기록, 연구 논문 네트워크, 공급망 등.

**단점**

- 인덱싱 시 LLM 호출이 매우 많아 **구축 비용이 큽니다.**
- 문서가 바뀌면 그래프 갱신이 복잡합니다.
- 단순 사실 질문에서는 기존 벡터 RAG보다 나을 것이 없을 수 있습니다.

**실무:** 하이브리드로, 일반 질문은 벡터 RAG, 관계·전체 질문은 그래프 경로로 라우팅하는 구성이 많습니다. LightRAG처럼 비용을 줄인 변형도 있습니다.

**더 읽어보기 (영문):** [GraphRAG](https://outcomeschool.com/blog/graphrag)

<summary><b>Q19. 벡터 없는 RAG(Vectorless RAG)</b></summary>

**벡터 없는 RAG** 는 임베딩과 벡터 DB를 쓰지 않고, **LLM이 문서의 구조(목차, 섹션)를 직접 탐색하며 필요한 부분을 찾아 읽는** 검색 방식을 말합니다. 사람이 두꺼운 보고서에서 목차를 보고 해당 장을 찾아가는 방식과 비슷합니다.

**동작 방식 (예시)**

1. 문서를 파싱해 **계층적 트리 구조**(장 → 절 → 항, 각 노드의 제목과 요약)를 만듭니다.
2. 질문이 들어오면 LLM에게 트리(목차와 요약)를 보여 주고 "어느 섹션을 읽어야 하는가?"를 추론하게 합니다.
3. 선택된 섹션 내용을 읽고, 부족하면 다른 섹션으로 이동합니다.
4. 찾은 내용으로 답을 생성합니다.

**벡터 RAG의 한계를 보완하는 점**

- **유사도 ≠ 관련성:** 임베딩 유사도가 높다고 실제로 답에 필요한 부분은 아닐 수 있습니다. 추론 기반 탐색은 "어디에 답이 있을지"를 논리적으로 판단합니다.
- **청킹 문제 없음:** 문서를 임의로 자르지 않고 원래 구조 단위로 읽습니다.
- **설명 가능성:** 어떤 경로로 그 섹션을 찾았는지 추적할 수 있습니다.

**적합한 경우**

- 구조가 명확한 긴 전문 문서: 재무 보고서, 법률 문서, 규정집, 기술 매뉴얼
- 정확성이 매우 중요하고 문서 수가 많지 않은 경우

**한계**

- 질의마다 LLM 호출이 여러 번 필요해 느리고 비쌉니다.
- 수백만 개 문서 규모의 검색에는 맞지 않습니다.
- 구조가 없는 데이터(채팅 로그, 짧은 메모)에는 효과가 적습니다.

**참고:** 키워드 검색(BM25)·grep처럼 벡터 없이 하는 다른 검색 방식도 넓게는 이 범주에 넣어 이야기하기도 합니다. 코딩 에이전트가 grep으로 코드를 찾는 것도 비슷한 철학입니다.

**더 읽어보기 (영문):** [Vectorless RAG](https://outcomeschool.com/blog/vectorless-rag)

<summary><b>Q20. RAG 파이프라인에서 구조화된 데이터(테이블, SQL 데이터베이스)는 어떻게 처리하나요?</b></summary>

**왜 일반 RAG로는 어려운가**

- 표를 텍스트로 펼쳐 임베딩하면 행·열 관계가 깨지고, "3분기 매출 합계" 같은 **계산·집계 질문** 은 검색으로 답할 수 없습니다.

**방법 1: Text-to-SQL (DB가 있을 때)**

1. 질문 + 관련 테이블 스키마(컬럼 설명, 예시 값)를 LLM에 주고 SQL을 생성하게 합니다.
2. 생성된 SQL을 **읽기 전용 계정** 으로 실행합니다.
3. 결과를 LLM이 자연어 답으로 정리합니다.

- 테이블이 많으면 스키마도 RAG로 검색해 관련 테이블만 넣습니다.
- 안전장치: SELECT만 허용, 쿼리 검증, 행 수·실행 시간 제한, 행 수준 권한.
- 정확도 향상: 비즈니스 용어 사전, 예시 질문-SQL 쌍(퓨샷), 오류 시 재시도.

**방법 2: 문서 속 표 처리**

- 파싱 단계에서 표를 **마크다운이나 HTML 형식** 으로 구조를 유지해 추출합니다.
- 표 전체를 하나의 청크로 두고, LLM이 만든 **표 요약** 을 임베딩용으로 함께 저장합니다(요약으로 검색 → 원본 표를 LLM에 전달).
- 큰 표는 행 단위로 쪼개되 헤더를 각 청크에 반복합니다.

**방법 3: 코드 실행**

- 표를 DataFrame으로 불러와 LLM이 pandas 코드를 작성·실행해 계산하게 합니다.

**방법 4: 라우팅**

- 질문 유형을 분류해 "집계·수치 질문 → SQL", "설명·정책 질문 → 문서 RAG"로 보내고, 필요하면 두 결과를 합칩니다.

**평가:** 실행 정확도(SQL 결과가 정답과 같은가)를 별도 지표로 관리합니다.

<summary><b>Q21. RAG 시스템에서 흔히 발생하는 실패 유형은 무엇이며, 어떻게 디버깅하나요?</b></summary>

**실패 지점별 분류**

| 단계 | 실패 유형 | 예 |
|---|---|---|
| 데이터 | 문서가 없음, 오래됨, 파싱 깨짐 | 표·스캔 PDF가 엉망으로 추출 |
| 청킹 | 정보가 청크 경계에서 잘림 | 질문과 답이 다른 청크로 분리 |
| 검색 | 관련 문서를 못 찾음 | 용어 불일치, 짧은 질문, 임베딩 약점 |
| 순위 | 찾았지만 top-k 밖 | 리랭킹 없음 |
| 컨텍스트 | 너무 많거나 노이즈 | 중간 정보 누락, 상충 문서 |
| 생성 | 컨텍스트를 무시하거나 환각 | 사전 지식으로 답함 |
| 형식 | 인용·출처 누락, 형식 오류 | |
| 범위 | 답이 없는데 답함 | 거절 처리 없음 |

**디버깅 절차**

1. **트레이스 확인:** 실패한 질문의 전체 경로를 봅니다. 재작성된 질의, 검색된 청크와 점수, 리랭킹 결과, 최종 프롬프트, 응답.
2. **정답 위치 찾기:** 정답이 담긴 문서·청크를 직접 찾습니다.
   - 인덱스에 없다 → 데이터·파싱 문제
   - 있는데 검색 안 됨 → 청킹·임베딩·검색 문제
   - 검색됐는데 top-k 밖 → 순위 문제
   - 프롬프트에 있었는데 답이 틀림 → 생성 문제
3. **원인별 수정:** 위 단계에 맞는 해결책을 적용합니다(하이브리드 검색, 쿼리 재작성, 리랭커, 프롬프트 개선 등).
4. **평가셋 회귀 테스트:** 수정이 다른 질문을 망가뜨리지 않았는지 확인합니다.

**관측 도구:** LangSmith, Langfuse, Arize Phoenix 등으로 단계별 트레이스를 남기고, 검색 점수 분포와 "답 없음" 비율을 모니터링합니다.

<summary><b>Q22. RAG 시스템에서 문서 업데이트를 어떻게 처리하고 최신성을 유지하나요?</b></summary>

**과제:** 문서가 추가·수정·삭제되는데 인덱스가 따라가지 못하면, 오래된 정보로 답하거나 삭제된(권한이 회수된) 문서를 노출합니다.

**업데이트 파이프라인 설계**

1. **변경 감지**
   - 원본 시스템의 이벤트·웹훅(CDC), 수정 시각 비교, 콘텐츠 해시 비교로 바뀐 문서만 찾습니다.
2. **증분 인덱싱**
   - 문서마다 고유 ID를 두고, 청크에 `doc_id`, `version`, `chunk_index`를 저장합니다.
   - 문서가 바뀌면 해당 `doc_id`의 기존 청크를 모두 삭제하고 새로 청킹·임베딩해 넣습니다(upsert).
   - 청크 해시를 비교해 실제로 바뀐 청크만 다시 임베딩하면 비용을 줄일 수 있습니다.
3. **삭제 처리**
   - 원본에서 삭제된 문서와 권한이 바뀐 문서는 즉시 인덱스에서 제거·갱신합니다. 보안상 가장 중요합니다.
4. **주기와 우선순위**
   - 자주 바뀌는 데이터(가격, 재고)는 실시간 또는 짧은 주기, 정적 문서는 일 단위 배치.

**검색 시 최신성 반영**

- 메타데이터에 `updated_at`, `effective_date`를 저장하고, 최신 문서에 가중치를 주거나 기간 필터를 적용합니다.
- 같은 문서의 여러 버전이 있으면 최신 버전만 검색되게 합니다.
- 답변에 문서 날짜를 함께 표시해 사용자가 판단할 수 있게 합니다.

**운영**

- 인덱스 신선도(원본 대비 지연 시간), 인덱싱 실패 건수를 모니터링합니다.
- 임베딩 모델을 바꿀 때는 전체 재인덱싱이 필요하므로 새 인덱스를 따로 만들고 전환합니다(블루-그린).

<summary><b>Q23. 프로덕션에서 RAG의 지연 시간을 어떻게 최적화하나요?</b></summary>

**먼저 측정:** 단계별 지연을 쪼개 봅니다. 보통 **LLM 생성 > 리랭킹 > 쿼리 재작성 > 검색 > 임베딩** 순으로 큽니다.

**단계별 최적화**

1. **쿼리 처리**
   - 쿼리 재작성용 LLM 호출이 있다면 작은 모델을 쓰거나, 필요한 경우(대명사가 있는 후속 질문 등)에만 실행합니다.
   - 질문 임베딩은 작은 모델·로컬 실행·캐싱.
2. **검색**
   - ANN 인덱스(HNSW) 파라미터 조정, 메타데이터 필터를 인덱스 수준에서 적용합니다.
   - 벡터 검색과 BM25 검색을 **병렬로** 실행합니다.
3. **리랭킹**
   - 후보 수를 줄이고(100 → 30), 더 작은 리랭커 모델이나 GPU 추론을 씁니다.
4. **LLM 생성 (가장 큼)**
   - **스트리밍** 으로 첫 토큰을 빨리 보여 줍니다(체감 지연이 가장 크게 줄어듦).
   - 컨텍스트를 줄여 TTFT를 낮춥니다(상위 3~5개 청크만).
   - 출력 길이를 제한합니다.
   - 고정된 시스템 프롬프트에 **프롬프트 캐싱** 을 적용합니다.
   - 쉬운 질문은 더 작고 빠른 모델로 라우팅합니다.
5. **캐싱**
   - 자주 묻는 질문은 **시맨틱 캐시** 로 LLM 호출 자체를 건너뜁니다.
   - 검색 결과 캐시, 임베딩 캐시.
6. **아키텍처**
   - 독립적인 단계는 병렬화하고, 서비스 간 네트워크 왕복을 줄입니다(같은 리전 배치).

**목표 설정:** p50뿐 아니라 p95/p99 지연을 SLA로 두고, 품질 지표와 함께 트레이드오프를 관리합니다.

</details>

<summary><b>Q24. RAG 시스템에서 메타데이터 필터링은 어떤 역할을 하나요?</b></summary>

**메타데이터 필터링** 은 청크에 함께 저장한 속성(문서 종류, 날짜, 부서, 언어, 제품, 권한 등)으로 **검색 대상 범위를 제한** 하는 것입니다.

**역할**

1. **정확도 향상**
   - "2024년 정책"을 물으면 `year = 2024`로 거른 뒤 의미 검색을 하면, 비슷하지만 다른 연도의 문서가 섞이는 것을 막습니다.
   - 제품별, 지역별 문서처럼 내용은 비슷하고 대상만 다른 경우에 특히 중요합니다.
2. **접근 제어 (보안)**
   - 사용자의 권한 그룹을 필터로 걸어, 볼 수 없는 문서는 아예 검색되지 않게 합니다. 생성 후 필터링보다 안전합니다.
3. **멀티테넌시**
   - 고객사(tenant)별 데이터를 `tenant_id`로 분리합니다.
4. **최신성**
   - 날짜 범위 필터, 최신 버전만 검색.
5. **성능**
   - 검색 공간이 줄어 속도가 빨라질 수 있습니다.

**필터 값은 어디서 오나**

- 앱 맥락에서 자동으로: 로그인 사용자 권한, 현재 보고 있는 제품 페이지
- 질문에서 추출: LLM으로 "작년", "서울 지점" 같은 조건을 구조화된 필터로 변환(self-query retrieval)

**구현 주의점**

- **사전 필터링(pre-filter)** 과 **사후 필터링(post-filter)** 의 차이: 벡터 검색 후 필터링하면 top-k 안에 조건에 맞는 문서가 거의 없을 수 있습니다. 벡터 DB가 필터를 인덱스 검색 단계에서 지원하는지 확인합니다.
- 인덱싱할 때 메타데이터를 일관되게 채우는 것이 전제입니다.

**더 읽어보기 (영문):** [How does a Vector Database work?](https://outcomeschool.com/blog/how-does-a-vector-database-work)

<summary><b>Q25. RAG와 파인튜닝을 비교하세요. 각각은 언제 사용하나요?</b></summary>

| 기준 | RAG | 파인튜닝 |
|---|---|---|
| 주된 목적 | **지식** 제공 (무엇을 아는가) | **행동** 변경 (어떻게 답하는가) |
| 지식 갱신 | 문서만 바꾸면 즉시 반영 | 재학습 필요 |
| 출처 제시 | 가능 | 불가능 |
| 환각 | 근거 문서로 줄일 수 있음 | 새 지식은 오히려 환각 유발 가능 |
| 형식·말투·작업 특화 | 프롬프트 수준에서만 | 강하게 고정 가능 |
| 초기 비용 | 낮음~중간 (인프라 구축) | 데이터 준비·학습 비용 |
| 추론 비용·지연 | 검색 + 긴 프롬프트 | 짧은 프롬프트, 작은 모델로 대체 가능 |
| 접근 제어 | 문서 단위로 가능 | 학습된 지식은 통제 불가 |

**RAG를 쓸 때**

- 자주 바뀌는 정보, 사내 문서, 근거 제시가 필요한 답변, 사용자별 권한이 다른 데이터.

**파인튜닝을 쓸 때**

- 특정 출력 형식·어조를 매우 일관되게 지켜야 할 때
- 분류·추출 같은 좁은 작업을 작은 모델로 싸고 빠르게 처리하고 싶을 때
- 도메인 특유의 언어 패턴(전문 용어 사용법)을 익히게 할 때
- 긴 프롬프트(많은 지시·예시)를 모델에 내재화해 비용을 줄이고 싶을 때

**함께 쓰기**

- 둘은 경쟁 관계가 아닙니다. 예: RAG로 지식을 제공하고, 모델은 "주어진 문서로 인용하며 답하기"를 잘하도록 파인튜닝(RAFT 같은 방식).

**결정 순서:** 프롬프트 엔지니어링 → RAG → 파인튜닝 순으로 검토하고, 각 단계에서 평가로 효과를 확인합니다.

**더 읽어보기 (영문):** [AI Engineering Explained: LLM, RAG, MCP, Agent, Fine-Tuning, Quantization](https://www.youtube.com/watch?v=lnfWvX66FUk) (영상)

<summary><b>Q26. 긴 컨텍스트 윈도우가 점점 저렴해지고 있습니다. 언제 검색(RAG)을 쓰고, 언제 모든 내용을 컨텍스트 윈도우에 넣어야 하나요?</b></summary>

**모두 넣기(long context)가 나은 경우**

- **전체 데이터가 윈도우에 여유 있게 들어감:** 예를 들어 수십~수백 페이지 정도의 고정된 문서 세트.
- **전체를 이해해야 하는 작업:** 문서 전체 요약, 여러 부분 비교, 전체 일관성 검토, 코드베이스 전반 리팩터링.
- **검색이 어려운 질문:** 무엇이 관련 있는지 미리 알기 어려운 질문.
- **같은 문서로 반복 질의:** 프롬프트 캐싱을 쓰면 두 번째 질의부터 비용과 지연이 크게 줄어듭니다.
- **빠른 프로토타이핑:** 검색 파이프라인 없이 바로 시작할 수 있습니다.

**RAG가 나은 경우**

- **데이터가 윈도우보다 훨씬 큼:** 수만~수백만 문서.
- **비용·지연이 중요한 대량 트래픽:** 질문마다 수십만 토큰을 넣으면 캐싱을 해도 비싸고 TTFT가 깁니다.
- **자주 바뀌는 데이터:** 문서가 바뀌면 캐시가 무효화됩니다.
- **접근 제어:** 사용자마다 볼 수 있는 문서가 다를 때.
- **정밀도:** 긴 컨텍스트에서는 중간 정보 누락(lost in the middle)과 관련 없는 내용에 의한 혼란이 생길 수 있습니다.
- **출처 제시** 가 중요할 때.

**하이브리드 접근 (실무에서 흔함)**

- RAG로 관련 **문서 단위** 를 넉넉히(작은 청크가 아니라 문서 통째로) 찾아 긴 컨텍스트에 넣습니다. 검색의 확장성과 긴 컨텍스트의 이해력을 함께 얻습니다.

**결정 방법:** 데이터 크기, 질의량, 업데이트 빈도, 정확도 요구사항으로 비용을 계산하고, 평가셋에서 두 방식의 정확도를 직접 비교합니다.

**더 읽어보기 (영문):** [The Lost in the Middle Problem in LLMs](https://outcomeschool.com/blog/lost-in-the-middle-problem-in-llms)

<summary><b>Q27. RAG의 쿼리 변환(HyDE, 쿼리 분해, step-back 프롬프팅)이란 무엇인가요?</b></summary>

**쿼리 변환** 은 사용자의 원래 질문을 그대로 검색하지 않고, **검색이 더 잘 되는 형태로 바꾸는** 기법들입니다. 사용자 질문은 짧고 모호하거나, 문서와 표현 방식이 다르기 때문입니다.

**1. 쿼리 재작성 (Query Rewriting)**

- 대화 맥락을 반영해 독립 질문으로 바꾸거나, 오타·구어체를 정리합니다.
- "그거 환불돼?" → "프리미엄 요금제 중도 해지 시 환불 정책"

**2. 멀티 쿼리 (Multi-Query)**

- 같은 질문을 여러 표현으로 생성해 각각 검색하고 결과를 합칩니다(RRF). 한 표현이 놓친 문서를 다른 표현이 잡습니다.

**3. HyDE (Hypothetical Document Embeddings)**

- LLM이 질문에 대한 **가상의 답변 문서** 를 먼저 작성하고, 그 가상 문서의 임베딩으로 검색합니다.
- 질문(짧은 의문문)보다 답변 형태의 글이 실제 문서와 임베딩 공간에서 더 가깝다는 아이디어입니다.
- 가상 답이 틀려도 "답이 어떤 모양일지"만 맞으면 검색에 도움이 됩니다. 단, LLM 호출이 추가되고, 모델이 전혀 모르는 분야에서는 엉뚱한 방향으로 갈 수 있습니다.

**4. 쿼리 분해 (Query Decomposition)**

- 복잡한 질문을 하위 질문으로 나눠 각각 검색합니다. 멀티홉·비교 질문에 효과적입니다.
- "A사와 B사의 2024년 매출 성장률 비교" → "A사 2024 매출", "B사 2024 매출", ...

**5. Step-back 프롬프팅**

- 구체적인 질문에서 한 단계 **더 일반적인 질문** 을 만들어 배경 지식도 함께 검색합니다.
- "1995년 X 선수가 뛴 팀은?" → "X 선수의 경력 이력" 검색 → 그 정보로 원래 질문에 답

**선택 가이드:** 대화형이면 재작성은 거의 필수, 용어 불일치가 많으면 멀티 쿼리·HyDE, 복잡한 질문이면 분해. 모두 지연을 늘리므로 평가로 효과를 확인하고 필요한 경우에만 적용합니다.

**더 읽어보기 (영문):** [How does HyDE work in RAG?](https://outcomeschool.com/blog/how-does-hyde-work), [How do Query Rewriting and Multi-Query Retrieval work?](https://outcomeschool.com/blog/how-do-query-rewriting-and-multi-query-retrieval-work)

<summary><b>Q28. RAG에서 인용(citation)과 출처 표시를 어떻게 구현하나요?</b></summary>

**1. 컨텍스트에 식별자 부여**

```
<doc id="1" title="환불 정책" url="...">...</doc>
<doc id="2" title="요금제 안내" url="...">...</doc>
```

**2. 인용 형식 지시**

- "각 문장 끝에 근거 문서 번호를 [1], [2] 형식으로 표시하라. 문서에 없는 내용은 쓰지 마라."
- 더 정밀하게 하려면 문서의 **원문 문장(quote)** 을 함께 인용하게 합니다.

**3. 구조화된 출력으로 받기**

```json
{"answer": "...", "citations": [{"doc_id": 1, "quote": "구매 후 7일 이내..."}]}
```

- 일부 API는 문서를 넣으면 인용 위치를 자동으로 반환하는 기능(citations)을 제공합니다.

**4. 인용 검증 (중요)**

- 모델이 인용한 `doc_id`가 실제로 제공된 문서인지 확인합니다.
- 인용 문장(quote)이 해당 문서에 **실제로 존재하는지** 문자열 매칭으로 확인합니다.
- 주장과 인용 문장이 의미상 일치하는지 NLI 모델이나 LLM 판정자로 확인합니다.
- 검증에 실패한 문장은 제거하거나 "출처 확인 불가"로 표시합니다.

**5. UI 표시**

- 각 인용 번호에 문서 제목, 링크, 해당 구간 하이라이트를 연결합니다.
- 문서의 날짜와 버전도 보여 줍니다.

**메타데이터 관리:** 청크에 원본 문서 ID, 페이지 번호, 섹션, URL을 저장해 두어야 정확한 위치로 연결할 수 있습니다.

**평가:** 인용 정밀도(인용이 주장을 뒷받침하는 비율)와 인용 재현율(주장 중 인용이 있는 비율)을 측정합니다.

<summary><b>Q29. RAG 시스템을 수백만 건의 문서로 확장하려면 어떻게 하나요?</b></summary>

**1. 인덱싱 파이프라인 확장**

- 문서 로딩·파싱·청킹·임베딩을 **분산 배치 작업** 으로 처리합니다(작업 큐, Spark/Ray 등).
- 임베딩은 GPU 배치 처리, 자체 호스팅 모델로 비용을 낮춥니다.
- 증분 인덱싱으로 바뀐 문서만 처리합니다.

**2. 벡터 검색 확장**

- **ANN 인덱스** 를 사용합니다. 정확한 전수 비교(flat)는 수백만 건에서 너무 느립니다.
  - **HNSW:** 빠르고 재현율이 높지만 메모리를 많이 씀
  - **IVF(+PQ):** 클러스터로 나눠 일부만 검색, 양자화로 메모리 절약
  - **DiskANN 계열:** SSD에 인덱스를 두고 대규모 처리
- **샤딩:** 데이터를 여러 노드에 나누고 결과를 합칩니다. 테넌트별·카테고리별 파티셔닝도 효과적입니다.
- **벡터 압축:** 차원 축소(Matryoshka), 스칼라/곱 양자화, 이진 양자화로 메모리를 크게 줄이고, 상위 후보만 원본 벡터로 재채점합니다.

**3. 검색 품질 유지**

- 문서가 많을수록 "비슷하지만 틀린" 문서가 늘어 정밀도가 떨어집니다.
  - 메타데이터 필터로 검색 범위 축소
  - 하이브리드 검색 + 리랭커
  - 계층적 검색: 문서 요약으로 먼저 문서를 고르고, 그 안에서 청크 검색

**4. 운영**

- 검색 지연(p99), 인덱스 크기, 재현율을 모니터링합니다.
- 관리형 벡터 DB(Pinecone, Weaviate Cloud 등)나 확장성 있는 오픈소스(Milvus, Qdrant, Vespa, OpenSearch)를 데이터 규모와 운영 역량에 맞춰 선택합니다.

<summary><b>Q30. 부모-자식(parent-child) 청킹이란 무엇이며, 검색을 어떻게 개선하나요?</b></summary>

**문제:** 청크 크기에는 딜레마가 있습니다.

- **작은 청크:** 주제가 하나라 임베딩이 정확해 **검색은 잘 되지만**, LLM에 넘기면 앞뒤 맥락이 부족합니다.
- **큰 청크:** 맥락은 풍부하지만 여러 주제가 섞여 **검색 정확도가 떨어집니다.**

**부모-자식 청킹의 해결책: 검색 단위와 전달 단위를 분리**

1. 문서를 큰 **부모 청크**(예: 섹션, 1,500~2,000 토큰)로 나눕니다.
2. 각 부모를 작은 **자식 청크**(예: 200~400 토큰)로 다시 나눕니다.
3. **자식 청크만 임베딩** 해 인덱싱하고, 각 자식에 부모 ID를 저장합니다.
4. 검색 시 자식 청크로 정확하게 찾은 뒤, **LLM에는 해당 부모 청크를 전달** 합니다.
5. 같은 부모의 자식이 여러 개 검색되면 부모는 한 번만 넣습니다(중복 제거).

```
섹션(부모) ─┬─ 자식1  ← 검색 적중
            ├─ 자식2
            └─ 자식3
→ LLM에는 섹션 전체를 전달
```

**비슷한 변형**

- **문장 윈도우 검색:** 문장 단위로 검색하고 앞뒤 N문장을 붙여 전달
- **요약-원문 분리:** 요약으로 검색하고 원문 전달
- **자동 병합(auto-merging):** 한 부모의 자식이 여러 개 검색되면 부모로 합쳐서 전달

**트레이드오프:** 프롬프트 토큰이 늘어나므로, 부모 크기와 넣는 개수를 컨텍스트 예산에 맞춰 조정합니다.

**더 읽어보기 (영문):** [Chunking Strategies for RAG](https://outcomeschool.com/blog/chunking-strategies-for-rag)

<summary><b>Q31. RAG 시스템이 올바른 컨텍스트가 있는데도 환각을 일으킵니다. 어떻게 고치나요?</b></summary>

검색은 성공했는데 생성 단계에서 틀리는 경우입니다(컨텍스트 재현율은 높고 충실도는 낮음).

**원인**

- 모델이 컨텍스트보다 **자기 사전 지식** 을 우선함 (특히 사전 지식과 문서 내용이 다를 때)
- 컨텍스트가 너무 길거나 노이즈가 많아 핵심을 놓침
- 지시가 "문서에 근거해 답하라"를 명확히 요구하지 않음
- 질문이 문서에 부분적으로만 답이 있어, 나머지를 지어냄
- 작은 모델의 낮은 지시 따르기 능력

**해결책**

1. **근거 제약 강화**
   - "제공된 문서에 있는 정보만 사용하라. 문서와 당신의 지식이 다르면 문서를 따르라. 문서에 없으면 없다고 하라."
2. **인용 강제**
   - 각 문장에 출처를 달게 하고, 답하기 전에 관련 문장을 먼저 인용하게 합니다(quote-then-answer).
3. **컨텍스트 정리**
   - 리랭킹으로 관련 청크만 소수로 넣고, 중요한 문서를 앞/뒤에 배치합니다.
4. **생성 설정**
   - 온도를 낮춥니다.
5. **사후 검증**
   - 답을 주장 단위로 나눠 각 주장이 컨텍스트에 의해 뒷받침되는지 NLI·LLM 판정자로 검사하고, 근거 없는 주장은 제거하거나 재생성합니다.
6. **모델 개선**
   - 근거 충실성이 좋은 모델로 교체하거나, "문서 기반 답변" 데이터로 파인튜닝합니다(방해 문서가 섞인 상태에서 정답 문서만 인용하는 학습).

**측정:** 충실도(faithfulness) 지표를 평가셋에서 추적하고, 프로덕션에서도 샘플을 자동 검증합니다.

<summary><b>Q32. RAG 청크의 중첩(overlap) 때문에 결과가 중복됩니다. 중복을 어떻게 줄이나요?</b></summary>

**원인:** 청크 경계에서 정보가 잘리지 않도록 겹침을 두면, 같은 문장이 인접한 두 청크에 모두 들어갑니다. 두 청크가 함께 검색되면 같은 내용이 프롬프트에 두 번 들어가 토큰을 낭비하고, 다른 유용한 문서가 들어갈 자리를 차지합니다.

**해결책**

1. **겹침 크기 줄이기**
   - 겹침을 10% 이내로 줄이거나, 문장·문단 경계 기반 청킹(재귀 청킹)으로 바꿔 겹침 없이도 의미가 잘리지 않게 합니다.
2. **인접 청크 병합**
   - 같은 문서의 연속된 청크(`chunk_index`가 이웃)가 함께 검색되면, 겹치는 부분을 제거하고 하나의 구간으로 합쳐 전달합니다.
3. **부모 청크로 치환**
   - 부모-자식 구조라면 같은 부모의 자식들이 검색될 때 부모 하나만 넣습니다.
4. **MMR (Maximal Marginal Relevance)**
   - 결과를 고를 때 **질문과의 관련성** 과 **이미 고른 결과와의 차이** 를 함께 고려합니다. 이미 뽑힌 청크와 너무 비슷한 청크는 순위를 낮춥니다.
   ```
   MMR = λ·sim(질문, d) − (1−λ)·max sim(d, 이미 선택된 문서)
   ```
5. **텍스트 수준 중복 제거**
   - 프롬프트 조립 전에 문장 단위 해시나 n-gram 겹침 비율로 중복 문장을 제거합니다.

**검증:** 프롬프트에 들어간 컨텍스트의 중복 토큰 비율과, 중복 제거 후 답변 품질 변화를 함께 확인합니다.

<summary><b>Q33. 지식 베이스가 커서 RAG 검색이 너무 느립니다. 어떻게 빠르게 만드나요?</b></summary>

**1. 병목 확인**

- 질문 임베딩 시간, 벡터 검색 시간, 필터링, 리랭킹, 네트워크를 각각 측정합니다.

**2. 벡터 검색 가속**

- **정확 검색 → ANN:** flat 인덱스(전수 비교)를 쓰고 있다면 HNSW, IVF로 바꿉니다.
- **인덱스 파라미터 조정:** HNSW의 `ef_search`, IVF의 `nprobe`를 줄이면 빨라지고 재현율은 약간 떨어집니다. 평가셋으로 균형점을 찾습니다.
- **벡터 압축:** 양자화(스칼라, PQ, 이진)로 메모리와 계산량을 줄이고, 상위 후보만 원본 벡터로 재채점합니다.
- **차원 축소:** Matryoshka 임베딩을 지원하는 모델이면 낮은 차원을 사용합니다.
- **메모리 상주:** 인덱스가 디스크에서 읽히고 있다면 RAM에 올리거나 노드를 늘립니다.

**3. 검색 범위 축소**

- 메타데이터 필터, 파티셔닝(테넌트·카테고리별 인덱스)으로 검색 대상을 줄입니다.
- 계층적 검색: 문서 수준 인덱스로 후보 문서를 먼저 고르고 그 안에서만 청크 검색.

**4. 수평 확장**

- 샤딩과 레플리카로 처리량을 늘립니다.

**5. 그 외 단계**

- 임베딩·리랭커 모델을 더 작게, GPU에서, 배치로 실행합니다.
- 리랭킹 후보 수를 줄입니다.
- 자주 나오는 질의는 캐싱합니다.

**목표:** 재현율 하락 없이(예: recall@20 유지) 지연을 줄였는지 함께 확인해야 합니다.

<summary><b>Q34. RAG 시스템이 중복된 결과를 반환합니다. 중복을 어떻게 제거하나요?</b></summary>

청크 겹침 외에도, 지식 베이스 자체에 **같은 내용의 문서가 여러 개** 있는 경우(같은 문서의 여러 버전, 복사본, 다른 형식으로 저장된 같은 자료)가 흔합니다.

**인덱싱 단계 (근본적 해결)**

1. **정확한 중복 제거:** 정규화한 텍스트의 해시(SHA-256)가 같으면 하나만 인덱싱합니다.
2. **근사 중복 제거:** MinHash/LSH, SimHash로 거의 같은 문서(서식만 다름, 몇 단어 수정)를 찾아 대표 하나만 남기거나 그룹으로 묶습니다.
3. **버전 관리:** 같은 문서의 여러 버전은 최신 버전만 검색 대상으로 둡니다(`is_latest` 메타데이터).
4. **원본 정리:** 데이터 소스 쪽의 중복 복사본을 정리하는 것이 장기적으로 가장 좋습니다.

**검색 단계**

1. **결과 수준 중복 제거:** 검색 결과의 임베딩 유사도가 매우 높은(예: 0.95 이상) 청크는 하나만 남깁니다.
2. **문서 단위 그룹화:** 같은 `doc_id`에서 여러 청크가 나오면 묶거나 개수를 제한합니다.
3. **MMR로 다양성 확보:** 관련성과 함께 결과 간 다양성을 고려해 비슷한 결과가 상위를 독차지하지 않게 합니다.

**왜 중요한가**

- 중복 결과는 토큰을 낭비하고, 다른 유용한 정보가 들어갈 자리를 빼앗습니다.
- 버전이 다른 중복은 **서로 다른(오래된) 정보** 를 섞어 모순된 답을 만들 수 있습니다.

**측정:** 상위 k개 결과 중 고유 문서 비율을 지표로 모니터링합니다.

</details>

<summary><b>Q35. RAG 시스템에서 내부 문서에 사용자별 접근 제어가 필요합니다. 어떻게 구현하나요?</b></summary>

**핵심 원칙:** 사용자가 볼 권한이 없는 문서는 **검색 단계에서 아예 나오지 않아야** 합니다. LLM에게 "권한 없는 내용은 말하지 마라"고 지시하는 것은 보안이 아닙니다.

**구현 방법**

1. **인덱싱 시 권한 메타데이터 저장**
   - 각 청크에 원본 문서의 ACL을 저장합니다: `allowed_groups`, `allowed_users`, `department`, `classification`.
2. **질의 시 사전 필터링**
   - 인증된 사용자의 신원·그룹을 서버에서 가져와(클라이언트가 보낸 값을 믿지 않음) 벡터 검색의 **필터 조건** 으로 강제 적용합니다.
   ```python
   results = vector_db.search(query_vec, top_k=20,
       filter={"allowed_groups": {"$in": user.groups}})
   ```
3. **권한 동기화**
   - 원본 시스템(SharePoint, Google Drive, Confluence 등)의 권한 변경을 빠르게 반영하는 동기화 작업을 둡니다. 퇴사자·권한 회수가 늦게 반영되면 유출 사고가 됩니다.
4. **실시간 재확인 (높은 보안 요구 시)**
   - 검색 결과를 LLM에 넘기기 전에 원본 시스템 API로 현재 권한을 한 번 더 확인합니다.
5. **인덱스 분리**
   - 보안 등급이 크게 다르거나 고객사(테넌트)별 데이터라면 인덱스나 네임스페이스를 물리적으로 분리합니다.

**추가로 막아야 할 경로**

- 시맨틱 캐시: 다른 사용자의 답이 캐시에서 재사용되지 않도록 캐시 키에 권한 범위를 포함합니다.
- 대화 기록, 요약 메모리, 로그에도 같은 권한 원칙을 적용합니다.
- 프롬프트 인젝션으로 필터를 우회할 수 없도록 필터는 반드시 코드에서 적용합니다.

**테스트:** 권한이 다른 테스트 계정으로 같은 질문을 던져 결과가 정확히 분리되는지 자동화 테스트를 둡니다.

</details>

<summary><b>Q36. RAG 시스템이 도메인 특화 전문 용어에서 실패합니다. 어떻게 고치나요?</b></summary>

**원인**

- 범용 임베딩 모델이 전문 용어(의학 약어, 사내 제품 코드, 법률 용어)의 의미를 잘 모릅니다.
- 같은 개념을 여러 표현으로 부릅니다(약어 vs 정식 명칭, 영문 vs 국문).
- 토크나이저가 용어를 잘게 쪼개 임베딩이 흐려집니다.

**해결책 (적용 쉬운 순)**

1. **하이브리드 검색**
   - BM25 키워드 검색을 함께 쓰면 정확한 용어 매칭이 보장됩니다. 전문 용어 문제에 가장 빠르고 효과적인 해결책입니다.
2. **동의어·약어 사전**
   - 도메인 용어집을 만들어 쿼리 확장에 씁니다. "MI" → "심근경색(myocardial infarction)".
   - 인덱싱 시 청크에도 정식 명칭을 보강할 수 있습니다.
3. **LLM 쿼리 재작성**
   - 용어집을 프롬프트에 넣고 질문을 검색에 유리한 형태로 바꾸게 합니다.
4. **리랭커 도입**
   - 크로스 인코더가 용어의 문맥을 더 잘 판단합니다.
5. **도메인 특화 임베딩 모델**
   - 해당 분야 데이터로 학습된 모델(의료, 법률, 코드 등)을 평가해 봅니다.
6. **임베딩 모델 파인튜닝**
   - (질문, 관련 문서) 쌍을 수천 개 만들어 대조 학습합니다. 라벨 데이터가 없으면 LLM으로 문서에서 질문을 생성해 학습 데이터를 만듭니다.
7. **생성 단계 보완**
   - 용어 정의를 프롬프트에 함께 넣어 LLM이 용어를 올바르게 해석하게 합니다.

**평가:** 전문 용어가 포함된 질문만 모은 평가셋을 따로 만들어 개선 효과를 측정합니다.

<summary><b>Q37. 텍스트 전용 RAG 시스템이 이제 이미지와 표도 처리해야 합니다. 어떻게 확장하나요?</b></summary>

**방법 1: 모든 것을 텍스트로 변환 (가장 쉬움)**

- **표:** 마크다운·HTML 구조를 유지해 추출하고, LLM으로 표 요약을 만들어 함께 저장합니다.
- **이미지·차트·도면:** 비전 언어 모델(VLM)로 상세 캡션과 설명(차트 수치, 도면 내용)을 생성해 텍스트로 인덱싱합니다.
- **스캔 문서:** OCR 또는 VLM 기반 문서 파서.
- 장점: 기존 텍스트 RAG 파이프라인을 그대로 씁니다.
- 단점: 변환 과정에서 정보가 손실될 수 있습니다.

**방법 2: 멀티모달 임베딩**

- CLIP 같은 텍스트-이미지 공용 임베딩 모델로 이미지를 직접 임베딩해 텍스트 질문으로 검색합니다.
- 문서 페이지를 이미지 그대로 임베딩하는 방식(ColPali 같은 접근)은 파싱 없이 레이아웃·표·그림을 함께 검색할 수 있습니다.

**방법 3: 요약으로 검색, 원본으로 답변**

- 표·이미지의 텍스트 요약으로 검색하고, 생성 단계에서는 **원본 이미지나 표** 를 멀티모달 LLM에 직접 넣어 정확하게 해석하게 합니다.

**설계 고려 사항**

- 청크에 `type`(text/table/image), 원본 위치(페이지, 그림 번호)를 메타데이터로 저장합니다.
- 표 질문 중 계산이 필요한 것은 표를 DataFrame으로 변환해 코드로 처리하는 경로를 둡니다.
- 멀티모달 LLM 호출은 비용·지연이 크므로, 이미지가 필요한 질문일 때만 원본 이미지를 넣습니다.

**평가:** 표·차트·이미지 기반 질문을 평가셋에 별도 카테고리로 추가해 측정합니다.

<summary><b>Q38. RAG 지식 베이스가 자주 업데이트되어 버전 관리가 필요합니다. 어떻게 관리하나요?</b></summary>

**요구사항 정리**

- 현재 유효한 버전으로 답해야 함
- 특정 시점 기준 답이 필요할 수 있음 ("작년 3월 기준 정책은?")
- 문제가 생기면 이전 인덱스 상태로 되돌릴 수 있어야 함
- 어떤 답이 어떤 문서 버전에서 나왔는지 추적해야 함(감사)

**문서 수준 버전 관리**

- 청크 메타데이터: `doc_id`, `version`, `valid_from`, `valid_to`, `is_latest`, `content_hash`
- 기본 검색은 `is_latest = true`(또는 현재 날짜가 유효 기간 안)로 필터링합니다.
- 시점 질의는 해당 날짜에 유효했던 버전으로 필터링합니다.
- 이전 버전은 삭제하지 않고 비활성화해 이력을 보존합니다(보존 정책에 따라 정리).

**인덱스 수준 버전 관리**

- 임베딩 모델이나 청킹 방식을 바꾸는 대규모 변경은 **새 인덱스를 별도로 구축** 하고, 평가 후 별칭(alias)을 전환합니다(블루-그린 배포). 문제가 생기면 별칭을 되돌립니다.
- 인덱스에 사용된 임베딩 모델, 청킹 설정, 파이프라인 버전을 기록합니다.

**추적성**

- 응답 로그에 사용된 청크 ID와 문서 버전을 저장해, 나중에 "왜 이런 답이 나왔는지" 재현할 수 있게 합니다.

**업데이트 파이프라인**

- 변경 감지 → 새 버전 청킹·임베딩 → 이전 버전 `is_latest=false` → 새 버전 활성화를 하나의 트랜잭션처럼 처리해, 중간 상태(두 버전 모두 활성)가 검색되지 않게 합니다.

<summary><b>Q39. RAG 시스템이 여러 사실을 결합해야 하는 멀티홉 질문에서 실패합니다. 어떻게 고치나요?</b></summary>

**왜 실패하나**

- 단일 검색은 질문과 **직접 비슷한** 문서만 찾습니다. 두 번째 사실을 찾으려면 첫 번째 사실(중간 엔티티)을 알아야 하는데, 그 정보가 질문에 없습니다.
- 예: "우리 회사 CTO가 졸업한 대학의 소재지는?" → CTO 이름을 먼저 알아야 학력 문서를 찾을 수 있습니다.

**해결책**

1. **질문 분해 + 순차 검색**
   - LLM이 질문을 하위 질문으로 나누고, 앞 질문의 답을 다음 검색 질의에 넣습니다.
2. **반복 검색과 추론 교차 (IRCoT 방식)**
   - 추론 한 단계마다 새로 알게 된 정보로 검색하고, 결과를 보고 다음 단계를 추론합니다.
3. **에이전틱 RAG**
   - 에이전트가 검색 도구를 필요한 만큼 반복 호출하고, 정보가 충분한지 스스로 판단하게 합니다. 최대 반복 횟수를 둡니다.
4. **지식 그래프 / GraphRAG**
   - 엔티티와 관계를 미리 그래프로 만들어 두면 "CTO → 졸업 대학 → 소재지"를 그래프 탐색으로 바로 따라갈 수 있습니다. 관계 질문이 많은 도메인에서 효과적입니다.
5. **문서 보강**
   - 인덱싱 시 엔티티 정보를 청크에 연결해 두거나(엔티티 링크), 자주 묻는 조합 정보를 요약 문서로 미리 만들어 둡니다.
6. **검색 범위 확대 + 강한 리랭커**
   - top-k를 늘리고 리랭커로 정밀하게 고르면 일부 2홉 질문은 단일 검색으로도 해결됩니다.

**평가:** 멀티홉 질문셋에서 단계별 검색 성공률과 최종 정확도를 함께 측정해, 어느 홉에서 실패하는지 파악합니다.

**더 읽어보기 (영문):** [Agentic RAG](https://outcomeschool.com/blog/agentic-rag), [GraphRAG](https://outcomeschool.com/blog/graphrag)

</details>

<summary><b>Q40. 기업용 RAG 시스템이 서로 다른 출처 문서에서 모순된 답을 반환합니다. 충돌을 어떻게 해결하나요?</b></summary>

**충돌의 유형**

- **시간 차이:** 옛 정책과 새 정책 (가장 흔함)
- **범위 차이:** 지역·부서·제품별로 규정이 다름
- **권위 차이:** 공식 정책 문서 vs 개인 메모·슬랙 대화
- **실제 오류:** 둘 중 하나가 틀림

**해결 전략**

1. **메타데이터 기반 우선순위**
   - 각 문서에 `updated_at`, `source_type`(공식 정책/위키/채팅), `authority`(작성 부서), `scope`(적용 지역·대상)를 저장합니다.
   - 검색·리랭킹 시 최신 문서와 공식 출처에 가중치를 줍니다.
   - 사용자의 맥락(지역, 부서)에 맞는 범위의 문서를 필터링합니다.
2. **생성 단계 지시**
   - 각 문서의 날짜·출처를 컨텍스트에 함께 넣고 규칙을 줍니다: "문서 간 내용이 다르면 가장 최신의 공식 문서를 우선하라. 충돌이 있음을 답에 명시하고 각 출처를 인용하라."
3. **충돌을 숨기지 않기**
   - 확실히 해결할 수 없으면 "A 문서(2024.03)에는 X, B 문서(2023.11)에는 Y로 되어 있습니다. 최신 문서 기준으로는 X입니다"처럼 투명하게 보여 줍니다.
4. **데이터 거버넌스 (근본 해결)**
   - 오래된 문서를 보관 처리하거나 "대체됨(superseded)" 표시를 합니다.
   - 시스템이 감지한 충돌을 문서 담당자에게 알려 원본을 정리하게 합니다.
   - 핵심 정보(가격, 정책)는 단일 정답 소스(source of truth)를 정해 그 소스만 인덱싱합니다.

**모니터링:** 충돌이 감지된 질의를 로그로 모아 자주 충돌하는 문서 쌍을 정리 대상으로 삼습니다.

<summary><b>Q41. 계속 변하는 지식 베이스에서 RAG 시스템이 오래된 답을 반환합니다. 어떻게 최신 상태로 유지하나요?</b></summary>

**원인 점검**

1. 인덱스가 원본보다 늦게 갱신됨 (동기화 지연, 실패한 인덱싱 작업)
2. 수정된 문서의 **이전 청크가 삭제되지 않고** 남아 있음
3. 오래된 문서와 새 문서가 모두 검색되고, 오래된 쪽이 더 높은 순위
4. **캐시**(시맨틱 캐시, 응답 캐시)가 오래된 답을 재사용함
5. 컨텍스트에 날짜 정보가 없어 LLM이 어느 것이 최신인지 모름

**해결책**

1. **동기화 파이프라인 개선**
   - 이벤트 기반(웹훅, CDC)으로 변경 즉시 재인덱싱하고, 정기 전체 비교로 누락분을 잡습니다.
   - 인덱싱 실패를 알림으로 받습니다.
2. **문서 단위 교체**
   - 문서가 바뀌면 해당 `doc_id`의 모든 청크를 지우고 새로 넣는 upsert 로직을 확실히 합니다.
3. **최신성 반영 검색**
   - 버전 관리로 최신 버전만 검색하거나, 날짜 가중치(recency boost)를 줍니다.
4. **캐시 무효화**
   - 캐시 항목에 근거 문서 ID와 버전을 저장하고, 문서가 바뀌면 관련 캐시를 지웁니다. TTL도 설정합니다.
5. **날짜를 컨텍스트에 포함**
   - 각 청크에 문서 날짜를 함께 넣고, "가장 최신 정보를 우선하라"고 지시합니다. 현재 날짜도 프롬프트에 넣습니다.
6. **실시간 데이터는 도구로**
   - 가격, 재고, 상태처럼 매우 자주 바뀌는 정보는 인덱싱하지 말고 **API를 호출하는 도구** 로 실시간 조회합니다.

**모니터링:** 원본 변경 시각과 인덱스 반영 시각의 차이(신선도 지연)를 지표로 추적하고, 최근 변경된 문서에 대한 질문을 테스트로 주기적으로 실행합니다.

</details>

<summary><b>Q42. RAG 시스템이 표와 레이아웃이 포함된 PDF 문서를 제대로 다루지 못합니다. PDF 파싱을 어떻게 고치나요?</b></summary>

**왜 PDF가 어려운가**

- PDF는 "문서 구조"가 아니라 "페이지 위 글자의 위치"를 저장한 형식입니다.
- 단순 텍스트 추출 시 다단 레이아웃의 읽는 순서가 뒤섞이고, 표의 행·열이 한 줄로 뭉개지며, 머리말·꼬리말·페이지 번호가 본문에 끼어듭니다.
- 스캔 PDF는 텍스트 레이어가 아예 없습니다.

**개선 방법**

1. **레이아웃 인식 파서 사용**
   - 페이지 레이아웃을 분석해 제목, 문단, 표, 그림, 목록을 구분하는 도구를 씁니다. 예: Docling, Unstructured, Marker, LlamaParse, 클라우드 문서 AI 서비스(Azure Document Intelligence, AWS Textract, Google Document AI).
2. **표 전용 처리**
   - 표 감지·구조 인식 모델로 셀 구조를 복원하고 **마크다운·HTML 표** 로 저장합니다.
   - 표를 하나의 청크로 유지하고 요약을 함께 저장합니다.
3. **OCR**
   - 스캔 문서에는 OCR(Tesseract, PaddleOCR 등)이나 문서 AI 서비스를 사용합니다.
4. **VLM 기반 파싱**
   - 페이지를 이미지로 렌더링해 비전 언어 모델이 마크다운으로 변환하게 합니다. 복잡한 레이아웃에 강하지만 비용이 크고, 숫자를 잘못 읽는 경우가 있어 검증이 필요합니다.
