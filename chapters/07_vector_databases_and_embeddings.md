<summary><b>Q1. AI 엔지니어링에서 임베딩이란 무엇인가요?</b></summary>

**임베딩** 은 텍스트, 이미지, 오디오, 사용자, 상품 같은 대상을 **의미를 담은 고정 길이의 숫자 벡터** 로 표현한 것입니다. 의미가 비슷한 대상끼리는 벡터 공간에서 가까이 놓입니다.

**AI 엔지니어링에서의 쓰임**

- **의미 검색 / RAG:** 질문과 문서를 임베딩해 의미가 가까운 문서를 찾습니다.
- **추천:** 사용자와 상품을 같은 공간에 임베딩해 가까운 상품을 추천합니다.
- **분류·클러스터링:** 임베딩을 특징으로 사용해 가벼운 분류기를 학습하거나 주제별로 묶습니다.
- **중복·유사 탐지:** 비슷한 문의, 중복 문서, 표절 탐지.
- **시맨틱 캐시:** 의미가 같은 질문을 찾아 이전 답을 재사용합니다.
- **이상 탐지:** 기존 분포에서 멀리 떨어진 데이터를 찾습니다.
- **멀티모달 검색:** 텍스트로 이미지 찾기(CLIP 계열).

**핵심 성질**

- 벡터 연산으로 의미를 다룰 수 있습니다(코사인 유사도, 거리).
- **같은 모델로 만든 임베딩끼리만** 비교할 수 있습니다. 모델을 바꾸면 전체를 다시 임베딩해야 합니다.
- 차원 수(384~3072 등)가 클수록 표현력은 좋아지지만 저장·검색 비용이 늘어납니다.

**한계**

- 정확한 키워드·숫자·고유명사 구분에 약할 수 있어 키워드 검색과 함께 씁니다.
- 학습 도메인과 다른 전문 분야에서는 품질이 떨어질 수 있습니다.

<summary><b>Q2. 임베딩 모델은 텍스트를 어떻게 벡터로 변환하나요?</b></summary>

**과정 (트랜스포머 기반 문장 임베딩 모델)**

1. **토큰화:** 텍스트 → 토큰 ID 시퀀스.
2. **인코딩:** 트랜스포머(주로 양방향 인코더, 최근엔 LLM 기반 디코더도 사용)가 각 토큰에 대해 문맥을 반영한 벡터를 계산합니다.
3. **풀링:** 토큰 벡터들을 하나의 벡터로 요약합니다.
   - **평균 풀링:** 모든 토큰 벡터의 평균 (가장 흔함)
   - **[CLS] 토큰:** 문장 대표 토큰의 벡터
   - **마지막 토큰:** 디코더 기반 모델에서 사용
4. **정규화:** 벡터 길이를 1로 맞춰 코사인 유사도와 내적을 같게 만듭니다.

```python
from sentence_transformers import SentenceTransformer
model = SentenceTransformer("BAAI/bge-m3")
vecs = model.encode(["환불 정책이 궁금해요", "돈을 돌려받고 싶어요"], normalize_embeddings=True)
print(vecs.shape, vecs[0] @ vecs[1])   # (2, 1024), 높은 유사도
```

**"의미가 가까우면 벡터도 가깝게"는 어떻게 학습되나**

- **대조 학습:** (질문, 관련 문서) 같은 양성 쌍은 가깝게, 관련 없는 쌍은 멀게 만드는 손실(InfoNCE)로 학습합니다.
- 대규모 약지도 쌍(제목-본문, 질문-답변)으로 먼저 학습하고, 고품질 라벨 데이터와 **어려운 음성 예시(hard negatives)** 로 다듬습니다.

**사용 시 주의**

- 일부 모델은 질문과 문서에 서로 다른 접두어(`query:`, `passage:`)나 지시문을 붙여야 성능이 나옵니다.
- 최대 입력 길이를 넘는 텍스트는 잘리므로 청크 크기를 맞춥니다.

<summary><b>Q3. 대조 학습(Contrastive Learning)이란 무엇이며, 임베딩 모델을 학습하는 데 어떻게 사용되나요?</b></summary>

**대조 학습** 은 "비슷한 것은 가깝게, 다른 것은 멀게" 배치하도록 표현을 학습하는 방법입니다. 정답 라벨 대신 **쌍(pair)의 관계** 를 학습 신호로 씁니다.

**구성**

- **앵커(anchor):** 기준 샘플 (예: 질문)
- **양성(positive):** 앵커와 의미가 같은 샘플 (예: 정답 문서)
- **음성(negative):** 앵커와 관련 없는 샘플 (예: 다른 문서)

**대표 손실: InfoNCE**

$$L = -\log \frac{\exp(\text{sim}(q, d^+)/\tau)}{\sum_{j} \exp(\text{sim}(q, d_j)/\tau)}$$

- 양성 쌍의 유사도를 분모 전체(양성 + 음성들) 대비 크게 만드는 손실입니다. τ는 온도입니다.
- **배치 내 음성(in-batch negatives):** 같은 배치의 다른 샘플들의 양성을 음성으로 재사용합니다. 배치가 클수록 음성이 많아져 효과적입니다.

**임베딩 모델 학습 과정**

1. **약지도 사전 학습:** 웹의 대량 쌍(제목-본문, 질문-답변, 앵커 텍스트-페이지)으로 대조 학습
2. **지도 파인튜닝:** 고품질 라벨 데이터(검색 데이터셋, NLI 데이터)
3. **어려운 음성 마이닝:** 그럴듯하지만 틀린 문서를 음성으로 넣으면 모델이 미세한 차이를 구분하게 됩니다. 성능에 가장 큰 영향을 주는 요소 중 하나입니다.

**다른 분야 사례**

- **CLIP:** (이미지, 캡션) 쌍으로 이미지와 텍스트를 같은 공간에 정렬
- **SimCLR:** 같은 이미지의 두 증강본을 양성으로 사용하는 자기 지도 학습
- **MoCo:** 큐와 모멘텀 인코더로 배치 크기와 상관없이 많은 음성을 확보
- **SigLIP(2023):** CLIP의 소프트맥스 손실 대신 쌍별 시그모이드 손실을 써 매우 큰 배치에 덜 의존
- **음성 없는 방식:** BYOL, SimSiam, DINO는 음성 예시 없이 stop-gradient·모멘텀 인코더 같은 장치로 표현이 한 점으로 무너지는 것을 막습니다.

**주의:** 실제로는 관련 있는데 음성으로 들어간 "거짓 음성(false negative)"이 성능을 해칠 수 있어 필터링이 필요합니다.

<summary><b>Q4. 희소(sparse) 임베딩과 밀집(dense) 임베딩의 차이는 무엇인가요?</b></summary>

| | 희소 임베딩 (Sparse) | 밀집 임베딩 (Dense) |
|---|---|---|
| 형태 | 어휘 크기(수만~수십만) 차원, **대부분 0** | 수백~수천 차원, **모든 값이 0이 아님** |
| 차원의 의미 | 각 차원 = 특정 단어(해석 가능) | 각 차원의 의미는 해석 불가 |
| 대표 방법 | TF-IDF, BM25, SPLADE(학습형) | BERT 계열 임베딩 모델, OpenAI 임베딩 |
| 강점 | 정확한 키워드·고유명사·코드 매칭, 도메인 이동에 강함 | 동의어·바꿔 말하기·의미 유사성 |
| 약점 | 다른 표현의 같은 의미를 못 찾음 | 정확 일치가 중요한 용어에 약함 |
| 인덱스 | 역색인(inverted index) | ANN 벡터 인덱스(HNSW 등) |

**학습형 희소 임베딩 (SPLADE 등)**

- 신경망이 각 단어의 가중치를 학습하고, 문서에 없는 관련 단어로 **확장** 까지 합니다(예: "자동차" 문서에 "차량" 가중치 부여).
- 키워드 검색의 효율·해석 가능성과 의미 검색의 장점을 일부 결합합니다.

**실무 결론**

- 둘은 상호 보완적이라 **하이브리드 검색**(희소 + 밀집 결과를 RRF로 결합)이 대부분의 경우 단독보다 성능이 좋습니다.
- BGE-M3처럼 한 모델이 밀집·희소·다중 벡터 표현을 함께 출력하는 모델도 있습니다.

<summary><b>Q5. 벡터 검색에서 코사인 유사도, 내적(dot product), 유클리드 거리를 설명하세요.</b></summary>

**코사인 유사도**

$$\cos(a, b) = \frac{a \cdot b}{\|a\|\|b\|}$$

- 두 벡터의 **방향(각도)** 만 비교합니다. 범위 -1~1, 1이면 같은 방향.
- 벡터 길이(크기)는 무시되므로 문서 길이 등에 덜 민감합니다. 텍스트 임베딩에서 가장 많이 씁니다.

**내적 (Dot Product)**

$$a \cdot b = \sum_i a_i b_i$$

- 방향과 **크기를 함께** 반영합니다.
- 벡터를 길이 1로 정규화하면 **코사인 유사도와 같아집니다.** 정규화 후 내적을 쓰면 계산이 더 빠릅니다.
- 추천 시스템처럼 크기에 의미(인기도, 확신도)가 있을 때 정규화하지 않은 내적을 쓰기도 합니다.

**유클리드 거리 (L2)**

$$\|a - b\| = \sqrt{\sum_i (a_i - b_i)^2}$$

- 두 점 사이의 직선 거리. 작을수록 비슷합니다.
- 정규화된 벡터에서는 `‖a-b‖² = 2 - 2·cos(a,b)`이므로 **코사인과 같은 순위** 를 줍니다.

**어떤 것을 쓰나**

- **임베딩 모델이 학습된 방식에 맞춰야 합니다.** 모델 문서가 권장하는 지표를 씁니다(대부분 코사인 또는 정규화 + 내적).
- 벡터 DB 인덱스를 만들 때 지표를 지정하므로, 모델과 인덱스 설정이 일치해야 합니다.
- 정규화된 벡터라면 셋 중 무엇을 써도 순위는 같고, 내적이 계산상 가장 효율적입니다.

```python
import numpy as np
a, b = np.array([1, 2, 3.]), np.array([2, 4, 6.5])
cos = a @ b / (np.linalg.norm(a) * np.linalg.norm(b))
l2 = np.linalg.norm(a - b)
```

<summary><b>Q6. 벡터 데이터베이스란 무엇이며, 기존 데이터베이스와 어떻게 다른가요?</b></summary>

**벡터 데이터베이스** 는 임베딩 벡터를 저장하고, 주어진 벡터와 **가장 비슷한 벡터를 빠르게 찾는(최근접 이웃 검색)** 데 특화된 데이터베이스입니다.

**기존 데이터베이스와의 차이**

| | 관계형 DB (SQL) | 벡터 DB |
|---|---|---|
| 질의 방식 | 정확한 조건 일치 (`WHERE id = 5`) | 유사도 기반 (`가장 비슷한 10개`) |
| 인덱스 | B-트리, 해시 | HNSW, IVF 같은 ANN 인덱스 |
| 결과 | 정확한 결과 | 근사 결과 (속도와 정확도 트레이드오프) |
| 데이터 | 구조화된 행·열 | 고차원 벡터 + 메타데이터 |
| 주 용도 | 트랜잭션, 집계 | 의미 검색, 추천, RAG |

**주요 기능**

- **ANN 검색:** 수백만~수십억 벡터에서 밀리초 단위 검색
- **메타데이터 필터링:** "카테고리 = 법률이고 2024년 이후인 문서 중에서 유사 검색"
- **하이브리드 검색:** 키워드(BM25) + 벡터 검색 결합
- **CRUD와 실시간 업데이트**, 네임스페이스·멀티테넌시
- **확장성:** 샤딩, 복제, 양자화로 메모리 절약

**선택지**

- **전용 벡터 DB:** Pinecone, Weaviate, Qdrant, Milvus, Chroma
- **기존 DB의 벡터 기능:** PostgreSQL + pgvector, Elasticsearch/OpenSearch, MongoDB Atlas, Redis
- **라이브러리:** FAISS, Annoy, hnswlib (DB 기능 없이 인덱스만)

**선택 기준:** 데이터 규모, 필터링 요구, 하이브리드 검색 필요성, 운영 역량(관리형 vs 자체 운영), 기존 인프라. 수백만 건 이하이고 이미 PostgreSQL을 쓴다면 pgvector로 시작하는 것도 실용적입니다.

<summary><b>Q7. 근사 최근접 이웃(ANN, Approximate Nearest Neighbor) 검색은 어떻게 동작하나요?</b></summary>

**문제:** 정확한 최근접 이웃을 찾으려면 질의 벡터를 **모든 벡터와 비교** 해야 합니다(`O(N·d)`). 수백만 개 이상에서는 너무 느립니다.

**ANN의 아이디어:** 정확도를 약간 포기하고(예: 진짜 상위 10개 중 9~10개를 찾음), 검색 대상을 크게 줄여 **수십~수천 배 빠르게** 검색합니다.

**주요 알고리즘**

1. **그래프 기반: HNSW (Hierarchical Navigable Small World)**
   - 벡터들을 "가까운 이웃끼리 연결된 그래프"로 만들고, 여러 층으로 쌓습니다. 위층은 듬성듬성(고속도로), 아래층은 촘촘(동네 길)합니다.
   - 검색: 맨 위층에서 시작해 질의와 가까운 쪽으로 이동하며 층을 내려가 최종 이웃을 찾습니다.
   - 빠르고 재현율이 높아 가장 널리 쓰이지만, 메모리를 많이 씁니다.
2. **클러스터 기반: IVF (Inverted File Index)**
   - k-means로 벡터를 수천 개 클러스터로 나눕니다.
   - 검색 시 질의와 가까운 클러스터 몇 개(`nprobe`)만 탐색합니다.
   - 메모리 효율이 좋고, 양자화(PQ)와 함께 쓰면 대규모 데이터에 적합합니다.
3. **양자화: PQ (Product Quantization)**
   - 벡터를 여러 조각으로 나누고 각 조각을 대표값 코드로 압축해, 메모리를 수십 배 줄이고 거리 계산을 빠르게 합니다.
4. **해싱: LSH (Locality-Sensitive Hashing)**
   - 비슷한 벡터가 같은 버킷에 들어가도록 해시합니다. 고차원 텍스트 임베딩에서는 지금은 덜 쓰입니다.
5. **디스크 기반: DiskANN**
   - SSD에 그래프를 두고 대규모 데이터를 적은 메모리로 검색합니다.

**튜닝 파라미터:** HNSW의 `M`(연결 수), `ef_construction`, `ef_search` / IVF의 클러스터 수, `nprobe`. 값을 키우면 재현율이 오르고 속도는 느려집니다.

**더 읽어보기 (영문):** [How does Approximate Nearest Neighbor (ANN) search work?](https://outcomeschool.com/blog/how-does-approximate-nearest-neighbor-ann-search-work)

<summary><b>Q8. HNSW, IVF, 플랫(flat) 인덱스를 비교하세요. 어떻게 하나를 고르며, recall@k를 높이면 지연 시간은 얼마나 늘어나나요?</b></summary>

| | Flat (전수 검색) | IVF (+PQ) | HNSW |
|---|---|---|---|
| 방식 | 모든 벡터와 비교 | 가까운 클러스터만 탐색 | 계층 그래프 탐색 |
| 재현율 | 100% (정확) | 중간~높음 (`nprobe`에 의존) | 높음 (`ef_search`에 의존) |
| 검색 속도 | 느림, `O(N)` | 빠름 | 매우 빠름 |
| 메모리 | 원본 벡터만 | 작음 (PQ 시 매우 작음) | 큼 (그래프 연결 정보 추가) |
| 구축 시간 | 없음 | 클러스터 학습 필요 | 느린 편 |
| 업데이트 | 쉬움 | 데이터 분포가 바뀌면 재학습 필요 | 삽입은 쉬움, 삭제는 까다로움 |
| 적합 규모 | ~수십만 | 수백만~수십억 | 수백만~수억 (메모리 허용 시) |

**선택 가이드**

- **수만~수십만 개:** Flat으로도 충분히 빠를 수 있고 정확도 100%입니다. GPU를 쓰면 더 큰 규모도 가능합니다.
- **수백만 개, 메모리 여유 있음, 낮은 지연 필요:** HNSW (대부분 벡터 DB의 기본값)
- **수억~수십억 개, 메모리 제한:** IVF-PQ 또는 DiskANN, 양자화 + 재채점(rescoring)
- **필터링이 많음:** 사용하는 DB가 필터와 인덱스를 어떻게 결합하는지(사전 필터 지원 여부)가 더 중요할 수 있습니다.

**재현율과 지연의 관계**

- 재현율은 탐색 범위(`ef_search`, `nprobe`)를 늘려 올립니다. 탐색 범위를 늘리면 지연도 함께 늘어납니다.
- 일반적인 패턴: 재현율 90% → 95%는 비교적 적은 비용으로 가능하지만, **95% → 99%로 갈수록 지연이 급격히 증가** 하는 수확 체감 곡선을 보입니다. 정확한 배수는 데이터·차원·하드웨어에 따라 다르므로 반드시 측정해야 합니다.
- 실무 방법: 내 데이터로 Flat 결과를 정답으로 두고, 파라미터별 recall@k와 p95 지연을 그래프로 그려 요구사항을 만족하는 지점을 고릅니다.

**팁:** RAG에서는 리랭커가 뒤에 있으므로, 1단계 ANN의 재현율을 적당히(예: recall@100) 확보하고 정밀도는 리랭커로 올리는 것이 효율적입니다.

<summary><b>Q9. 임베딩 캐시는 어떻게 동작하나요?</b></summary>

**임베딩 캐시** 는 한 번 계산한 텍스트의 임베딩 벡터를 저장해 두고, **같은 텍스트가 다시 들어오면 모델을 호출하지 않고 저장된 벡터를 재사용** 하는 것입니다.

**왜 필요한가**

- 임베딩 API는 호출마다 비용과 지연이 발생합니다.
- 같은 문서를 재인덱싱하거나, 같은 질문이 반복되는 경우가 많습니다(인기 질문, 문서 변경 시 바뀌지 않은 청크).

**동작**

1. 입력 텍스트를 정규화(공백 정리 등)합니다.
2. **캐시 키 = 해시(임베딩 모델 이름 + 버전 + 텍스트)** 를 만듭니다. 모델이 다르면 벡터도 다르므로 모델 정보가 반드시 키에 들어가야 합니다.
3. 캐시(Redis, 로컬 DB, 파일)에 키가 있으면 저장된 벡터를 반환합니다.
4. 없으면 모델로 임베딩을 계산하고 캐시에 저장한 뒤 반환합니다.

```python
import hashlib
def embed_cached(text, model="text-embedding-3-small"):
    key = hashlib.sha256(f"{model}:{text}".encode()).hexdigest()
    if (v := cache.get(key)) is not None:
        return v
    v = embed_api(text, model)
    cache.set(key, v)
    return v
```

**활용 장면**

- **인덱싱:** 문서 업데이트 시 바뀌지 않은 청크는 캐시에서 가져와 재임베딩 비용 절감
- **질의:** 자주 들어오는 질문의 임베딩 재사용
- **실험:** 같은 데이터로 여러 검색 설정을 실험할 때

**운영 포인트**

- 저장 공간이 한정되면 LRU(가장 오래 쓰지 않은 항목 제거)나 TTL(만료 시간)로 정리합니다.
- 같은 모델이라도 출력 차원, 정규화 여부, 잘라내기(truncation) 길이, 전처리 방식이 다르면 벡터가 달라지므로 이런 설정도 키에 포함합니다.

**시맨틱 캐시와의 차이:** 임베딩 캐시는 **텍스트가 정확히 같을 때** 벡터를 재사용하고, 시맨틱 캐시는 **의미가 비슷한 질문** 에 대해 LLM의 **최종 답변** 을 재사용합니다.

<summary><b>Q10. 사용 사례에 맞는 임베딩 모델은 어떻게 고르나요?</b></summary>

**1. 요구사항 정의**

- 언어(한국어, 다국어, 교차 언어 검색), 도메인(일반, 법률, 의료, 코드), 데이터 유형(짧은 질문, 긴 문서, 표, 이미지)
- 데이터 규모, 지연 시간 요구, 예산, 데이터 외부 전송 가능 여부

**2. 후보 선정**

- 공개 리더보드(MTEB의 **검색 항목**, 다국어·한국어 항목)에서 상위 모델을 후보로 고릅니다.
- API 모델(OpenAI, Cohere, Voyage, Google)과 오픈 모델(BGE, E5, GTE, Jina, Qwen 임베딩 등)을 함께 고려합니다.

**3. 내 데이터로 평가 (가장 중요)**

- 실제 질문 100~500개와 정답 문서로 평가셋을 만듭니다(없으면 LLM으로 문서에서 질문을 생성하고 검수).
- 지표: recall@k, MRR, nDCG.
- 리더보드 순위와 내 데이터 성능은 다를 수 있습니다.

**4. 운영 요소 비교**

| 요소 | 확인 내용 |
|---|---|
| 차원 수 | 저장 공간과 검색 속도. 차원 축소 지원(Matryoshka) 여부 |
| 최대 입력 길이 | 청크 크기보다 충분한가 |
| 속도·처리량 | 인덱싱 시간, 질의 지연 |
| 비용 | API 단가 vs 자체 호스팅 GPU 비용 |
| 라이선스 | 상업적 사용 가능 여부 |
| 장기 안정성 | 모델 지원 중단 시 재인덱싱 부담 |

**5. 최종 판단**

- 리랭커와 하이브리드 검색을 붙였을 때의 **최종 RAG 품질** 로 비교합니다. 임베딩 차이가 리랭킹 후 줄어드는 경우가 많아, 더 싸고 빠른 모델이 충분할 수 있습니다.
- 성능이 부족하면 도메인 데이터로 파인튜닝하는 것도 선택지입니다.

<summary><b>Q11. 임베딩 차원 수란 무엇이며, 성능과 비용에 어떤 영향을 주나요?</b></summary>

**임베딩 차원 수** 는 벡터를 이루는 숫자의 개수입니다. 예: 384, 768, 1024, 1536, 3072차원.

**영향**

| 측면 | 차원이 클수록 |
|---|---|
| 표현력 | 더 세밀한 의미 구분 가능 (일정 수준까지) |
| 저장 공간 | 선형 증가 (float32 기준 차원당 4바이트) |
| 검색 속도 | 거리 계산 비용 증가, 메모리 대역폭 부담 |
| 인덱스 메모리 | HNSW 등 인덱스 크기 증가 |
| 비용 | 벡터 DB 요금(메모리·저장 기준)이 증가 |

**저장 공간 계산 예**

- 1,000만 개 × 1536차원 × 4바이트 ≈ **61 GB** (인덱스 오버헤드 제외)
- 같은 개수 × 384차원 ≈ **15 GB**

**성능은 차원에 비례하지 않습니다**

- 차원보다 **모델 학습 품질** 이 성능에 더 중요합니다. 작은 차원의 좋은 모델이 큰 차원의 평범한 모델보다 나을 수 있습니다.
- 일정 차원 이상에서는 성능 향상이 작아집니다.

**비용을 줄이는 방법**

- **Matryoshka 표현 학습(MRL):** 앞쪽 차원에 중요한 정보가 몰리도록 학습된 모델은 벡터를 잘라서(예: 3072 → 256) 써도 성능 저하가 작습니다. OpenAI text-embedding-3, 여러 오픈 모델이 지원합니다.
- **양자화:** float32 → int8(4배 절약), 이진 양자화(32배 절약). 상위 후보만 원본 벡터로 재채점하면 품질 손실을 줄일 수 있습니다.
- **PCA 등 차원 축소:** 모델이 MRL을 지원하지 않을 때.

**결정 방법:** 여러 차원 설정으로 평가셋의 recall@k와 저장·지연 비용을 비교해, 요구 품질을 만족하는 가장 작은 설정을 고릅니다.

<summary><b>Q12. 임베딩 모델이 업데이트될 때 생기는 임베딩 드리프트(embedding drift)를 어떻게 처리하나요?</b></summary>

**문제:** 임베딩 모델(버전)이 바뀌면 **벡터 공간 자체가 달라집니다.** 새 모델로 만든 질문 벡터와 옛 모델로 만든 문서 벡터는 비교할 수 없어, 검색 품질이 무너집니다. 차원이 같아도 마찬가지입니다.

**원칙: 하나의 인덱스 = 하나의 임베딩 모델 버전**

- 인덱스(컬렉션) 메타데이터에 모델 이름과 버전을 기록하고, 질의 시 같은 모델을 쓰는지 코드에서 확인합니다.
- API 모델은 버전을 고정(pin)해 제공사가 모델을 조용히 바꾸지 않게 합니다.

**모델 교체 절차 (블루-그린 재인덱싱)**

1. **새 인덱스 구축:** 전체 문서를 새 모델로 다시 임베딩해 별도 인덱스를 만듭니다. 기존 인덱스는 그대로 서비스합니다.
2. **새 문서는 이중 쓰기:** 전환 기간에 들어오는 문서는 두 인덱스 모두에 넣습니다.
3. **평가:** 평가셋에서 새 인덱스의 검색 품질과 최종 RAG 품질을 비교합니다.
4. **점진적 전환:** 일부 트래픽부터 새 인덱스로 보내고(카나리), 지표를 확인한 뒤 전체 전환합니다.
5. **롤백 준비:** 문제가 생기면 별칭(alias)을 되돌립니다. 안정화 후 옛 인덱스를 삭제합니다.

**재임베딩 비용 줄이기**

- 원본 텍스트(청크)를 반드시 보관해야 재임베딩이 가능합니다.
- 배치 처리, 자체 호스팅 GPU, 우선순위(자주 검색되는 문서 먼저).

**대안 (재임베딩이 너무 비쌀 때)**

- 옛 공간과 새 공간 사이의 변환 행렬(선형 어댑터)을 학습해 근사적으로 맞추는 연구적 방법도 있지만, 품질 손실이 있어 임시 방편으로만 고려합니다.

**모니터링:** 검색 점수 분포, "결과 없음" 비율, 사용자 피드백이 갑자기 바뀌면 드리프트를 의심합니다.

<summary><b>Q13. 멀티모달 임베딩이란 무엇이며, 어떻게 생성되나요?</b></summary>

**멀티모달 임베딩** 은 텍스트, 이미지, 오디오, 영상 같은 **서로 다른 모달리티를 하나의 공통 벡터 공간** 에 표현하는 것입니다. "강아지 사진"과 "공원에서 뛰는 강아지"라는 문장이 가까운 벡터가 됩니다.

**생성 방법: 대조 학습으로 공간 정렬 (CLIP 방식)**

1. **모달리티별 인코더:** 이미지 인코더(ViT 등)와 텍스트 인코더(트랜스포머)를 따로 둡니다.
2. **투영:** 각 인코더 출력을 같은 차원의 공통 공간으로 투영합니다.
3. **대조 학습:** 수억 개의 (이미지, 캡션) 쌍으로, 짝이 맞는 쌍은 가깝게, 배치 안의 다른 쌍은 멀게 학습합니다.
4. 학습 후 텍스트 벡터와 이미지 벡터를 직접 비교할 수 있습니다.

**확장**

- **오디오-텍스트:** CLAP
- **여러 모달리티 동시 정렬:** ImageBind (이미지를 중심으로 6개 모달리티 정렬)
- **문서 페이지 이미지 임베딩:** 텍스트·표·그림이 섞인 페이지를 이미지로 임베딩해 텍스트 질문으로 검색(ColPali 계열)
- **멀티모달 LLM 기반 임베딩:** VLM의 표현을 임베딩으로 활용

**활용**

- 텍스트로 이미지·영상 검색, 이미지로 비슷한 상품 찾기
- 제로샷 이미지 분류 ("고양이 사진", "개 사진" 텍스트와 비교)
- 멀티모달 RAG (도면, 차트, 제품 사진 검색)
- 콘텐츠 모더레이션, 중복 이미지 탐지

**주의:** 같은 공간이라도 텍스트-텍스트 유사도와 텍스트-이미지 유사도의 점수 분포가 달라, 임계값을 모달리티 조합별로 따로 정해야 합니다.

<summary><b>Q14. 벡터 데이터베이스에서 멀티테넌트 데이터를 어떻게 인덱싱하고 조회하나요?</b></summary>

**요구사항:** 여러 고객사(테넌트)의 데이터를 한 시스템에 두되, **한 테넌트의 질의가 다른 테넌트 데이터를 절대 보지 못해야** 합니다. 동시에 비용과 성능도 관리해야 합니다.

**격리 방식 비교**

| 방식 | 구현 | 장점 | 단점 |
|---|---|---|---|
| **메타데이터 필터** | 하나의 컬렉션, 모든 벡터에 `tenant_id`, 질의 시 필터 | 단순, 자원 효율 | 필터 누락 시 유출 위험, 큰 테넌트가 작은 테넌트 검색 성능에 영향 |
| **네임스페이스·파티션** | 같은 클러스터 안에서 테넌트별 논리 분리 | 검색 범위가 자연히 분리, 테넌트 삭제 쉬움 | DB가 지원해야 함 |
| **테넌트별 컬렉션·인덱스** | 테넌트마다 별도 인덱스 | 강한 격리, 테넌트별 설정 가능 | 테넌트가 많으면 관리·자원 부담 |
| **테넌트별 클러스터·DB** | 물리적 분리 | 가장 강한 격리, 규제 대응 | 비용 큼 |

**실무 패턴**

- 소규모 테넌트가 많으면 네임스페이스·파티션 또는 필터 방식, 대형·고보안 고객은 전용 인덱스로 분리하는 **혼합 방식** 이 흔합니다.
- 필터 방식을 쓸 때는 사전 필터링(인덱스 검색 단계에서 필터 적용)이 지원되는지 확인합니다. 사후 필터링이면 top-k 안에 해당 테넌트 결과가 거의 없을 수 있습니다.

**보안 원칙**

- `tenant_id`는 **인증 토큰에서 서버가 추출** 해 강제 적용합니다. 클라이언트 입력이나 LLM 출력으로 정하지 않습니다.
- 데이터 접근 계층을 하나로 모아, 모든 질의에 테넌트 필터가 빠짐없이 들어가도록 코드 수준에서 보장합니다.
- 캐시, 로그, 임베딩 캐시에도 테넌트 경계를 적용합니다.
- 테넌트 간 격리 테스트(다른 테넌트 계정으로 질의)를 자동화합니다.

**운영:** 테넌트별 사용량·저장 공간 모니터링, 테넌트 해지 시 데이터 완전 삭제 절차.

<summary><b>Q15. 임베딩 양자화란 무엇이며, 저장 비용을 어떻게 줄이나요?</b></summary>

**임베딩 양자화** 는 벡터의 각 값을 더 적은 비트로 표현해 **저장 공간과 메모리, 검색 계산량을 줄이는** 기법입니다.

**방식별 비교 (1024차원 벡터 1개 기준)**

| 방식 | 값당 크기 | 벡터 크기 | 절약 | 품질 손실 |
|---|---|---|---|---|
| float32 (원본) | 4바이트 | 4 KB | - | 없음 |
| float16 / bfloat16 | 2바이트 | 2 KB | 2배 | 거의 없음 |
| int8 (스칼라 양자화) | 1바이트 | 1 KB | 4배 | 작음 |
| 이진(binary) | 1비트 | 128 바이트 | 32배 | 상대적으로 큼 |
| PQ (곱 양자화) | 설정에 따라 | 수십 바이트 | 수십 배 이상 | 설정에 따라 |

**방법 설명**

- **스칼라 양자화(int8):** 각 차원의 값 범위를 256단계로 나눠 정수로 저장합니다.
- **이진 양자화:** 각 값이 0보다 크면 1, 아니면 0. 거리 계산을 비트 연산(해밍 거리)으로 매우 빠르게 할 수 있습니다.
- **곱 양자화(PQ):** 벡터를 여러 조각으로 나누고 각 조각을 코드북의 가장 가까운 대표값 번호로 저장합니다.

**품질 손실 줄이기: 재채점(rescoring)**

1. 양자화된 벡터로 넓게 후보를 찾습니다(예: 상위 200개).
2. 후보만 원본(또는 덜 압축된) 벡터로 정확히 다시 점수를 매겨 상위 k개를 고릅니다.
3. 원본 벡터는 디스크에 두고 필요할 때만 읽으면 메모리를 크게 절약할 수 있습니다.

**참고**

- 어떤 임베딩 모델은 양자화를 고려해 학습되어(양자화 인식 학습) 손실이 더 작습니다.
- 차원 축소(Matryoshka)와 양자화를 함께 쓰면 절약 효과가 곱해집니다.

**검증:** 양자화 전후 recall@k를 평가셋으로 비교해 허용 가능한 손실인지 확인합니다.

<summary><b>Q16. 임베딩 모델의 품질을 어떻게 벤치마크하고 평가하나요?</b></summary>

**1. 공개 벤치마크 (후보 선별용)**

- **MTEB (Massive Text Embedding Benchmark):** 검색, 분류, 클러스터링, 재순위, 의미 유사도 등 여러 작업을 포함합니다. 내 용도에 맞는 **작업 유형(대부분 Retrieval)** 과 **언어** 점수를 봅니다.
- **BEIR:** 다양한 도메인의 검색 데이터셋으로 일반화 성능 확인.
- 주의: 일부 모델은 벤치마크 데이터로 학습되어 점수가 부풀려졌을 수 있습니다.

**2. 자체 평가셋 (최종 판단용)**

- 실제 사용자 질문(또는 LLM이 문서에서 생성한 질문 + 사람 검수)과 정답 문서(관련도 라벨)를 만듭니다.
- 쉬운 질문, 어려운 질문, 전문 용어, 짧은 질문, 다국어 질문을 고르게 포함합니다.

**3. 검색 지표**

| 지표 | 의미 |
|---|---|
| **Recall@k** | 정답 문서가 상위 k개 안에 포함된 비율 (RAG에서 가장 중요) |
| **Precision@k** | 상위 k개 중 관련 문서 비율 |
| **MRR** | 첫 번째 정답 문서의 순위 역수 평균 |
| **nDCG@k** | 관련도 등급과 순위를 함께 고려 |
| **Hit rate** | 하나라도 정답이 있으면 성공 |

**4. 시스템 수준 평가**

- 임베딩만 바꿨을 때 **최종 RAG 답변 품질**(정확성, 충실도)이 어떻게 변하는지 확인합니다.
- 리랭커·하이브리드 검색과 결합했을 때의 성능도 비교합니다.

**5. 운영 지표**

- 임베딩 속도(문서/초), 질의 지연, 비용, 저장 공간.

**6. 오류 분석**

- 실패한 질문들을 유형별로 분류해(동의어, 숫자, 부정문, 긴 질문 등) 모델의 약점을 파악합니다.

**메타데이터** 는 각 벡터와 함께 저장하는 구조화된 속성입니다. 예: `doc_id`, `title`, `source`, `created_at`, `category`, `language`, `tenant_id`, `allowed_groups`, `page`, `chunk_index`.

8. **분석과 디버깅:** 어떤 출처가 자주 검색되는지, 어떤 문서가 실패를 유발하는지 추적합니다.

**설계 팁**

- 필터에 자주 쓰는 필드는 인덱스를 생성해 빠르게 필터링되게 합니다.

<summary><b>Q18. 수십억 개의 벡터를 대상으로 하는 대규모 벡터 검색을 어떻게 처리하나요?</b></summary>

- **GPU 가속:** FAISS GPU, CAGRA 같은 GPU 인덱스로 구축과 검색 가속.

- **의미 기반 파티셔닝:** 테넌트·카테고리·지역으로 나누면 질의 시 필요한 샤드만 검색할 수 있습니다.

**4. 검색 범위 줄이기**

<summary><b>Q19. 하이브리드 검색(키워드 검색과 벡터 검색의 결합)이란 무엇인가요?</b></summary>

**하이브리드 검색** 은 **키워드 기반 검색**(BM25 같은 희소 검색)과 **임베딩 기반 의미 검색**(밀집 검색)을 동시에 실행하고 결과를 합치는 방식입니다.

**왜 결합하나**

- **키워드 검색:** 정확한 용어, 제품 코드(`SKU-4821`), 이름, 숫자, 약어를 잘 찾지만, 다른 표현("해지" vs "구독 취소")은 놓칩니다.
- **벡터 검색:** 의미가 비슷한 다른 표현을 잘 찾지만, 정확히 일치해야 하는 드문 용어는 놓치기 쉽습니다.
- 서로의 약점을 보완해 대부분의 데이터에서 **재현율이 단독 검색보다 높습니다.**

**결과 합치는 방법**

1. **RRF (Reciprocal Rank Fusion):** 각 검색 결과의 순위만 사용합니다.
   ```
   score(d) = Σ_i 1 / (k + rank_i(d)),  보통 k = 60
   ```
   점수 척도를 맞출 필요가 없어 가장 많이 씁니다.
2. **가중 점수 결합:** 두 점수를 정규화(min-max 등)한 뒤 `α·dense + (1-α)·sparse`. α를 평가셋으로 조정합니다.

**흐름**

```
질문 ─┬─ BM25 검색 → 상위 50
      └─ 벡터 검색 → 상위 50
            → RRF 병합 → 상위 30 → 리랭커 → 상위 5 → LLM
```

**구현:** Elasticsearch/OpenSearch, Weaviate, Qdrant, Vespa, pgvector + PostgreSQL 전문 검색 등이 지원합니다. 한국어는 형태소 분석기를 키워드 검색에 적용해야 품질이 좋아집니다.

<summary><b>Q20. 특정 도메인에 맞게 임베딩 모델을 어떻게 파인튜닝하나요?</b></summary>

**언제 하나:** 범용 임베딩 모델이 도메인 용어·문서 구조를 잘 이해하지 못해, 하이브리드 검색·리랭커를 붙여도 재현율이 부족할 때.

**1. 학습 데이터 만들기: (질문, 관련 문서) 쌍**

- **실제 로그:** 사용자 검색어와 클릭·채택된 문서
- **합성:** LLM에게 문서 청크를 주고 "이 내용으로 답할 수 있는 질문"을 생성 → 품질 필터링
- **구조 활용:** FAQ의 질문-답, 문서 제목-본문
- 보통 수천~수만 쌍이면 의미 있는 개선이 가능합니다.

**2. 어려운 음성 예시(hard negatives) 마이닝**

- 현재 모델로 검색했을 때 상위에 나오지만 **정답이 아닌 문서** 를 음성으로 사용합니다. 모델이 미세한 차이를 배우게 하는 핵심입니다.
- 실제로는 관련 있는 "거짓 음성"을 걸러내기 위해 리랭커나 LLM으로 확인합니다.

**3. 학습**

- 손실: 대조 손실(MultipleNegativesRankingLoss / InfoNCE). 배치 내 음성 + 어려운 음성.
- 낮은 학습률, 1~3 에포크, 큰 배치가 유리합니다.
- 도구: sentence-transformers, FlagEmbedding 등.

```python
from sentence_transformers import SentenceTransformer, losses
model = SentenceTransformer("BAAI/bge-base-en-v1.5")
loss = losses.MultipleNegativesRankingLoss(model)
# train_dataset: (anchor=질문, positive=정답 문서, negative=어려운 음성)
```

**4. 평가**

- 학습에 쓰지 않은 질문으로 recall@k, nDCG를 원래 모델과 비교합니다.
- 일반 도메인 성능이 크게 떨어지지 않았는지도 확인합니다.

**5. 배포**

- 파인튜닝한 모델로 **전체 문서를 재임베딩** 해야 합니다(벡터 공간이 바뀜). 블루-그린 방식으로 인덱스를 교체합니다.

**대안:** 문서 쪽은 그대로 두고 질문 임베딩에만 작은 선형 어댑터를 학습하는 방식은 재인덱싱 없이 일부 개선을 얻을 수 있습니다.

<summary><b>Q21. RAG용 벡터 데이터베이스가 메모리를 너무 많이 씁니다. 어떻게 줄이나요?</b></summary>

**먼저 메모리 구성 파악:** 원본 벡터, 인덱스 구조(HNSW 그래프 연결), 메타데이터·원문 텍스트, 캐시 중 무엇이 큰지 봅니다.

**줄이는 방법**

1. **벡터 양자화**
   - float32 → int8(4배), 이진(32배), PQ. 상위 후보만 원본으로 재채점해 품질을 유지합니다.
2. **차원 축소**
   - Matryoshka 지원 모델이면 낮은 차원으로 잘라 씁니다. 아니면 더 작은 차원의 모델로 교체를 검토합니다.
3. **디스크 기반 인덱스**
   - 원본 벡터를 디스크(mmap)에 두고 메모리에는 압축 벡터·인덱스만 둡니다. DiskANN 계열이나 DB의 on-disk 옵션을 사용합니다.
4. **인덱스 파라미터 조정**
   - HNSW의 `M`(이웃 연결 수)을 줄이면 그래프 메모리가 줄어듭니다(재현율 확인 필요).
   - 대규모라면 IVF-PQ처럼 메모리 효율이 좋은 인덱스로 변경합니다.
5. **불필요한 데이터 정리**
   - 중복 청크 제거, 오래된·사용되지 않는 문서 삭제, 지나친 겹침(overlap) 줄이기.
   - 원문 텍스트·큰 메타데이터는 벡터 DB 대신 별도 저장소(객체 저장소, 일반 DB)에 두고 ID로 연결합니다.
6. **청킹 재검토**
   - 너무 작은 청크는 벡터 수를 크게 늘립니다. 청크 크기를 늘리거나 부모-자식 구조를 활용합니다.
7. **계층·티어링**
   - 자주 검색되는 데이터는 메모리, 오래된 데이터는 디스크·저비용 티어로 나눕니다.

**검증:** 각 조치 후 recall@k와 지연이 요구사항을 만족하는지 평가셋으로 확인합니다.

<summary><b>Q22. 벡터 데이터베이스가 수백만 개의 임베딩으로 확장되지 않습니다. 병목을 어떻게 해결하나요?</b></summary>

**병목 진단:** 증상별로 원인을 좁힙니다.

| 증상 | 가능한 원인 |
|---|---|
| 검색이 느림 | 전수 검색(flat) 사용, 인덱스 파라미터 과다, 사후 필터링, 메모리 부족으로 디스크 스왑 |
| 삽입·인덱싱이 느림 | HNSW 구축 비용, 건별 삽입, 동기 재인덱싱 |
| 메모리 부족 | float32 원본 벡터 전부 메모리 상주, 큰 메타데이터 |
| 동시 요청에 약함 | 단일 노드, CPU 포화, 커넥션 제한 |
| 필터 질의만 느림 | 필터 필드 인덱스 없음, 사후 필터 |

**해결책**

1. **ANN 인덱스 사용:** flat → HNSW 또는 IVF. pgvector라면 HNSW/IVFFlat 인덱스를 생성했는지 확인합니다.
2. **파라미터 튜닝:** `ef_search`, `nprobe`를 재현율 요구에 맞게 조정합니다.
3. **메모리 최적화:** 양자화, 차원 축소, 디스크 기반 저장(Q21 참고).
4. **배치 삽입:** 건별 대신 대량으로 삽입하고, 인덱스 구축을 비동기·백그라운드로 처리합니다.
5. **필터 최적화:** 메타데이터 필드 인덱스 생성, 사전 필터링 지원 DB 사용, 자주 쓰는 필터 기준으로 파티셔닝.
6. **수평 확장:** 샤딩과 레플리카. 필요하면 확장성이 좋은 전용 벡터 DB(Milvus, Qdrant, Weaviate, 관리형 서비스)로 이전합니다.
7. **하드웨어:** 메모리 증설, 빠른 SSD, GPU 인덱스.

**측정 방법:** 데이터 양을 늘려 가며 부하 테스트(동시 질의 수, p95/p99 지연, 처리량)를 하고, 병목 지점(CPU, 메모리, I/O)을 프로파일링합니다.

**더 읽어보기 (영문):** [How does Approximate Nearest Neighbor (ANN) search work?](https://outcomeschool.com/blog/how-does-approximate-nearest-neighbor-ann-search-work)

<summary><b>Q23. 새 임베딩 모델의 차원이 프로덕션에 있는 기존 벡터와 다릅니다. 이 불일치를 어떻게 처리하나요?</b></summary>

**핵심 원칙:** 차원이 다르면 물론이고, **차원이 같더라도 다른 모델의 벡터끼리는 비교할 수 없습니다.** 0을 채워 차원을 맞추거나 잘라서 맞추는 것은 해결책이 아닙니다(같은 모델의 Matryoshka 축소는 예외).

**올바른 해결: 전체 재임베딩 + 인덱스 교체**

1. **새 인덱스(컬렉션) 생성:** 새 차원과 거리 지표로 별도 인덱스를 만듭니다. 대부분의 벡터 DB는 한 인덱스에 하나의 차원만 허용합니다.
2. **전체 문서 재임베딩:** 보관해 둔 원문 청크를 새 모델로 임베딩합니다. 배치 처리, 병렬화, 임베딩 캐시 활용.
3. **이중 쓰기:** 전환 기간 동안 새로 들어오는 문서는 옛 인덱스와 새 인덱스 모두에 넣습니다.
4. **평가:** 평가셋으로 새 인덱스의 검색 품질과 최종 답변 품질을 비교합니다.
5. **점진적 전환:** 질의 경로를 새 모델 + 새 인덱스로 일부 트래픽부터 전환합니다. 질의 임베딩 모델과 인덱스가 반드시 짝을 이루도록 설정에서 묶어 관리합니다.
6. **롤백 대비 후 정리:** 안정화되면 옛 인덱스를 삭제합니다.

**운영 장치**

- 인덱스 메타데이터에 모델 이름·버전·차원을 저장하고, 질의 시 불일치를 감지하면 오류를 내도록 합니다.
- 원문 텍스트 보관은 필수입니다. 벡터만 저장해 두면 재임베딩이 불가능합니다.

**비용이 문제라면**

- 자주 검색되는 문서부터 우선 재임베딩하고, 나머지는 백그라운드로 처리합니다.
- 정말 불가능한 경우에만 두 공간을 근사적으로 연결하는 변환(선형 어댑터) 학습을 임시로 검토하되, 품질 손실을 측정해야 합니다.

<summary><b>Q24. 유사도 점수가 높은데도 벡터 검색이 관련 없는 결과를 반환합니다. 어떻게 고치나요?</b></summary>

**원인**

1. **점수의 절대값을 오해:** 임베딩 모델마다 점수 분포가 다릅니다. 어떤 모델은 관련 없는 문서도 코사인 0.7~0.8이 나옵니다. "0.8이면 관련 있다"는 기준이 틀렸을 수 있습니다.
2. **이방성(anisotropy):** 임베딩들이 공간의 좁은 영역에 몰려 있어 모든 쌍의 유사도가 높게 나옵니다.
3. **주제는 같지만 질문에 답하지 않음:** "환불 정책"을 물었는데 "환불 처리 지연 공지"가 나옴. 임베딩은 주제 유사성을 잘 잡지만 질문-답변 관계(관련성)는 약할 수 있습니다.
4. **비대칭 검색 설정 오류:** 질문용·문서용 접두어를 빼먹음, 거리 지표가 모델과 다름, 정규화 누락.
5. **청크 문제:** 청크에 여러 주제가 섞여 있거나, 머리말·목차 같은 일반적인 텍스트가 모든 질문과 비슷하게 나옴.
6. **도메인 불일치:** 범용 모델이 전문 용어의 차이를 구분 못 함.

**해결책**

- **설정 확인:** 모델이 요구하는 접두어·지시문, 거리 지표, 정규화를 맞춥니다.
- **리랭커 추가:** 크로스 인코더가 "이 문서가 질문에 답하는가"를 판단해 순위를 바로잡습니다. 가장 효과적인 해결책입니다.
- **하이브리드 검색:** 키워드 일치를 함께 반영합니다.
- **임계값 재설정:** 평가셋에서 관련/비관련 문서의 점수 분포를 보고 모델별로 임계값을 정합니다. 리랭커 점수로 임계값을 거는 것이 더 안정적입니다.
- **청크 정리:** 목차·머리말·반복 텍스트 제거, 의미 단위 청킹, 청크에 제목·맥락 추가.
- **쿼리 변환:** 짧거나 모호한 질문을 재작성·확장합니다.
- **모델 개선:** 더 나은 모델로 교체하거나 도메인 데이터로 파인튜닝합니다(어려운 음성 예시 포함).

**재발 방지 장치**

- 벡터와 인덱스에 모델 ID·버전을 저장하고, 질의 시 불일치를 감지하면 배포가 실패하거나 경고가 나게 합니다.
- API 임베딩 모델은 버전을 고정합니다(제공사의 자동 업데이트 방지).
- 배포 파이프라인에 검색 품질 회귀 테스트를 게이트로 둡니다.
- 검색 점수 분포·상위 결과 변화 모니터링으로 이상을 조기에 감지합니다.

<summary><b>Q26. 짧은 쿼리에서 의미 검색(semantic search)이 실패합니다. 어떻게 개선하나요?</b></summary>

**왜 짧은 쿼리에 약한가**

- "가격", "환불", "API 키"처럼 한두 단어 질의는 **의미 정보가 적고 모호** 합니다.
- 임베딩 모델은 주로 문장 수준 쌍으로 학습되어, 단어 하나의 임베딩은 질문 의도를 잘 담지 못합니다.
- 짧은 질의 벡터와 긴 문서 벡터 사이의 비대칭이 커집니다.

**개선 방법**

1. **하이브리드 검색:** 짧은 질의는 키워드가 곧 의도인 경우가 많아 **BM25가 특히 강합니다.** 짧은 질의에서 키워드 검색 가중치를 높이는 적응형 가중치도 효과적입니다.
2. **쿼리 확장·재작성**
   - LLM으로 짧은 질의를 완전한 질문으로 확장합니다: "환불" → "제품 환불 정책과 환불 신청 방법은 무엇인가요?"
   - **HyDE:** 가상의 답변 문서를 생성해 그 임베딩으로 검색합니다.
   - 대화 맥락이 있으면 이전 대화를 반영해 재작성합니다.
   - 동의어 사전·멀티 쿼리 생성.
3. **비대칭 모델·지시문 사용:** 짧은 질의 ↔ 긴 문서 검색용으로 학습된 모델을 쓰고, 질의 접두어(`query:`)나 작업 지시문을 정확히 붙입니다.
4. **문서 쪽 보강**
   - 청크마다 "이 청크가 답하는 질문들"을 LLM으로 생성해 함께 인덱싱하면, 짧은 질의와 매칭이 쉬워집니다.
   - 제목·키워드 필드를 따로 인덱싱합니다.
5. **리랭커:** 후보를 넓게 가져와 리랭커로 정밀하게 정렬합니다.
6. **UX로 보완:** 자동 완성, 추천 질문, 결과가 모호하면 되묻기("환불 정책을 찾으시나요, 환불 신청 방법을 찾으시나요?").
7. **파인튜닝:** 실제 짧은 검색어 로그와 클릭 데이터로 임베딩 모델을 학습합니다.

**평가:** 질의 길이별로 평가셋을 나눠, 짧은 질의 그룹의 recall@k를 따로 추적합니다.
