<summary><b>Q1. 프롬프트 캐싱(Prompt Caching)은 어떻게 동작하나요?</b></summary>

**프롬프트 캐싱** 은 여러 요청에서 반복되는 **프롬프트 앞부분(프리픽스)의 계산 결과(KV 캐시)를 저장해 두고 재사용** 하는 기법입니다.

**동작 원리**

1. LLM은 입력을 처리할 때 각 토큰의 Key·Value를 계산합니다(프리필). 이 계산은 입력 길이에 비례해 비쌉니다.
2. 두 요청의 앞부분 토큰이 **정확히 같다면** 그 부분의 KV 값도 같습니다.
3. 첫 요청에서 계산한 KV 캐시를 저장해 두고, 다음 요청에서 같은 프리픽스를 만나면 재계산 없이 가져다 쓰고 **새로 달라진 뒷부분만 계산** 합니다.

```
요청 1: [시스템 프롬프트 5,000토큰][문서 20,000토큰][질문 A]  → 전체 계산, 캐시 저장
요청 2: [시스템 프롬프트 5,000토큰][문서 20,000토큰][질문 B]  → 25,000토큰은 캐시, 질문 B만 계산
```

**효과**

- **비용:** 캐시된 입력 토큰은 일반 입력보다 크게 할인됩니다(제공사마다 다름).
- **지연:** 프리필 계산이 줄어 첫 토큰까지의 시간(TTFT)이 크게 감소합니다.

**사용 조건과 설계 요령**

- **접두어가 완전히 같아야 합니다.** 한 글자만 달라도 그 지점 이후는 캐시되지 않습니다.
- 고정 내용(시스템 프롬프트, 도구 정의, 공통 문서, 퓨샷 예시)을 **앞에**, 바뀌는 내용(사용자 질문, 현재 시각)을 **뒤에** 둡니다.
- 캐시는 일정 시간(수 분 등) 후 만료되므로 자주 반복되는 요청에서 효과가 큽니다.
- 제공사에 따라 자동 캐싱이거나, 캐시 지점을 명시적으로 지정해야 합니다.
- 자체 호스팅에서는 vLLM·SGLang의 프리픽스 캐싱 기능이 같은 역할을 합니다.

**잘 맞는 경우:** 긴 시스템 프롬프트, 같은 문서에 대한 반복 질의, 멀티턴 대화(이전 대화가 프리픽스), 에이전트 루프(매 단계 이전 기록 재전송).

<summary><b>Q2. 프리필(Prefill)과 디코드(Decode)</b></summary>

LLM 추론은 성격이 매우 다른 **두 단계** 로 나뉩니다.

| | 프리필 (Prefill) | 디코드 (Decode) |
|---|---|---|
| 하는 일 | 입력 프롬프트 전체를 한 번에 처리, KV 캐시 생성 | 토큰을 하나씩 생성, KV 캐시에 추가 |
| 처리 토큰 수 | 수백~수십만 개를 병렬로 | 단계당 1개 (요청당) |
| 병목 | **연산(compute-bound)** | **메모리 대역폭(memory-bound)** |
| 영향 지표 | TTFT (첫 토큰까지 시간) | TPOT/ITL (토큰 간 시간), 처리량 |
| 늘어나는 요인 | 프롬프트 길이 | 출력 길이, 모델 크기 |

**왜 이 구분이 중요한가**

- 두 단계의 최적화 방법이 다릅니다.
  - **프리필 최적화:** 프롬프트 길이 줄이기, 프롬프트 캐싱, 텐서 병렬화, Flash Attention
  - **디코드 최적화:** 배치 크기 늘리기(연속 배칭), KV 캐시 압축(GQA, 양자화), 가중치 양자화, 추측 디코딩
- 같은 GPU에서 둘이 섞이면 긴 프리필이 다른 요청의 디코드를 멈춰 토큰 간 지연이 튀는 문제가 생깁니다. 그래서 **청크 프리필**, **프리필-디코드 분리** 같은 기법이 나왔습니다.

**예:** 10만 토큰 문서를 요약해 500토큰을 출력하는 요청은 프리필이 대부분의 계산을 차지하고, 짧은 질문에 긴 글을 쓰는 요청은 디코드가 대부분의 시간을 차지합니다.

**더 읽어보기 (영문):** [Prefill vs Decode: LLM Inference Optimization](https://outcomeschool.com/blog/prefill-vs-decode-llm-inference-optimization)

<summary><b>Q3. 프리필은 왜 연산 병목(compute-bound)이고, 디코드는 왜 메모리 대역폭 병목(memory-bandwidth-bound)인가요?</b></summary>

**핵심 개념: 산술 강도(arithmetic intensity)** = 메모리에서 읽은 바이트당 수행하는 연산 수(FLOPs/byte). GPU는 연산 능력에 비해 메모리 대역폭이 상대적으로 작기 때문에, 산술 강도가 낮으면 연산 장치가 데이터를 기다리며 놀게 됩니다.

**프리필: 연산 병목**

- 프롬프트 T개 토큰을 한 번에 처리합니다. 가중치 행렬을 메모리에서 **한 번 읽어 T개 토큰 모두에 재사용** 합니다(행렬 × 행렬 곱).
- 읽은 가중치 1바이트당 연산이 T에 비례해 많아져 산술 강도가 높습니다.
- GPU의 연산 장치(텐서 코어)가 꽉 차서 연산 속도가 한계가 됩니다.

**디코드: 메모리 대역폭 병목**

- 매 단계 새 토큰 1개(배치 크기 B개)만 처리합니다. 그런데도 **모델 가중치 전체와 KV 캐시를 메모리에서 다시 읽어야** 합니다(행렬 × 벡터 곱).
- 가중치를 읽는 양에 비해 연산은 아주 적어 산술 강도가 낮습니다.
- 예: 70B 모델(FP16 약 140GB)을 배치 1로 디코딩하면 토큰 하나마다 약 140GB를 읽습니다. HBM 대역폭이 초당 약 3TB라면 이론상 초당 약 20토큰 남짓이 한계이고, 이때 연산 장치는 대부분 쉬고 있습니다.

**실무적 의미**

- **디코드는 배치를 키울수록 효율적:** 가중치를 한 번 읽어 여러 요청에 재사용하므로 처리량이 크게 오릅니다(연속 배칭의 근거). 단, KV 캐시 메모리가 배치 크기를 제한합니다.
- **양자화가 디코드를 빠르게 하는 이유:** 읽어야 할 바이트가 줄기 때문입니다.
- **추측 디코딩:** 메모리를 한 번 읽을 때 여러 토큰을 검증해 남는 연산을 활용합니다.
- **프리필 가속:** 연산을 줄이거나(캐싱) 연산 장치를 늘리는(병렬화) 방향.

**더 읽어보기 (영문):** [Prefill vs Decode: LLM Inference Optimization](https://outcomeschool.com/blog/prefill-vs-decode-llm-inference-optimization)

<summary><b>Q4. 청크 프리필(chunked prefill)이란 무엇이며, 혼합 트래픽에서 꼬리 지연(tail latency)을 왜 개선하나요?</b></summary>

**문제 상황**

- 하나의 GPU가 여러 요청을 연속 배칭으로 처리하고 있습니다. 대부분은 디코드 중(토큰을 하나씩 생성)입니다.
- 이때 10만 토큰짜리 긴 프롬프트가 들어오면, 그 프리필을 한 번에 처리하는 동안(수백 ms~수 초) **다른 모든 요청의 디코드가 멈춥니다.**
- 사용자 입장에서는 스트리밍 중 글자가 갑자기 멈췄다가 나오는 현상이 생기고, 토큰 간 지연(ITL)의 p99가 크게 튑니다.

**청크 프리필**

- 긴 프리필을 **일정 크기의 조각(예: 512~2048토큰)** 으로 나눕니다.
- 매 스케줄링 단계에서 **디코드 토큰들 + 프리필 조각 하나** 를 함께 배치로 처리합니다.
- 프리필이 여러 단계에 걸쳐 진행되는 동안에도 다른 요청의 디코드는 계속 진행됩니다.

```
기존:  [디코드][디코드][====== 긴 프리필 ======][디코드][디코드]
청크:  [디코드+프리필1][디코드+프리필2][디코드+프리필3][디코드]...
```

**왜 효과적인가**

- 디코드는 메모리 병목, 프리필은 연산 병목이므로 **같은 배치에 섞으면 GPU 자원을 함께 활용** 할 수 있습니다.
- 디코드 요청이 오래 멈추지 않아 **토큰 간 지연의 꼬리(p99)가 안정** 됩니다.

**트레이드오프**

- 긴 프롬프트 요청 자체의 TTFT는 조금 늘어날 수 있습니다(조각으로 나눠 처리하므로).
- 조각 크기가 작을수록 디코드 지연은 안정되지만 프리필 효율이 떨어집니다. 워크로드에 맞게 조정합니다.

**지원:** vLLM, SGLang, TensorRT-LLM 등 주요 서빙 엔진이 지원합니다.

**더 읽어보기 (영문):** [Prefill vs Decode: LLM Inference Optimization](https://outcomeschool.com/blog/prefill-vs-decode-llm-inference-optimization)

<summary><b>Q5. 프리필-디코드 분리(Prefill-Decode Disaggregation)란 무엇이며, 언제 효과가 있나요?</b></summary>

**프리필-디코드 분리** 는 프리필과 디코드를 **서로 다른 GPU(인스턴스) 풀에서 실행** 하는 서빙 아키텍처입니다.

**동작**

1. 요청이 **프리필 노드** 로 가서 프롬프트를 처리하고 KV 캐시를 만듭니다.
2. KV 캐시를 고속 네트워크(NVLink, InfiniBand, RDMA)로 **디코드 노드** 에 전송합니다.
3. 디코드 노드가 토큰을 생성해 스트리밍합니다.

**왜 분리하나**

- 두 단계는 병목이 다릅니다(연산 vs 메모리 대역폭). 한 GPU에서 섞으면 서로 간섭해 TTFT와 토큰 간 지연이 모두 불안정해집니다.
- 분리하면 각 단계를 **독립적으로 최적화·확장** 할 수 있습니다.
  - 프리필 풀: 연산 성능 위주, 큰 텐서 병렬화
  - 디코드 풀: 큰 배치, 메모리 용량·대역폭 위주
  - 트래픽 특성에 따라 두 풀의 비율 조정 (긴 입력이 많으면 프리필 노드 증가)
- TTFT와 TPOT에 대해 각각 SLO를 맞추기 쉬워집니다.

**언제 효과가 있나**

- **대규모 서빙** (많은 GPU, 높은 트래픽)
- 입력이 길고 출력도 상당한 **혼합 워크로드**
- TTFT와 토큰 간 지연 모두에 엄격한 SLO가 있을 때
- 노드 간 고속 네트워크가 있을 때

**효과가 적거나 손해인 경우**

- 소규모 배포(GPU 몇 장): 운영 복잡도와 KV 캐시 전송 비용이 이득보다 큼
- 프롬프트가 짧아 프리필이 가벼운 워크로드
- 네트워크가 느려 KV 전송이 병목이 되는 환경

**관련 구현:** DistServe, Splitwise 연구, vLLM·SGLang·NVIDIA Dynamo 등의 분리 서빙 기능.

**더 읽어보기 (영문):** [Prefill-Decode Disaggregation in LLM Inference](https://outcomeschool.com/blog/prefill-decode-disaggregation)

<summary><b>Q6. 아이디어 구상부터 프로덕션까지 AI 제품의 수명 주기를 설명하세요.</b></summary>

**1. 문제 정의**

- 해결할 사용자 문제, 성공 지표(업무 시간 단축, 해결률), AI가 정말 필요한지(규칙이나 기존 소프트웨어로 충분하지 않은지) 판단합니다.
- 위험 수준(고위험 도메인 여부), 데이터 가용성, 규제를 확인합니다.

**2. 프로토타입**

- 가장 강한 모델과 간단한 프롬프트로 빠르게 가능성 검증.
- 실제 데이터 샘플로 "어느 정도 되는지" 감 잡기.

**3. 평가 기준 수립**

- 평가셋(실제 입력 + 기대 결과·채점 기준)과 평가 방법 정의. 이후 모든 개선의 기준이 됩니다.

**4. 개발과 반복 개선**

- 프롬프트 엔지니어링 → RAG → 도구·에이전트 → 필요 시 파인튜닝.
- 평가셋 점수, 비용, 지연을 기준으로 반복 개선.
- 가드레일, 오류 처리, 폴백 구현.

**5. 프로덕션 준비**

- 보안 검토(프롬프트 인젝션, 데이터 유출), 개인정보·규정 검토, 레드 팀.
- 관측(트레이싱, 로깅), 비용 모니터링, 속도 제한.
- 부하 테스트, 용량 계획.

**6. 출시**

- 내부 테스트 → 소수 사용자(베타) → 점진적 확대, 기능 플래그와 롤백 준비.
- A/B 테스트로 실제 지표 확인.

**7. 운영과 개선 (지속)**

- 품질 모니터링(자동 평가 샘플링, 사용자 피드백), 드리프트·회귀 감지.
- 실패 사례를 평가셋에 추가 → 개선 → 회귀 테스트 → 배포의 순환.
- 모델 업데이트(새 버전·새 제공사) 시 재평가.
- 비용 최적화(라우팅, 캐싱, 작은 모델 전환).

**전통 ML과의 차이:** 학습보다 **평가·프롬프트·시스템 통합·운영 모니터링** 의 비중이 훨씬 크고, 출시 후에도 빠르게 반복합니다.

<summary><b>Q7. LLMOps란 무엇이며, 기존 MLOps와 어떻게 다른가요?</b></summary>

**LLMOps** 는 LLM 기반 애플리케이션을 개발·배포·운영·개선하는 데 필요한 실천법과 도구입니다. MLOps의 확장이지만 중점이 다릅니다.

| 영역 | 전통 MLOps | LLMOps |
|---|---|---|
| 모델 | 직접 학습한 작은 모델 | 대부분 사전 학습된 거대 모델(API 또는 오픈 모델) |
| 주 작업 | 피처 엔지니어링, 학습, 하이퍼파라미터 튜닝 | 프롬프트, RAG, 에이전트, (가끔) 파인튜닝 |
| 버전 관리 대상 | 데이터, 코드, 모델 | + **프롬프트**, 도구 정의, 검색 인덱스, 모델 제공사·버전 |
| 평가 | 정확도·AUC 등 명확한 지표 | 자유 형식 출력 → LLM 판정자, 사람 평가, 다면 평가 |
| 비용 구조 | 학습 비용 중심 | **토큰당 추론 비용** 이 지속적으로 발생 |
| 지연 | 보통 ms 단위 | 수백 ms~수십 초, 스트리밍 |
| 모니터링 | 데이터·예측 드리프트 | 환각, 안전성, 비용, 토큰 사용량, 사용자 피드백, 트레이스 |
| 보안 | 모델 공격 일부 | 프롬프트 인젝션, 탈옥, 데이터 유출 |
| 외부 의존 | 적음 | 제공사 장애·속도 제한·모델 변경 |

**LLMOps 핵심 구성 요소**

- 프롬프트 관리(버전, 템플릿, 실험)
- 평가 파이프라인(오프라인 평가셋, CI 회귀 테스트, 온라인 평가)
- 관측(LLM 호출 트레이싱, 토큰·비용, 지연, 품질 신호)
- 게이트웨이(라우팅, 폴백, 속도 제한, 캐싱, 가드레일)
- RAG 데이터 파이프라인(인덱싱, 신선도)
- 서빙 인프라(자체 호스팅 시 vLLM 등)
- 피드백 루프(사용자 피드백 → 평가셋·학습 데이터)

**면접 포인트:** "LLMOps의 핵심은 평가와 관측이다. 출력이 확률적이고 자유 형식이라, 무엇이 잘되고 안되는지 측정하는 체계가 없으면 개선도 운영도 할 수 없다."

<summary><b>Q8. 프로덕션에서 LLM을 어떻게 서빙하나요?</b></summary>

**선택지 1: 관리형 API (OpenAI, Anthropic, Google, 클라우드의 Bedrock·Azure·Vertex)**

- 인프라 운영이 필요 없고 최신 모델을 바로 사용합니다.
- 고려 사항: 속도 제한, 데이터 정책, 제공사 장애 대비 폴백, 비용 모니터링.

**선택지 2: 자체 호스팅 (오픈 웨이트 모델)**

```
클라이언트 → [로드 밸런서/게이트웨이] → [추론 서버 인스턴스들 (GPU)]
             인증, 속도 제한, 라우팅      vLLM / SGLang / TensorRT-LLM / TGI
                                         + 모델 저장소, 오토스케일러, 모니터링
```

**추론 서버의 핵심 최적화**

- **연속 배칭(continuous batching):** 요청이 끝나는 즉시 새 요청을 배치에 넣어 GPU를 쉬지 않게 함
- **PagedAttention:** KV 캐시를 블록 단위로 관리해 메모리 낭비 제거, 더 큰 배치
- **프리픽스 캐싱:** 공통 프롬프트 재사용
- **양자화:** FP8, INT8, AWQ/GPTQ(INT4)로 메모리·속도 개선
- **텐서 병렬화:** 큰 모델을 여러 GPU에 분산
- **추측 디코딩:** 작은 드래프트 모델·MTP로 생성 가속
- **스트리밍:** SSE로 토큰 단위 전송

**운영 요소**

- **오토스케일링:** 대기열 길이·GPU 사용률·TTFT 기준. 모델 로딩 시간이 길어 웜 풀 유지
- **모니터링:** TTFT, TPOT, 처리량, 오류율, KV 캐시 사용률, GPU 메모리
- **배포:** 모델 버전 관리, 카나리 배포, 롤백
- **비용:** GPU 사용률 최적화, 예약 인스턴스, 작은 모델로 라우팅

**선택 기준:** 트래픽 규모, 데이터 통제 요구, 맞춤 모델 필요 여부, 팀의 인프라 역량. 많은 조직이 관리형 API로 시작하고, 규모·규정 요구가 커지면 일부를 자체 호스팅으로 옮깁니다.

<summary><b>Q9. 모델 양자화(quantization)란 무엇인가요?</b></summary>

**양자화** 는 모델의 가중치(그리고 선택적으로 활성화 값, KV 캐시)를 FP32/FP16 같은 높은 정밀도에서 **INT8, FP8, INT4 같은 낮은 비트 표현으로 바꾸는** 기법입니다.

**기본 아이디어**

- 실수 값 범위를 정해진 개수의 단계로 나눠 정수로 표현합니다.
- `q = round(x / scale) + zero_point`, 복원 시 `x ≈ (q - zero_point) × scale`
- 값들을 그룹(예: 128개씩)으로 나눠 그룹마다 scale을 두면 정밀도 손실이 줄어듭니다.

**얻는 것**

| 정밀도 | 7B 모델 가중치 크기 | 효과 |
|---|---|---|
| FP16 | ~14 GB | 기준 |
| INT8 / FP8 | ~7 GB | 메모리 절반, 대체로 품질 거의 동일 |
| INT4 | ~3.5~4 GB | 메모리 1/4, 약간의 품질 저하 |

- 더 작은 GPU·노트북·휴대폰에서 실행 가능
- 디코드(메모리 대역폭 병목)가 빨라짐 — 읽을 바이트가 줄어서
- 같은 GPU에서 KV 캐시에 쓸 공간이 늘어 더 큰 배치 가능

**종류**

- **가중치 전용 양자화(W4A16 등):** 가중치만 낮은 비트, 계산은 FP16. 메모리·디코드 가속에 효과적. GPTQ, AWQ, GGUF 형식.
- **가중치+활성화 양자화(W8A8, FP8):** 행렬곱 자체를 낮은 정밀도로 → 연산 속도도 향상(지원 하드웨어 필요).
- **KV 캐시 양자화:** 긴 컨텍스트에서 메모리 절약.
- **학습 후 양자화(PTQ) vs 양자화 인식 학습(QAT).**

**주의:** 품질 영향은 모델·작업·방법에 따라 다르므로 반드시 평가셋으로 확인합니다. 특히 수학·코드·긴 추론에서 저하가 먼저 나타나는 경우가 많습니다.

<details>
<summary><b>Q10. 학습 후 양자화(PTQ)와 양자화 인식 학습(QAT)을 비교해 설명하세요. 가중치를 2~4비트까지 낮추면 무엇이 깨지나요?</b></summary>

**PTQ (Post-Training Quantization)**

- 학습이 끝난 모델을 **추가 학습 없이** 양자화합니다.
- 소량의 보정 데이터(calibration data)로 값 범위를 측정하거나, 오차를 최소화하는 방향으로 가중치를 조정합니다.
- 대표 방법: **GPTQ**(층별로 양자화 오차를 2차 정보로 보정), **AWQ**(활성화가 큰 중요 채널을 보호), SmoothQuant(활성화 이상치를 가중치 쪽으로 옮김), GGUF k-quants.
- 장점: 빠르고 싸며 원본 학습 파이프라인이 필요 없음. LLM 실무의 주류.

**QAT (Quantization-Aware Training)**

- 학습(또는 파인튜닝) 중에 순전파에서 **양자화를 흉내(fake quantization)** 내고, 역전파는 근사(straight-through estimator)로 처리합니다.
- 모델이 양자화 오차에 적응하도록 학습되어, 같은 비트 수에서 PTQ보다 품질이 좋습니다.
- 단점: 학습 비용과 데이터가 필요합니다. 극저비트(2~4비트)나 품질이 중요한 배포에서 씁니다.

| | PTQ | QAT |
|---|---|---|
| 추가 학습 | 없음 (보정만) | 필요 |
| 비용 | 낮음 | 높음 |
| 8비트 품질 | 거의 무손실 | 무손실 |
| 4비트 품질 | 대체로 양호 | 더 좋음 |
| 2~3비트 품질 | 크게 저하 | 상대적으로 버팀 |

**2~4비트에서 무엇이 깨지나**

- **이상치(outlier) 문제:** LLM에는 값이 매우 큰 소수의 가중치·활성화 채널이 있습니다. 적은 단계로 넓은 범위를 표현하면 작은 값들이 거의 0으로 뭉개지거나 이상치가 잘립니다.
- **오차 누적:** 층마다 작은 오차가 쌓여 긴 생성에서 문맥 일관성이 무너집니다.
- **먼저 나빠지는 능력:** 수학·다단계 추론, 코드 정확성, 긴 컨텍스트 활용, 사실 회상, 저자원 언어, 지시 따르기의 세밀함. 일반 대화 품질은 상대적으로 오래 유지되어 저하를 놓치기 쉽습니다.
- **작은 모델일수록 민감:** 큰 모델은 중복성이 커 저비트에서도 잘 버티는 경향이 있습니다.

**대응:** 그룹 크기 줄이기, 혼합 정밀도(민감한 층은 높은 비트), 이상치 처리 기법, QAT 또는 양자화 후 짧은 파인튜닝, 작업별 평가.

<summary><b>Q11. 프로덕션의 LLM 애플리케이션을 어떻게 모니터링하나요?</b></summary>

**모니터링 영역**

1. **운영 지표**
   - 지연: TTFT, 전체 응답 시간, 토큰 간 지연 (p50/p95/p99)
   - 처리량, 오류율(제공사 오류, 타임아웃, 429), 폴백 발생률
   - 자체 호스팅: GPU 사용률, KV 캐시 사용률, 대기열 길이
2. **비용**
   - 요청별 입력·출력·캐시 토큰, 기능·사용자·모델별 비용, 캐시 적중률
3. **품질**
   - 자동 평가: 프로덕션 트레이스 샘플을 LLM 판정자로 채점(관련성, 충실도, 형식 준수)
   - 사용자 신호: 좋아요/싫어요, 재생성, 복사, 대화 중단, 같은 질문 반복, 상담원 이관
   - 작업 지표: 해결률, 전환율
4. **안전**
   - 가드레일 차단 건수, 프롬프트 인젝션 탐지, PII 노출, 정책 위반 응답
5. **RAG·에이전트 특화**
   - 검색 결과 수·점수 분포, "답 없음" 비율, 도구 호출 실패율, 에이전트 단계 수·루프 발생

**구현**

- **트레이싱:** 요청 하나의 전체 경로(프롬프트, 검색, 도구 호출, 모델 응답)를 스팬으로 기록. OpenTelemetry 기반 또는 LangSmith, Langfuse, Arize Phoenix 같은 LLM 관측 도구.
- **로그 정책:** 민감 정보 마스킹, 보존 기간, 접근 권한.
- **대시보드와 알림:** 지연·오류·비용 급증, 품질 점수 하락, 안전 이벤트에 알림.

**개선 루프:** 낮은 점수·부정 피드백 사례를 정기적으로 검토 → 원인 분류 → 평가셋에 추가 → 수정 → 회귀 테스트.

<summary><b>Q12. LLM 관측 가능성(observability)이란 무엇인가요?</b></summary>

**관측 가능성** 은 시스템의 외부 출력(로그, 지표, 트레이스)을 보고 **내부에서 무슨 일이 일어났는지, 왜 그런 결과가 나왔는지를 이해할 수 있는 능력** 입니다. LLM 애플리케이션에서는 일반적인 모니터링보다 훨씬 중요합니다.

**왜 LLM에서 특히 중요한가**

- 출력이 확률적이라 같은 입력도 결과가 다를 수 있습니다.
- 실패 원인이 여러 계층에 있습니다: 프롬프트, 검색 결과, 도구 응답, 모델 버전, 컨텍스트 압축.
- 에이전트는 수십 단계를 거치므로 어디서 잘못됐는지 기록 없이는 알 수 없습니다.
- "오류가 없는데 답이 틀린" 조용한 실패가 많습니다.

**구성 요소**

1. **트레이스:** 요청 하나를 루트로, 그 아래 LLM 호출·검색·도구 호출·하위 에이전트를 스팬으로 기록. 각 스팬에 입력, 출력, 모델, 파라미터, 토큰, 지연, 비용.
2. **지표:** 지연, 오류율, 토큰·비용, 품질 점수, 사용자 피드백 집계.
3. **로그·이벤트:** 가드레일 차단, 폴백, 예외.
4. **평가 연결:** 트레이스에 자동 평가 점수와 사용자 피드백을 붙여, "어떤 유형의 요청에서 품질이 낮은지" 분석.
5. **세션·사용자 단위 묶음:** 멀티턴 대화와 에이전트 작업 전체를 한 흐름으로 보기.

**활용**

- 특정 실패를 재현하고 원인 단계 파악
- 프롬프트·모델 변경 전후 비교
- 비용이 큰 요청·단계 찾기
- 프로덕션 실패 사례를 평가셋으로 수집

**도구:** LangSmith, Langfuse, Arize Phoenix, Helicone, Datadog·New Relic의 LLM 기능, OpenTelemetry GenAI 시맨틱 규약.

<summary><b>Q13. LLM 가드레일이란 무엇이며, 어떻게 구현하나요?</b></summary>

**가드레일** 은 LLM의 입력과 출력을 검사·제어해 **안전하지 않거나, 범위를 벗어나거나, 정책을 어기는 동작을 막는 보호 장치** 입니다.

**가드레일 종류**

| 위치 | 검사 내용 |
|---|---|
| **입력** | 유해 요청, 프롬프트 인젝션·탈옥, 서비스 범위 밖 주제, PII 입력, 과도한 길이 |
| **검색·도구 결과** | 간접 인젝션, 민감 문서 노출 |
| **행동(에이전트)** | 위험한 도구 호출, 권한 밖 작업, 금액·범위 한도 |
| **출력** | 유해 콘텐츠, PII·비밀 유출, 환각(근거 없는 주장), 형식 위반, 경쟁사 언급 등 비즈니스 규칙 |

**구현 방법**

1. **규칙 기반:** 정규식(카드번호, 주민번호), 금칙어, 길이 제한, 스키마 검증. 빠르고 결정적.
2. **분류 모델:** 유해성·인젝션·주제 분류기(Llama Guard, 콘텐츠 안전 API, 자체 학습 모델). 대량·저지연 처리.
3. **LLM 판정자:** 복잡한 정책 판단, 근거 충실도 검사. 정확하지만 느리고 비쌈 → 필요한 경우에만.
4. **프레임워크:** NeMo Guardrails, Guardrails AI 등.

**설계 고려 사항**

- **지연:** 입력 검사는 LLM 호출과 병렬로 실행하고, 위반 시 응답을 취소하는 방식으로 지연을 숨길 수 있습니다. 스트리밍 출력은 문장 단위로 검사합니다.
- **오탐 관리:** 너무 엄격하면 정상 요청까지 막아 사용자 경험이 나빠집니다. 정책별 정밀도·재현율을 측정합니다.
- **위반 시 동작:** 차단, 수정(마스킹), 안전한 대체 응답, 사람에게 이관.
- **계층화:** 하나의 가드레일에 의존하지 않고 여러 겹으로.

<summary><b>Q14. AI 출력에 대한 콘텐츠 필터링을 어떻게 구현하나요?</b></summary>

**1. 정책 정의**

- 무엇을 막을지 범주별로 정의합니다: 혐오·괴롭힘, 성적 콘텐츠, 폭력, 자해, 불법 행위 조언, 개인정보, 의료·법률·금융 조언 범위, 브랜드 규칙.

```
LLM 출력 → [규칙 필터: PII 정규식, 금칙어, URL 허용 목록]

        → [애매한 경우 LLM 판정자: 정책 문서 기반 판단]

```

- 토큰 단위 스트리밍 중에는 문장 또는 일정 길이 단위로 버퍼링해 검사한 뒤 내보냅니다.

**4. 예방 조치와 결합**

- 시스템 프롬프트에 정책을 명시해 애초에 위반 출력이 덜 나오게 합니다.
- 입력 필터로 위험 요청을 미리 차단합니다.

**5. 운영**

- 필터 결과 로그(차단 사유, 점수)를 모아 오탐·미탐을 분석합니다.
- 범주별 평가셋(안전한데 막히기 쉬운 사례 포함)으로 정기 측정.
- 새 우회 패턴이 발견되면 규칙·분류기 업데이트.
- 사용자 신고 기능으로 미탐 수집.

**주의:** 의료 정보 제공처럼 맥락에 따라 허용되는 내용도 있으므로, 단순 키워드 차단보다 맥락을 이해하는 분류기·판정자를 함께 씁니다.

<summary><b>Q15. AI 기반 기능을 프로덕션에서 운영하는 비용을 어떻게 추정하나요?</b></summary>

**1. 요청당 비용 계산**

```
요청당 LLM 비용 = (입력 토큰 - 캐시 토큰) × 입력 단가
               + 캐시 토큰 × 캐시 단가
               + 출력 토큰(추론 토큰 포함) × 출력 단가
```

- 입력 토큰 = 시스템 프롬프트 + 도구 정의 + 대화 기록 + 검색 컨텍스트 + 사용자 입력
- 에이전트는 단계 수만큼 호출이 반복되고, 매번 누적된 컨텍스트가 다시 입력되므로 **단계 수 × 평균 컨텍스트** 로 계산해야 합니다.
- 기타: 임베딩, 리랭커, 가드레일 모델, 음성(ASR/TTS), 이미지 생성 비용.

**2. 사용량 추정**

- 사용자 수 × 사용자당 일 요청 수 × 30일
- 프로토타입·베타의 실제 로그에서 요청당 토큰 분포(평균뿐 아니라 p95)를 측정해 사용합니다. 추정보다 실측이 훨씬 정확합니다.

**3. 인프라 비용**

- 벡터 DB(저장·메모리), 캐시, 로그·트레이스 저장, 서버
- 자체 호스팅이면 GPU 시간 × 필요 인스턴스 수(피크 기준 + 여유)

**4. 운영 비용**

- 평가(판정 LLM 호출), 사람 검토·라벨링, 모니터링 도구

**예시 계산**

- 일 10만 요청, 요청당 입력 3,000토큰(그중 2,000 캐시) + 출력 400토큰
- 단가를 입력 $X, 캐시 0.1X, 출력 4X(백만 토큰당)로 두면 → 요청당 비용과 월 비용을 이 공식으로 산출
- 실제 단가는 모델·제공사마다 다르므로 최신 가격표로 계산합니다.

**5. 민감도 분석과 최적화 여지**

- 사용량 2배, 컨텍스트 길이 증가, 에이전트 단계 증가 시나리오를 계산합니다.
- 라우팅(소형 모델 비율), 캐싱, 프롬프트 축소, 배치 API 적용 시 절감 효과를 함께 제시합니다.

<summary><b>Q16. 프로덕션에서 LLM 추론 비용을 어떻게 최적화하나요?</b></summary>

**1. 토큰 줄이기**

- 프롬프트 정리(중복 지시 제거), 퓨샷 예시 최소화·동적 선택

**5. 자체 호스팅 시**

- 연속 배칭으로 GPU 사용률 극대화, 양자화(FP8/INT4), 추측 디코딩
- 예약 인스턴스·스팟 인스턴스, 오토스케일링으로 유휴 GPU 최소화
- 작업에 특화된 작은 모델 파인튜닝·증류로 대형 모델 대체

**6. 측정과 거버넌스**

- 기능·사용자별 비용 대시보드, 예산 알림, 이상 사용 탐지
- 모든 최적화는 **품질 평가와 함께** 진행(비용 절감이 품질 저하로 이어지지 않는지)

<summary><b>Q17. LLM 시스템의 A/B 테스트를 어떻게 구현하나요?</b></summary>

**무엇을 비교하나:** 모델(제공사·버전), 프롬프트, RAG 설정(청크, 검색기, 리랭커), 에이전트 구조, 샘플링 파라미터, UI.

**구현 절차**

1. **오프라인 평가 먼저:** 평가셋에서 새 버전이 기존보다 나쁘지 않은지 확인한 뒤 온라인 실험으로 갑니다. 위험한 변경이 실제 사용자에게 바로 가지 않게 합니다.
2. **트래픽 분할:** 사용자 ID 해시로 그룹을 고정 배정합니다(같은 사용자가 대화 중 버전이 바뀌지 않게). 처음엔 5~10%처럼 작게.
3. **실험 설정 관리:** 버전별 설정(모델, 프롬프트 버전 등)을 기능 플래그·실험 플랫폼으로 관리하고, 모든 로그에 실험 그룹을 기록합니다.
4. **지표 정의**
   - **주 지표:** 작업 성공률, 해결률, 전환율 같은 비즈니스 지표
   - **품질 지표:** 좋아요/싫어요 비율, 재생성률, 자동 평가 점수, 이관률
   - **가드레일 지표:** 지연, 비용, 오류율, 안전성 위반 — 이것들이 나빠지면 실험 중단
5. **통계적 판단:** 필요한 표본 크기를 미리 계산하고, 충분히 모인 뒤 유의성을 검정합니다. LLM 출력은 분산이 커서 생각보다 많은 표본이 필요할 수 있습니다.
6. **결과 분석:** 전체 평균뿐 아니라 사용자 세그먼트·요청 유형별로 나눠 봅니다(어떤 유형에서는 좋아지고 다른 유형에서는 나빠질 수 있음).

**LLM 특화 주의점**

- 사용자 피드백 비율이 낮아 신호가 희박하므로, 암묵적 신호(복사, 재질문, 이탈)와 자동 평가를 함께 씁니다.
- 신기함 효과(novelty effect)를 고려해 충분한 기간 실행합니다.
- 비용 차이도 결과에 포함해 "품질 대비 비용"으로 판단합니다.

<summary><b>Q18. AI 애플리케이션의 CI/CD란 무엇이며, 기존 CI/CD와 어떻게 다른가요?</b></summary>

**기존 CI/CD:** 코드 변경 → 빌드 → 단위·통합 테스트(결정적, 통과/실패) → 배포.

**AI 애플리케이션 CI/CD의 차이**

| 측면 | 기존 | AI 애플리케이션 |
|---|---|---|
| 변경 대상 | 코드 | 코드 + **프롬프트, 모델 버전, RAG 데이터·인덱스, 도구 정의, 파라미터** |
| 테스트 성격 | 결정적, 통과/실패 | 확률적, **점수 기반**(평가셋 정확도, 판정 점수) |
| 테스트 비용 | 거의 없음 | LLM 호출 비용·시간 발생 |
| 회귀 판단 | 테스트 실패 | 점수가 기준선 대비 일정 이상 하락 |
| 외부 변화 | 의존성 버전 | 제공사가 모델을 바꾸면 코드 변경 없이도 동작이 바뀜 |

**AI CI 파이프라인 구성**

1. **빠른 결정적 테스트:** 코드 단위 테스트, 프롬프트 템플릿 렌더링, 스키마 검증, 모의(mock) LLM 응답으로 로직 테스트.
2. **평가 스위트 실행:** 프롬프트·모델·검색 설정 변경 시 평가셋을 실제 LLM으로 실행해 점수 계산. 비용을 고려해 PR에서는 소규모 핵심 세트, 머지 전·야간에는 전체 세트.
3. **품질 게이트:** 주요 지표가 기준선 대비 일정 임계값 이상 떨어지면 배포 차단. 반복 실행해 분산 고려.
4. **안전성 테스트:** 탈옥·인젝션·유해 요청 세트.
5. **비용·지연 측정:** 변경이 토큰 사용량이나 지연을 크게 늘리지 않는지.

**CD (배포)**

- 프롬프트·설정은 코드와 같은 버전 관리, 배포 단위를 명확히
- 카나리·점진적 배포, 온라인 지표 모니터링, 자동 롤백
- RAG 인덱스 변경은 블루-그린 전환
- 모델 제공사 버전 고정, 새 버전은 평가 후 전환

**지속 평가:** 배포 후에도 프로덕션 샘플을 정기 평가해, 코드 변경 없이 생기는 품질 변화(모델 업데이트, 데이터 변화)를 감지합니다.

</details>

<summary><b>Q19. 프로덕션에서 프롬프트를 어떻게 버전 관리하나요?</b></summary>

**원칙:** 프롬프트는 **코드와 같은 수준의 자산** 입니다. 한 줄 수정이 품질과 비용을 크게 바꿀 수 있으므로 변경 이력, 리뷰, 테스트, 롤백이 필요합니다.

**방법 1: 코드 저장소에서 관리**

- 프롬프트를 별도 파일(YAML, Jinja, 마크다운)로 Git에 저장
- PR 리뷰 + CI 평가 게이트를 거쳐 배포
- 장점: 코드와 함께 버전이 묶여 재현성이 좋음. 단점: 비개발자가 수정하기 어렵고 배포 주기에 묶임

**방법 2: 프롬프트 관리 플랫폼(레지스트리)**

- Langfuse, LangSmith, PromptLayer 같은 도구나 자체 레지스트리에 프롬프트를 버전별로 저장
- 앱은 `get_prompt("support-agent", label="production")`처럼 **라벨** 로 불러옴
- 장점: 코드 배포 없이 프롬프트 변경·롤백, 비개발자 협업, 실험 관리. 단점: 런타임 의존성(캐시·폴백 필요)

**어느 방식이든 지켜야 할 것**

- **불변 버전:** 한 번 배포된 버전은 수정하지 않고 새 버전을 만듭니다.
- **메타데이터:** 작성자, 변경 이유, 대상 모델, 파라미터(온도 등), 평가 결과를 함께 기록.
- **프롬프트 + 모델 + 파라미터를 한 묶음으로:** 같은 프롬프트도 모델이 바뀌면 동작이 다르므로 함께 버전 관리합니다.
- **로그 연결:** 모든 요청 로그에 사용된 프롬프트 버전을 기록해 문제를 재현할 수 있게 합니다.
- **평가 게이트:** 새 버전은 평가셋 점수가 기준 이상일 때만 production 라벨을 받습니다.
- **점진적 배포와 롤백:** 일부 트래픽에 새 버전 적용 → 지표 확인 → 확대, 문제 시 라벨을 이전 버전으로 되돌림.

</details>

<details>
<summary><b>Q20. 모델 버전 관리란 무엇이며, 모델 롤백은 어떻게 처리하나요?</b></summary>

**모델 버전 관리** 는 서비스에 쓰이는 모델(외부 API 모델 ID, 자체 학습·파인튜닝 모델 가중치, LoRA 어댑터, 임베딩 모델)을 식별 가능한 버전으로 관리하고, 언제 어떤 버전이 서비스되었는지 추적하는 것입니다.

**외부 API 모델**

- 별칭(`latest`) 대신 **날짜·버전이 고정된 모델 ID** 를 사용해 제공사가 조용히 모델을 바꾸지 않게 합니다.
- 제공사의 지원 종료(deprecation) 일정을 추적하고, 새 버전은 평가 후 전환합니다.

**자체 모델**

- **모델 레지스트리**(MLflow, Hugging Face Hub 비공개 저장소, 클라우드 레지스트리)에 가중치와 메타데이터를 저장합니다: 기반 모델, 학습 데이터 버전, 하이퍼파라미터, 평가 결과, 학습 코드 커밋.
- 단계 라벨(staging, production)로 배포 상태를 관리합니다.

**배포와 롤백 전략**

1. **블루-그린:** 새 버전을 별도 인스턴스에 띄우고 트래픽을 한 번에 전환. 롤백은 트래픽을 이전 인스턴스로 되돌리기만 하면 됩니다(이전 인스턴스를 일정 기간 유지).
2. **카나리:** 트래픽의 일부만 새 버전으로 보내고, 지표가 나빠지면 자동으로 되돌립니다.
3. **설정 기반 전환:** 게이트웨이나 기능 플래그에서 모델 ID를 바꾸는 방식이면 롤백이 설정 변경 하나로 끝납니다.

**롤백 시 주의할 점**

- **연관 구성 요소를 함께 되돌리기:** 모델에 맞춰 바꾼 프롬프트, 출력 파서, 임베딩 모델과 벡터 인덱스는 짝을 맞춰 함께 롤백해야 합니다. 특히 임베딩 모델을 롤백하면 이전 인덱스도 함께 필요합니다.
- **롤백 판단 기준을 미리 정의:** 오류율, 지연, 품질 점수, 사용자 피드백 임계값.
- **롤백 리허설:** 실제로 빠르게 되돌릴 수 있는지 정기적으로 확인합니다.

</details>

<summary><b>Q21. LLM API의 속도 제한(rate limiting)과 스로틀링을 어떻게 구현하나요?</b></summary>

**두 방향의 속도 제한**

1. **우리 서비스가 사용자에게 거는 제한** (남용 방지, 공정한 자원 배분, 비용 통제)
2. **우리가 LLM 제공사로부터 받는 제한** (RPM, TPM 한도) 안에서 요청을 관리

**1. 사용자 대상 제한 구현**

- **측정 단위:** 요청 수(RPM)와 **토큰 수(TPM)** 를 함께. LLM은 요청마다 비용 차이가 커서 토큰 기준이 중요합니다.
- **알고리즘:** 토큰 버킷(일정 속도로 충전, 버스트 허용) 또는 슬라이딩 윈도우.
- **토큰 예약과 정산:** 요청 시작 시 `입력 토큰 + max_tokens`를 예상 비용으로 차감하고, 완료 후 실제 사용량으로 정산합니다.
- **분산 저장소:** 여러 서버에서 공유하도록 Redis 등에 카운터 저장(원자적 연산).
- **계층:** 사용자, API 키, 조직, 요금제별 한도. 동시 요청 수 제한도 함께.
- **응답:** 429와 `Retry-After`, 남은 한도 헤더.

**2. 제공사 한도 관리 (스로틀링)**

- **중앙 대기열:** 모든 LLM 호출을 게이트웨이의 대기열로 모아 제공사 한도에 맞춰 내보냅니다.
- **우선순위 스케줄링:** 실시간 사용자 요청 > 백그라운드 배치 작업. 배치 작업은 여유가 있을 때 처리.
- **429 대응:** 지수 백오프 + 지터로 재시도, 반복되면 다른 리전·제공사로 폴백.
- **용량 확보:** 한도 상향 요청, 여러 계정·리전 분산, 예약 용량(provisioned throughput) 구매.

**3. 사용자 경험**

- 제한에 걸렸을 때 명확한 안내, 요금제 업그레이드 경로.
- 클라이언트 SDK에 재시도 로직 내장.

**모니터링:** 429 발생률, 대기열 대기 시간, 한도 사용률을 대시보드로 보고 용량 계획에 반영합니다.

</details>

<details>
<summary><b>Q22. 다운타임 없이 모델 업데이트와 마이그레이션을 어떻게 처리하나요?</b></summary>

**1. 사전 준비**

- 새 모델을 평가셋으로 검증(품질, 형식 준수, 안전성, 지연, 비용).
- 새 모델에 맞게 프롬프트·파서를 조정하고, 이전 모델과 새 모델 각각에서 동작하는지 확인합니다(모델마다 같은 프롬프트에 다르게 반응).
- 새 모델의 용량(GPU 또는 API 한도)을 미리 확보합니다.

**2. 무중단 전환 방식**

- **블루-그린:** 새 모델 서빙 환경을 완전히 준비한 뒤 로드 밸런서·게이트웨이에서 트래픽을 전환. 이전 환경은 롤백용으로 유지.
- **카나리·점진적 롤아웃:** 1% → 10% → 50% → 100%로 트래픽을 옮기며 지표 확인. 이상 시 자동 롤백.
- **섀도 테스트:** 실제 트래픽을 새 모델에도 복제해 보내고(사용자에게는 이전 모델 응답) 결과를 비교. 위험 없이 실제 분포로 검증.
- **롤링 업데이트(자체 호스팅):** 인스턴스를 하나씩 교체하되, 모델 로딩 시간 동안 용량이 부족하지 않게 여유 인스턴스를 먼저 띄웁니다.

**3. 진행 중인 요청 처리**

- 스트리밍·장시간 요청이 끝날 때까지 기존 인스턴스를 유지하는 연결 드레이닝(draining).
- 멀티턴 대화는 세션 단위로 같은 모델을 유지하거나, 대화 기록이 모델 간에 호환되는지 확인합니다.

**4. 임베딩 모델 마이그레이션 (특수 사례)**

- 벡터 공간이 바뀌므로 새 인덱스를 미리 전부 구축하고, 질의 모델과 인덱스를 함께 전환합니다. 전환 기간에는 이중 쓰기.

**5. 사후 관리**

- 전환 후 일정 기간 품질·지연·비용·사용자 피드백 모니터링.
- 이전 모델 자원 정리는 안정화 확인 후.

</details>

<summary><b>Q23. AI 배포에서 기능 플래그(feature flag)는 어떤 역할을 하나요?</b></summary>

**기능 플래그** 는 코드 배포 없이 런타임 설정으로 기능을 켜고 끄거나, 대상 사용자를 바꾸는 장치입니다. AI 기능은 불확실성이 커서 특히 유용합니다.

**AI 배포에서의 역할**

1. **점진적 출시:** 새 AI 기능을 내부 직원 → 베타 사용자 → 일부 비율 → 전체로 확대.
2. **즉시 차단(킬 스위치):** 환각·안전 문제·비용 폭증 발견 시 몇 초 만에 기능을 끄거나 이전 동작으로 되돌림.
3. **모델·프롬프트 전환:** 플래그 값으로 사용할 모델 ID, 프롬프트 버전, RAG 설정을 지정해 코드 변경 없이 교체.
4. **A/B 실험:** 사용자 그룹별로 다른 설정을 적용하고 지표 비교.
5. **세그먼트별 제어:** 요금제, 지역(규제), 고객사별로 다른 모델이나 기능 제공.
6. **비용·부하 관리:** 피크 시간에 비싼 기능(추론 모델, 긴 컨텍스트)을 일시적으로 제한.
7. **우아한 성능 저하:** 장애 시 AI 기능을 끄고 비AI 대체 경로로 전환.

**구현 시 주의**

- 플래그 평가 결과를 요청 로그에 기록해 어떤 설정으로 응답했는지 추적합니다.
- 오래된 플래그는 정리합니다(조합이 많아지면 테스트가 어려워짐).
- 플래그 변경 권한과 변경 이력(감사 로그)을 관리합니다.
- 플래그 서비스 장애 시 안전한 기본값으로 동작하게 합니다.

</details>

<summary><b>Q24. LLM 애플리케이션의 로깅과 트레이싱을 어떻게 구현하나요?</b></summary>

**무엇을 기록하나 (LLM 호출 단위)**

- 요청 ID, 사용자·세션 ID(가명), 타임스탬프
- 모델·제공사, 프롬프트 템플릿 이름·버전, 파라미터(온도, max_tokens)
- 입력 메시지와 출력(민감 정보 마스킹 후), 도구 호출과 결과
- 토큰 수(입력, 출력, 캐시), 비용, 지연(TTFT, 전체), 종료 이유
- 오류·재시도·폴백 정보, 가드레일 결과

**트레이싱 구조**

```
Trace: 사용자 요청 1건
 ├─ Span: 입력 가드레일
 ├─ Span: 질문 재작성 (LLM)
 ├─ Span: 하이브리드 검색 (검색어, 결과 문서 ID·점수)
 ├─ Span: 리랭킹
 ├─ Span: 답변 생성 (LLM)
 │    └─ Span: 도구 호출 get_order
 └─ Span: 출력 가드레일
```

- 에이전트는 루프 단계마다 스팬을 만들고, 서브에이전트는 하위 트레이스로 연결합니다.

**구현 방법**

- **OpenTelemetry** 로 계측하고, GenAI 시맨틱 규약에 맞춰 속성 이름을 통일하면 도구 간 이동이 쉽습니다.
- LLM 관측 도구(Langfuse, LangSmith, Arize Phoenix 등)의 SDK나 프레임워크 자동 계측을 사용합니다.
- 게이트웨이에서 공통 필드를 자동으로 기록하면 앱마다 구현할 필요가 줄어듭니다.

**운영 정책**

- **개인정보:** PII 마스킹, 민감 기능은 내용 대신 메타데이터만 기록하는 옵션, 접근 권한 제한
- **보존 기간과 샘플링:** 전체 메타데이터는 모두, 전체 내용은 샘플링·기간 제한
- **피드백 연결:** 사용자 피드백·자동 평가 점수를 트레이스 ID에 연결

**활용:** 실패 재현, 느린 단계 찾기, 비용 분석, 평가셋 수집, 사고 조사.

**더 읽어보기 (영문):** [AI Agent Observability](https://outcomeschool.com/blog/ai-agent-observability)

<details>
<summary><b>Q25. LLM의 입력과 출력에 포함된 개인 식별 정보(PII)와 민감 데이터를 어떻게 처리하나요?</b></summary>

**위험 지점**

- 사용자 입력에 포함된 PII가 외부 LLM 제공사로 전송됨
- 로그·트레이스·평가 데이터·캐시에 PII가 저장됨
- 모델 출력에 다른 사람의 PII가 노출됨(RAG 문서, 학습 데이터 암기)
- 파인튜닝 데이터에 PII가 포함됨

**처리 방법**

1. **데이터 최소화:** 작업에 필요하지 않은 개인정보는 애초에 프롬프트에 넣지 않습니다.
2. **탐지:** 정규식(전화번호, 이메일, 카드번호, 주민번호) + NER 모델(이름, 주소) + 전용 도구(Microsoft Presidio, 클라우드 DLP 서비스).
3. **가명화·마스킹**
   - 전송 전 `홍길동 → [PERSON_1]`처럼 치환하고, 매핑은 서버에 보관해 응답에서 다시 복원(되돌릴 수 있는 가명화).
   - 복원이 필요 없으면 완전 마스킹.
4. **출력 검사:** 응답에 PII가 포함되었는지 검사하고, 권한 없는 사용자에게 노출되면 마스킹·차단.
5. **저장 정책:** 로그·트레이스에는 마스킹된 버전만, 보존 기간 설정, 암호화, 접근 권한 제한.
6. **제공사 계약·설정:** 학습 데이터로 사용하지 않는 조건(zero data retention 옵션 등), 데이터 처리 지역, 데이터 처리 계약(DPA).
7. **민감 작업은 내부 처리:** 규제가 엄격한 데이터는 자체 호스팅 모델로 내부에서 처리.
8. **사용자 권리 대응:** 삭제 요청 시 대화 기록, 메모리, 캐시, 로그에서 모두 삭제할 수 있는 구조.

**주의:** 마스킹이 과하면 모델이 작업을 못 할 수 있습니다(예: 이름이 중요한 문서 요약). 작업별로 필요한 정보 수준을 정의하고 품질을 평가합니다.

</details>

<details>
<summary><b>Q26. LLM API 관리를 위한 게이트웨이 패턴이란 무엇인가요?</b></summary>

**게이트웨이 패턴** 은 애플리케이션이 LLM 제공사를 직접 호출하지 않고, **모든 LLM 호출이 하나의 중앙 프록시(게이트웨이)를 거치도록** 하는 아키텍처입니다.

```
앱 A ─┐
앱 B ─┼─> [LLM 게이트웨이] ─┬─> OpenAI
앱 C ─┘   (통합 API)        ├─> Anthropic
                            ├─> Google / Bedrock / Azure
                            └─> 자체 호스팅 vLLM
```

**게이트웨이가 제공하는 기능**

| 기능 | 설명 |
|---|---|
| 통합 API | 여러 제공사를 하나의 형식(보통 OpenAI 호환)으로 호출 |
| 라우팅 | 모델 별칭 → 실제 모델, 비용·지연·작업 유형에 따른 선택 |
| 신뢰성 | 재시도, 폴백, 서킷 브레이커, 타임아웃 |
| 보안 | 제공사 키 중앙 보관, 팀별 키 발급, 접근 정책 |
| 속도 제한·예산 | 팀·키별 RPM/TPM, 비용 한도 |
| 캐싱 | 정확 일치·시맨틱 캐시 |
| 가드레일 | PII 마스킹, 인젝션·유해 콘텐츠 필터 |
| 관측 | 모든 호출 로그, 토큰·비용, 지연 집계 |

**장점**

- 모델·제공사 교체가 앱 수정 없이 가능 (공급자 종속 완화)
- 조직 전체에 보안·비용 정책을 일관되게 적용
- 사용량과 비용이 한눈에 보임

**단점과 대응**

- 단일 장애 지점 → 다중화·오토스케일링
- 추가 지연 → 가볍게 구현(수 ms), 같은 리전 배치
- 제공사별 고유 기능(특수 파라미터) 지원이 늦을 수 있음 → 패스스루 옵션

**구현 예:** LiteLLM Proxy, Portkey, Kong AI Gateway, Cloudflare AI Gateway, 클라우드 제공사의 AI 게이트웨이 기능.

<summary><b>Q27. 토큰 스트리밍은 어떻게 동작하나요?</b></summary>

**토큰 스트리밍** 은 LLM이 응답 전체를 다 만들 때까지 기다리지 않고, **토큰이 생성되는 즉시 조금씩 클라이언트로 보내는** 방식입니다.

**왜 가능한가:** LLM은 자기회귀적으로 토큰을 하나씩 생성합니다. 각 토큰이 나오는 순간 이미 확정된 결과이므로 바로 보낼 수 있습니다.

**전송 흐름**

```
[추론 서버] 토큰 생성 → 디토크나이즈(조각을 텍스트로) → 이벤트로 전송
   → [게이트웨이/백엔드] 중계 (필요 시 가드레일 검사)
   → [클라이언트] 이벤트 수신 → 화면에 이어 붙여 렌더링
```

**프로토콜: SSE (Server-Sent Events)가 가장 흔함**

```
HTTP/1.1 200 OK
Content-Type: text/event-stream

data: {"delta": "안녕"}

data: {"delta": "하세요"}

data: [DONE]
```

- 하나의 HTTP 응답을 열어 두고 서버가 `data:` 줄을 계속 씁니다.
- 양방향 실시간 통신(음성, 협업)이 필요하면 WebSocket을 쓰기도 합니다.

**세부 사항**

- **토큰 ≠ 글자:** 한 토큰이 단어 조각이거나, 한글·이모지의 UTF-8 바이트가 여러 토큰에 걸칠 수 있어 디코딩 시 완성된 문자만 내보내도록 처리합니다.
- **도구 호출 스트리밍:** 함수 인자 JSON도 조각으로 스트리밍되므로 끝까지 모아 파싱합니다.
- **마지막 이벤트:** 종료 이유(`stop`, `length`)와 토큰 사용량 정보.

**효과:** 전체 생성 시간은 같아도 사용자는 첫 토큰부터 읽기 시작하므로 **체감 지연(TTFT)** 이 크게 줄어듭니다.

<summary><b>Q28. 실시간 AI 애플리케이션에서 스트리밍 응답을 어떻게 구현하나요?</b></summary>

**백엔드 (예: Python FastAPI + SSE)**

```python
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
import json

app = FastAPI()

@app.post("/chat")
async def chat(req: ChatRequest):
    async def event_stream():
        async for chunk in llm_client.stream(messages=req.messages):
            if chunk.text:
                yield f"data: {json.dumps({'delta': chunk.text})}\n\n"
        yield "data: [DONE]\n\n"
    return StreamingResponse(event_stream(), media_type="text/event-stream")
```

**프론트엔드**

- `fetch` + `ReadableStream`으로 읽거나(POST 지원), `EventSource`(GET 전용) 사용.
- 받은 조각을 상태에 이어 붙여 렌더링하고, 마크다운은 점진적으로 렌더링(미완성 코드 블록 처리).

**구현 시 고려 사항**

1. **중간 계층 버퍼링 끄기:** 프록시·로드 밸런서(Nginx 등)가 응답을 모아서 보내지 않도록 버퍼링 비활성화, 압축 설정 확인, 타임아웃 연장.
2. **취소 처리:** 사용자가 "중지"를 누르거나 연결이 끊기면 LLM 생성도 취소해 비용 낭비를 막습니다.
3. **오류 처리:** 스트림 중간 오류를 이벤트로 알리고, 클라이언트는 부분 응답을 표시하며 재시도 옵션 제공.
4. **가드레일:** 문장·문단 단위로 버퍼링해 검사 후 전송, 위반 시 중단·대체.
5. **구조화 출력:** JSON을 스트리밍할 때는 부분 JSON 파서로 점진적으로 UI를 채우거나, 완료 후 검증.
6. **도구 호출과 진행 상황:** 에이전트가 도구를 실행하는 동안 "검색 중…" 같은 상태 이벤트를 보내 사용자가 기다리는 이유를 알게 합니다.
7. **재연결:** 긴 응답은 이벤트 ID로 이어 받기(재개) 지원을 고려합니다.
8. **로깅:** 스트림이 끝난 뒤 전체 응답과 토큰 사용량을 한 번에 기록합니다.

**음성 등 초저지연:** 텍스트 스트림을 문장 단위로 끊어 TTS로 바로 넘기는 파이프라인 스트리밍.

<summary><b>Q29. vLLM은 어떻게 동작하나요?</b></summary>

**vLLM** 은 UC 버클리에서 시작된 오픈소스 LLM 추론·서빙 엔진으로, 높은 처리량과 메모리 효율로 가장 널리 쓰이는 서빙 엔진 중 하나입니다.

**핵심 기술**

1. **PagedAttention**
   - 운영체제의 가상 메모리처럼 KV 캐시를 **고정 크기 블록** 으로 나누고, 블록 테이블로 논리적 위치와 물리적 위치를 매핑합니다.
   - 시퀀스 길이를 미리 몰라도 필요할 때 블록을 할당하므로, 기존 방식의 메모리 낭비(최대 길이 예약, 단편화)가 거의 사라집니다.
   - 같은 프롬프트를 공유하는 요청(병렬 샘플링, 공통 시스템 프롬프트)은 블록을 공유합니다(copy-on-write).
2. **연속 배칭(continuous batching)**
   - 배치 전체가 끝나기를 기다리지 않고, 요청이 끝나는 즉시 대기 중인 요청을 배치에 넣습니다(반복 단위 스케줄링). GPU가 쉬는 시간이 줄어 처리량이 크게 오릅니다.
3. **최적화된 커널과 기능**
   - Flash Attention 계열 커널, CUDA 그래프
   - 프리픽스 캐싱, 청크 프리필, 추측 디코딩
   - 양자화(FP8, AWQ, GPTQ 등), 텐서·파이프라인 병렬화
   - 멀티 LoRA 서빙, 구조화 출력(가이드 디코딩)

**사용 방식**

```bash
vllm serve meta-llama/Llama-3.1-8B-Instruct --tensor-parallel-size 1
```

- OpenAI 호환 API 서버를 제공해 기존 클라이언트 코드를 그대로 쓸 수 있습니다.
- 오프라인 배치 추론용 Python API도 있습니다.

**강점:** 넓은 모델 지원, 쉬운 사용, 높은 처리량, 활발한 커뮤니티. 다양한 하드웨어(NVIDIA, AMD 등) 지원.

<summary><b>Q30. SGLang은 어떻게 동작하나요?</b></summary>

**SGLang** 은 LMSYS 팀 등이 개발한 오픈소스 LLM 서빙 프레임워크로, 특히 **프롬프트 앞부분을 공유하는 복잡한 워크로드**(멀티턴 대화, 에이전트, 퓨샷, 여러 단계 LLM 프로그램)에서 높은 성능을 냅니다.

**핵심 기술**

1. **RadixAttention (자동 프리픽스 캐시)**
   - 모든 요청의 KV 캐시를 **기수 트리(radix tree)** 구조로 저장합니다. 트리의 경로가 토큰 시퀀스에 대응합니다.
   - 새 요청이 오면 트리에서 가장 긴 공통 프리픽스를 찾아 그 KV 캐시를 재사용하고 나머지만 계산합니다.
   - LRU 방식으로 오래된 캐시를 정리하고, 캐시 적중을 높이도록 요청 순서를 스케줄링합니다.
   - 멀티턴 대화(이전 대화가 프리픽스), 같은 시스템 프롬프트, 트리 탐색형 추론에서 효과가 큽니다.
2. **구조화 출력 가속**
   - 압축된 유한 상태 기계로 JSON 스키마·정규식 제약 디코딩을 빠르게 처리합니다.
3. **효율적인 런타임**
   - 연속 배칭, 페이지 단위 KV 캐시, 청크 프리필, 추측 디코딩, 양자화, 텐서·데이터·전문가 병렬화
   - CPU 오버헤드를 줄인 스케줄러(GPU가 기다리지 않게)
4. **프런트엔드 언어(선택)**
   - 여러 LLM 호출, 분기, 병렬 생성을 파이썬으로 표현하는 DSL을 제공해 복잡한 LLM 프로그램을 효율적으로 실행합니다.

**사용:** OpenAI 호환 서버로 띄워 일반 API처럼 사용할 수 있습니다.

**강점:** 프리픽스 재사용이 많은 워크로드, 에이전트·구조화 출력, 대형 MoE 모델(DeepSeek 등) 서빙에서 높은 성능.

<summary><b>Q31. TensorRT-LLM은 어떻게 동작하나요?</b></summary>

**TensorRT-LLM** 은 NVIDIA가 만든 오픈소스 LLM 추론 최적화 라이브러리로, **NVIDIA GPU에서 최대 성능** 을 끌어내는 데 초점을 둡니다.

**동작 방식**

1. **모델 정의·변환:** Hugging Face 등의 모델 가중치를 TensorRT-LLM 형식으로 변환합니다(양자화 적용 가능).
2. **엔진 빌드(컴파일):** 대상 GPU, 배치 크기, 시퀀스 길이, 병렬화 설정에 맞춰 최적화된 **추론 엔진** 을 생성합니다.
   - 커널 퓨전(여러 연산을 하나의 GPU 커널로 합쳐 메모리 왕복 감소)
   - 해당 GPU 아키텍처에 맞춘 최적 커널 자동 선택
   - 최신 버전은 PyTorch 기반 워크플로도 제공해 컴파일 부담을 줄였습니다.
3. **런타임 실행:** 연속 배칭(in-flight batching), 페이지 단위 KV 캐시, 프리픽스 캐시 재사용, 청크 프리필, 추측 디코딩(드래프트 모델, Medusa, EAGLE 등).

**강점**

- **양자화 지원:** FP8, FP4(최신 GPU), INT8 SmoothQuant, INT4 AWQ/GPTQ, KV 캐시 양자화. Hopper·Blackwell 같은 최신 GPU의 저정밀도 텐서 코어를 적극 활용합니다.
- **멀티 GPU·멀티 노드:** 텐서·파이프라인·전문가 병렬화.
- **NVIDIA 생태계 통합:** Triton Inference Server, NIM, Dynamo와 연동.

**트레이드오프**

- NVIDIA GPU 전용입니다.
- 엔진 빌드·설정 과정이 vLLM보다 복잡하고, 모델·설정을 바꾸면 다시 빌드해야 할 수 있습니다.
- 새 모델 지원이 커뮤니티 엔진보다 늦을 수 있습니다.

**언제 쓰나:** NVIDIA GPU에서 지연·처리량을 극한까지 최적화해야 하는 대규모 프로덕션.

<summary><b>Q32. llama.cpp는 어떻게 일반 하드웨어에서 LLM을 실행하나요?</b></summary>

**llama.cpp** 는 C/C++로 작성된 오픈소스 LLM 추론 엔진으로, 고가의 데이터센터 GPU 없이 **노트북, 데스크톱, 맥, 휴대폰, CPU 서버** 에서 LLM을 실행할 수 있게 해 줍니다.

**핵심 기술**

1. **공격적인 양자화 + GGUF 형식**
   - 가중치를 2~8비트로 양자화(Q4_K_M, Q5_K_M, Q8_0 등)해 메모리를 크게 줄입니다. 7~8B 모델이 약 4~5GB로 줄어 일반 노트북 메모리에 들어갑니다.
   - **GGUF:** 가중치, 토크나이저, 모델 설정을 하나의 파일에 담는 형식. 메모리 매핑(mmap)으로 빠르게 로딩합니다.
2. **하드웨어별 최적화 백엔드**
   - CPU: AVX2/AVX-512(x86), NEON(ARM) SIMD 명령으로 행렬 연산 가속, 멀티스레드
   - Apple Silicon: Metal GPU + 통합 메모리 활용 (맥에서 큰 모델도 실행 가능한 이유)
   - NVIDIA(CUDA), AMD(ROCm/HIP), Vulkan, SYCL 등
3. **부분 오프로딩**
   - GPU 메모리가 부족하면 일부 층만 GPU에 올리고 나머지는 CPU에서 실행합니다(`-ngl` 옵션).
4. **최소 의존성**
   - 무거운 프레임워크(PyTorch) 없이 단일 실행 파일로 동작해 다양한 기기에 이식하기 쉽습니다.

**왜 일반 하드웨어에서 빠른가:** LLM 디코딩은 메모리 대역폭 병목이므로, 양자화로 읽을 데이터 양을 줄이는 것이 속도에 직결됩니다.

**기능:** OpenAI 호환 서버(`llama-server`), 문법 기반 구조화 출력, 임베딩, 멀티모달 일부 지원. Ollama, LM Studio 같은 도구가 llama.cpp를 기반으로 합니다.

**한계:** 대규모 동시 사용자 서빙의 처리량은 vLLM 같은 GPU 서버 엔진보다 낮습니다. 개인용·엣지·소규모 배포에 적합합니다.

<summary><b>Q33. Ollama는 어떻게 동작하나요?</b></summary>

**Ollama** 는 로컬 컴퓨터에서 LLM을 **설치하고 실행하기 쉽게 만든 도구** 입니다. 내부적으로 llama.cpp 계열 엔진을 사용하고, 그 위에 모델 관리와 API 서버를 편리하게 감싸 제공합니다.

**사용 경험**

```bash
ollama pull llama3.1      # 모델 다운로드
ollama run llama3.1       # 대화형 실행
```

**구성 요소**

1. **모델 레지스트리와 관리**
   - Docker 이미지처럼 모델을 이름과 태그로 받아오고(`pull`), 로컬에 저장합니다.
   - 모델은 양자화된 GGUF 가중치 + 설정(채팅 템플릿, 기본 파라미터)으로 구성됩니다.
2. **Modelfile**
   - 기반 모델, 시스템 프롬프트, 파라미터(온도, 컨텍스트 길이), 어댑터를 지정해 나만의 모델 변형을 만듭니다.
   ```
   FROM llama3.1
   SYSTEM "당신은 친절한 한국어 비서입니다."
   PARAMETER temperature 0.3
   ```
3. **로컬 서버**
   - 백그라운드 서버가 REST API(기본 포트 11434)와 OpenAI 호환 API를 제공해, 다른 앱·프레임워크(LangChain 등)에서 쉽게 연결합니다.
4. **자동 하드웨어 활용**
   - GPU(NVIDIA, AMD, Apple Metal)를 자동 감지하고, 메모리에 맞게 GPU/CPU 분할 실행합니다.
   - 요청이 오면 모델을 메모리에 로드하고, 일정 시간 사용하지 않으면 내립니다.

**장점:** 설치가 매우 쉽고, 오프라인·개인정보 보호, 개발·프로토타이핑에 편리.

**한계:** 다중 사용자 고처리량 프로덕션 서빙에는 vLLM·SGLang 같은 전용 엔진이 더 적합합니다.

**더 읽어보기 (영문):** [How does Ollama work?](https://outcomeschool.com/blog/how-does-ollama-work)

<summary><b>Q34. vLLM, SGLang, TensorRT-LLM 중 각각은 언제 선택하나요?</b></summary>

| 기준 | vLLM | SGLang | TensorRT-LLM |
|---|---|---|---|
| 강점 | 범용성, 넓은 모델 지원, 쉬운 사용, 큰 커뮤니티 | 프리픽스 재사용(RadixAttention), 구조화 출력, 에이전트·멀티턴, 대형 MoE | NVIDIA GPU에서 최고 수준 성능, 최신 저정밀도(FP8/FP4) 활용 |
| 하드웨어 | NVIDIA, AMD, 기타 다양 | NVIDIA, AMD 등 | NVIDIA 전용 |
| 설정 난이도 | 쉬움 | 쉬움~보통 | 보통~어려움 (엔진 빌드·튜닝) |
| 새 모델 지원 속도 | 빠름 | 빠름 | 상대적으로 늦을 수 있음 |
| 적합 워크로드 | 일반 채팅·API 서빙, 멀티 LoRA | 공통 프리픽스가 많은 대화·에이전트, 복잡한 LLM 프로그램, JSON 출력 다량 | 대규모 고정 모델 서빙, 지연·비용 극한 최적화 |

**선택 가이드**

- **기본값으로 시작:** 대부분의 팀은 vLLM이나 SGLang으로 시작합니다. 둘 다 OpenAI 호환 API를 제공해 교체가 비교적 쉽습니다.
- **SGLang을 고려할 때:** 멀티턴 대화, 같은 시스템 프롬프트·문서를 반복 사용, 에이전트 루프, 구조화 출력이 많을 때 캐시 재사용 이득이 큽니다.
- **TensorRT-LLM을 고려할 때:** NVIDIA GPU에 장기적으로 고정 투자하고, 특정 모델을 대규모로 서빙하며, 엔지니어링 투자로 GPU 비용을 줄일 수 있을 때. Triton·NIM 등 NVIDIA 스택과 통합할 때.

**가장 중요한 원칙: 내 워크로드로 직접 벤치마크**

- 엔진 간 성능 순위는 모델, GPU, 입력·출력 길이 분포, 동시성, 버전에 따라 자주 바뀝니다.
- 실제 트래픽과 비슷한 조건에서 TTFT, TPOT, 처리량, 비용을 측정해 결정합니다.

<summary><b>Q35. 프로덕션 AI 시스템의 핵심 SLA와 지표(지연 시간, 처리량, 가용성)는 무엇인가요?</b></summary>

**지연 시간 지표**

| 지표 | 의미 | 중요한 경우 |
|---|---|---|
| **TTFT** (Time To First Token) | 요청부터 첫 토큰까지 | 채팅, 음성 등 대화형 UX |
| **TPOT / ITL** (토큰당 출력 시간, 토큰 간 지연) | 토큰 하나 생성에 걸리는 시간 | 스트리밍 읽기 속도 (사람 읽기 속도보다 빨라야 함) |
| **E2E 지연** | 전체 응답 완료까지 | 비스트리밍 API, 에이전트 작업 |
| **백분위수** | p50, p95, p99 | SLA는 평균이 아닌 꼬리 지연으로 정의 |

**처리량 지표**

- 초당 요청 수(RPS), 초당 생성 토큰 수(전체·사용자당), 동시 처리 가능 세션 수
- **굿풋(goodput):** SLO를 만족한 요청만 센 처리량 — 지연을 무시하고 처리량만 높이면 의미가 없기 때문

**가용성·신뢰성**

- 가용성(성공 응답 비율, 예: 99.9%), 오류율(5xx, 타임아웃, 429), 폴백 발생률

**비용 지표**

- 요청당·사용자당·작업당 비용, 백만 토큰당 비용, GPU 사용률

**품질 지표 (AI 특화 SLO)**

- 자동 평가 점수, 사용자 만족도, 작업 성공률, 환각률, 가드레일 위반률

**SLA/SLO 설정 예시**

- "채팅 API: 월 가용성 99.9%, TTFT p95 < 1.5초, 토큰 간 지연 p95 < 80ms"
- "배치 문서 처리: 24시간 내 완료율 99%"

**운영:** SLO별 오류 예산(error budget)을 두고, 예산을 다 쓰면 기능 출시보다 안정성 작업을 우선합니다. 대시보드와 알림을 SLO에 맞춰 구성합니다.

**하이브리드 (가장 흔한 실무 구성)**

- 기기에서 간단한 작업·전처리·라우팅을 하고, 어려운 요청만 클라우드로 보냅니다.

<summary><b>Q37. 주 모델을 사용할 수 없거나 속도 제한에 걸렸을 때의 폴백 전략을 어떻게 구현하나요?</b></summary>

**폴백 체인 정의**

```python
FALLBACKS = [
    {"provider": "A", "model": "large-v2", "region": "us"},
    {"provider": "A", "model": "large-v2", "region": "eu"},     # 같은 모델, 다른 리전
    {"provider": "B", "model": "comparable-large"},             # 다른 제공사 동급
    {"provider": "self-hosted", "model": "open-8b"},           # 기능 축소
]
```

**트리거 조건**

- 5xx 오류, 연결 실패, 타임아웃(짧게 설정: 예를 들어 TTFT 기준 수 초)
- 429(속도 제한): 짧은 재시도 후에도 지속되면 다음 후보로
- 품질 이상(빈 응답, 형식 오류 반복)

**구현 요소**

1. **재시도 정책:** 같은 대상에 지수 백오프 + 지터로 1~2회, 이후 폴백.
2. **서킷 브레이커:** 특정 제공사 오류율이 임계치를 넘으면 일정 시간 아예 호출하지 않고 바로 폴백(장애 중 대기 시간 누적 방지). 반개방 상태에서 일부 요청으로 회복 확인.
3. **모델별 프롬프트 어댑터:** 모델마다 형식·도구 호출 방식·잘 따르는 지시가 다르므로, 폴백 모델용 프롬프트와 파서를 미리 검증해 둡니다.
4. **기능 매트릭스:** 폴백 모델이 지원하지 않는 기능(이미지 입력, 긴 컨텍스트, 특정 도구)은 요청 단위로 확인해 적절히 축소하거나 거절.
5. **헤지 요청(선택):** 지연이 중요한 요청은 일정 시간 응답이 없으면 두 번째 제공사에도 동시에 요청.
6. **상태 일관성:** 스트리밍 도중 실패하면 처음부터 폴백 모델로 다시 생성하거나, 부분 응답 처리 정책을 정합니다.

**구현 위치:** LLM 게이트웨이(LiteLLM 등)에 두면 모든 앱이 같은 정책을 씁니다.

**검증과 모니터링**

- 장애 주입 테스트로 폴백이 실제로 동작하는지 정기 확인
- 폴백 발생률, 폴백 모델의 품질 점수, 비용 변화를 모니터링

<summary><b>Q38. 프로덕션에서 LLM의 구조화 출력을 어떻게 안정적으로 구현하나요?</b></summary>

**계층별 방법 (강한 순서)**

1. **스키마 강제 디코딩**
   - API의 구조화 출력 기능(JSON 스키마 지정, strict 모드)이나 도구 호출 스키마를 사용합니다. 스키마에 맞지 않는 토큰이 생성되지 않으므로 파싱 실패가 사실상 없어집니다.
   - 자체 호스팅: vLLM·SGLang의 가이드 디코딩(XGrammar, Outlines 등).
2. **스키마 설계**
   - 단순하고 평탄한 구조, enum으로 허용 값 제한, 필드 설명 추가.
   - 모델이 추론해야 한다면 `reasoning` 필드를 **결과 필드보다 앞에** 두어 먼저 생각하고 답하게 합니다.
   - 선택 필드와 null 허용을 명확히.
3. **검증 계층**
   - Pydantic 등으로 타입·범위·비즈니스 규칙(합계 일치, 날짜 순서)까지 검증.
   - 스키마 강제로는 "형식"만 보장되고 "내용 정확성"은 보장되지 않기 때문입니다.
4. **재시도·복구**
   - 검증 실패 시 오류 메시지를 넣어 재요청(최대 횟수 제한), 계속 실패하면 폴백 모델이나 사람 검토로.
5. **프롬프트 보조**
   - 필드별 작성 규칙과 예시 출력, 낮은 온도.

```python
class Invoice(BaseModel):
    vendor: str
    total: Decimal
    currency: Literal["KRW", "USD", "EUR"]
    due_date: date | None

resp = client.responses.parse(model=MODEL, input=doc_text, text_format=Invoice)
invoice = resp.output_parsed     # 스키마 보장 + Pydantic 검증
```

**운영**

- 파싱 성공률, 검증 실패 유형, 재시도율을 모니터링합니다.
- 모델·프롬프트 변경 시 형식 준수율을 회귀 테스트에 포함합니다.

<summary><b>Q39. 프로덕션에서 긴 컨텍스트를 효율적으로 처리하려면 어떻게 하나요(컨텍스트 압축, 프리픽스 캐싱)?</b></summary>

**긴 컨텍스트의 비용:** 입력 토큰 비용, TTFT 증가(프리필), KV 캐시 메모리, 그리고 중간 정보 누락 같은 품질 문제.

**1. 프리픽스(프롬프트) 캐싱 — 반복되는 긴 컨텍스트**

- 같은 문서·시스템 프롬프트·도구 정의를 여러 요청이 공유하면 KV 캐시를 재사용해 비용과 TTFT를 크게 줄입니다.
- 설계: 고정 부분을 앞에, 가변 부분을 뒤에. 앞부분에 타임스탬프·요청 ID 같은 가변 값을 넣지 않기.
- 멀티턴 대화·에이전트 루프는 이전 기록이 자연스럽게 프리픽스가 되어 효과가 큽니다.

**2. 컨텍스트 압축 — 쌓이는 긴 컨텍스트**

- **요약:** 오래된 대화·작업 기록을 요약으로 교체(핵심 결정·목표·미해결 사항 보존).
- **정리:** 처리 끝난 큰 도구 결과(파일 내용, 로그)를 짧은 메모로 대체.
- **선택적 포함:** RAG로 관련 부분만 넣기, 리랭킹 후 상위만.
- **프롬프트 압축 기법:** 중요도가 낮은 토큰을 제거하는 방법(LLMLingua 등)도 있지만 품질 검증이 필요합니다.

**3. 구조적 접근**

- 서브에이전트로 대량의 내용을 별도 컨텍스트에서 처리하고 요약만 받기.
- Map-reduce로 청크별 처리 후 종합.

**4. 서빙 측 최적화 (자체 호스팅)**

- 청크 프리필, Flash Attention, KV 캐시 양자화, GQA 모델 선택, 긴 요청과 짧은 요청 분리 서빙.

**선택 기준**

- 같은 컨텍스트를 반복 사용 → 캐싱
- 컨텍스트가 계속 쌓임 → 압축
- 컨텍스트가 거대하지만 일부만 필요 → 검색

<summary><b>Q40. 시맨틱 라우팅(semantic routing)이란 무엇이며, 멀티 모델 시스템에서 어떻게 구현하나요?</b></summary>

**시맨틱 라우팅** 은 요청의 **의미(의도, 주제, 난이도)** 를 파악해 가장 적합한 모델·프롬프트·파이프라인으로 보내는 기법입니다.

**목적**

- **비용 절감:** 쉬운 요청은 작고 싼 모델로
- **품질 향상:** 코드는 코딩 특화 모델, 수학은 추론 모델, 특정 도메인은 파인튜닝 모델로
- **기능 분기:** FAQ는 캐시·검색, 주문 문의는 도구가 있는 에이전트, 잡담은 간단한 응답

**구현 방법**

1. **임베딩 유사도 라우터**
   - 각 경로(route)마다 대표 예시 문장을 여러 개 등록하고 임베딩합니다.
   - 요청 임베딩과 가장 비슷한 경로를 선택(유사도가 임계값 이하이면 기본 경로).
   - 매우 빠르고 싸며 구현이 간단합니다.
2. **분류 모델**
   - 라벨된 요청 데이터로 작은 분류기(BERT 계열, 로지스틱 회귀)를 학습합니다.
3. **LLM 라우터**
   - 작은 LLM이 요청을 보고 경로·난이도를 판단합니다. 유연하지만 지연이 추가됩니다.
4. **학습된 품질 예측 라우터**
   - "이 요청을 작은 모델이 잘 처리할 확률"을 예측해, 일정 이상이면 작은 모델로 보냅니다(RouteLLM 같은 접근).
5. **캐스케이드**
   - 작은 모델이 먼저 답하고, 확신도가 낮거나 검증에 실패하면 큰 모델로 다시 요청합니다.

```
요청 → [라우터] ─ "간단 FAQ"     → 캐시/소형 모델
               ─ "코드 질문"     → 코딩 모델
               ─ "복잡한 분석"   → 대형 추론 모델
               ─ "주문/계정"     → 도구 에이전트
```

**운영**

- 라우팅 결정을 로그에 남기고, 경로별 품질·비용을 모니터링합니다.
- 잘못 라우팅된 사례(작은 모델이 실패한 경우)를 모아 라우터를 재학습합니다.

**더 읽어보기 (영문):** [LLM Routing](https://outcomeschool.com/blog/llm-routing)

<summary><b>Q41. LLM 애플리케이션에서 시크릿과 API 키를 어떻게 안전하게 관리하나요?</b></summary>

**기본 원칙**

- **코드·저장소에 절대 넣지 않기:** 하드코딩, `.env` 파일 커밋 금지. 커밋 전 비밀 스캔(gitleaks, GitHub secret scanning).
- **시크릿 관리 서비스 사용:** AWS Secrets Manager, GCP Secret Manager, Azure Key Vault, HashiCorp Vault. 런타임에 주입하고 접근 권한을 서비스 단위로 최소화.
- **로테이션:** 주기적 교체와 유출 의심 시 즉시 폐기·재발급 절차.

**LLM 애플리케이션 특유의 위험과 대응**

1. **프롬프트에 비밀을 넣지 않기**
   - 시스템 프롬프트·컨텍스트에 API 키, DB 비밀번호, 내부 토큰을 넣으면 프롬프트 인젝션으로 유출될 수 있습니다. 모델은 비밀을 "볼 필요가 없게" 설계합니다.
2. **도구 실행 계층에서만 자격 증명 사용**
   - 에이전트가 API를 호출할 때 모델은 도구 이름과 인자만 출력하고, 실제 인증은 서버의 도구 실행 코드가 시크릿 저장소에서 가져와 처리합니다.
3. **사용자 대신 행동할 때는 위임 토큰**
   - OAuth로 받은 사용자 범위의 짧은 수명 토큰을 사용하고, 서비스 전체 권한 키를 쓰지 않습니다.
4. **LLM 제공사 키 중앙화**
   - 게이트웨이만 제공사 키를 보유하고, 각 앱·팀에는 내부 키를 발급해 사용량 추적·회수가 쉽게 합니다.
5. **로그·트레이스 마스킹**
   - 요청 헤더, 도구 인자, 출력에서 비밀 패턴을 마스킹합니다.
6. **샌드박스·코드 실행 환경**
   - 에이전트가 코드를 실행하는 환경에는 시크릿을 두지 않고, 필요하면 범위가 제한된 임시 자격 증명만 제공합니다.
7. **클라이언트 측 노출 금지**
   - 브라우저·모바일 앱에 LLM API 키를 넣지 말고 반드시 백엔드를 거칩니다.

**탐지:** 출력 가드레일로 키 형식의 문자열 유출을 차단하고, 키 사용량 이상 패턴을 모니터링합니다.

<summary><b>Q42. LLM API의 지연 시간이 피크 시간대에 급증합니다. 어떻게 안정화하나요?</b></summary>

**먼저 원인 위치를 구분합니다**

- **제공사 측:** 제공사의 피크 혼잡(다른 고객과 공유 자원), 대기열
- **우리 측:** 게이트웨이·대기열 적체, 동시성 제한, 네트워크
- **요청 특성:** 피크 시간에 긴 프롬프트·긴 출력 요청이 몰림
- **자체 호스팅:** GPU 용량 부족, KV 캐시 포화로 배치가 줄거나 요청이 대기

**안정화 방법**

1. **용량 확보**
   - 제공사의 예약 처리량(provisioned throughput, 전용 용량) 구매로 공유 혼잡 회피
   - 여러 리전·제공사로 부하 분산
   - 자체 호스팅: 피크 전 예측 기반 사전 증설, 대기열 길이 기반 오토스케일링
2. **부하 줄이기**
   - 프롬프트 캐싱과 시맨틱 캐시로 실제 모델 호출·연산량 감소
   - 프롬프트·출력 길이 최적화
   - 쉬운 요청은 작은·빠른 모델로 라우팅
3. **트래픽 형태 조정**
   - 우선순위 대기열: 실시간 사용자 요청 우선, 배치·백그라운드 작업은 비피크 시간이나 배치 API로 이동
   - 요청 시간 분산(예약 작업이 정각에 몰리지 않게)
4. **지연 꼬리 줄이기**
   - 타임아웃 + 헤지 요청(일정 시간 지나면 다른 경로에도 요청)
   - 자체 호스팅: 청크 프리필, 프리필-디코드 분리
5. **사용자 경험 보호**
   - 스트리밍, 진행 상태 표시, 지연이 클 때 기능 축소 모드

**모니터링:** 시간대별 TTFT·E2E p95/p99, 제공사별 지연, 대기열 대기 시간을 분리해서 보면 원인을 빨리 찾습니다.

<summary><b>Q43. 모델은 그대로인데 배포 후 LLM 엔드포인트의 p99 지연 시간이 두 배가 되었습니다. 어떻게 진단하나요?</b></summary>

**1. 변경 사항 확인 (가장 먼저)**

- 이번 배포의 diff: 코드, 프롬프트 템플릿, 설정(max_tokens, 온도), 라이브러리·서빙 엔진 버전, 인프라(인스턴스 유형, 리전), 기능 플래그.
- 가능하면 즉시 롤백해 지연이 돌아오는지 확인하면 원인 범위가 확정됩니다.

**2. 지연을 단계별로 분해**

- 트레이스로 게이트웨이 → 전처리 → 검색 → LLM 호출(TTFT, 생성 시간) → 후처리 각 구간 비교.
- **TTFT가 늘었나?** → 입력이 길어졌거나 캐시가 깨졌을 가능성
- **생성 시간이 늘었나?** → 출력이 길어졌거나 디코드 속도 저하
- **LLM 밖 구간이 늘었나?** → 새 가드레일, 추가 검색, 동기 로깅, 직렬화된 호출

**3. 흔한 원인 체크리스트**

- **프롬프트 캐시 깨짐:** 프롬프트 앞부분에 타임스탬프·사용자 ID·무작위 순서가 들어가 캐시 적중률이 급락. 캐시 적중률 지표를 확인합니다.
- **입력 토큰 증가:** 검색 문서 수 증가, 대화 기록 정리 로직 버그, 도구 정의 추가.
- **출력 토큰 증가:** 프롬프트 변경으로 응답이 장황해짐, max_tokens 상향, 추론 예산 증가.
- **직렬화:** 병렬이던 호출이 순차로 바뀜, 재시도 증가.
- **자체 호스팅:** 서빙 엔진 설정 변경(배치 크기, 청크 프리필 비활성화), 양자화 해제, GPU 메모리 설정, 인스턴스 수 감소, CUDA 그래프 비활성화.
- **라우팅 변경:** 트래픽이 다른 리전·제공사로 감.
- **p99만 늘었다면:** 일부 요청 유형(아주 긴 입력)이나 콜드 스타트, 재시도 꼬리, 가비지 컬렉션 등 간헐적 원인.

**4. 검증**

- 배포 전후 버전을 같은 요청 세트로 부하 테스트해 재현합니다.
- 원인을 고친 뒤 지연 회귀를 CI·카나리 단계에서 잡도록 성능 테스트를 추가합니다.

**4. 거버넌스**

- 기능별 예산과 알림, 비용 대시보드, 새 기능의 비용 검토.
- 비용 절감 조치마다 품질 지표(평가 점수, 사용자 피드백)를 함께 모니터링해 "보이지 않는 품질 저하"를 막습니다.

<summary><b>Q45. 애플리케이션이 피크 시간대에 LLM 제공업체의 속도 제한에 걸립니다. 어떻게 처리하나요?</b></summary>

**즉시 대응**

1. **올바른 재시도:** 429 응답의 `Retry-After`를 존중하고, 지수 백오프 + 지터로 재시도. 모든 클라이언트가 동시에 재시도해 더 악화시키는 상황(thundering herd)을 막습니다.
2. **클라이언트 측 스로틀링:** 제공사 한도(RPM, TPM)를 미리 알고, 게이트웨이에서 한도를 넘지 않도록 요청 속도를 조절합니다. 한도에 부딪힌 뒤 대응하는 것보다 효율적입니다.

**구조적 해결**

1. **우선순위 대기열**
   - 실시간 사용자 요청 > 내부 도구 > 배치 작업. 배치는 비피크 시간이나 배치 API로 이동.
2. **한도 늘리기**
   - 제공사에 한도 상향 요청(사용량 등급 상승), 예약 처리량 구매.
   - 여러 리전·배포(예: 클라우드 제공사의 여러 리전 엔드포인트)·계정으로 분산.
3. **다중 제공사 폴백**
   - 한도에 걸리면 다른 제공사의 동급 모델로 넘김(프롬프트 호환성 사전 검증).
4. **토큰 사용량 줄이기**
   - TPM 한도라면 입력·출력 토큰을 줄이는 것이 곧 처리량 증가입니다: 프롬프트 캐싱(일부 제공사는 캐시 토큰을 한도 계산에서 다르게 취급), 컨텍스트 축소, 출력 제한.
   - 시맨틱 캐시로 호출 자체를 줄이기.
5. **작은 모델 라우팅**
   - 모델별로 한도가 따로인 경우가 많아, 쉬운 요청을 다른 모델로 보내면 주 모델의 한도 여유가 생깁니다.

**모니터링:** 모델·제공사별 한도 사용률(%), 429 비율, 대기열 대기 시간을 추적해 한도 도달 전에 경고합니다.

<summary><b>Q46. 애플리케이션이 하나의 LLM 제공업체에 의존하고 있습니다. 다운타임 없이 제공업체를 어떻게 전환하나요?</b></summary>

**1. 추상화 계층 도입**

- 앱 코드에서 제공사 SDK를 직접 호출하지 않고, LLM 게이트웨이나 내부 클라이언트 인터페이스를 거치게 합니다(OpenAI 호환 형식 등).
- 메시지 형식, 도구 호출 형식, 스트리밍 이벤트, 오류 코드의 차이를 이 계층에서 변환합니다.

**2. 새 제공사 모델 검증**

- 평가셋으로 품질 비교(같은 프롬프트로 시작해 필요한 만큼 조정).
- **차이 점검 항목:** 도구 호출 형식과 신뢰성, 구조화 출력 지원, 컨텍스트 길이, 토크나이저(비용·한도 계산), 안전 정책(거절 경향), 지연, 가격, 데이터 처리 조건.
- 모델별 프롬프트 변형을 준비합니다.

**3. 점진적 전환**

1. **섀도 모드:** 실제 요청을 새 제공사에도 복제해 결과를 비교(사용자에게는 기존 응답).
2. **카나리:** 일부 트래픽(1% → 10% → 50%)을 새 제공사로. 품질·지연·오류·비용 지표 비교.
3. **전체 전환** 후에도 기존 제공사를 **폴백으로 유지** 합니다.

**4. 연관 요소 처리**

- **파인튜닝 모델:** 새 제공사에서 다시 학습하거나 오픈 모델로 이전.
- **프롬프트 캐싱 동작 차이:** 캐시 방식이 달라 비용이 달라질 수 있음.
- **진행 중인 대화:** 세션 단위로 같은 제공사를 유지하거나, 대화 기록 형식 호환 확인.

**5. 결과: 다중 제공사 구조**

- 전환이 끝나면 오히려 두 제공사를 모두 운영해 장애 대비·가격 협상력·특정 작업별 최적 모델 선택이 가능한 구조가 됩니다.

<summary><b>Q47. AI 시스템이 초당 100건의 요청은 처리하지만 5,000건에서는 다운됩니다. 동시 요청에 맞게 어떻게 확장하나요?</b></summary>

**1. 병목 찾기 (부하 테스트 + 프로파일링)**

- 요청 수를 단계적으로 올리며 어느 구성 요소가 먼저 포화되는지 확인합니다: API 서버 CPU·커넥션, 스레드 풀, DB·벡터 DB, 캐시, LLM 제공사 한도, GPU, 네트워크, 로깅 파이프라인.
- LLM 요청은 수 초~수십 초 동안 연결을 점유하므로 **동시 연결 수** 가 일반 웹 서비스보다 훨씬 큰 문제가 됩니다.

**2. 애플리케이션 계층**

- **비동기 I/O:** 요청마다 스레드를 막는 동기 호출 대신 async(예: Python asyncio)로 수천 개 동시 연결 처리.
- **무상태 서버 + 수평 확장:** 오토스케일링, 로드 밸런서.
- **커넥션 풀:** 제공사·DB 연결 재사용, 풀 크기 조정.
- **타임아웃·백프레셔:** 감당 못 할 요청은 빨리 거절(429)하거나 대기열로, 전체가 무너지지 않게.

**3. 비동기 작업 분리**

- 즉시 응답이 필요 없는 작업은 메시지 큐(SQS, Kafka) + 워커로 처리하고 결과는 나중에 전달.

**4. LLM 계층**

- 제공사 한도: 한도 상향, 예약 용량, 다중 리전·제공사 분산, 우선순위 대기열.
- 자체 호스팅: GPU 인스턴스 오토스케일링(웜 풀), 연속 배칭·양자화로 인스턴스당 처리량 증가.
- **호출량 줄이기:** 캐싱(시맨틱·프롬프트), 작은 모델 라우팅, 불필요한 호출 제거.

**5. 데이터 계층**

- 벡터 DB 레플리카·샤딩, 캐시(Redis) 앞단 배치, DB 읽기 복제본.

**6. 검증**

- 목표(5,000 RPS)의 1.5~2배로 부하 테스트, 장애 상황(인스턴스 다운, 제공사 지연) 포함.
- 용량 계획과 SLO 대시보드 운영.

<details>
<summary><b>Q48. 트래픽 급증으로 AI 시스템이 다운됩니다. 피크 트래픽을 어떻게 처리하나요?</b></summary>

**흡수(Absorb)**

- **오토스케일링:** 대기열 길이·지연 기반 스케일링. LLM 서빙 GPU는 기동이 느리므로 **웜 풀**(미리 띄운 대기 인스턴스)과 예측 기반 사전 증설(이벤트·마케팅 일정, 요일·시간 패턴).
- **여유 용량:** 평상시 사용률을 100%로 운영하지 않습니다.
- **버퍼링:** 메시지 큐로 급증한 요청을 받아 두고 처리 가능한 속도로 소비(비실시간 작업).

**제한(Shed)**

- **속도 제한:** 사용자·키별 한도로 남용·폭주 차단.
- **부하 차단(load shedding):** 시스템이 포화되면 우선순위가 낮은 요청부터 빠르게 거절해 핵심 요청을 보호합니다. 느리게 실패하는 것보다 빠르게 거절하는 것이 전체 붕괴를 막습니다.
- **우선순위:** 유료·핵심 기능 > 무료·부가 기능 > 백그라운드.

**경량화(Degrade)**

- 피크 시 더 작은 모델로 전환, 출력 길이 축소, 리랭킹·추가 검증 같은 비싼 단계 생략, 캐시 응답 우선.
- 부가 AI 기능(추천 문구, 자동 요약) 일시 중단 — 기능 플래그로 즉시 제어.

**분산(Distribute)**

- 여러 리전·제공사로 부하 분산, CDN·엣지 캐시(정적·반복 응답).

**보호(Protect)**

- 서킷 브레이커로 느려진 의존성이 전체를 끌어내리지 않게, 벌크헤드로 기능 간 자원 격리.
- 재시도 폭주 방지(지터, 재시도 예산).

**사후:** 장애 분석 후 용량 계획 수정, 정기 부하·장애 훈련.

</details>

<details>
<summary><b>Q49. LLM 제공업체 한 곳의 장애로 시스템 전체가 다운되었습니다. 단일 장애 지점(SPOF)을 어떻게 없애나요?</b></summary>

**1. 의존성 지도 그리기**

- 시스템의 모든 외부 의존성(LLM 제공사, 임베딩 API, 벡터 DB, 인증, 결제)과 각각이 멈추면 무엇이 멈추는지 정리합니다.

**2. LLM 계층 다중화**

- **다중 리전:** 같은 제공사라도 여러 리전 엔드포인트.
- **다중 제공사:** 동급 모델을 가진 두 번째 제공사를 폴백으로 준비하고 프롬프트를 미리 검증.
- **자체 호스팅 최후 수단:** 오픈 모델을 소규모로 운영해 핵심 기능만이라도 유지.
- **게이트웨이에서 자동 전환:** 헬스 체크, 서킷 브레이커, 폴백 체인.

**3. 임베딩·검색 의존성**

- 임베딩 API 장애 시 질의 임베딩이 불가 → 자체 호스팅 임베딩 모델(같은 모델)을 대비하거나, 키워드 검색으로 폴백.
- 벡터 DB 레플리카, 다중 AZ.

**4. 장애 격리**

- AI 기능 실패가 핵심 서비스(로그인, 결제, 일반 페이지)까지 막지 않도록 비동기 호출, 타임아웃, 벌크헤드, 독립 배포.
- 우아한 성능 저하: AI 기능 비활성화 시 대체 동작 제공.

**5. 운영 체계**

- 제공사 상태 모니터링(상태 페이지 구독 + 자체 합성 모니터링)
- 장애 시나리오 런북, 정기 장애 훈련(제공사 차단 상태에서 테스트)
- 폴백 경로의 품질·비용을 사전에 파악

**핵심 메시지:** "다중화는 준비된 상태여야 의미가 있다." 폴백 프롬프트·한도·권한·키가 평소에 검증되어 있지 않으면 장애 순간에 작동하지 않습니다.

</details>

<summary><b>Q50. 체인 안의 모델 하나가 고장 나면 멀티 LLM 파이프라인 전체가 실패합니다. 오케스트레이션 실패를 어떻게 처리하나요?</b></summary>

**원인:** 파이프라인이 단계별로 강하게 연결되어, 한 단계의 오류·지연·형식 오류가 그대로 전파됩니다.

**단계별 내결함성 설계**

1. **단계마다 실패 정책 정의**
   - **필수 단계** (예: 핵심 추출): 재시도 → 대체 모델 → 실패 시 명확한 오류 반환
   - **선택 단계** (예: 리랭킹, 요약 보강, 번역 다듬기): 실패하면 건너뛰고 계속 진행
2. **재시도와 폴백**
   - 일시적 오류는 백오프 재시도, 지속되면 대체 모델·대체 방법(규칙 기반)으로.
3. **단계 간 계약 검증**
   - 각 단계 출력을 스키마로 검증해, 잘못된 출력이 다음 단계로 넘어가 연쇄 오류를 일으키지 않게 합니다. 검증 실패는 해당 단계에서 재생성.
4. **타임아웃과 예산**
   - 단계별 타임아웃, 전체 파이프라인 시간·비용 예산.
5. **체크포인트와 재개**
   - 단계 결과를 저장해, 실패 시 처음부터가 아니라 실패한 단계부터 다시 실행합니다. 내구성 있는 워크플로 엔진(Temporal, Step Functions, LangGraph 체크포인터) 활용.
6. **멱등성**
   - 재실행해도 부작용(중복 이메일, 중복 저장)이 생기지 않도록 단계 설계.
7. **병렬화와 부분 결과**
   - 독립 단계는 병렬로 실행하고, 일부 실패해도 성공한 결과로 부분 응답을 만들 수 있게(예: 5개 문서 중 4개 요약 성공).
8. **실패 시 사람에게**
   - 자동 복구가 불가능하면 진행 상황과 함께 사람 검토 대기열로.

**관측:** 단계별 성공률·지연·재시도율을 대시보드로 보고, 트레이스로 실패 단계를 즉시 찾을 수 있게 합니다.

<summary><b>Q51. AI 파이프라인에서 어느 단계가 실패하는지 전혀 보이지 않습니다. 관측 가능성을 어떻게 추가하나요?</b></summary>

**1단계: 분산 트레이싱 도입**

- 요청마다 **트레이스 ID** 를 발급하고, 파이프라인의 모든 단계(LLM 호출, 검색, 도구, 후처리, 하위 에이전트)를 **스팬** 으로 기록합니다.
- 서비스 간 호출에도 트레이스 컨텍스트를 전파해 하나의 흐름으로 연결합니다.
- OpenTelemetry로 계측하거나, LLM 프레임워크의 자동 계측·LLM 관측 도구 SDK를 사용합니다.

**2단계: 스팬에 충분한 정보 기록**

- LLM: 모델, 프롬프트 버전, 입력·출력(마스킹), 토큰, 지연(TTFT 포함), 종료 이유, 오류
- 검색: 질의, 결과 수, 상위 문서 ID와 점수
- 도구: 이름, 인자, 결과 요약, 소요 시간, 오류
- 검증: 통과·실패 여부와 이유

**3단계: 지표와 대시보드**

- 단계별 성공률, 지연(p50/p95/p99), 재시도·폴백 비율, 토큰·비용
- 품질 신호: 자동 평가 점수, 사용자 피드백을 트레이스에 연결

**4단계: 알림**

- 단계별 오류율·지연 급증, 품질 점수 하락, 비용 급증에 알림.

**5단계: 디버깅 워크플로**

- 실패한 요청을 트레이스 ID로 찾아 어느 스팬에서 실패했는지 확인 → 해당 입력으로 재현 → 수정 → 평가셋에 추가.

**바로 적용할 수 있는 최소 버전:** 모든 로그에 요청 ID 포함 + 단계 시작·끝 로그 + LLM 호출 래퍼에서 공통 필드 자동 기록. 이것만으로도 "어디서 실패하는지"는 바로 보이기 시작합니다.

<summary><b>Q52. LLM을 양자화했더니 정확도가 크게 떨어졌습니다. 양자화 손실을 어떻게 최소화하나요?</b></summary>

**1. 진단**

- 어떤 작업에서 떨어졌는지 확인합니다(수학, 코드, 긴 컨텍스트, 특정 언어 등 민감한 작업이 먼저 나빠짐).
- 양자화 대상(가중치만? 활성화·KV 캐시까지?)과 비트 수, 방법, 그룹 크기를 확인합니다.
- 보정 데이터가 실제 사용 데이터와 비슷한지 확인합니다.

**2. 방법 개선**

- **비트 수 올리기:** INT4 → INT8 또는 FP8. 많은 경우 8비트는 거의 무손실입니다.
- **더 나은 PTQ 알고리즘:** 단순 반올림 대신 GPTQ, AWQ처럼 오차를 보정하는 방법.
- **그룹 크기 줄이기:** 그룹별 scale(예: 128 → 64)로 정밀도 향상(메모리 약간 증가).
- **보정 데이터 개선:** 실제 사용 분포(도메인, 언어, 길이)를 반영한 보정 세트 사용.
- **이상치 처리:** SmoothQuant(활성화 이상치를 가중치 쪽으로 이동), 회전 기반 기법 등으로 이상치 영향 완화.

**3. 혼합 정밀도**

- 민감한 층(첫·마지막 층, 어텐션 출력, LM head)은 높은 정밀도로 두고 나머지만 낮은 비트로.
- 가중치만 양자화하고 활성화·KV 캐시는 FP16 유지.

**4. 학습으로 보완**

- **QAT 또는 양자화 후 짧은 파인튜닝:** 양자화 오차에 모델이 적응하도록 학습.
- **QLoRA 방식:** 양자화된 기반 모델 위에 LoRA를 학습해 손실 회복.

**5. 모델 선택 재검토**

- 큰 모델을 강하게 양자화하는 것과 작은 모델을 덜 양자화하는 것을 같은 메모리 예산에서 비교합니다.

**검증:** 작업별 평가셋, 원본 대비 지표 차이를 측정해 허용 기준을 정합니다(일반 벤치마크만 보면 손실을 놓칠 수 있음).

**더 읽어보기 (영문):** [How does Model Quantization work?](https://outcomeschool.com/blog/how-does-model-quantization-work)

</details>

<details>
<summary><b>Q53. AI 컴포넌트 하나의 장애가 플랫폼 전체를 다운시킬 수 있습니다. 우아한 성능 저하(graceful degradation)를 어떻게 설계하나요?</b></summary>

**1. 의존성과 중요도 분류**

- 각 기능을 **핵심**(없으면 서비스 불가: 결제, 로그인)과 **부가**(있으면 좋음: AI 추천, 자동 요약, 챗봇)로 나눕니다.
- 부가 AI 기능이 핵심 흐름의 필수 경로에 들어 있지 않게 설계합니다.

**2. 격리 (장애가 퍼지지 않게)**

- **타임아웃:** AI 호출이 오래 걸려도 전체 요청이 막히지 않게 짧은 타임아웃.
- **서킷 브레이커:** 반복 실패하는 구성 요소 호출을 즉시 차단.
- **벌크헤드:** AI 기능용 스레드 풀·커넥션·인스턴스를 분리해 자원 고갈 전파 차단.
- **비동기 처리:** 응답에 꼭 필요하지 않은 AI 작업은 백그라운드로.

**3. 대체 동작 (기능별 폴백)**

| AI 기능 | 장애 시 대체 |
|---|---|
| AI 검색 | 키워드 검색 |
| 개인화 추천 | 인기 상품 목록 |
| 챗봇 | FAQ 페이지, 문의 접수, 상담원 연결 |
| 자동 분류 | 기본 대기열에 넣고 사람이 분류 |
| 요약 | 원문 표시 |
| 대형 모델 | 소형 모델 (복잡한 요청은 정중히 제한) |

**4. 제어와 소통**

- 기능 플래그·킬 스위치로 운영자가 즉시 저하 모드 전환.
- UI는 AI 영역 실패를 부분적으로 표시("추천을 불러올 수 없습니다")하고 나머지 화면은 정상 동작.
- 사용자에게 상황을 알리는 상태 안내.

**5. 검증**

- 각 AI 구성 요소를 일부러 끄는 장애 주입 테스트를 정기적으로 실행해 대체 동작과 격리를 확인합니다.
- 저하 모드에서의 핵심 지표(전환율, 오류율)를 측정해 대체 경로의 품질을 관리합니다.

</details>
