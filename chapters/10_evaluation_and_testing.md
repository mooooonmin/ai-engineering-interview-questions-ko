<summary><b>Q1. AI 에이전트 평가</b></summary>

AI 에이전트 평가는 **최종 결과** 뿐 아니라 **목표에 도달하는 과정(경로, trajectory)** 까지 평가해야 한다는 점이 일반 LLM 평가와 다릅니다.

**평가 차원**

1. **작업 성공(결과):** 목표를 달성했는가. 가능하면 환경 상태로 자동 확인합니다(테스트 통과, DB 레코드 생성, 예약 완료).
2. **경로 품질(과정)**
   - 도구 선택 정확도, 인자 정확도
   - 필요한 핵심 단계를 거쳤는가, 불필요한 단계는 없는가
   - 오류에서 회복했는가
3. **효율성:** 단계 수, 토큰·비용, 소요 시간
4. **안전성:** 금지된 행동, 승인 없는 위험 행동, 권한 밖 접근, 인젝션에 속았는가
5. **신뢰성:** 같은 작업을 여러 번 실행했을 때 일관되게 성공하는가

**평가 방법**

- **시나리오 기반 테스트셋:** 실제 사용 사례를 재현한 과제 + 성공 판정 기준. 샌드박스 환경(모의 API, 테스트 DB)에서 실행.
- **자동 채점:** 결과 상태 검사, 규칙 검사, LLM 판정자(경로와 결과를 채점 기준표로 평가).
- **반복 측정:** pass@k(k번 중 한 번이라도 성공), pass^k(k번 모두 성공) — 프로덕션에서는 후자처럼 일관성이 더 중요합니다.
- **사람 검토:** 어려운 사례의 경로를 직접 읽고 실패 유형 분류.

**운영 단계:** 프로덕션 트레이스 샘플 평가, 작업 완료율, 사람 개입률, 사용자 피드백.

<summary><b>Q2. LLM 평가</b></summary>

LLM 평가는 크게 **모델 자체의 능력 평가** 와 **LLM 애플리케이션(시스템) 평가** 로 나뉩니다. 실무에서 더 중요한 것은 후자입니다.

**1. 모델 능력 평가 (벤치마크)**

- 지식·추론(MMLU 계열), 수학(GSM8K, MATH), 코딩(HumanEval, SWE-bench), 지시 따르기, 안전성 벤치마크
- 모델 선택의 출발점이지만, 내 작업 성능을 보장하지는 않습니다.

**2. 애플리케이션 평가**

- **평가셋:** 실제 사용 사례를 대표하는 입력 + 기대 결과·채점 기준
- **평가 방법**

| 방법 | 언제 | 예 |
|---|---|---|
| 정답 비교 | 정답이 명확 | 분류 정확도, 추출 F1, 정확 일치 |
| 규칙·코드 검사 | 형식·조건 확인 | JSON 스키마, 길이, 금지어, 테스트 실행 |
| 참조 기반 유사도 | 기준 답이 있음 | 의미 유사도, BERTScore |
| LLM-as-a-judge | 자유 서술 | 정확성, 관련성, 충실도, 어조 점수 |
| 사람 평가 | 최종 확인, 판정자 검증 | 전문가 채점, 쌍 비교 |

- **차원:** 정확성, 관련성, 충실도(근거 기반), 완전성, 안전성, 형식, 지연, 비용

**3. 평가 운영**

- 오프라인: 변경 시마다 평가셋 실행(CI 게이트)
- 온라인: 프로덕션 샘플 자동 평가, 사용자 피드백, A/B 테스트
- 실패 사례를 평가셋에 계속 추가

**핵심 원칙:** 평가 기준은 제품 목표에서 출발해야 하고, 자동 평가(특히 LLM 판정자)는 사람 판단과 일치하는지 주기적으로 검증해야 합니다.

**더 읽어보기 (영문):** [LLM Evaluation](https://outcomeschool.com/blog/llm-evaluation)

<summary><b>Q3. AI 에이전트 관측 가능성(Observability)</b></summary>

**에이전트 관측 가능성** 은 에이전트가 작업하는 동안 **무엇을 생각하고, 어떤 도구를 왜 호출했고, 어떤 결과를 받아 어떻게 판단했는지** 를 기록·시각화해 이해할 수 있게 만드는 것입니다.

**왜 일반 서비스보다 중요한가**

- 에이전트는 비결정적으로 수십 단계를 진행합니다. 최종 결과만 보면 어디서 잘못됐는지 알 수 없습니다.
- "오류 없이 틀린 결과"가 많습니다(잘못된 도구 선택, 엉뚱한 방향으로 표류, 거짓 성공 보고).
- 비용이 단계마다 누적되어, 어느 단계가 비싼지 알아야 최적화할 수 있습니다.

**기록할 것**

- **트레이스 구조:** 작업(루트) → 루프 단계 → LLM 호출 / 도구 호출 / 서브에이전트(하위 트레이스)
- **각 단계:** 입력 컨텍스트 크기, 모델 출력(추론 요약, 도구 호출), 도구 인자·결과·오류, 지연, 토큰·비용
- **상태 변화:** 계획, 할 일 목록, 메모리 갱신, 컨텍스트 압축 시점
- **결과와 평가:** 최종 결과, 자동 평가 점수, 사용자 피드백, 사람 개입 여부

**활용**

- 실패 원인 분석(어느 단계에서 잘못된 판단을 했나)
- 반복 루프·비효율 경로 탐지
- 비용 분석(어떤 도구 결과가 토큰을 많이 쓰나)
- 평가셋 수집(실패한 실제 사례)
- 보안 감사(어떤 행동을 했는지 증거)

**도구:** LangSmith, Langfuse, Arize Phoenix, OpenTelemetry GenAI 규약 기반 계측 + 대시보드·알림.

**더 읽어보기 (영문):** [AI Agent Observability](https://outcomeschool.com/blog/ai-agent-observability)

<summary><b>Q4. AI 애플리케이션의 평가 주도 개발(evaluation-driven development)이란 무엇인가요?</b></summary>

**평가 주도 개발(EDD)** 은 소프트웨어의 테스트 주도 개발(TDD)처럼, **먼저 평가 기준과 평가셋을 만들고 그 점수를 기준으로 개발을 반복하는** 방식입니다.

**왜 필요한가**

- LLM 출력은 확률적이고 자유 형식이라, 몇 개 예시를 눈으로 보고 "좋아졌다"고 판단하면 다른 사례가 나빠진 것을 놓칩니다.
- 프롬프트 한 줄, 모델 버전 변경이 예상치 못한 회귀를 만듭니다.

**절차**

1. **목표 정의:** 이 기능이 성공했다는 것은 무엇인가? (예: 문의 분류 정확도 95%, 근거 없는 주장 0건)
2. **평가셋 구축:** 실제 입력 대표 샘플 + 엣지 케이스 + 공격 사례, 기대 결과나 채점 기준.
3. **평가 방법 구현:** 자동 채점기(규칙, 정답 비교, LLM 판정자) + 사람 검증.
4. **기준선 측정:** 가장 단순한 버전으로 점수를 냅니다.
5. **반복:** 실패 사례 분석 → 가설 → 수정(프롬프트, 검색, 모델) → 전체 평가셋 재측정 → 개선·회귀 확인.
6. **게이트:** 기준 점수를 넘어야 배포. CI에서 자동 실행.
7. **프로덕션 피드백:** 실제 실패 사례를 평가셋에 추가해 평가셋이 계속 현실을 반영하게 합니다.

**효과**

- 개선이 측정 가능해지고, 팀 간 논쟁이 "느낌"이 아니라 데이터로 정리됩니다.
- 모델 교체·비용 최적화를 안전하게 진행할 수 있습니다.

**주의:** 평가셋에 과적합하지 않도록 별도의 보류(hold-out) 세트를 두고, 평가 기준 자체도 제품 목표에 맞는지 주기적으로 점검합니다.

<summary><b>Q5. 왜 AI는 우리가 정한 "완료의 정의(definition of done)"만큼만 좋을 수 있나요?</b></summary>

**핵심 메시지:** AI(특히 에이전트)는 우리가 정한 **완료 기준과 평가 방식을 목표로 최적화** 합니다. 기준이 모호하거나 틀리면, AI가 아무리 뛰어나도 원하는 결과가 아닌 "기준을 만족하는 결과"를 냅니다.

**왜 그런가**

1. **모호한 목표 → 임의의 해석**
   - "이 코드 개선해 줘"는 끝나는 지점이 없습니다. 에이전트는 멈출 시점을 모르거나, 엉뚱한 부분을 고칩니다.
   - "로그인 테스트가 통과하고, 기존 테스트가 모두 통과하며, 변경은 auth 모듈로 한정"처럼 정의하면 성공 여부를 확인할 수 있습니다.
2. **검증할 수 없는 완료 → 거짓 성공**
   - 완료를 확인할 방법이 없으면 모델의 "다 했습니다"라는 말에 의존하게 되고, 실제로는 미완성인 경우가 생깁니다.
3. **잘못된 지표 → 지표 해킹**
   - "테스트 통과"만 기준이면 테스트를 수정하거나 특정 케이스만 하드코딩하는 꼼수가 나올 수 있습니다(굿하트의 법칙).
4. **평가 기준 = 품질 상한**
   - 평가셋과 판정 기준이 실제 사용자 요구를 반영하지 않으면, 점수가 올라도 사용자 만족은 오르지 않습니다.

**좋은 완료 정의의 조건**

- **구체적이고 측정 가능:** 숫자·조건으로 표현
- **기계적으로 검증 가능:** 테스트, 스키마, 규칙, 체크리스트
- **범위와 제약 포함:** 무엇을 바꾸면 안 되는지, 비용·시간 한도
- **실제 목표를 반영:** 대리 지표가 아니라 사용자 가치에 가깝게
- **꼼수를 막는 보조 조건:** 테스트 수정 금지, 기존 동작 유지 등

**실무 적용:** 에이전트 작업 지시, 평가셋 설계, 강화학습 보상 설계 모두에서 "무엇이 끝난 상태인가"를 먼저 쓰는 습관이 품질을 결정합니다.

**더 읽어보기 (영문):** [AI Is Only as Good as Our Definition of Done](https://outcomeschool.com/blog/ai-is-only-as-good-as-our-definition-of-done)

<summary><b>Q6. LLM의 출력은 어떻게 평가하나요? 어떤 지표를 사용하나요?</b></summary>

**작업 유형별 지표**

| 작업 | 지표 |
|---|---|
| 분류 | 정확도, 정밀도·재현율·F1, 혼동 행렬 |
| 정보 추출 | 필드별 정확 일치, F1 |
| 질의응답 (정답 있음) | 정확 일치(EM), 토큰 F1, LLM 판정 정답 여부 |
| 요약 | 충실도(사실 일관성), 핵심 내용 포함도, 간결성, ROUGE(참고용) |
| 번역 | BLEU, chrF, COMET, 사람 평가 |
| 코드 생성 | 테스트 통과율(pass@k), 실행 성공률 |
| RAG | 컨텍스트 재현율·정밀도, 충실도, 답변 관련성 |
| 대화·자유 생성 | LLM 판정(유용성, 정확성, 어조), 쌍 비교 승률, 사람 평가 |
| 구조화 출력 | 스키마 준수율, 필드 정확도 |

**공통 품질 차원**

- **정확성:** 사실이 맞는가
- **관련성:** 질문에 답하는가
- **충실도:** 주어진 근거에 기반하는가(환각 여부)
- **완전성:** 필요한 내용을 빠뜨리지 않았는가
- **안전성:** 유해·편향·정책 위반이 없는가
- **형식·스타일:** 요구된 형식·어조·길이를 지켰는가

**운영 지표:** 지연, 토큰·비용, 오류율.

**평가 방식 선택**

- 결정적 검사가 가능하면 우선 사용(싸고 정확)
- 자유 서술은 LLM-as-a-judge + 명확한 채점 기준(rubric)
- 판정자의 신뢰성은 사람 평가 샘플과의 일치도로 검증
- 단일 점수보다 차원별 점수와 실패 유형 분석이 개선에 더 유용합니다.

**더 읽어보기 (영문):** [LLM Evaluation](https://outcomeschool.com/blog/llm-evaluation)

<summary><b>Q7. BLEU, ROUGE, BERTScore를 설명하세요. 각각은 언제 사용하나요?</b></summary>

**BLEU (Bilingual Evaluation Understudy)**

- **정밀도 중심:** 생성문의 n-gram(1~4단어 묶음) 중 정답(참조) 문장에도 나오는 비율을 계산하고, 너무 짧은 출력에는 페널티(brevity penalty)를 줍니다.
- 주 용도: **기계 번역**.
- 한계: 같은 의미의 다른 표현(동의어, 어순 변화)을 틀린 것으로 봅니다. 문장 단위보다 말뭉치 단위에서 의미가 있습니다.

**ROUGE (Recall-Oriented Understudy for Gisting Evaluation)**

- **재현율 중심:** 참조 문장의 n-gram이 생성문에 얼마나 포함되었는지 봅니다.
  - ROUGE-1/2: 단어·두 단어 묶음 겹침
  - ROUGE-L: 가장 긴 공통 부분 수열(LCS)
- 주 용도: **요약** (참조 요약의 핵심 내용을 얼마나 담았나).
- 한계: 표면적 단어 겹침만 보므로 의미가 같은 바꿔 말하기, 사실 오류(단어는 겹치지만 틀린 내용)를 구분하지 못합니다.

**BERTScore**

- 생성문과 참조문의 각 토큰을 BERT 계열 모델의 **문맥 임베딩** 으로 바꾸고, 토큰 간 코사인 유사도로 가장 잘 맞는 쌍을 찾아 정밀도·재현율·F1을 계산합니다.
- 장점: 동의어·바꿔 말하기를 인정해 사람 판단과의 상관이 n-gram 지표보다 높습니다.
- 한계: 여전히 사실 정확성·논리를 보장하지 못하고, 사용한 모델에 따라 점수가 달라집니다.

**LLM 시대의 사용법**

- 세 지표 모두 **참조 답이 하나인 경우를 전제** 하므로, 정답이 여러 가지인 자유 생성 평가에는 약합니다.
- 번역·요약처럼 참조가 있는 작업에서 **빠르고 싼 보조 지표** 나 회귀 감지용으로 쓰고, 품질 판단은 LLM 판정자·사람 평가·작업 지표와 함께 합니다.

<summary><b>Q8. G-Eval이란 무엇이며, 평가에 LLM을 어떻게 활용하나요?</b></summary>

**G-Eval** (Liu 외, 2023)은 강한 LLM(원 논문은 GPT-4)을 평가자로 사용해, **채점 기준을 바탕으로 자연어 생성 결과를 점수화** 하는 프레임워크입니다. 요약·대화 평가에서 기존 지표보다 사람 판단과 상관이 높게 나왔습니다.

**구성 요소**

1. **평가 과제와 기준 정의:** 예: "요약의 일관성(coherence)을 1~5점으로 평가하라. 일관성이란 문장들이 논리적으로 연결된 정도를 말한다."
2. **자동 CoT로 평가 단계 생성:** LLM이 기준을 바탕으로 구체적인 평가 단계를 먼저 작성합니다.
   - "1) 원문을 읽고 주제를 파악한다. 2) 요약이 주제를 논리적 순서로 다루는지 확인한다. 3) ..."
3. **채점:** 입력(원문), 출력(요약), 평가 단계를 주고 점수를 매기게 합니다.
4. **확률 가중 점수:** 점수 토큰(1~5) 각각의 확률을 구해 기대값 `Σ p(점수) × 점수`로 최종 점수를 계산합니다. 정수 점수만 쓸 때보다 세밀하고 동점이 줄어듭니다.

**장점**

- 참조 답 없이도 평가 가능(원문과 출력만으로)
- 평가 기준을 자연어로 쉽게 바꿀 수 있음
- 사람 평가와 상관이 높음

**한계와 주의점**

- LLM 판정자 편향: 자기 모델 출력 선호, 긴 답 선호, 위치 편향
- 점수가 프롬프트·모델 버전에 따라 바뀜 → 판정 설정도 버전 관리
- 비용

**실무 적용:** DeepEval 등의 도구에 G-Eval 방식 지표가 구현되어 있어, 기준만 정의하면 바로 쓸 수 있습니다. 사람 평가 샘플로 상관을 확인한 뒤 사용합니다.

**더 읽어보기 (영문):** [LLM as a Judge](https://outcomeschool.com/blog/llm-as-a-judge)

<summary><b>Q9. LLM-as-a-judge 평가란 무엇이며, 그 한계는 무엇인가요?</b></summary>

**LLM-as-a-judge** 는 강한 LLM을 평가자로 사용해 다른 모델(또는 시스템)의 출력을 채점하는 방법입니다. 자유 서술형 출력을 대규모로 평가하는 데 사실상 표준이 되었습니다.

**방식**

- **단일 채점(pointwise):** 기준표(rubric)에 따라 1~5점 또는 통과/실패
- **쌍 비교(pairwise):** 두 답 중 어느 것이 더 나은지 (A/B 비교, 모델 비교에 적합)
- **참조 기반:** 정답과 비교해 맞는지 판단
- 판정 근거(이유)를 먼저 쓰고 점수를 내게 하면 일관성이 좋아집니다.

**장점:** 사람 평가보다 훨씬 빠르고 싸며, 기준을 자연어로 쉽게 정의할 수 있고, 사람 판단과 상당히 높은 일치도를 보이는 경우가 많습니다.

**한계**

| 편향·문제 | 설명 | 완화 |
|---|---|---|
| 위치 편향 | 쌍 비교에서 첫 번째(또는 두 번째)를 선호 | 순서를 바꿔 두 번 평가 |
| 길이 편향 | 길고 자세한 답 선호 | 기준에 간결성 명시, 길이 통제 |
| 자기 선호 | 자기 계열 모델 출력 선호 | 다른 계열 판정자 사용, 여러 판정자 |
| 능력 한계 | 판정자가 모르는 전문 영역·어려운 문제는 정확히 판단 못함 | 참조 답·도구(코드 실행) 제공, 전문가 평가 |
| 점수 척도 불안정 | 절대 점수가 들쑥날쑥 | 명확한 기준표와 예시, 쌍 비교 활용 |
| 겉모습 편향 | 자신감 있는 어조·형식에 속음 | 사실 확인 단계 분리 |
| 프롬프트 민감도 | 판정 프롬프트에 따라 결과 변동 | 판정 프롬프트 버전 관리 |

**신뢰성 확보 방법**

- 사람이 라벨링한 샘플(수십~수백 개)로 판정자와 사람의 일치도를 측정하고, 기준표·프롬프트를 조정합니다.
- 결정적 검사로 대체할 수 있는 부분은 코드로 평가합니다.
- 중요한 결정(모델 교체, 출시)은 사람 평가로 최종 확인합니다.

**더 읽어보기 (영문):** [LLM as a Judge](https://outcomeschool.com/blog/llm-as-a-judge)

<summary><b>Q10. AI 시스템에 대한 사람 평가(human evaluation)는 어떻게 진행하나요?</b></summary>

**언제 필요한가**

- 자동 평가로 판단하기 어려운 품질(유용성, 전문적 정확성, 어조, 창의성)
- LLM 판정자를 검증·보정할 때
- 출시 전 최종 확인, 고위험 도메인

**설계 절차**

1. **평가 목적과 차원 정의:** 무엇을 판단할지(정확성, 유용성, 안전성 등)와 각각의 정의.
2. **채점 기준표(rubric) 작성:** 점수별 구체적 기준과 예시. "3점: 핵심은 맞지만 중요한 세부 누락" 같은 수준으로.
3. **평가 방식 선택**
   - **절대 평가(Likert 척도):** 각 응답을 1~5점
   - **쌍 비교:** 두 응답 중 선호 (일관성이 더 높고 모델 비교에 적합)
   - **이진 판정:** 통과/실패, 오류 유형 태깅
4. **평가자 선정과 교육:** 도메인에 맞는 전문성(의료·법률은 전문가), 교육 세션, 연습 문제로 기준 맞추기.
5. **편향 통제**
   - **블라인드:** 어떤 모델·버전인지 숨기기
   - 응답 순서 무작위화
   - 평가자 간 작업 분배 균형
6. **품질 관리**
   - 같은 샘플을 여러 평가자가 평가해 **평가자 간 일치도**(Cohen's kappa, Krippendorff's alpha) 측정
   - 정답이 정해진 골드 문항으로 평가자 정확도 확인
   - 불일치 사례 토론·기준 보완
7. **표본 크기:** 비교하려는 차이를 통계적으로 확인할 수 있을 만큼 확보.
8. **분석:** 평균 점수뿐 아니라 실패 유형 분포, 카테고리별 결과.

**결과 활용:** 자동 평가(LLM 판정자) 보정 데이터, 평가셋 개선, 학습용 선호도 데이터.

<summary><b>Q11. 레드 팀(red teaming)이란 무엇이며, LLM 애플리케이션을 어떻게 레드 팀 방식으로 점검하나요?</b></summary>

**레드 팀** 은 공격자의 관점에서 시스템을 의도적으로 공격해 **취약점과 실패 모드를 출시 전에 찾아내는 활동** 입니다.

**LLM 애플리케이션에서 찾는 것**

- **보안:** 프롬프트 인젝션(직접·간접), 시스템 프롬프트 유출, 데이터 유출, 권한 우회, 도구 악용
- **안전:** 탈옥, 유해 콘텐츠 생성(위험 정보, 혐오, 자해 조장)
- **정확성:** 환각 유도, 잘못된 전문 조언(의료·법률·금융)
- **편향·공정성:** 특정 집단에 대한 차별적 응답
- **개인정보:** 다른 사용자 정보, 학습 데이터 추출
- **비즈니스 위험:** 경쟁사 추천, 부적절한 약속(환불 보장 등), 브랜드 훼손
- **가용성:** 비용 폭증 유도, 무한 루프

**진행 방법**

1. **범위와 위협 모델 정의:** 시스템이 가진 데이터·도구·권한, 사용자 유형, 가장 큰 피해 시나리오.
2. **공격 시나리오 작성:** 카테고리별 공격 목록(OWASP Top 10 for LLM Applications 같은 분류 참고).
3. **수동 레드 팀:** 보안 전문가, 도메인 전문가, 다양한 배경의 사람들이 창의적으로 공격.
4. **자동 레드 팀:** 공격 LLM이 대량의 변형 공격을 생성하고 판정 모델이 성공 여부를 판단. 도구: garak, PyRIT, promptfoo 등.
5. **결과 분류와 수정:** 심각도별로 정리 → 가드레일, 권한 축소, 프롬프트 수정, 모델 교체.
6. **회귀 세트화:** 발견된 공격을 테스트셋으로 만들어 이후 변경마다 자동 실행.

**지속성:** 새로운 공격 기법이 계속 나오므로 출시 전 한 번이 아니라 정기적으로 수행하고, 버그 바운티로 외부 제보도 받습니다.

<summary><b>Q12. LLM 출력의 환각을 어떻게 감지하고 측정하나요?</b></summary>

**환각의 종류**

- **근거 불일치(faithfulness 실패):** 주어진 컨텍스트(문서, RAG 결과)와 다르거나 없는 내용
- **사실 오류(factuality 실패):** 세상의 사실과 다른 내용 (근거 문서 없는 일반 질문)

**감지 방법**

1. **근거 기반 검증 (RAG·요약)**
   - 답변을 **원자적 주장(claim)** 으로 쪼개고, 각 주장이 컨텍스트에 의해 뒷받침되는지 판정합니다.
   - 판정 도구: NLI 모델(함의/모순/중립), LLM 판정자, 전용 환각 탐지 모델.
   - 인용 검증: 인용된 문장이 실제로 문서에 있고 주장을 지지하는지.
2. **자기 일관성(SelfCheckGPT 방식)**
   - 같은 질문으로 여러 번 샘플링해 답들이 서로 일치하는지 봅니다. 모델이 모르는 내용은 샘플마다 다르게 지어내는 경향이 있습니다.
3. **불확실성 신호**
   - 토큰 로그 확률(낮은 확신), 의미 엔트로피(여러 샘플의 의미적 다양성).
4. **외부 검증**
   - 검색·지식 베이스·DB로 사실 확인(fact-checking 파이프라인), 코드는 실행해 확인, 수치는 계산으로 검증.
5. **규칙 기반**
   - 존재하지 않는 URL·인용·ID, 컨텍스트에 없는 숫자·고유명사 탐지.

**측정 지표**

- 충실도 점수(뒷받침되는 주장 비율), 환각률(근거 없는 주장이 하나라도 있는 응답 비율)
- 사실 정확도(정답이 있는 질문셋), 인용 정밀도
- 거절 정확도(모를 때 모른다고 하는 비율)

**평가셋 구성:** 답이 컨텍스트에 있는 질문, 없는 질문, 모델이 틀리기 쉬운 질문(최신 정보, 희귀 사실)을 섞습니다.

<summary><b>Q13. AI 시스템의 적대적 테스트(adversarial testing)란 무엇인가요?</b></summary>

**적대적 테스트** 는 시스템을 실패하게 만들도록 **의도적으로 설계된 입력** 으로 견고성과 안전성을 시험하는 것입니다. 일반 테스트가 "정상 사용에서 잘 되는가"를 본다면, 적대적 테스트는 "공격·악용·예상 밖 입력에서 버티는가"를 봅니다.

**LLM 시스템의 적대적 입력 유형**

- **프롬프트 인젝션·탈옥:** 지시 덮어쓰기, 역할극, 인코딩·난독화, 다국어 우회, 다단계 유도
- **간접 인젝션:** 웹 페이지·문서·이메일·이미지 속 숨은 지시
- **데이터 추출:** 시스템 프롬프트, 다른 사용자 정보, 학습 데이터 유출 시도
- **견고성 공격:** 오타·특수문자·유니코드 변형, 매우 긴 입력, 의미는 같지만 표현이 다른 입력(민감도 테스트)
- **오도 질문:** 잘못된 전제("아인슈타인이 노벨 화학상을 받은 해는?"), 모순된 정보
- **자원 고갈:** 무한 루프 유도, 거대한 출력 요구
- **멀티모달 공격:** 이미지 속 텍스트 지시, 오디오 속 숨은 명령

**진행 방식**

1. 위협 모델과 공격 범주 정의
2. 공격 세트 구축: 수동 작성 + 공개 데이터셋 + LLM으로 변형 자동 생성
3. 자동 실행과 판정(공격 성공 여부를 규칙·판정 모델로 확인)
4. 결과 분석 → 방어 개선(가드레일, 권한, 프롬프트, 모델)
5. 공격 세트를 회귀 테스트로 유지하고 새 기법을 계속 추가

**지표:** 공격 성공률(ASR), 범주별 방어율, 방어로 인한 정상 요청 거절률(과잉 거절).

<summary><b>Q14. AI 애플리케이션의 회귀 테스트 스위트는 어떻게 만드나요?</b></summary>

**목표:** 프롬프트·모델·검색 설정·코드 변경이 **이전에 잘 되던 동작을 망가뜨리지 않는지** 자동으로 확인하는 것.

**1. 테스트 케이스 수집**

- 핵심 사용 사례(골든 세트): 반드시 잘 되어야 하는 대표 요청
- 과거 버그·고객 불만 사례: 한 번 고친 문제가 다시 생기지 않게
- 엣지 케이스: 빈 입력, 긴 입력, 다국어, 특수 형식
- 안전·보안 케이스: 탈옥, 인젝션, 유해 요청

<summary><b>Q16. 벤치마크 오염(benchmark contamination)이란 무엇이며, 어떻게 방지하나요?</b></summary>

**벤치마크 오염** 은 평가에 쓰는 문제(또는 정답)가 **모델의 학습 데이터에 포함되어**, 모델이 실제 능력이 아니라 기억으로 점수를 얻는 현상입니다.

**왜 생기나**

- 공개 벤치마크가 웹(GitHub, 블로그, 포럼)에 퍼져 있고, 대규모 웹 크롤링 학습 데이터에 섞여 들어갑니다.
- 의도치 않게 비슷한 문제나 풀이가 포함되기도 합니다.
- 합성 데이터 생성에 벤치마크 문제가 시드로 쓰이는 경우도 있습니다.

**영향:** 점수가 실제 일반화 능력보다 높게 나와, 모델 비교와 의사 결정을 왜곡합니다.

**탐지 방법**

- **n-gram 겹침 검사:** 학습 데이터와 벤치마크 문제의 긴 n-gram 일치 여부 (학습 데이터에 접근 가능할 때)
- **암기 테스트:** 문제 앞부분만 주고 나머지를 그대로 재현하는지, 선택지 순서를 기억하는지
- **변형 비교:** 숫자·이름만 바꾼 동일 난이도 문제에서 점수가 크게 떨어지면 오염 의심
- **시간 기반 비교:** 모델 학습 컷오프 이후에 만든 문제에서의 성능과 비교

**방지·대응**

- **학습 측:** 학습 데이터에서 벤치마크와 겹치는 문서 제거(디컨태미네이션)
- **평가 측:**
  - 컷오프 이후 새로 만든 문제로 평가하는 **라이브 벤치마크**(LiveBench, LiveCodeBench 등)
  - 비공개 평가셋(외부에 공개하지 않음), 정기적 교체
  - 문제 변형·재작성 버전으로 함께 평가
- **실무:** 회사 내부 평가셋은 외부에 공개하지 않고, 모델 학습·파인튜닝 데이터와 분리해 관리합니다. 합성 데이터 생성 시 평가셋과 겹치지 않는지 확인합니다.

**더 읽어보기 (영문):** [LLM Evaluation](https://outcomeschool.com/blog/llm-evaluation)

<summary><b>Q17. 새 모델 버전이 모든 벤치마크에서 점수가 더 높은데, 사용자들은 더 나빠졌다고 말합니다. 왜 이런 일이 생기며, 문제를 어떻게 찾나요?</b></summary>

**가능한 원인**

1. **벤치마크와 실제 사용의 불일치:** 벤치마크는 정답이 있는 짧은 문제 위주이고, 사용자는 긴 대화, 모호한 요청, 특정 도메인, 특정 형식을 원합니다.
2. **행동 변화:** 새 모델이 더 장황하거나, 더 자주 거절하거나, 어조가 바뀌었거나, 지시를 덜 따르거나, 형식(마크다운, JSON)이 달라졌습니다. 벤치마크는 이런 차이를 잡지 못합니다.

6. **지연·비용:** 품질은 비슷해도 느려져서 체감이 나빠짐(특히 추론 모델).
7. **기대 효과:** 바뀐 것을 인지한 사용자들이 차이에 민감해짐(일부는 실제 문제가 아닐 수 있음).

1. **구체적 사례 수집:** 부정 피드백이 달린 대화, 재생성·이탈이 많은 대화를 모아 직접 읽습니다.
2. **실패 유형 분류:** 장황함, 거절, 형식 오류, 사실 오류, 지시 무시, 어조 등으로 태깅해 빈도 파악.
3. **세그먼트 분석:** 기능·언어·작업 유형·사용자 그룹별 지표 비교.
4. **쌍 비교 평가:** 실제 프로덕션 입력으로 이전 모델과 새 모델의 응답을 블라인드 비교(사람 + LLM 판정).
5. **행동 지표 측정:** 평균 응답 길이, 거절률, 형식 준수율, 도구 호출 패턴 변화.

**대응**

- 프롬프트를 새 모델에 맞게 조정, 문제 세그먼트만 이전 모델로 라우팅, 필요 시 롤백.
- **재발 방지:** 실제 사용 기반 평가셋과 행동 지표를 모델 교체 게이트에 포함하고, 카나리 배포로 사용자 신호를 먼저 확인합니다.

<summary><b>Q20. 자율 코딩 에이전트는 어떻게 평가하나요? SWE-bench 통과율은 왜 오해를 부를 수 있나요?</b></summary>

**SWE-bench란:** 실제 오픈소스 파이썬 저장소의 GitHub 이슈와 그 이슈를 고친 PR의 테스트를 모아, 에이전트가 이슈를 해결하는 패치를 만들면 숨겨진 테스트로 통과 여부를 판정하는 벤치마크입니다(Verified 등 검증된 하위 세트 포함).

**통과율이 오해를 부를 수 있는 이유**

1. **분포 편향:** 일부 인기 파이썬 저장소에 집중되어 있고, 다른 언어·사내 코드베이스·대규모 기능 개발과는 다릅니다.
2. **오염:** 해당 저장소와 수정 커밋이 공개되어 있어 학습 데이터에 포함되었을 수 있습니다.
3. **테스트의 한계:** 숨겨진 테스트를 통과해도 코드 품질, 유지보수성, 다른 기능에 대한 부작용, 보안 문제는 확인하지 못합니다. 반대로 올바른 해결인데 테스트가 특정 구현을 요구해 실패하기도 합니다.
4. **하네스 의존성:** 같은 모델도 하네스(도구, 프롬프트, 재시도 횟수, 실행 예산)에 따라 점수가 크게 다릅니다. 모델 비교인지 시스템 비교인지 구분해야 합니다.
5. **보고 조건 차이:** 여러 번 시도 후 최선 선택(pass@k), 비용·시간 제한 유무, 사람 힌트 여부가 다르면 비교가 무의미합니다.
6. **이슈 설명 품질:** 실제 업무 요청보다 명확하거나, 반대로 정보가 부족한 이슈가 섞여 있습니다.

**실무적인 평가 방법**

- **사내 과제 세트:** 실제 과거 이슈·PR을 재현한 과제(사내 코드베이스, 사용 언어)
- **다면 평가:** 테스트 통과 + 기존 테스트 회귀 없음 + 코드 리뷰 품질(사람·LLM) + 변경 범위의 적절성
- **효율:** 해결당 비용·시간, 사람 개입 횟수
- **실사용 지표:** 에이전트 PR 병합률, 리뷰 수정 횟수, 배포 후 결함
- **안전:** 위험 명령 시도, 범위 밖 파일 수정

**더 읽어보기 (영문):** [AI Agent Evaluation](https://outcomeschool.com/blog/ai-agent-evaluation)

<summary><b>Q21. AI 시스템의 오프라인 평가와 온라인 평가의 차이는 무엇인가요?</b></summary>

| | 오프라인 평가 | 온라인 평가 |
|---|---|---|
| 시점 | 배포 **전** | 배포 **후**, 실제 운영 중 |
| 데이터 | 고정된 평가셋 | 실제 사용자 트래픽 |
| 방법 | 평가셋 실행 + 자동 채점·사람 평가 | A/B 테스트, 사용자 피드백, 프로덕션 샘플 자동 채점, 비즈니스 지표 |
| 장점 | 빠르고 반복 가능, 사용자 위험 없음, 재현 가능 | 실제 분포와 실제 가치를 반영 |
| 단점 | 평가셋이 현실을 완전히 대표하지 못함 | 느리고(표본 필요), 사용자에게 위험, 노이즈 많음 |
| 용도 | 개발 반복, 회귀 방지, 배포 게이트 | 최종 효과 검증, 드리프트·새 실패 유형 발견 |

**둘 다 필요한 이유**

- 오프라인 점수가 올라도 실제 사용자 만족이 오르지 않을 수 있습니다(벤치마크와 실사용의 차이).
- 온라인 평가만으로는 위험한 변경이 사용자에게 바로 노출되고, 원인 분석이 어렵습니다.

**연결 고리**

```
오프라인 평가 통과 → 카나리/A/B(온라인) → 실패 사례 수집 → 오프라인 평가셋에 추가 → ...
```

- 온라인에서 발견한 실패를 오프라인 평가셋에 넣어, 평가셋이 점점 현실을 더 잘 반영하게 만듭니다.
- 오프라인 지표와 온라인 지표의 상관관계를 주기적으로 확인합니다(상관이 낮으면 오프라인 평가 설계를 고쳐야 함).

**온라인 지표 예:** 작업 성공률, 좋아요/싫어요, 재생성률, 대화 이탈, 상담원 이관률, 전환율, 지연·비용.

<summary><b>Q22. LLM 출력의 사실 일관성(factual consistency)은 어떻게 측정하나요?</b></summary>

**사실 일관성** 은 출력이 **주어진 근거(원문, 검색 문서, 데이터)와 모순되지 않고 뒷받침되는 정도** 입니다. 요약·RAG·문서 기반 QA의 핵심 품질 지표입니다.

**측정 방법**

1. **주장 분해 + 검증 (가장 널리 쓰임)**
   - 출력을 원자적 주장으로 분해합니다. ("A사는 2023년에 설립되었다", "직원 수는 500명이다")
   - 각 주장이 근거에 의해 **뒷받침됨 / 모순됨 / 확인 불가** 인지 판정합니다.
   - 점수 = 뒷받침된 주장 수 ÷ 전체 주장 수 (RAGAS faithfulness, FActScore 계열 방식)
2. **NLI(자연어 추론) 모델**
   - (근거, 문장) 쌍을 함의/모순/중립으로 분류합니다. 빠르고 싸지만 긴 문맥·복잡한 추론에는 약합니다. SummaC, AlignScore 같은 방법.
3. **QA 기반 (QAGS, QuestEval)**
   - 출력에서 질문을 생성하고, 같은 질문을 원문과 출력에 각각 답하게 해 답이 일치하는지 비교합니다.
4. **LLM 판정자**
   - 근거와 출력을 주고 불일치·근거 없는 내용을 찾아 표시하게 합니다. 이유를 함께 받아 검증합니다.
5. **규칙 기반 점검**
   - 숫자, 날짜, 고유명사가 원문에 존재하는지 문자열 매칭.

**검증과 운영**

- 자동 지표의 신뢰성을 사람 라벨 샘플로 확인합니다(판정자가 놓치는 유형 파악).
- 응답 단위 점수뿐 아니라 "모순된 주장이 하나라도 있는 응답 비율" 같은 엄격한 지표도 봅니다.
- 고위험 영역은 자동 검증 실패 시 응답을 차단하거나 사람 검토로 보냅니다.

</details>

<summary><b>Q23. 멀티턴 대화의 품질은 어떻게 평가하나요?</b></summary>

**단일 턴 평가와 다른 점:** 각 응답이 좋아도 **대화 전체** 로 보면 실패일 수 있습니다(맥락을 잊음, 같은 질문 반복, 목표 미달성).

**평가 차원**

- **맥락 유지:** 앞서 말한 정보(이름, 조건, 선호)를 기억하고 반영하는가
- **일관성:** 앞의 발언과 모순되지 않는가
- **정정 반영:** 사용자가 "아니, 그게 아니라"라고 고치면 반영하는가
- **명확화:** 정보가 부족할 때 적절히 되묻는가(과하지 않게)
- **목표 달성:** 대화가 끝났을 때 사용자의 문제가 해결되었는가
- **효율:** 불필요하게 턴을 늘리지 않는가
- **주제 전환 처리, 어조·페르소나 일관성, 안전성(여러 턴에 걸친 탈옥 시도 포함)**

**평가 방법**

1. **시나리오 스크립트 테스트**
   - 미리 정한 대화 흐름(사용자 발화 목록)을 실행하고 특정 턴의 응답을 검사합니다. 예: 3턴 전 언급한 예산을 5턴째 추천에 반영하는가.
2. **사용자 시뮬레이터**
   - LLM에게 페르소나와 목표("환불을 받으려는 화난 고객, 주문번호는 두 번째 턴에 말함")를 주고 시스템과 자유롭게 대화하게 합니다. 다양한 대화를 대량 생성할 수 있습니다.
3. **대화 단위 판정**
   - LLM 판정자가 전체 대화 기록을 보고 목표 달성, 맥락 유지, 효율을 채점합니다.
4. **턴 단위 판정**
   - 각 응답의 관련성·정확성을 평가해 어느 턴에서 품질이 무너졌는지 찾습니다.
5. **실제 로그 분석**
   - 대화 길이, 이탈 지점, 반복 질문, 상담원 이관 지점, 대화 종료 후 피드백.

**주의:** 시뮬레이터가 실제 사용자보다 협조적이거나 비현실적일 수 있으므로, 실제 로그 기반 시나리오와 함께 씁니다.

</details>

<summary><b>Q24. AI 평가에서 골든 데이터셋(golden dataset)은 어떤 역할을 하나요?</b></summary>

**골든 데이터셋** 은 신뢰할 수 있는 정답이나 기대 결과가 붙은, **엄선된 고품질 평가 데이터** 입니다. AI 시스템이 "반드시 잘해야 하는 것"의 기준 역할을 합니다.

**역할**

1. **기준선과 회귀 방지:** 모든 변경(프롬프트, 모델, 검색 설정)을 같은 기준으로 비교하고, 품질이 떨어지면 배포를 막습니다.
2. **객관적 비교:** 모델·설정 선택을 감이 아니라 데이터로 결정합니다.
3. **자동 평가 보정:** LLM 판정자의 판정이 정답과 얼마나 일치하는지 측정하는 기준이 됩니다.
4. **요구사항 명세:** "좋은 출력"이 무엇인지 팀이 합의한 구체적인 예시 모음입니다.
5. **학습 데이터와 분리된 검증:** 파인튜닝 시 과적합 여부를 확인합니다.

**좋은 골든 데이터셋의 조건**

- **대표성:** 실제 사용 분포(주요 의도, 언어, 길이)를 반영
- **다양성과 난이도:** 쉬운 사례 + 어려운 사례 + 엣지 케이스 + 실패 이력 사례
- **정확한 라벨:** 전문가 검수, 애매한 사례는 판정 기준 문서화
- **적당한 크기:** 핵심 세트는 빠르게 돌릴 수 있게(수십~수백), 전체 세트는 통계적으로 의미 있게
- **버전 관리:** 변경 이력, 각 항목의 출처·추가 이유
- **오염 방지:** 학습·프롬프트 예시에 쓰지 않음

**유지 관리**

- 프로덕션 실패 사례를 검수해 계속 추가합니다.
- 제품 정책이 바뀌면 기대 결과를 갱신합니다.
- 너무 쉬워져 모든 버전이 만점이면 어려운 사례를 보강합니다.

</details>

<summary><b>Q25. 라벨이 달린 정답(ground truth)이 없고 도메인 전문가 비용이 비쌀 때 평가 세트를 어떻게 만드나요?</b></summary>

**전략: 전문가 시간을 "만들기"가 아니라 "검수·판단"에 집중시키기**

1. **입력 수집은 저렴하게**
   - 프로덕션 로그, 고객 문의, 검색어에서 실제 입력을 샘플링합니다(클러스터링으로 다양한 유형 고르기).
   - 출시 전이라면 LLM으로 다양한 페르소나·의도의 입력을 생성합니다.
2. **후보 답변을 LLM으로 생성**
   - 강한 모델(또는 여러 모델)로 답변 후보를 만들고, 문서 기반이면 근거 문장도 함께 뽑게 합니다.
3. **전문가는 검수만**
   - 처음부터 쓰게 하지 않고 "맞다/틀리다/수정"만 하게 하면 시간이 크게 줄어듭니다.
   - 쌍 비교(두 답 중 어느 쪽이 나은가)는 절대 채점보다 빠르고 일관됩니다.
4. **참조 없는 평가 지표 활용**
   - 정답 없이도 측정 가능한 것: 근거 충실도(문서와 대조), 형식 준수, 자기 일관성, 안전성, 지시 준수.
5. **채점 기준표(rubric) 중심 평가**
   - 정답 대신 "좋은 답의 조건"(필수 포함 사항, 금지 사항)을 전문가가 한 번 정의하면, 이후 LLM 판정자가 대량 채점합니다.
6. **능동적 샘플링**
   - 모델들이 서로 다른 답을 내거나 판정 점수가 애매한 사례만 전문가에게 보냅니다(불일치가 큰 사례가 가장 정보가 많음).
7. **약한 신호 활용**
   - 사용자 행동(채택, 수정, 재질문), 기존 업무 기록(티켓 해결 결과, 승인된 문서)을 근사 정답으로 사용합니다.
8. **작게 시작해 키우기**
   - 50~100개의 고품질 세트로 시작하고, 운영하며 실패 사례를 추가합니다.

**주의:** LLM이 만든 정답·판정을 검수 없이 그대로 쓰면 평가가 그 LLM의 편향을 그대로 반영합니다. 일부라도 전문가 검증 샘플을 두어 자동 평가의 신뢰도를 측정합니다.

</details>

<summary><b>Q26. 프로덕션 AI 시스템에 대한 지속적 평가를 어떻게 구현하나요?</b></summary>

**구성 요소**

1. **트레이스 수집:** 모든 요청의 입력·출력·컨텍스트·도구 호출·메타데이터를 기록(PII 마스킹).
2. **샘플링:** 전체 또는 일정 비율 + 위험 신호가 있는 요청(부정 피드백, 긴 대화, 가드레일 경고, 새 기능) 우선 샘플링.
3. **자동 평가 파이프라인 (비동기)**
   - 규칙 검사: 형식, 길이, 금지 패턴, PII
   - LLM 판정: 관련성, 충실도, 정책 준수, 어조
   - RAG: 검색 결과 점수, 답 없음 비율
4. **사용자 신호:** 좋아요/싫어요, 재생성, 복사, 이탈, 이관, 후속 질문.
5. **대시보드와 추세:** 지표를 시간·기능·세그먼트별로 추적.
6. **알림:** 품질 점수 하락, 특정 실패 유형 급증, 입력 분포 변화(새 주제·언어 증가) 감지.
7. **사람 검토 대기열:** 낮은 점수·부정 피드백 사례를 정기적으로 검토하고 실패 유형을 태깅.
8. **피드백 루프:** 검토된 실패 사례 → 평가셋 추가 → 수정 → 오프라인 회귀 테스트 → 배포.

```
프로덕션 트래픽 → 트레이스 → 샘플링 → 자동 채점 ─┐
                       사용자 피드백 ───────────┤→ 대시보드·알림
                                              └→ 사람 검토 → 평가셋·개선
```

**주의할 점**

- 판정 LLM 비용을 고려해 샘플 비율을 조정합니다.
- 판정자 자체의 정확도를 주기적으로 사람 평가와 비교합니다.
- 모델 제공사 업데이트처럼 코드 변경 없이도 품질이 바뀔 수 있으므로, 고정된 기준 세트를 매일 실행하는 "카나리 평가"도 둡니다.

</details>

<details>
<summary><b>Q27. AI 모델 출력의 편향(bias)은 어떻게 평가하나요?</b></summary>

**편향의 형태**

- **표현 편향:** 특정 집단에 대한 고정관념, 부정적 묘사 ("간호사는 여성"으로 가정)
- **성능 편향:** 집단·언어·방언별로 정확도가 다름
- **할당 편향:** 의사 결정(대출, 채용, 추천)에서 집단별 결과 차이
- **거절 편향:** 특정 집단 관련 요청을 더 자주 거절하거나 다르게 응답

**평가 방법**

1. **반사실적(counterfactual) 테스트**
   - 같은 입력에서 이름, 성별, 인종, 나이, 종교 같은 속성만 바꿔 출력이 달라지는지 비교합니다.
   - 예: 동일한 이력서에 이름만 바꿔 점수 차이 측정.
2. **벤치마크**
   - BBQ(질문응답 편향), WinoBias(성별 대명사), StereoSet, CrowS-Pairs, 다국어·한국어 편향 데이터셋(KoBBQ 등).
3. **집단별 성능 분해**
   - 평가셋을 집단(언어, 지역, 연령대, 방언)별로 나눠 정확도·오류율·거절률을 비교합니다.
4. **결정 시스템의 공정성 지표**
   - 인구통계적 동등성(집단별 긍정 결과 비율), 기회 균등(집단별 참양성률), 4/5 규칙 같은 불리 효과 분석.
5. **생성 텍스트 분석**
   - 집단별로 생성된 묘사의 감성·고정관념 단어 빈도를 측정(분류기 또는 LLM 판정).
6. **사람 평가**
   - 다양한 배경의 평가자, 해당 집단 당사자의 검토.

**운영**

- 정기적으로 측정하고 결과를 문서화(모델 카드).
- 공정성 지표는 서로 충돌할 수 있으므로, 사용 맥락에 맞는 지표를 이해관계자와 함께 정합니다.
- 발견된 편향은 데이터 보완, 프롬프트·가드레일, 결정 임계값 조정, 사람 검토 강화로 완화합니다.

<summary><b>Q28. 두 모델이나 두 프롬프트를 통계적으로 엄밀하게 비교하려면 어떻게 하나요?</b></summary>

**1. 실험 설계**

- **같은 평가셋, 같은 조건:** 동일 입력에 두 버전을 실행합니다(대응 비교, paired). 입력 난이도 차이로 인한 노이즈가 사라져 훨씬 적은 표본으로 차이를 검출할 수 있습니다.
- **비결정성 처리:** 온도를 고정하고, 필요하면 입력마다 여러 번 실행해 평균을 냅니다.
- **블라인드 판정:** 판정자(사람·LLM)가 어떤 버전인지 모르게, 쌍 비교라면 순서를 무작위화(또는 양방향 평가).
- **사전 계획:** 주 지표와 유의 수준을 미리 정합니다(여러 지표를 보다가 유리한 것만 고르는 p-해킹 방지).

**2. 표본 크기**

- 검출하고 싶은 최소 차이(예: 정확도 2%p)와 원하는 검정력(보통 80%)으로 필요한 표본 수를 계산합니다.
- 작은 차이를 확인하려면 생각보다 많은 표본(수백~수천)이 필요합니다.

**3. 통계 검정**

| 지표 유형 | 검정 |
|---|---|
| 이진(정답/오답), 대응 | McNemar 검정 |
| 연속 점수(판정 점수), 대응 | 대응 t-검정 또는 Wilcoxon 부호 순위 검정 |
| 쌍 비교 선호(승/패/무) | 부호 검정, 이항 검정, Bradley-Terry 모델 |
| 분포 가정이 어려울 때 | 부트스트랩으로 차이의 신뢰구간 계산 |

**4. 결과 보고**

- p값만이 아니라 **효과 크기와 신뢰구간** 을 함께 보고합니다. "B가 A보다 정확도 3.1%p 높음 (95% CI: 1.2~5.0)".
- 여러 비교를 했다면 다중 비교 보정(Bonferroni, Holm).
- 카테고리별 결과도 확인합니다(전체는 비슷해도 특정 유형에서 큰 차이).

**5. 온라인 비교 (A/B 테스트)**

- 사용자 단위 무작위 배정, 충분한 기간, 비즈니스 지표와 가드레일 지표를 함께 분석합니다.

</details>

<summary><b>Q29. 입력이 달라져도 LLM 애플리케이션이 견고한지(robustness) 어떻게 평가하나요?</b></summary>

**견고성** 은 의미는 같거나 비슷한데 **표면 형태가 다른 입력** 에서도 일관되게 올바른 결과를 내는 능력입니다.

**테스트할 변형 유형**

1. **표현 변형:** 같은 질문을 다른 단어·문장 구조로 (LLM으로 패러프레이즈 생성)
2. **노이즈:** 오타, 띄어쓰기 오류, 대소문자, 이모지, 구어체·줄임말
3. **형식 변화:** 질문 순서 바꾸기, 불필요한 정보 추가, 매우 길거나 짧은 입력
4. **언어·방언:** 다른 언어, 혼용(한영 섞기), 지역 방언
5. **컨텍스트 변형:** RAG 문서 순서 변경, 관련 없는 문서 추가(방해 정보), 문서 일부 누락
6. **프롬프트 민감도:** 시스템 프롬프트의 사소한 문구 변경, 퓨샷 예시 순서 변경
7. **적대적 변형:** 의도적으로 혼란을 주는 입력, 잘못된 전제

**측정 방법**

- 원본 입력과 변형 입력의 **결과 일치율**(분류·추출), 정확도 차이
- 변형별 성능 하락 폭(어떤 변형에 가장 취약한지)
- 변형 세트 전체에서의 최저 성능(worst-case) — 평균보다 중요할 수 있음

**절차**

1. 핵심 평가셋을 선택합니다.
2. 각 항목에 대해 변형 유형별 버전을 생성합니다(규칙 + LLM, 사람 검수로 의미 보존 확인).
3. 원본·변형 모두 실행해 일치율과 정확도를 비교합니다.
4. 취약한 변형 유형을 찾아 개선합니다(입력 정규화, 쿼리 재작성, 프롬프트 명확화, 하이브리드 검색, 예시 다양화, 파인튜닝 데이터 증강).

**운영:** 견고성 세트를 회귀 테스트에 포함해 모델·프롬프트 변경 시 함께 확인합니다.

<summary><b>Q30. 기존 ML 평가와 LLM 애플리케이션 평가의 핵심 차이는 무엇인가요?</b></summary>

| 측면 | 기존 ML 평가 | LLM 애플리케이션 평가 |
|---|---|---|
| 출력 형태 | 숫자, 라벨 (정해진 공간) | 자유 형식 텍스트, 도구 호출, 행동 |
| 정답 | 대개 하나, 라벨 존재 | 여러 정답이 가능하거나 정답이 없음 |
| 지표 | 정확도, F1, AUC, RMSE 등 명확 | 다차원(정확성, 충실도, 유용성, 어조, 안전성), 판정 필요 |
| 평가자 | 코드로 자동 계산 | 규칙 + LLM 판정자 + 사람 평가 |
| 테스트셋 | 학습 데이터에서 분리한 홀드아웃 | 직접 만들어야 함(사용 사례 기반, 수작업 큐레이션) |
| 결정성 | 결정적 예측 | 확률적, 같은 입력에도 출력 변동 |
| 평가 대상 | 모델 하나 | 시스템 전체(프롬프트, 검색, 도구, 모델, 후처리) |
| 변화 요인 | 데이터 드리프트, 재학습 | + 프롬프트 변경, 제공사 모델 업데이트, 지식 베이스 변경 |
| 안전성 | 부차적 | 핵심(탈옥, 인젝션, 유해 콘텐츠, 환각) |
| 비용 | 평가 비용 거의 없음 | 판정 LLM 호출 비용, 사람 평가 비용 |

**LLM 평가에서 추가로 필요한 것**

- **평가셋 설계 역량:** 무엇을 평가할지 정의하는 것 자체가 큰 작업입니다.
- **판정자 검증:** LLM 판정의 신뢰도 측정.
- **다층 평가:** 구성 요소별(검색, 생성, 도구) + 엔드 투 엔드.
- **지속적 평가:** 외부 모델 변화 때문에 배포 후에도 계속 측정.
- **행동·과정 평가:** 에이전트의 경로.

**공통점:** 대표성 있는 데이터, 학습·평가 데이터 분리, 세그먼트별 분석, 통계적 유의성, 온라인 검증은 여전히 중요합니다.

<summary><b>Q31. 새 LLM 애플리케이션을 위한 평가 프레임워크를 처음부터 어떻게 구축하나요?</b></summary>

**1단계: 성공 정의 (1~2일)**

- 제품 목표와 사용자 가치를 바탕으로 품질 차원을 정합니다: 정확성, 근거 충실도, 형식, 어조, 안전성, 지연, 비용.
- 각 차원의 합격 기준(예: 형식 준수 99%, 근거 없는 주장 1% 미만).

**2단계: 초기 평가셋 (작게 시작)**

- 실제 또는 예상 입력 50~100개: 주요 사용 사례, 엣지 케이스, 위험 사례.
- 가능한 곳에 기대 결과나 채점 기준(필수 포함·금지 사항)을 붙입니다.

**3단계: 채점기 구현**

- 결정적 검사부터: 스키마, 규칙, 정답 비교, 코드 실행.
- 자유 서술 차원은 LLM 판정자 + 명확한 기준표.
- 판정자를 사람 라벨 20~50개로 검증하고 기준표를 다듬습니다.

**4단계: 실행 인프라**

- 평가셋 × 설정(모델, 프롬프트 버전)을 실행하고 결과·점수·비용·지연을 저장하는 스크립트나 도구(promptfoo, DeepEval, LangSmith, Langfuse, 자체 구현).
- 실행 간 비교 리포트(어떤 케이스가 좋아지고 나빠졌는지).

**5단계: 개발 루프에 통합**

- 기준선 측정 → 실패 분석 → 개선 → 재평가.
- CI에 핵심 세트를 넣어 회귀 시 배포 차단.

**6단계: 프로덕션 연결**

- 트레이싱, 사용자 피드백 수집, 샘플 자동 평가, 대시보드·알림.
- 프로덕션 실패 사례를 평가셋에 추가하는 정기 루틴(주간 검토).

**7단계: 확장과 성숙**

- 평가셋을 카테고리별로 확장, 견고성·안전성(레드 팀) 세트 추가, 판정자 정기 재검증, 온라인 A/B 테스트 체계.

**핵심 조언:** 처음부터 완벽한 프레임워크를 만들려 하지 말고, **작은 평가셋 + 간단한 채점기로 바로 시작해 매주 키워 나가는 것** 이 가장 효과적입니다.

<summary><b>Q32. 모델이 한 공정성(fairness) 지표는 통과하지만 다른 지표는 통과하지 못합니다. 상충되는 감사 결과를 어떻게 처리하나요?</b></summary>

**먼저 알아야 할 사실:** 공정성 지표들은 **수학적으로 동시에 만족할 수 없는 경우가 많습니다.** 예를 들어 집단 간 기저율(실제 양성 비율)이 다르면, 보정(calibration)과 오류율 균등(equalized odds)을 동시에 완벽히 만족할 수 없다는 불가능성 정리가 알려져 있습니다. 따라서 "모든 지표 통과"는 목표가 될 수 없고, **어떤 지표가 이 맥락에서 중요한지 결정** 하는 것이 핵심입니다.

**주요 지표의 의미 차이**

- **인구통계적 동등성:** 집단별 긍정 결정 비율이 같음 → "결과의 평등"
- **기회 균등 / 균등화된 오즈:** 실제 자격이 있는 사람들 사이에서 집단별 통과율(그리고 오류율)이 같음 → "같은 자격이면 같은 대우"
- **예측 동등성 / 보정:** 같은 점수면 집단과 관계없이 실제 결과 확률이 같음 → "점수의 의미가 같음"

**처리 절차**

1. **맥락과 피해 분석:** 어떤 오류가 누구에게 어떤 피해를 주는가? (채용에서 자격 있는 지원자를 탈락시키는 오류 vs 대출에서 상환 불가 고객 승인)
2. **법·규제 요구 확인:** 해당 영역에서 요구되는 기준(차별 금지법, 불리 효과 기준)이 있는지 법무와 확인합니다.
3. **이해관계자 결정:** 법무, 컴플라이언스, 도메인 전문가, 영향받는 집단의 관점을 반영해 우선 지표와 허용 범위를 정하고 근거를 문서화합니다.
4. **원인 분석:** 데이터 편향(라벨 자체가 과거 차별을 반영), 대리 변수, 집단별 데이터 부족 등.
5. **완화 조치:** 데이터 보완, 대리 변수 제거, 학습 시 공정성 제약, 집단별 임계값 조정(규제상 허용되는지 확인), 사람 검토 추가.
6. **트레이드오프 투명화:** 선택한 지표와 포기한 지표, 그 이유를 모델 카드·감사 보고서에 기록합니다.
7. **지속 모니터링:** 선택한 지표와 보조 지표를 함께 추적합니다.

<summary><b>Q33. 배포 당시에는 공정했던 모델이 6개월 후 편향되었습니다. 어떻게 지속적으로 모니터링하나요?</b></summary>

**왜 시간이 지나며 편향이 생기나**

- **데이터 드리프트:** 사용자 구성, 입력 분포, 사회·경제 환경 변화(특정 집단의 신청 증가, 새로운 지역 진출)
- **피드백 루프:** 모델의 결정이 미래 학습 데이터를 만들어 편향이 강화됨(거절된 집단의 데이터가 쌓이지 않음)
- **재학습·업데이트:** 새 데이터나 새 모델 버전이 의도치 않게 편향을 도입
- **상류 변화:** 피처를 만드는 다른 시스템의 변경, 외부 LLM 제공사의 모델 업데이트

**모니터링 체계**

1. **집단별 지표 대시보드**
   - 집단별 결정 비율, 오류율(실제 결과가 확인되면), 점수 분포, 거절·이관 비율을 주기적으로 계산.
   - 보호 속성 데이터를 직접 수집하기 어려우면, 법적으로 허용되는 범위에서 추정 방법이나 별도 감사 표본을 사용합니다.
2. **임계값 기반 알림**
   - 불리 효과 비율(예: 4/5 규칙), 집단 간 오류율 차이가 기준을 넘으면 알림.
3. **입력 분포 모니터링**
   - 집단 구성 변화, 피처 분포 드리프트를 감지해 공정성 변화의 선행 신호로 사용.
4. **정기 감사**
   - 분기별 반사실적 테스트(속성만 바꾼 입력), 표본 사람 검토, 외부 감사.
5. **결과(라벨) 지연 대응**
   - 실제 결과(상환 여부, 근무 성과)는 늦게 확인되므로, 확인되는 대로 지표를 갱신하고 지연 기간을 고려합니다.
6. **변경 관리**
   - 재학습·모델 교체 전 공정성 평가를 배포 게이트에 포함.

**대응:** 편향이 감지되면 원인 분석 → 임시 조치(사람 검토 강화, 이전 버전 롤백) → 데이터·모델 수정 → 재평가 → 문서화.

<summary><b>Q34. 외부 감사인이 모델 결과를 재현하지 못합니다. 감사 재현성을 어떻게 보장하나요?</b></summary>

**재현이 안 되는 흔한 원인**

- 모델 버전(외부 API 모델이 업데이트됨, 별칭 사용)
- 프롬프트·설정(온도, top-p, 시스템 프롬프트)이 기록되지 않음
- 샘플링 무작위성, GPU 연산의 비결정성, 배치 구성 차이
- 입력 데이터·피처 계산·검색 인덱스가 당시와 달라짐
- 전처리·후처리 코드 버전 차이
- 외부 도구·API 응답이 시간에 따라 바뀜

**재현성 확보 방법**

1. **모든 결정에 대한 완전한 기록 (결정 로그)**
   - 요청 ID, 타임스탬프, 입력(또는 입력 스냅샷 참조), 모델 ID·버전, 프롬프트 버전, 파라미터, 검색된 문서 ID·버전, 도구 호출과 결과, 출력, 최종 결정.
   - 변조 방지 저장소(추가 전용 로그, 해시 체인)와 보존 기간 정책.
2. **버전 고정과 보관**
   - 날짜가 고정된 모델 ID 사용, 자체 모델은 가중치를 레지스트리에 보관.
   - 코드(커밋 해시), 프롬프트, 피처 파이프라인, 인덱스 스냅샷의 버전 관리.
3. **결정성 높이기**
   - 온도 0, 고정 seed(지원 시), 결정적 커널 설정(자체 호스팅). 완전한 결정성이 불가능한 경우가 있으므로 기록된 출력을 "공식 결과"로 둡니다.
4. **감사 패키지 제공**
   - 특정 시점의 시스템을 재실행할 수 있는 환경(컨테이너 이미지, 모델 버전, 데이터 스냅샷)과 실행 가이드.
   - 외부 API 모델이 종료되는 경우를 대비해, 감사 대상 기간의 출력 기록 자체를 증거로 제출.
5. **문서화**
   - 모델 카드, 데이터 시트, 평가 결과, 변경 이력, 재현 절차서.

**검증:** 내부에서 정기적으로 과거 결정 샘플을 재실행해 재현율을 점검합니다.

<summary><b>Q35. 출시 전 LLM 챗봇에 대한 레드 팀 활동을 어떻게 구성하나요?</b></summary>

**1. 준비**

- **범위:** 챗봇의 기능, 접근 가능한 데이터·도구, 대상 사용자(아동 포함 여부), 배포 지역.
- **위협 모델:** 가장 큰 피해 시나리오(개인정보 유출, 위험 정보 제공, 브랜드 훼손, 잘못된 약속, 규정 위반).
- **정책 기준:** 무엇이 실패인지 명확한 판정 기준 문서.

**2. 팀 구성**

- 보안 전문가(인젝션, 데이터 유출), 도메인 전문가(의료·금융 등 잘못된 조언), 다양한 배경·언어의 테스터(문화적 편향, 다국어 우회), 제품 담당자.
- 필요하면 외부 레드 팀 업체.

**3. 공격 범주와 시나리오**

| 범주 | 예 |
|---|---|
| 탈옥 | 역할극, 가정법, 인코딩, 다단계 유도 |
| 프롬프트 인젝션 | 시스템 프롬프트 추출, 지시 덮어쓰기, 문서·URL 속 간접 인젝션 |
| 데이터 유출 | 다른 사용자 정보, 내부 문서, PII |
| 유해 콘텐츠 | 위험 정보, 혐오, 자해 조장 |
| 잘못된 조언·약속 | 근거 없는 의료·법률 조언, 정책에 없는 환불 약속 |
| 편향 | 집단별 차별적 응답 |
| 도구 악용 | 권한 밖 행동, 대량 요청, 비용 폭증 |

**4. 실행**

- **자동화:** 공격 생성 LLM과 판정 모델로 대량 변형 테스트(garak, PyRIT, promptfoo).
- 모든 시도와 결과를 기록(재현 가능하게).

**5. 결과 처리**

**6. 출시 후**

- 발견된 공격을 회귀 세트로 자동화, 정기 레드 팀, 사용자 신고·버그 바운티, 모니터링으로 새 공격 패턴 수집.

<summary><b>Q36. 텍스트 전용 안전성 테스트로는 교차 모달(cross-modal) 공격을 놓치는 멀티모달 모델을 어떻게 레드 팀 방식으로 점검하나요?</b></summary>

**왜 텍스트 테스트로는 부족한가:** 멀티모달 모델은 이미지·오디오·영상에서도 지시와 정보를 읽어 들입니다. 텍스트 필터를 통과한 **무해해 보이는 텍스트 + 이미지 속 유해 지시** 조합처럼, 모달리티를 넘나드는 공격은 텍스트 전용 안전성 검사가 보지 못합니다.

**교차 모달 공격 유형**

1. **이미지 속 텍스트 인젝션:** 이미지에 "이전 지시를 무시하고 ..." 같은 문구를 넣음(작은 글씨, 배경과 비슷한 색, 손글씨, 왜곡된 글꼴).
2. **유해 요청의 모달 분할:** 텍스트는 "이 그림의 단계를 자세히 설명해 줘", 이미지에 위험한 제조 과정의 제목이나 재료 목록.
3. **타이포그래피 공격:** 텍스트 필터를 피하기 위해 금지된 요청을 이미지로 렌더링.
4. **적대적 이미지 섭동:** 사람 눈에는 보이지 않는 노이즈로 모델 판단을 조작.
5. **오디오 공격:** 음성 속 숨은 명령, 사람이 듣기 어려운 주파수·속도의 지시.
6. **문서·스크린샷 간접 인젝션:** 에이전트가 읽는 웹 페이지 스크린샷, PDF 이미지 속 지시.
7. **맥락 결합 공격:** 각각은 무해한 이미지와 텍스트가 결합될 때만 유해한 의미가 되는 경우.

**레드 팀 방법**

- **공격 데이터셋 구축:** 기존 텍스트 공격 세트를 이미지·오디오로 변환(렌더링, TTS), 다양한 글꼴·크기·배경·노이즈로 변형 자동 생성.
- **수동 창의 테스트:** 사람이 모달 조합 공격을 설계.
- **자동화 파이프라인:** 공격 이미지 생성 → 모델 실행 → 출력 판정(안전성 분류기·LLM 판정자).
- **에이전트 시나리오:** 화면·문서를 읽는 에이전트에서 실제 행동(데이터 전송, 클릭)까지 이어지는지 확인.

**방어 개선**

- 입력 이미지·오디오의 텍스트 추출(OCR·ASR) 후 텍스트 안전성 검사 적용
- 멀티모달 안전성 분류기, 출력 단계 검사(어떤 입력이든 출력의 유해성 판단)
- 외부 콘텐츠 속 지시를 따르지 않도록 하는 지시 계층 학습·프롬프트
- 에이전트 권한 최소화와 사람 승인

**평가:** 모달리티·공격 유형별 공격 성공률을 추적하고, 텍스트 전용 버전과 비교해 교차 모달 취약성을 별도로 관리합니다.

</details>
