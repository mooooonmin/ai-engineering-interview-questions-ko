<summary><b>Q1. AI 엔지니어링이란 무엇이며, 머신러닝 엔지니어링과 어떻게 다른가요?</b></summary>

**답변 골자**

- **AI 엔지니어링:** 파운데이션 모델(LLM, 멀티모달 모델)을 활용해 **실제 제품과 시스템을 만드는 일** 입니다. 모델을 처음부터 학습하기보다 프롬프트, RAG, 에이전트, 도구 연동, 평가, 가드레일, 서빙·비용 최적화를 설계합니다.
- **머신러닝 엔지니어링:** 데이터 수집·피처 엔지니어링·모델 학습·튜닝·배포 등 **모델 자체를 만들고 운영하는 일** 에 무게가 있습니다.

| | ML 엔지니어링 | AI 엔지니어링 |
|---|---|---|
| 출발점 | 데이터와 라벨 | 사전 학습된 모델 |
| 핵심 작업 | 학습, 피처, 하이퍼파라미터 | 프롬프트, RAG, 에이전트, 평가, 통합 |
| 평가 | 명확한 지표(정확도, AUC) | 자유 형식 출력 평가(LLM 판정, 사람 평가) |
| 비용 구조 | 학습 비용 중심 | 토큰당 추론 비용 |
| 반복 속도 | 느림(재학습) | 빠름(프롬프트·구성 변경) |
| 위험 | 데이터 드리프트 | + 환각, 프롬프트 인젝션, 제공사 의존 |

**좋은 답의 포인트**

- 경계가 겹친다는 점을 인정합니다(파인튜닝, 평가, 서빙은 두 분야 공통).
- 자신의 경험과 연결합니다: "제 업무의 70%는 평가 체계와 검색 품질 개선이었습니다"처럼 구체적으로.

**피할 점:** "프롬프트만 잘 쓰면 되는 일"처럼 가볍게 표현하는 것. 시스템 설계·평가·운영의 깊이를 보여 주세요.

<summary><b>Q2. 어떤 문제에 AI가 필요한지, 기존 소프트웨어 방식으로 충분한지 어떻게 판단하나요?</b></summary>

**판단 기준 (질문 목록으로 답하기)**

1. **규칙으로 명확히 정의할 수 있는가?** 입력→출력 규칙이 명확하고 예외가 적으면 일반 코드가 더 정확하고 싸고 예측 가능합니다(세금 계산, 형식 검증).
2. **입력이 비정형인가?** 자유 텍스트, 이미지, 음성, 다양한 문서처럼 규칙으로 다루기 어려우면 AI가 적합합니다.
3. **오류 허용도는?** 틀리면 안 되는 작업(결제 금액, 법적 확정)은 AI 단독 처리 대신 결정적 로직 + AI 보조 + 사람 검토.
4. **설명·감사 요구는?** 강한 설명 가능성이 필요하면 규칙 기반이나 해석 가능한 모델을 우선합니다.
5. **데이터와 평가 가능성:** 성공을 측정할 방법과 테스트 데이터가 있는가.
6. **비용·지연:** 대량·저지연 처리에서 LLM 호출 비용이 가치에 비해 큰가.
7. **변화 속도:** 규칙이 계속 바뀌고 예외가 끝없이 생긴다면 AI가 유지보수 비용을 줄일 수 있습니다.

**실무 접근:** 가장 단순한 해법(규칙, 검색, 기존 ML)을 기준선으로 먼저 만들고, AI가 의미 있게 더 나은 경우에만 도입합니다. 많은 경우 **하이브리드**(규칙으로 대부분 처리, 애매한 경우만 LLM)가 최선입니다.

**예시 답변 한 줄:** "지원 티켓 분류 프로젝트에서 70%는 키워드 규칙으로 정확히 처리되어, 나머지 30%만 LLM으로 보내 비용을 줄이고 정확도도 높였습니다."

<summary><b>Q3. AI 기능의 ROI(투자 대비 수익)를 어떻게 측정하나요?</b></summary>

**1. 목표를 비즈니스 지표로 정의**

- 비용 절감: 처리 시간 단축, 상담원 1인당 처리량, 자동 해결률
- 매출 증가: 전환율, 객단가, 이탈 감소
- 품질·리스크: 오류율 감소, 규정 위반 감소, 고객 만족도(CSAT, NPS)

**2. 비용을 빠짐없이 계산**

- 추론 비용(토큰·GPU), 인프라(벡터 DB, 로깅), 개발·유지보수 인력, 평가·라벨링, 사람 검토 비용, 오류로 인한 비용(잘못된 답변 처리)

**3. 인과 효과 측정**

- **A/B 테스트** 나 단계적 출시로 AI 기능이 있는 그룹과 없는 그룹을 비교합니다(사전·사후 단순 비교는 다른 요인이 섞임).
- 선행 지표(사용률, 채택률)와 후행 지표(매출, 이탈)를 함께 봅니다.

**4. 계산 예시**

```
월 문의 10만 건, 자동 해결률 35%, 건당 상담 비용 3,000원
→ 월 절감 = 100,000 × 0.35 × 3,000 = 1억 500만 원
월 AI 운영 비용(추론 + 인프라 + 검토 인력) = 2,500만 원
→ 순효과 약 8,000만 원/월 (+ 응답 시간 단축으로 CSAT 상승)
```

**5. 지속 추적:** 대시보드로 비용과 효과를 함께 추적하고, 기능별로 ROI가 낮은 부분은 축소·개선합니다.

**좋은 답의 포인트:** 숫자로 말하고, 측정 방법(A/B)과 숨은 비용(사람 검토, 오류 비용)까지 언급하는 것.

<summary><b>Q4. 프로덕션 AI 시스템에서 환각이 발생하면 어떻게 대응하나요?</b></summary>

**답변 구조: 즉시 대응 → 원인 분석 → 근본 수정 → 재발 방지**

1. **즉시 대응**
   - 영향 범위 파악(어떤 기능, 얼마나 많은 사용자, 피해 정도).
   - 심각하면 해당 기능을 제한하거나 이전 버전으로 롤백, 가드레일 강화.
   - 잘못된 정보를 받은 사용자에게 필요 시 정정 안내.
2. **원인 분석 (트레이스 확인)**
   - 검색 실패인가(근거 문서가 없었나), 생성 실패인가(근거가 있었는데 무시했나)?
   - 최근 변경(모델 버전, 프롬프트, 데이터)이 있었나?
   - 특정 유형의 질문에 집중되는가?
3. **근본 수정**
   - 검색: 청킹·하이브리드 검색·리랭커 개선, 누락 문서 추가
   - 생성: 근거 기반 답변 지시, 인용 강제, 모를 때 거절 허용, 온도 낮추기
   - 검증: 주장-근거 대조 검사, 고위험 답변은 사람 검토
4. **재발 방지**
   - 해당 사례를 평가셋에 추가해 회귀 테스트로 관리
   - 프로덕션 샘플에 대한 충실도 자동 평가와 알림
   - UX: 출처 표시, 불확실성 표시

**예시 답변 골자 (STAR):** "상황: RAG 챗봇이 존재하지 않는 환불 정책을 안내. 과제: 원인 파악과 재발 방지. 행동: 트레이스로 확인해 보니 관련 문서가 검색되지 않았는데도 답을 생성. 검색 점수 임계값과 '문서 없으면 거절' 규칙 추가, 정책 질문 평가셋 구축. 결과: 근거 없는 답변 비율이 크게 감소하고 정책 관련 불만이 줄었음."

</details>

<summary><b>Q5. LLM API를 사용할지, 오픈소스 모델을 자체 호스팅할지 어떻게 결정하나요?</b></summary>

**결정 프레임 (5가지 축)**

1. **품질 요구:** 작업에 최고 수준 모델이 필요한가, 오픈 모델로 충분한가? → 내 평가셋으로 직접 비교
2. **데이터·규제:** 데이터가 외부로 나가도 되는가(계약·리전·학습 사용 금지 조건으로 해결 가능한가)?
3. **비용:** 트래픽 규모와 패턴. 대량·안정적이면 자체 호스팅이 저렴할 수 있고, 적거나 변동이 크면 API가 유리
4. **맞춤화:** 파인튜닝, 양자화, 지연 최적화, 온디바이스 배포가 필요한가?
5. **팀 역량과 운영 부담:** GPU 인프라, 모니터링, 장애 대응을 운영할 수 있는가?

**일반적인 결론**

- 초기·검증 단계 → API로 빠르게 시작
- 규모가 커지고 작업이 명확해지면 → 대량·단순 작업부터 오픈 모델 자체 호스팅으로 이전 검토
- 대부분 **혼합 구조**: 어려운 요청은 API 대형 모델, 단순·대량 요청은 자체 호스팅 소형 모델 + 라우팅

**좋은 답의 포인트**

- "항상 X가 낫다"가 아니라 기준과 측정으로 결정한다는 점.
- 공급자 종속 위험(게이트웨이로 추상화), 숨은 운영 비용(인력, 유휴 GPU)을 언급.

**예시 한 줄:** "월 수억 토큰의 분류 작업을 8B 모델 파인튜닝 + 자체 호스팅으로 옮겨 비용을 크게 줄였고, 복잡한 상담 요약은 API 모델로 유지했습니다."

<summary><b>Q6. AI 프로젝트에서 이해관계자의 기대치를 어떻게 관리하나요?</b></summary>

**핵심 원칙: 초기에, 구체적으로, 지속적으로**

1. **초기에 "확률적 시스템"임을 공유**
   - AI는 100% 정확하지 않고, 같은 질문에도 결과가 다를 수 있으며, 성능은 실험으로 확인해야 한다는 점을 처음부터 합의합니다.
2. **성공 기준을 숫자로 합의**
   - "잘 동작하는 챗봇" 대신 "평가셋 기준 정답률 85% 이상, 응답 3초 이내, 자동 해결률 30%".
   - 허용 가능한 실패 유형과 불가능한 실패 유형(예: 잘못된 환불 약속은 0건)을 구분합니다.
3. **빠른 프로토타입으로 현실 보여 주기**
   - 2~3주 안에 실제 데이터로 동작하는 데모와 평가 결과를 공유해, 기대와 현실의 차이를 일찍 맞춥니다.
4. **단계적 범위**
   - 위험이 낮고 가치가 분명한 범위부터(사내 보조 도구 → 고객 대상), 사람 검토가 있는 형태로 시작합니다.
5. **정기적이고 투명한 보고**
   - 지표 대시보드, 잘 되는 것과 안 되는 것, 실패 사례 예시를 그대로 보여 줍니다.
6. **트레이드오프를 선택지로 제시**
   - "정확도를 더 올리려면 지연이 2배 늘거나 비용이 3배 듭니다. 어느 쪽을 택할까요?"

**예시 골자:** "경영진이 '모든 상담을 AI로'를 기대했지만, 첫 4주 평가에서 자동 처리가 안전한 유형이 40%였습니다. 이 데이터를 보여 주고 40%부터 시작해 분기마다 확대하는 로드맵으로 합의했습니다."

**피할 점:** 데모 한두 개의 성공 사례만 보여 주고 기대를 키우는 것.

<summary><b>Q7. 성능이 낮은 RAG 시스템을 디버깅하는 본인의 접근 방식을 설명하세요.</b></summary>

**체계적인 접근 (단계별로 원인 분리)**

1. **측정부터:** 실제 질문 기반 평가셋을 만들고 현재 상태를 수치화합니다(검색 재현율, 답변 정확도, 충실도).
2. **실패 사례 직접 읽기:** 실패한 질문 20~50개의 트레이스(재작성된 질의, 검색 결과, 프롬프트, 답변)를 직접 확인하고 유형별로 분류합니다.
3. **실패 지점 분리:**
   - 정답 문서가 **인덱스에 없음** → 데이터 수집·파싱 문제
   - 인덱스에는 있지만 **검색 안 됨** → 청킹, 임베딩, 질의 문제
   - 검색은 됐지만 **순위가 낮음** → 리랭킹 문제
   - 컨텍스트에 있었지만 **답이 틀림** → 프롬프트, 모델, 컨텍스트 배치 문제
4. **가장 큰 실패 유형부터 수정:**
   - 파싱 개선(표, PDF 레이아웃), 청크 크기·구조 조정, 하이브리드 검색, 리랭커, 질의 재작성, 메타데이터 필터, 프롬프트(인용·거절 규칙)
5. **한 번에 하나씩 바꾸고 재측정:** 변경마다 전체 평가셋으로 개선과 회귀를 확인합니다.
6. **운영 피드백 루프:** 프로덕션 실패 사례를 평가셋에 추가합니다.

**예시 골자:** "사내 문서 RAG 정답률이 60%였는데, 실패 분석 결과 절반이 표가 깨진 PDF 파싱 문제였습니다. 레이아웃 인식 파서로 바꾸고 하이브리드 검색과 리랭커를 추가해 정답률을 크게 끌어올렸습니다."

**좋은 답의 포인트:** "모델을 더 큰 걸로 바꿨다"가 아니라 **데이터로 원인을 찾아가는 과정** 을 보여 주는 것.

<summary><b>Q8. 빠르게 변하는 AI 분야의 최신 흐름을 어떻게 따라가나요?</b></summary>

**답변 구조: 정보원 + 필터링 + 직접 실험 + 공유**

1. **선별된 정보원**
   - 주요 연구소·회사의 공식 블로그와 기술 보고서, 모델 카드
   - 주목받는 논문(arXiv, 학회), 신뢰할 수 있는 뉴스레터·블로그·팟캐스트
   - 사용하는 도구(vLLM, LangGraph 등)의 릴리스 노트와 GitHub
2. **필터링 기준**
   - 모든 것을 따라가지 않고, "내 업무 문제(비용, 품질, 지연)에 영향을 주는가?"로 거릅니다.
   - 과장된 발표는 벤치마크 조건과 재현 결과를 확인합니다.
3. **직접 실험**
   - 새 모델·기법은 우리 평가셋으로 직접 돌려 봅니다. 예: 새 모델 출시 → 평가셋으로 품질·비용 비교 보고서.
   - 작은 사이드 프로젝트로 새 패러다임(에이전트 프레임워크, MCP 등)을 손으로 익힙니다.
4. **공유와 토론**
   - 팀 내 논문 리딩, 짧은 기술 공유, 커뮤니티 참여, 글쓰기.

**예시 한 줄:** "새 모델이 나오면 사내 평가셋 300개로 하루 안에 비교하는 스크립트를 만들어 두었고, 덕분에 지난 분기 모델 전환으로 비용을 줄였습니다."

**피할 점:** "트위터를 많이 봅니다"처럼 수동적인 답. 학습을 **실제 의사 결정과 결과** 로 연결하는 모습을 보여 주세요.

<summary><b>Q9. AI 시스템에서 혁신과 안정성 사이의 균형을 어떻게 맞추나요?</b></summary>

**원칙: 빠르게 실험하되, 안전하게 배포한다**

1. **실험과 프로덕션 분리**
   - 새 모델·기법은 실험 환경에서 자유롭게 시도하고, 프로덕션 반영은 정해진 관문을 거칩니다.
2. **평가 게이트**
   - 평가셋·회귀 테스트·안전성 테스트를 통과해야 배포. "더 좋아 보인다"가 아니라 "기준을 만족한다"로 판단합니다.
3. **점진적 배포와 되돌리기**
   - 기능 플래그, 카나리·A/B 배포, 자동 롤백, 이전 버전 유지.
4. **위험도에 따른 차등**
   - 내부 도구·저위험 기능은 빠르게, 고객 대상·고위험 기능(금융, 의료)은 더 엄격한 검토와 사람 감독.
5. **아키텍처로 변화 흡수**
   - 모델 게이트웨이·추상화 계층으로 모델을 쉽게 교체하되, 핵심 비즈니스 로직은 결정적 코드로 유지.
6. **오류 예산(error budget)**
   - SLO를 지키는 범위 안에서 실험을 허용하고, 예산을 소진하면 안정화에 집중합니다.

**예시 골자:** "새 추론 모델이 품질은 좋았지만 지연이 3배였습니다. 전면 교체 대신 복잡한 질문 10%만 라우팅하는 A/B를 진행해, 지연 SLO를 지키면서 어려운 질문의 정확도를 높였습니다."

<summary><b>Q10. 진행했던 어려운 AI 프로젝트에 대해 이야기해 주세요. 문제는 무엇이었나요? 어떤 접근 방식을 택했나요? 어떤 트레이드오프를 했나요? 결과는 어땠나요?</b></summary>

**답변 프레임 (STAR + 트레이드오프)**

1. **상황 (Situation):** 비즈니스 맥락과 규모. "월 20만 건 고객 문의를 처리하는 지원팀의 응답 시간이 길어지고 있었습니다."
2. **과제 (Task):** 본인의 역할과 목표 수치. "저는 기술 리드로서 6개월 안에 자동 해결률 30% 달성을 맡았습니다."
3. **행동 (Action):** 구체적인 기술 결정과 그 이유.
   - 평가셋 구축 → 기준선 측정
   - 아키텍처 선택(RAG + 도구 호출 에이전트), 검색 개선, 가드레일, 사람 이관 설계
   - 가장 어려웠던 문제와 해결(예: PDF 정책 문서 파싱, 환불 같은 고위험 행동 제어)
4. **트레이드오프:** 무엇을 포기하고 무엇을 얻었는지 명확히.
   - "더 큰 모델이 정확도가 5%p 높았지만 비용이 4배라, 작은 모델 + 리랭커 + 어려운 질문만 큰 모델로 보내는 라우팅을 선택했습니다."
   - "완전 자동화 대신 환불은 사람 승인 단계를 두어 속도보다 안전을 택했습니다."
5. **결과 (Result):** 수치와 배운 점.
   - "자동 해결률 34%, 평균 응답 시간 크게 단축, CSAT 상승. 배운 점: 모델 선택보다 평가셋과 검색 품질이 결과를 좌우했습니다."

**좋은 답의 포인트**

- 본인이 직접 한 일("우리"보다 "저")과 판단 근거를 분명히.
- 실패나 잘못된 판단과 그 수정 과정을 솔직히 포함하면 신뢰도가 높아집니다.
- 2~3분 분량으로 준비하고, 기술적 후속 질문에 깊게 답할 수 있게 세부를 기억해 둡니다.

<summary><b>Q11. 프로덕션에서 AI 모델이 편향되거나 해로운 출력을 낸다면 어떻게 대응하겠습니까?</b></summary>

**답변 구조: 억제 → 조사 → 수정 → 소통 → 재발 방지**

1. **즉시 억제**
   - 심각도 판단 후 해당 기능 제한·롤백, 출력 가드레일 긴급 강화, 문제 출력이 계속 노출되지 않도록 조치.
   - 사고 대응 절차 가동(담당자, 법무·홍보 필요 시 참여).
2. **조사**
   - 로그로 영향 범위(사용자 수, 기간, 유형) 파악.
   - 원인: 특정 프롬프트·입력 패턴, 모델 업데이트, 검색 데이터, 탈옥 시도, 학습 데이터 편향.
   - 반사실적 테스트로 편향 여부를 체계적으로 확인.
3. **수정**
   - 프롬프트·가드레일·안전 분류기 보강, 데이터 수정, 모델 교체·파인튜닝, 고위험 영역에 사람 검토 추가.
4. **소통**
   - 내부 이해관계자에게 사실 기반 보고, 영향받은 사용자에게 필요 시 사과·정정, 규제 보고 의무 확인.
5. **재발 방지**
   - 해당 사례를 안전성·편향 평가셋에 추가, 정기 레드 팀, 모니터링 알림, 비난 없는 사후 분석.

**좋은 답의 포인트**

- 빠른 피해 차단을 최우선으로 하면서도, 원인을 데이터로 확인하는 균형.
- 기술적 수정뿐 아니라 사람·프로세스(검토, 사고 대응, 커뮤니케이션)까지 다루는 것.

<summary><b>Q12. 예산을 초과하는 AI 시스템의 비용 최적화에 어떻게 접근하나요?</b></summary>

**좋은 답의 포인트:** 측정 → 우선순위 → 품질 검증을 동반한 최적화라는 과정을 보여 주는 것.

<summary><b>Q13. 모델의 정확도와 지연 시간 중 하나를 선택해야 했던 경험을 설명하세요. 어떻게 결정했나요?</b></summary>

**답변 프레임: 상황 → 선택지와 데이터 → 판단 기준 → 결정 → 결과**

**예시 골자**

- **상황:** "실시간 고객 상담 보조 기능에서, 대형 모델은 정답률이 높았지만 응답에 4초 이상 걸렸고, 소형 모델은 1초 안에 답했지만 정확도가 낮았습니다."
- **선택지와 데이터:**
  - 평가셋으로 두 모델의 정확도 차이를 측정(예: 8%p 차이)
  - 사용자 연구로 지연이 사용률에 미치는 영향 확인(2초를 넘으면 상담원이 기능을 거의 쓰지 않음)
  - 오류의 비용 분석(틀린 제안은 상담원이 걸러낼 수 있어 치명적이지 않음)
- **판단 기준:** "사용되지 않는 정확한 기능은 가치가 없다." 사용 맥락에서 지연이 채택률을 결정하므로, 지연 SLO(1.5초)를 먼저 고정하고 그 안에서 정확도를 최대화하기로 함.
- **결정:** 기본은 소형 모델 + 리랭커 개선, 상담원이 "자세히" 버튼을 누를 때만 대형 모델 호출. 스트리밍으로 체감 지연도 단축.
- **결과:** 채택률 상승, 정확도 격차는 검색 개선으로 절반 이상 줄임.

**좋은 답의 포인트**

- 둘 중 하나를 고르는 데서 끝나지 않고 **트레이드오프를 완화하는 설계**(라우팅, 캐싱, 스트리밍)를 함께 보여 주기.
- 결정 근거를 데이터(평가, 사용자 행동, 오류 비용)로 설명하기.
- 맥락에 따라 반대 결정도 옳을 수 있음(의료 판독 보조라면 정확도 우선)을 언급하면 좋습니다.

<summary><b>Q14. AI 시스템의 품질이 시간이 지나면서 저하되는 상황에 어떻게 대응하겠습니까?</b></summary>

**1. 감지 (조기 발견 체계)**

- 프로덕션 샘플 자동 평가 점수, 사용자 피드백(싫어요, 재생성, 이관률), 작업 성공률의 추세 모니터링과 알림.

**2. 원인 분석 (무엇이 바뀌었나)**

- **입력 분포 변화:** 새 사용자층, 새 제품·정책 출시로 질문 유형이 달라짐 → 질문 주제 분포 비교
- **데이터 노후화:** 지식 베이스가 최신이 아님, 문서가 바뀌었는데 인덱스 미반영
- **외부 변화:** 모델 제공사의 모델 업데이트, 의존 API 응답 변화
- **내부 변경:** 프롬프트·코드·설정 변경의 부작용
- **피드백 루프:** 시스템 출력이 다시 입력 데이터로 들어와 편향 강화

**3. 대응**

- 단기적으로 이전 안정 버전으로 롤백

**4. 재발 방지**

- 모델 버전 고정과 변경 관리, 데이터 신선도 모니터링, 새로운 실패 사례를 평가셋에 계속 추가, 정기 리뷰.

**예시 한 줄:** "3개월 사이 답변 만족도가 떨어져 분석해 보니, 신규 요금제 질문이 늘었는데 해당 문서가 인덱싱되지 않았던 것이 원인이었습니다. 문서 동기화 지연 알림을 추가해 같은 문제가 반복되지 않게 했습니다."

<summary><b>Q15. 비기술 이해관계자에게 AI의 한계를 어떻게 설명하나요?</b></summary>

**원칙: 전문 용어 대신 비유와 구체적 사례, 그리고 "그래서 어떻게 관리하는지"까지**

   - "그래서 환불 같은 중요한 결정은 AI가 초안만 만들고 직원이 승인합니다." 한계를 말하는 것이 곧 위험 관리 계획을 보여 주는 것이 되게 합니다.

<summary><b>Q19. 이 AI 엔지니어링 직무에 관심을 갖게 된 이유는 무엇인가요?</b></summary>

   - AI 엔지니어링에 끌린 구체적 계기: "LLM으로 사내 업무 자동화 도구를 만들었을 때 팀의 반복 업무가 크게 줄어드는 걸 보고, 모델 연구보다 실제 문제에 적용하는 일에 더 큰 보람을 느꼈습니다."

4. **앞으로의 기여와 성장**
   - 입사 후 기여할 수 있는 부분과 배우고 싶은 부분.

- 어느 회사에나 할 수 있는 일반적인 답 — 회사에 대한 조사가 드러나야 합니다.

<summary><b>Q20. PM이 엣지 케이스에서 환각률이 15%인 AI 기능을 출시하려고 합니다. 이 위험을 어떻게 전달하나요?</b></summary>

**1. 위험을 구체적인 영향으로 번역**

- "엣지 케이스 15%"가 실제로 무엇을 뜻하는지 계산합니다: 엣지 케이스가 전체 요청의 몇 %인가 → 하루 몇 건의 잘못된 답 → 어떤 피해(잘못된 가격 안내, 정책과 다른 약속, 법적 위험, 고객 불만).
- 실제 실패 사례 몇 개를 보여 줍니다. 숫자보다 사례가 설득력 있습니다.

**2. 위험의 심각도 구분**

- 모든 오류가 같지 않습니다. "15% 중 대부분은 어색한 답이지만, 일부는 존재하지 않는 환불 조건을 약속합니다" → 고위험 오류는 별도로.

**3. 반대가 아니라 선택지를 제시**

| 선택지 | 출시 시점 | 위험 |
|---|---|---|
| A. 그대로 출시 | 즉시 | 하루 약 N건 잘못된 답 |
| B. 엣지 케이스 감지 시 상담원 이관 | +1주 | 오류 대부분 차단, 이관 비용 증가 |
| C. 고위험 주제만 가드레일 + 출처 표시 | +2주 | 고위험 오류 대폭 감소 |
| D. 베타 사용자에게만 출시 후 개선 | 즉시(제한적) | 영향 범위 제한 |

**4. 권고와 판단 기준**

- "C와 D를 함께 추천합니다. 고위험 오류율이 1% 미만으로 내려가면 전체 출시하는 기준을 제안합니다."
- 최종 결정은 PM과 비즈니스가 하되, 위험이 문서로 기록되게 합니다.

**5. 출시 후 모니터링 계획**

- 오류율 대시보드, 사용자 신고 경로, 롤백 기준.

**좋은 답의 포인트:** 기술적 반대가 아니라 **비즈니스 언어로 위험을 정량화하고, 대안과 함께 협력적으로** 제시하는 것.

<summary><b>Q21. 비기술 임원이 AI 기능이 왜 100% 정확할 수 없는지 묻습니다. LLM의 한계를 어떻게 설명하나요?</b></summary>

- 방어적인 태도. 한계를 인정하고, 그것을 관리하는 계획이 있다는 점을 자신 있게 보여 주는 것이 신뢰를 얻는 방법입니다.

<summary><b>Q22. 벤치마크에서 15% 더 높은 점수를 받는 복잡한 에이전틱 시스템과, 유지보수가 쉬운 더 단순한 RAG 파이프라인 중 하나를 골라야 합니다. 어떻게 결정하나요?</b></summary>

**1. 벤치마크가 실제 문제를 대표하는지부터 확인**

- 그 15%가 **우리 사용자 질문 분포** 에서도 나오는가? 자체 평가셋(실제 질문)으로 두 시스템을 다시 비교합니다.
- 향상이 어떤 유형에서 나오는가? (예: 멀티홉 질문에서만 크게 좋아지고 나머지는 비슷한지)

**2. 전체 비용과 위험 비교**

| 기준 | 단순 RAG | 에이전틱 시스템 |
|---|---|---|
| 품질 | 기준 | 일부 유형에서 향상 |
| 지연 | 짧고 예측 가능 | 길고 변동 큼 (여러 단계) |
| 비용 | 낮음 | 요청당 수 배 |
| 신뢰성 | 높음 | 루프·도구 오류 등 실패 모드 증가 |
| 디버깅·유지보수 | 쉬움 | 어려움, 전문 인력 필요 |
| 보안 표면 | 작음 | 도구·권한으로 넓어짐 |

**3. 비즈니스 맥락으로 판단**

- 향상되는 질문 유형이 비즈니스에 얼마나 중요한가? (매출·위험과 직결되는가)
- 지연·비용 증가를 사용자와 예산이 감당할 수 있는가?
- 팀이 복잡한 시스템을 운영할 역량이 있는가?

**4. 흔히 최선인 답: 둘 중 하나가 아니라 조합**

- **기본은 단순 RAG, 어려운 질문만 에이전틱 경로로 라우팅.** 대부분의 요청은 빠르고 싸게, 복잡한 요청만 에이전트로 처리해 품질 향상의 대부분을 얻으면서 비용·위험을 제한합니다.
- 단계적으로: 단순 RAG를 개선(검색 품질, 질문 분해)해 격차를 먼저 줄여 보고, 남은 격차에 대해서만 에이전트를 도입합니다.

**5. 결정과 검증**

- A/B 테스트로 실제 사용자 지표(해결률, 만족도)와 비용을 비교한 뒤 결정하고, 결정 근거를 문서화합니다.

**좋은 답의 포인트:** 벤치마크 숫자를 그대로 믿지 않고 **실제 데이터·총비용·운영 복잡도** 를 함께 저울질하며, 라우팅 같은 절충안을 제시하는 것.

</details>
